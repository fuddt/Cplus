# 1. 「#include が通るのにビルドできない」現象

## Visual Studio で最も恐れられるエラー：LNK2019

ヘッダーをインクルードし、コード補完も効いているのに:

```text
error LNK2019: 未解決の外部シンボル
    "void __cdecl ProcessImage(uint8_t*, int, int)" が
    関数 _main で参照されました
```

* 文法エラー（赤い波線）は一切出ていない
* ヘッダーファイル（.h）も正しく見つかっている
* **なのに、なぜ実行ファイル（.exe）が作れないのか？**
* この疑問を解く鍵が **「コンパイルとリンクの分離」** です。

---

# 2. C++ビルドの2大フェーズ

## C++のビルドは「完全に別々の2段階」で動いている

```text
[フェーズ1: コンパイル]（各 .cpp を独立して機械語へ変換）
main.cpp     ──(コンパイラ)──> main.obj
Process.cpp  ──(コンパイラ)──> Process.obj
※ ここでは「宣言（.h）」だけ信じて、実装が無くてもパスする！

[フェーズ2: リンク]（全 .obj を合体させて 1つの .exe にする）
main.obj + Process.obj ──(リンカ)──> App.exe
※ ここで初めて「宣言に対応する実装が実在するか」を照合する！
```

### 一行で言えば
**#include は「宣言を読む」指示であり、「実装を探す」のはリンカの仕事である**

# シンボルと名前マングリングの正体

## C++コンパイラは、関数名を勝手に暗号化する

C++には「関数のオーバーロード（同名で引数違い）」があります。
コンパイラは区別のため、関数名に引数や型情報を合体させます。

```text
C++の元のコード:
void ProcessImage(int width, int height);

コンパイラが .obj 内に生成する名前（マングル名）:
?ProcessImage@@YAXHH@Z
```

* この暗号化された名前を **シンボル（Symbol）** と呼ぶ
* リンカはこのシンボル名を手がかりにして、呼び出し元と実装を結びつける
* 引数の型や `const` が 1文字でも違うと、**別のシンボルと判定されて LNK2019 が出る**

---

# 3. なぜプログラムを「部品（ライブラリ）」にするのか？

## 巨大なプログラムを毎回フルビルドするのは非効率

何百本もの .cpp を毎回コンパイルするのは時間がかかりすぎます。
そこで、完成した機能を **「ライブラリ」** としてまとめます。

```text
【静的ライブラリ（.lib）】
コンパイル済みの .obj を 1つの箱に詰めたもの
ビルド時に EXE の中に「丸ごと埋め込む」

【動的リンクライブラリ（.dll / .so）】
独立した実行可能ファイルとして外に置いておく
アプリ起動時や実行時に、OSが「必要なときだけメモリに呼ぶ」
```

* この2つの違いを理解することが、実務のアーキテクチャ設計の第一歩

---

# 静的リンク vs 動的リンクの比較

## メモリ効率・サイズ・更新性のトレードオフ

```text
【静的リンク（Static Link / .lib）】
長所: EXE 単体で動く（DLL行方不明エラーが絶対に起きない）
短所: アプリごとにサイズが肥大化、修正時に全EXEの再ビルドが必要

【動的リンク（Dynamic Link / .dll）】
長所: 複数のアプリで1つのDLLを共有可能（メモリと容量を節約）
      DLLを差し替えるだけで本体を再ビルドせずアップデート可能
短所: 「DLLが見つかりません」エラーが起きる、バージョン不一致の罠
```

* ゲームのエンジン部分や、C#と連携する高速処理コアには **DLL** が選ばれる

---

# 4. C++でDLLを作る基本作法

## 外界に向けて関数をエクスポートする

DLLの中の関数は、デフォルトでは外から見えません（非公開）。
公開したい関数には **`__declspec(dllexport)`** を付けます。

```cpp
// ImageCore.h
#ifdef BUILD_DLL
#define DLL_API __declspec(dllexport) // DLLを作る側
#else
#define DLL_API __declspec(dllimport) // DLLを使う側
#endif

// 公開する関数
extern "C" DLL_API void ProcessImage(uint8_t* buffer, int lineSpan);
```

* マクロを使って、作成時（export）と使用時（import）を切り替えるのが定石

---

# なぜ `extern "C"` が絶対に必須なのか？

## 異言語連携を阻む「マングリングの壁」を破壊する

先ほど学んだ通り、C++は関数名を暗号化（マングル）します。
しかし、この暗号化ルールは **コンパイラごとにバラバラ** です。

```text
C++のままだと:
C#「ProcessImage を呼んでくれ！」
DLL「そんな名前の関数はない (?ProcessImage@@YAXPAEH@Z ならあるが)」
  ↓ (名前が一致せずロード失敗！)

extern "C" を付けると:
コンパイラに「C言語の素直なルールで名前を残せ」と命令する
DLL内のシンボル名がそのまま「ProcessImage」になる！
```

* **C# や Python から呼ぶ DLL 関数には、100% `extern "C"` を付ける**

---

# 5. 実務連携：C# から C++ DLL を呼び出す

## P/Invoke（プラットフォーム呼び出し）の実装

C# 側のコードで、DLLのファイル名と関数名を指定します。

```csharp
using System;
using System.Runtime.InteropServices;

class Program {
    // DLLから関数をインポート
    [DllImport("ImageCore.dll", CallingConvention = CallingConvention.Cdecl)]
    public static extern void ProcessImage(IntPtr buffer, int lineSpan);

    static void Main() {
        byte[] data = new byte[1024];
        // バッファを固定してポインタを渡す
        GCHandle handle = GCHandle.Alloc(data, GCHandleType.Pinned);
        ProcessImage(handle.AddrOfPinnedObject(), 128);
        handle.Free();
    }
}
```

* C# の美しいUI ＋ C++ の超高速画像処理コアという **最強の布陣** が完成する

# 現場の落とし穴：メモリ所有権の境界線

## 「C++で確保したメモリは、C++で解放せよ」

C#（マネージド）と C++（ネイティブ）の間で最も危険なのがメモリです。

```text
【大惨事パターン】
C++ DLL「メモリを new で 10MB 確保してポインタを C# に返しました」
C#      「使い終わったからガベージコレクションで消しておこう...」
  ↓
C#のGCは C++のヒープを知らない！ メモリリーク or クラッシュ！
```

* **鉄則①**: メモリは C# 側で確保し、C++ にはポインタだけ渡して加工させる
* **鉄則②**: どうしても C++ 側で確保したなら、解放用の `FreeBuffer()` 関数を C++ に用意する

# 現場のトラブルシューティング① LNK2019

## リンカエラーが出たときの確実な診断フロー

```text
LNK2019 未解決の外部シンボル が出た！
  │
  ├─ 1. そもそも .cpp がプロジェクトに登録されているか？
  │      （ファイルを移動したときに登録が切れる定番ミス）
  │
  ├─ 2. 関数のシグネチャが完全一致しているか？
  │      （const の有無、引数の型、クラス名:: の付け忘れ）
  │
  └─ 3. 外部ライブラリ（.lib）のリンク設定がされているか？
         （追加の依存ファイルに .lib を指定し忘れている）
```

# 現場のトラブルシューティング② 実行時エラー

## 「DLLが見つかりません」が出たときの検索順序

ビルドは通ったのに、起動した瞬間に落ちる場合:

```text
Windows OS が DLL を探しに行く優先順位:
1. 実行ファイル（.exe）と同じフォルダ ★最優先！
2. カレントディレクトリ
3. Windows システムフォルダ（System32 など）
4. 環境変数 PATH に登録されたフォルダ
```

* **解決策**: 作成した DLL を、呼出元の `.exe` と **まったく同じフォルダにコピー** する
* または、Visual Studio のビルド後イベントで自動コピーする設定を入れる

# 本日のまとめ

## 持ち帰ってほしい 4つの重要ポイント

* **① コンパイルとリンクは別世界**
  * ヘッダーはコンパイラが見るもの、実装はリンカが探すもの
* **② LNK2019 は「実装が見当たらない」叫び**
  * .cpp 未登録、シグネチャ不一致、.lib 未指定のいずれか
* **③ 異言語連携には `extern "C"`**
  * C++の名前マングリングを無効化し、クリーンな関数名で公開する
* **④ メモリの所有権をまたがせない**
  * C#で確保したバッファを C++ で加工するのが最も安全
