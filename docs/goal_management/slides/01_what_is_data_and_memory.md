# データとは何か？

## ― ビット・バイトから始まるメモリの正体 ―

コンピュータシステム基礎研修 第1回

---

# 本日のアジェンダ

## 「0と1の並び」から、なぜ文字・画像・プログラムが生まれるのか？

* **① 最小単位：bit は「状態」である**
  * 0と1そのものには意味がない？
* **② 「bit列 ＋ 解釈ルール」の正体**
  * 同じbit列でも見方次第で文字・数値・画像に化ける
* **③ 0と1の並びが、CPUへの命令になる**
  * 「1 + 1」をCPUが計算するカラクリ（架空CPU）
* **④ 1byte と 256通りの状態**
  * 整数として解釈すると 0〜255 になる理由
* **⑤ 実務の罠：12bit packed と byte境界のズレ**
  * メモリの区切りとデータの意味の区切りが一致しない問題
* **⑥ プログラムから見るメモリの正体**
  * C++で覗く「型という解釈ルール」と1バイトのロッカー街

---

# 1. そもそも「データ」とは何か？

## コンピュータの世界は超極論すると「0 と 1」だけ

どんな画像も、プログラムも、文字列も、
最終的には **0 または 1** の並びで表現されています。

```text
最小単位: 1 bit = [0] または [1]
```

* **1 bit** で表せる状態は **2通り**（0, 1）
* **2 bit** で表せる状態は **4通り**（00, 01, 10, 11）
* **3 bit** で表せる状態は **8通り**（000 〜 111）
* **ビットが1つ増えるたびに、作れる「状態の数」は2倍になる**

---

# でも、0と1だけで何ができるの？

## bitは「意味」ではなく、単なる「状態」にすぎない

「0と1が増えて何通りも作れるのは分かった。でも、それで何ができるの？」
ここで最も重要な事実は、**bitそのものには何の意味もない** ということです。

```text
bit はただの「スイッチの状態」:
0 = スイッチが OFF
1 = スイッチが ON
```

* 2bit なら `00`, `01`, `10`, `11` という **4つの状態** が作れる
* これを「00=0, 01=1, 10=2, 11=3」と決めれば **整数** になる
* これを「00=青, 01=黄, 10=赤」と決めれば **信号機** になる
* **bitが増えるほど「作れる状態数」が増え、そこに人間が意味を割り当てる**

---

# 0と1に意味を与えるのは「解釈ルール」

## 「bit列 ＋ 解釈ルール ＝ 意味のあるデータ」

たとえば、メモリに **`01000001`** という 8bit の並びがあったとします。
これ単体では、何を表しているか誰にも分かりません。

```text
                  01000001（8つのbit列）
                            │
      ┌─────────────┬───────┴─────┬─────────────┐
      ↓             ↓             ↓             ↓
  【 整数 】    【 文字 】    【 画像 】    【 音声 】
     65             A          明るさ65      波の振幅値
 (数値ルール)  (ASCIIルール)  (画像ルール)  (波形ルール)
```

* **同じ bit 列でも、当てる「解釈ルール」によってまったく別のデータになる**
* コンピュータの世界では、bit列そのものではなく **「どう解釈するか」** が意味を決める

---

# 0と1の並びが、CPUへの命令になる

## データだけでなく、CPUへの命令もすべてbit列である

「画像や文字がbitなのは分かった。でもプログラムの処理はどうやって動くの？」
**実は、CPUを動かす「命令（プログラム）」も、まったく同じbit列です。**

```text
人間が書いたプログラム:
x = 1 + 1;

コンパイラが変換した機械語（CPUへの命令列・※架空のイメージ）:
[ 0010 (足し算せよ) ][ 00000001 (値1) ][ 00000001 (値1) ] ...
```

* CPUは **「このbit列が来たら足し算の回路を動かす」** と物理的に作られた機械
* メモリの上では、画像データもCPUの命令も **「同じbit列」** として並んでいる

---

# では「1 + 1」はどうやって計算される？

## 架空CPUで覗く「命令形式」と解釈の仕組み

※以下は仕組みを直感的に理解するための架空CPUの例です。

```text
【CPUが持っている解釈ルール】
「先頭の4bitは命令、それに続く8bit×2個はその命令が使う値」と決まっている
・0010     = ADD（足し算せよ）という命令
・00000001 = 数値の「1」
```

```text
① 命令形式に沿って読む: [ 0010 ][ 00000001 ][ 00000001 ]
② CPUが解釈する      : 「ADD命令だな。対象の値は 1 と 1 だ」
③ 回路で計算実行      : 1 + 1 を計算 ──> 結果「00000010」を出力！
```

* 出力された `00000010` を整数ルールで解釈すると **`2`** になる
* **CPUは「どこに置かれ、どう読まれたか」というルールに従ってbit列を解釈している**

---

# 1バイトは「256通りの状態を表せる箱」

## 現代の一般的なPCでは、8bitをひとまとめにした単位を1byteとして扱う

```text
1 byte = 8 bit
2^8 = 256 通りの「状態」を作れる箱
```

* **この256通りの状態は、さまざまなデータの「部品」になる**
  * **整数の一部になる** ──> 0〜255の数値、または合体させて大きな整数へ
  * **文字の一部になる** ──> 半角英数（ASCII）なら1byte、日本語（UTF-8）なら複数byte
  * **画像の1成分になる** ──> RGBの1色分の濃淡（0〜255）
  * **機械語の一部になる** ──> CPU命令やパラメータを構成する部品
* **数値も文字もプログラムも、必要に応じて「複数のbyte」を合体させて使う**

### 一行で言えば
**1バイトとは「256通りの状態を保持できる、最小の基本ブロック」である**

---

# 実務の罠：1つのデータが「8bit」とは限らない

## 「1byte = 8bit」と「データの意味の単位」は別の話

ここまで「1byte = 8bit」と学んできました。
しかし実際のデータ仕様書を開くと、驚くような形式が登場します。

```text
【よくある仕様の例】
・一般的な画像              : 1画素 = 8bit  (0〜255 / 256階調)
・12bitグレースケールやRAW  : 1サンプル = 12bit (0〜4095 / 4096階調)
・医療・産業用カメラ        : 1サンプル = 10bit や 14bit や 16bit
```

* **12bitのデータ** は、微妙な光のグラデーションを表現するために欠かせない
* しかし、ここでプログラマは **大きな壁** にぶつかります
* **「12bit の値って、8bit（1byte）の箱にどうやって入れるの？」**

---

# 12bitは「1byte」に入らない！

## 2byte使えば入るけれど… 4bitの隙間がもったいない

```text
1サンプル = 12bit
[ A A A A A A A A A A A A ] (12bit)

1byte = 8bit の箱:
[ A A A A A A A A ]  ← 4bit 分あふれて収まらない！
```

* **2byte（16bit）で保存した場合:**
  * `[ A A A A A A A A A A A A ][ 空き地 4bit ]` (16bit中12bit使用)
  * **確保した領域の 25%（4bit）が未使用** になる！
* 高解像度画像や大量保存では、この空き地は無視できない容量差になる
* そこでデータ形式によっては **「詰めて保存する（Packed形式）」** ことがあります

---

# 2つの12bit値を「3byte」にギュッと詰める

## 12bit ＋ 12bit ＝ 24bit（ちょうど 3byte！）

※以下は仕組みを直感的に理解するためのPacked形式の一例です。

```text
サンプルA (12bit) : AAAA AAAA AAAA
サンプルB (12bit) : BBBB BBBB BBBB

3つのbyteに詰め込んだ状態（Packed formatの一例）:
[ byte 0 (8bit) ]  [ byte 1 (8bit) ]  [ byte 2 (8bit) ]
[ A A A A A A A A ]  [ A A A A B B B B ]  [ B B B B B B B B ]
   (Aの前半8bit)      (Aの後半4bit ＋ Bの前半4bit)  (Bの後半8bit)
```

* 12bit + 12bit = 24bit なので、理論上は 3byte に詰められる
* **ただし「どのbitをどのbyteへ入れるか」はフォーマット仕様によって異なる**
* そして、これをプログラムで読み出そうとした瞬間、大きな罠が現れます

---

# byte境界と「意味の境界」がズレる！

## 1つのbyteの中に、2つの画素が同居する現象

メモリの区切りと、データの区切りを上下で見比べてみてください。

```text
【データとしての意味の区切り】
|          画素A (12bit)          |          画素B (12bit)          |

【メモリ上の区切り（byte境界）】
|    byte 0 (8bit)   |    byte 1 (8bit)   |    byte 2 (8bit)   |
|  A A A A A A A A   |  A A A A  B B B B  |  B B B B B B B B   |
                        ↑
                   ここが問題！
```

* **`byte 1` の中に「画素Aのお尻」と「画素Bの頭」が混ざっている！**
* 「1byte読めば1画素」「2byte読めば1画素」という常識は通用しない
* **仕様に従って、必要なbitだけを取り出して再構成する必要がある**

---

# なぜ `>>` や `&`（ビット演算）が必要なのか？

## 境界をまたいだbitを救出するための「ハサミとピンセット」

C++の画像処理コードで、次のような処理が出てくる理由がここにあります。

```cpp
// 混ざり合った byte1 から、画素Aのお尻（上位4bit）を右へ寄せて取り出す
uint16_t a_low = byte1 >> 4;

// byte1 から、画素Bの頭（下位4bit）だけをマスクして取り出す
uint16_t b_high = byte1 & 0x0F;
```

* **`>>`（ビットシフト）** : 必要な位置までbitをスライドさせる
* **`&`（ビットマスク）**  : 余計なbitを消して、欲しいbitだけをくり抜く
* **ビット演算は数学の計算ではなく、「byte境界をまたぐデータを切り貼りするツール」である**

---

# これは12bit画像だけの特殊な話ではない

## 実務の至る所で「byte境界と意味の境界」はズレている

```text
・10bit / 12bit 画像 : 医療機器、RAW現像、産業用カメラ
・RGB 24bit 画像     : 3byteで1ピクセル（R, G, B）
・ビットフラグ       : 1byteの中に「毒/麻痺/睡眠」などの状態を 1bit ずつ詰める
・通信パケット       : ヘッダーに 3bit のフラグや 5bit のデータ長が混在
```

### 最重要メッセージ
**「1byte = 8bit」はメモリの都合であり、データの意味の単位は「仕様」が決める**

* bit列だけでは意味は決まらない
* **「何bitを1単位として読むか」も解釈ルールの極めて重要な一部である**

---

# bit・byte・メモリを、実際のプログラムから見てみる

## 情報工学の理論から、プログラムによる実践的な観察へ

```text
【ここまで学んだこと】
bit（最小単位・状態）
  ↓
解釈ルール（文字・数値・画像・命令）
  ↓
1byte ＝ 8bit（256状態の基本箱）
  ↓
データの意味単位は byte 境界とズレることもある（12bit packed）
```

* ここまでは「コンピュータの仕組み」を理論として整理してきました
* **では、実際のプログラムから見ると、これらはどう扱われているのか？**
* ここからは、プログラムを動かしてメモリ内部の様子を観察してみましょう

---

# 今回はC++を「メモリを見る道具」として使う

## 言語の学習ではなく、コンピュータ内部を覗く「顕微鏡」として

```text
世の中には多様なプログラミング言語がある:
Python / Java / C# / JavaScript / C++ ...
```

* **C++は高水準な記述もできる一方で、低水準なメモリ操作まで扱えるシステムプログラミング言語**
* メモリの番地（アドレス）や生バイト列をごまかさずに直接覗き込める
* そのため、**「bit・byte・メモリの仕組み」を観察する顕微鏡** として最適
* ※今回はC++の文法習得が目的ではありません。「観察の道具」として使います

---

# C++の「型」は、bit列の読み方を決める

## 前半で学んだ「bit列 ＋ 解釈ルール ＝ データ」のプログラム版

メモリ上には、ただのbit列が置かれているだけです。

```text
メモリ上の bit 列:
00001000
    │
    ↓ 【解釈ルール＝型】 「符号なし 8bit 整数として読む」
uint8_t
    │
    ↓
数値の 「8」 になる！
```

* **プログラミング言語の「型（Type）」も、解釈ルールの一つにすぎない**
* メモリ上のbit列を「どう解釈するか」をコンパイラに指示するのが型の役目
* 型というレンズを通すことで、人間は生の0と1を意識せずに安全に扱える

---

# 基本型で見る「サイズの解釈」の違い

## uint8_t と int はメモリをどう読むのか？

```text
【uint8_t】 1 byte（8 bit = 256状態）
[ 0〜255 ]  ← 1つの箱をそのまま「符号なし整数」として解釈する型

【int】      4 byte（32 bit = 約43億状態）※一般的な環境
[ byte 0 ][ byte 1 ][ byte 2 ][ byte 3 ]
4つの箱を合体させ、約 -21億 〜 +21億 の「符号付き整数」として解釈する型
```

* `uint8_t` は **1つの箱（1byte）** をそのまま読む型
* `int` は **4つの箱（4byte）を合体** させて大きな数値として読む型
* **では、この1バイトの「箱」たちは、コンピュータの中でどう並んでいるのか？**

---

# 2. メモリの正体とは？

## 「1バイトの箱がズラリと一列に並んだ巨大なロッカー街」

メモリ（RAM）の構造は、驚くほどシンプルです。

```text
アドレス:  0x1000  0x1001  0x1002  0x1003  0x1004 ...
メモリ:   [ 1byte ][ 1byte ][ 1byte ][ 1byte ][ 1byte ]
             ↑
           この箱1つ1つが「256通りの状態」を保持する
```

* メモリの最小単位は **常に 1バイト**
* 各箱には重複しない番号札 **「アドレス（番地）」** が付いている
* ポインタとは、単にこの **「ロッカーの番号札（番地）」** のこと
* どんな複雑な構造体も、メモリ上では **1列に並んでいるだけ**

---

# 3. リトルエンディアンの罠

## 人間の直感と、CPUの並べ順は「逆」である

`int x = 100;`（16進数で `0x00000064`）をメモリに置くとき:

```text
【人間の直感（ビッグエンディアン）】
上位桁から素直に置く
[ 00 ][ 00 ][ 00 ][ 64 ]

【実際のPC / x86・ARM（リトルエンディアン）】
下位桁（小さい桁）から先に置く！
[ 64 ][ 00 ][ 00 ][ 00 ]
  1B    2B    3B    4B
```

* x86 や ARM などの主要 CPU は **リトルエンディアン** を採用
* メモリの先頭（若い番地）に、一番下の桁が配置される

---

# 【実験】2バイト目を書き換えると何が起きるか？

## int 100 の 2バイト目を 00 → 01 に変更してみる

```text
変更前（100）:
[ 64 ][ 00 ][ 00 ][ 00 ]  → 0x00000064 = 10進数の 100

変更後（2バイト目を 01 に書き換え）:
[ 64 ][ 01 ][ 00 ][ 00 ]  → 0x00000164 = 10進数でいくつ？
```

* 直感だと「101」になりそう？
* **いいえ、101 にはなりません！**
* 2バイト目の `01` は、16進数で `0x0100`（10進数で **256**）の重みを持つ
* `256 + 100 = 356` に化ける！

---

# 実験コード（C++）

## 実際にメモリを直接いじって確かめる

```cpp
#include <iostream>
#include <cstdint>

int main() {
    int x = 100;
    uint8_t* p = reinterpret_cast<uint8_t*>(&x);

    std::cout << "変更前: " << x << std::endl; // 100

    p[1] = 1; // 2バイト目を直接書き換える！

    std::cout << "変更後: " << x << std::endl; // 356
    return 0;
}
```

* **ポインタを使って 2バイト目（p[1]）だけを書き換えた**
* 結果は見事に **356** になる
* これが「メモリの上で何が起きているか」を直接見るということ

# 4. バッファとは何か？

## 生メモリに「型」というレンズを当てる感覚

実務でよく聞く「バッファ」という言葉。
正体は **ただの連続したメモリ領域（バイト配列）** です。

```text
生メモリ:
[ 64 ][ 01 ][ 00 ][ 00 ][ 05 ][ 00 ][ 00 ][ 00 ] ...

レンズA（int* として見る）:
[      356      ][       5       ] → 2つの int に見える！

レンズB（uint8_t* として見る）:
[ 64 ][ 1 ][ 0 ][ 0 ][ 5 ][ 0 ][ 0 ][ 0 ] → 8個のバイトに見える！
```

* メモリそのものには「型」など存在しない
* プログラムが **「この4バイトを int として解釈する」** と決めているだけ

---

# 5. 現場の落とし穴① アライメント

## なぜCPUは「中途半端なアドレス」を嫌うのか？

CPUはメモリからデータを読むとき、1バイトずつチマチマ読みません。
**4バイトや8バイトのブロック単位** で一気に読み込みます。

```text
4バイト境界（0, 4, 8, 12番地...）に揃っている場合:
[ アドレス 0x0004 ] ---- 1回のアクセスで一撃読み込み！

境界をまたいでいる場合（0x0003 から 4バイト）:
[ ブロック 0 ][ ブロック 1 ] ---- 2回読んで結合する（遅い＆CPUが悲鳴）
```

* **境界アライメント（Alignment）**: データを型に応じた境界に配置するルール
* 4バイトの `int` は、4の倍数番地に置かなければならない
* これを守らないと、**処理速度の低下やクラッシュ** を招く

---

# 現場の落とし穴② パディング

## 構造体のサイズが見た目と合わない謎

```cpp
struct PlayerData {
    uint8_t  id;    // 1バイト
    int      hp;    // 4バイト
};
// 1 + 4 = 5バイト？
std::cout << sizeof(PlayerData); // → 出力は「8」になる！
```

```text
実際のメモリ配置:
[ id (1B) ][ パディング空き地 (3B) ][      hp (4B)      ]
0x00        0x01 〜 0x03             0x04 〜 0x07
```

* `hp` を4の倍数番地に置くため、コンパイラが自動で **3バイトの隙間** を詰める
* この隙間を **パディング（Padding）** と呼ぶ
* **「構造体のサイズ ＝ 各メンバの足し算」とは限らない！**

---

# これが実務でどう問題になるか？

## 通信やファイル保存で絶対にやってはいけないこと

パディングを考慮せずに、構造体をそのままファイルに保存すると:

```text
保存した側（パディングが 3バイト入った状態）
[ id ][ pad ][ pad ][ pad ][ hp ][ hp ][ hp ][ hp ] (8バイト)

別の環境・別の言語（パディングなしを期待）
[ id ][ hp ][ hp ][ hp ][ hp ] (5バイトのはず！)
  ↓
データが 3バイト分まるごとズレて大惨事！
```

* 通信パケットや独自バイナリファイルでは、**パディングの混入** が最大のバグ源
* だから低レイヤでは「1バイトの並び」を正確に制御する必要がある

---

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① bit は「意味」ではなく「状態」である**
  * 0と1そのものに意味はなく、解釈ルールがあって初めてデータになる
* **② 1byte は「256通りの状態を表せる箱」**
  * 整数として解釈すれば 0〜255、文字や色や命令にも化ける
* **③ byte境界と「データの意味の境界」はズレることがある**
  * 12bit画像のように、1byteに収まらないデータはbit演算で取り出す
* **④ メモリは1バイトの箱が一列に並んだロッカー街**
  * リトルエンディアンでは「小さい桁」から先に並ぶ
* **⑤ 型はメモリを見る「レンズ」であり、パディングに注意**
  * アライメントによる隙間（余白）を常に意識する
