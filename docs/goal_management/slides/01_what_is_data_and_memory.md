# データとは何か？

## ― ビット・バイトから始まるメモリの正体 ―

コンピュータシステム基礎研修 第1回

---

# 本日のアジェンダ

## 「0と1の並び」から、なぜ文字・画像・プログラムが生まれるのか？

* **① 最小単位：bit は「状態」である**
  * 0と1そのものには意味がない？
* **② 「bit列 ＋ 解釈ルール」の正体**
  * 同じbit列でも見方次第で文字・数値・画像に化ける
* **③ プログラムも「0と1」で動いている**
  * 「1 + 1」をCPUが計算するカラクリ
* **④ 1byte と 256通りの状態**
  * 整数として解釈すると 0〜255 になる理由
* **⑤ メモリの正体・リトルエンディアン・パディング**
  * 1バイトのロッカー街と現場の落とし穴

---

# 1. そもそも「データ」とは何か？

## コンピュータの世界は超極論すると「0 と 1」だけ

どんな画像も、プログラムも、文字列も、
最終的には **0 または 1** の並びで表現されています。

```text
最小単位: 1 bit = [0] または [1]
```

* **1 bit** で表せる状態は **2通り**（0, 1）
* **2 bit** で表せる状態は **4通り**（00, 01, 10, 11）
* **3 bit** で表せる状態は **8通り**（000 〜 111）
* **ビットが1つ増えるたびに、作れる「状態の数」は2倍になる**

---

# でも、0と1だけで何ができるの？

## bitは「意味」ではなく、単なる「状態」にすぎない

「0と1が増えて何通りも作れるのは分かった。でも、それで何ができるの？」
ここで最も重要な事実は、**bitそのものには何の意味もない** ということです。

```text
bit はただの「スイッチの状態」:
0 = スイッチが OFF
1 = スイッチが ON
```

* 2bit なら `00`, `01`, `10`, `11` という **4つの状態** が作れる
* これを「00=0, 01=1, 10=2, 11=3」と決めれば **整数** になる
* これを「00=青, 01=黄, 10=赤」と決めれば **信号機** になる
* **bitが増えるほど「作れる状態数」が増え、そこに人間が意味を割り当てる**

---

# 0と1に意味を与えるのは「解釈ルール」

## 「bit列 ＋ 解釈ルール ＝ 意味のあるデータ」

たとえば、メモリに **`01000001`** という 8bit の並びがあったとします。
これ単体では、何を表しているか誰にも分かりません。

```text
                  01000001（8つのbit列）
                            │
      ┌─────────────┬───────┴─────┬─────────────┐
      ↓             ↓             ↓             ↓
  【 整数 】    【 文字 】    【 画像 】    【 CPU命令 】
     65             A          明るさ65      何かの命令
 (数値ルール)  (ASCIIルール)  (画像ルール)  (CPUのルール)
```

* **同じ bit 列でも、当てる「解釈ルール」によってまったく別の意味になる**
* コンピュータのデータとは、すべてこの「状態」と「ルール」の組み合わせ

---

# プログラムも「0と1」なの？

## データだけでなく、CPUへの命令もすべてbit列である

「画像や文字がbitなのは分かった。でもプログラムの処理はどうやって動くの？」
**実は、CPUを動かす「命令（プログラム）」も、まったく同じbit列です。**

```text
人間が書いたプログラム:
x = 1 + 1;

コンパイラが変換した機械語（CPUへの命令列）:
0010 00000001 00000001 ...（すべて 0 と 1 の並び！）
```

* CPUは **「このbit列が来たら足し算の回路を動かす」** と物理的に作られた機械
* メモリの上では、画像データもCPUの命令も **「同じbit列」** として並んでいる

---

# では「1 + 1」はどうやって計算される？

## 架空のシンプルCPUで計算の仕組みを覗いてみる

CPUの中に、あらかじめ次のような **「命令ルール」** があるとします。

```text
【CPUが知っているルール】
00000001 = 数値の「1」
00000010 = 数値の「2」
0010     = ADD（足し算せよ）という命令
```

```text
① 命令を読み込む: 0010 (ADD) ──> CPU「足し算の準備完了」
② 値1を読み込む : 00000001  ──> CPU「1つ目の値は 1」
③ 値2を読み込む : 00000001  ──> CPU「2つ目の値も 1」
④ 回路で計算実行: 1 + 1 を計算 ──> 00000010 を出力！
```

* 出力された `00000010` を整数ルールで解釈すると **`2`** になる！
* **CPU側に「このbit列は命令」「このbit列は値」というルールがあるから計算が成立する**

---

# 1バイトは「256通りの状態を表せる箱」

## 8ビットをひとまとめにしたコンピュータの標準規格

```text
1 byte = 8 bit
2^8 = 256 通りの「状態」を作れる箱
```

* **この256通りの状態を、どう解釈するか？**
  * **整数として解釈する** ──> **0 〜 255** の数値になる（最小 `00000000` 〜 最大 `11111111`）
  * **文字として解釈する** ──> アルファベットや記号（ASCIIコード）
  * **色として解釈する**   ──> モノクロ画像の濃淡（0:黒 〜 255:白）
  * **CPU命令として解釈する** ──> 機械語の1ステップ

### 一行で言えば
**1バイトとは「256通りの状態を保持できる小さな箱」である**

---

# C++の基本型で見てみる

## uint8_t と int は何が違うのか？

```text
【uint8_t】 1 byte（8 bit = 256状態）
[ 0〜255 ]  ← 1バイトをそのまま「符号なし整数」として解釈する型

【int】      4 byte（32 bit = 約43億状態）※一般的な環境
[ byte 0 ][ byte 1 ][ byte 2 ][ byte 3 ]
4つの箱を合体させ、約 -21億 〜 +21億 の「符号付き整数」として解釈する型
```

* 100 という整数なら、1バイト（0〜255）の箱1個で十分表せる
* **では、4バイトの int に入れた 100 は、メモリの中でどう並んでいるのか？**

---

# 2. メモリの正体とは？

## 「1バイトの箱がズラリと一列に並んだ巨大なロッカー街」

メモリ（RAM）の構造は、驚くほどシンプルです。

```text
アドレス:  0x1000  0x1001  0x1002  0x1003  0x1004 ...
メモリ:   [ 1byte ][ 1byte ][ 1byte ][ 1byte ][ 1byte ]
             ↑
           この箱1つ1つが「256通りの状態」を保持する
```

* メモリの最小単位は **常に 1バイト**
* 各箱には重複しない番号札 **「アドレス（番地）」** が付いている
* ポインタとは、単にこの **「ロッカーの番号札（番地）」** のこと
* どんな複雑な構造体も、メモリ上では **1列に並んでいるだけ**

---

# 3. リトルエンディアンの罠

## 人間の直感と、CPUの並べ順は「逆」である

`int x = 100;`（16進数で `0x00000064`）をメモリに置くとき:

```text
【人間の直感（ビッグエンディアン）】
上位桁から素直に置く
[ 00 ][ 00 ][ 00 ][ 64 ]

【実際のPC / x86・ARM（リトルエンディアン）】
下位桁（小さい桁）から先に置く！
[ 64 ][ 00 ][ 00 ][ 00 ]
  1B    2B    3B    4B
```

* x86 や ARM などの主要 CPU は **リトルエンディアン** を採用
* メモリの先頭（若い番地）に、一番下の桁が配置される

---

# 【実験】2バイト目を書き換えると何が起きるか？

## int 100 の 2バイト目を 00 → 01 に変更してみる

```text
変更前（100）:
[ 64 ][ 00 ][ 00 ][ 00 ]  → 0x00000064 = 10進数の 100

変更後（2バイト目を 01 に書き換え）:
[ 64 ][ 01 ][ 00 ][ 00 ]  → 0x00000164 = 10進数でいくつ？
```

* 直感だと「101」になりそう？
* **いいえ、101 にはなりません！**
* 2バイト目の `01` は、16進数で `0x0100`（10進数で **256**）の重みを持つ
* `256 + 100 = 356` に化ける！

---

# 実験コード（C++）

## 実際にメモリを直接いじって確かめる

```cpp
#include <iostream>
#include <cstdint>

int main() {
    int x = 100;
    uint8_t* p = reinterpret_cast<uint8_t*>(&x);

    std::cout << "変更前: " << x << std::endl; // 100

    p[1] = 1; // 2バイト目を直接書き換える！

    std::cout << "変更後: " << x << std::endl; // 356
    return 0;
}
```

* **ポインタを使って 2バイト目（p[1]）だけを書き換えた**
* 結果は見事に **356** になる
* これが「メモリの上で何が起きているか」を直接見るということ

# 4. バッファとは何か？

## 生メモリに「型」というレンズを当てる感覚

実務でよく聞く「バッファ」という言葉。
正体は **ただの連続したメモリ領域（バイト配列）** です。

```text
生メモリ:
[ 64 ][ 01 ][ 00 ][ 00 ][ 05 ][ 00 ][ 00 ][ 00 ] ...

レンズA（int* として見る）:
[      356      ][       5       ] → 2つの int に見える！

レンズB（uint8_t* として見る）:
[ 64 ][ 1 ][ 0 ][ 0 ][ 5 ][ 0 ][ 0 ][ 0 ] → 8個のバイトに見える！
```

* メモリそのものには「型」など存在しない
* プログラムが **「この4バイトを int として解釈する」** と決めているだけ

---

# 5. 現場の落とし穴① アライメント

## なぜCPUは「中途半端なアドレス」を嫌うのか？

CPUはメモリからデータを読むとき、1バイトずつチマチマ読みません。
**4バイトや8バイトのブロック単位** で一気に読み込みます。

```text
4バイト境界（0, 4, 8, 12番地...）に揃っている場合:
[ アドレス 0x0004 ] ---- 1回のアクセスで一撃読み込み！

境界をまたいでいる場合（0x0003 から 4バイト）:
[ ブロック 0 ][ ブロック 1 ] ---- 2回読んで結合する（遅い＆CPUが悲鳴）
```

* **境界アライメント（Alignment）**: データを型に応じた境界に配置するルール
* 4バイトの `int` は、4の倍数番地に置かなければならない
* これを守らないと、**処理速度の低下やクラッシュ** を招く

---

# 現場の落とし穴② パディング

## 構造体のサイズが見た目と合わない謎

```cpp
struct PlayerData {
    uint8_t  id;    // 1バイト
    int      hp;    // 4バイト
};
// 1 + 4 = 5バイト？
std::cout << sizeof(PlayerData); // → 出力は「8」になる！
```

```text
実際のメモリ配置:
[ id (1B) ][ パディング空き地 (3B) ][      hp (4B)      ]
0x00        0x01 〜 0x03             0x04 〜 0x07
```

* `hp` を4の倍数番地に置くため、コンパイラが自動で **3バイトの隙間** を詰める
* この隙間を **パディング（Padding）** と呼ぶ
* **「構造体のサイズ ＝ 各メンバの足し算」とは限らない！**

---

# これが実務でどう問題になるか？

## 通信やファイル保存で絶対にやってはいけないこと

パディングを考慮せずに、構造体をそのままファイルに保存すると:

```text
保存した側（パディングが 3バイト入った状態）
[ id ][ pad ][ pad ][ pad ][ hp ][ hp ][ hp ][ hp ] (8バイト)

別の環境・別の言語（パディングなしを期待）
[ id ][ hp ][ hp ][ hp ][ hp ] (5バイトのはず！)
  ↓
データが 3バイト分まるごとズレて大惨事！
```

* 通信パケットや独自バイナリファイルでは、**パディングの混入** が最大のバグ源
* だから低レイヤでは「1バイトの並び」を正確に制御する必要がある

---

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① bit は「意味」ではなく「状態」である**
  * 0と1そのものに意味はなく、解釈ルールがあって初めてデータになる
* **② 1byte は「256通りの状態を表せる箱」**
  * 整数として解釈すれば 0〜255、文字や色や命令にも化ける
* **③ プログラムもデータもメモリ上では同じ bit 列**
  * CPUの回路ルールによって 1+1 などの計算が実行される
* **④ メモリは1バイトの箱が一列に並んだロッカー街**
  * リトルエンディアンでは「小さい桁」から先に並ぶ
* **⑤ 型はメモリを見る「レンズ」であり、パディングに注意**
  * アライメントによる隙間（余白）を常に意識する
