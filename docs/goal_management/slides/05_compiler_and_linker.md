# 1. 赤線がないのにビルドに失敗する現象

## Visual Studio で誰もが遭遇する謎のエラー：LNK2019

エディタ上に赤い波線はなく、`#include` も通っているのに:

```text
error LNK2019: 未解決の外部シンボル
    "int __cdecl ProcessImage(uint8_t*, int, int)" が
    関数 _main で参照されました
fatal error LNK1120: 1 件の未解決の外部参照
```

* 文法エラー（赤線）は一切出ていない
* `#include "ProcessImage.h"` も正しく見つかり、コード補完も効く
* **なのに、なぜ実行ファイル（.exe）が作れないのか？**
* 初学者の疑問：
  * 「文法が合っているならビルドしてよ！」
  * 「中身がないなら、なぜ #include の時点で怒ってくれないの？」

# その疑問の根本原因：コンパイラとリンカは「別人」！

## 私たちが何気なく押す「ビルド」ボタンの裏側

「ビルド」は単一の作業ではありません。
**まったく役割の異なる職人たちによるバケツリレー** です。

```text
【コンパイラ（文法チェックと機械語化の職人）】
「お、ProcessImage の宣言（約束手形）があるな。
 文法は正しいから、呼び出す準備をした機械語の部品を作っておくよ！」
      ↓ （文法的にOKなので合格！）
      ↓
【リンカ（部品を合体させてEXEを完成させる職人）】
「じゃあ部品を合体させるぞ……ん？
 ProcessImage を呼ぶ命令はあるが、その実体（中身の機械語）がどこにもない！
 合体できないからEXEを作れないぞ！」
      ↓
error LNK2019: 未解決の外部シンボル（実体が見つからない！）
```

* **エディタやコンパイラが見ている世界** と **リンカが見ている世界** は全く違う！

# 2. ソースコードがEXEになるまでの全体地図

## ソースコードから完成品（EXE）までの4大工程

```text
main.cpp                      Process.cpp
   │                              │
   ↓ プリプロセス                 ↓ プリプロセス（#include展開・マクロ置換）
[ プリプロセス済みソース ]     [ プリプロセス済みソース ]
   │                              │
   ↓ コンパイル                   ↓ コンパイル（構文解析・機械語への変換）
   │ (※アセンブル)               │ (※機械語バイナリ化)
[ オブジェクトファイル ]       [ オブジェクトファイル ]
main.obj                      Process.obj
   │                              │
   └──────────────┬───────────────┘
                  │
                  ↓ リンク（リンカ：シンボルの結合・アドレス確定）
            [ 実行ファイル ]
               app.exe
```

* ※注記: 現代のコンパイラドライバ（`cl.exe` や `gcc`, `clang`）はこれらを一括で実行してくれますが、裏では明確に段階を踏んでいます。

# 3. `#include` の正体：リンクではなく「テキスト展開」

## よくある誤解：「ヘッダを読み込んでライブラリとリンクしている？」

`#include` は、ライブラリを結合する処理ではありません。
**「指定したファイルの中身を、その場所にそのまま展開する」** プリプロセッサの処理です。

```text
【Process.h（ヘッダ）】                【main.cpp】
int ProcessImage(uint8_t* p, int s);   #include "Process.h"
                                       int main() {
                                           ProcessImage(nullptr, 0);
                                       }
                                             │
                                             ↓ プリプロセッサが展開
                                       【main.cpp（展開後）】
                                       int ProcessImage(uint8_t* p, int s); // そのまま展開された！
                                       int main() {
                                           ProcessImage(nullptr, 0);
                                       }
```

* プリプロセッサは指定されたヘッダを見つけて内容を展開した時点で仕事完了となります
* この時点では、関数の処理内容（中身のコード）は1行も存在しません！

---

# ヘッダファイルには何を書くのか？

## 「宣言」を共有し、無用な重複を防ぐ

なぜヘッダファイルを `#include` するのか？
──> コンパイラに **「こういう関数や型がどこかにあるよ」という予告** を知らせるため。

* **通常の関数では**:
  * ヘッダ（`.h`）に **「宣言（呼び出しルール）」** を書き、複数の `.cpp` で共有する
  * 実装（`.cpp`）に **「定義（処理の実体）」** を書くことが多い

```text
※技術的注記:
「ヘッダには宣言しか書けない」わけではありません。
inline関数やテンプレート（template）、constexpr関数のように、
ヘッダ側に処理の定義（中身）を書く仕組みもC++には存在します。
まずは基本として「通常の関数では宣言と定義を分けることが多い」と押さえましょう。
```

---

# 4. 「宣言」と「定義」の決定的な違い

## コンパイラを納得させる「約束手形」と、メモリ上の「実体」

```cpp
// 【宣言（Declaration）】: 約束手形
// 「ProcessImage という名前で、この引数を受け取り、intを返す関数が世界のどこかにある」
int ProcessImage(uint8_t* buffer, int lineSpan);
```

* 関数の名前、引数の型、戻り値の型（シグネチャ）だけを伝える
* コンパイラはこれを見て、**呼び出し側のコードを安心して機械語に変換できる**

```cpp
// 【定義（Definition）】: 実体
// 「実際にCPUが実行する処理（メモリ上に機械語として配置される実体）」
int ProcessImage(uint8_t* buffer, int lineSpan) {
    if (buffer == nullptr) return -1;
    // ... 実際の画素処理 ...
    return 0;
}
```

* **宣言は「形」だけを教える。定義は「実体（メモリ上の機械語）」を作る。**

---

# なぜ宣言と定義を分けるのか？：独立コンパイルの思想

## 巨大なプログラムを高速にビルドするための大発明

もしすべてのコードが互いの実体を知る必要があったら、
1行書き換えるたびにプロジェクト全体（何百万行）を再コンパイルしなければなりません。

```text
main.cpp は Process.h（宣言）だけを見ている
  │
  ├─ Process.cpp の中身がどう実装されているか知らなくていい！
  ├─ 「宣言」という約束手形があるから、main.cpp 単独で機械語になれる！
  │
  ↓
main.cpp 単体で main.obj にコンパイル完了！
```

* **「各 .cpp ファイルは、互いに独立してコンパイルできる」**（独立コンパイル）
* 変更された `.cpp` だけを再コンパイルすればよいため、ビルド時間を大幅に短縮できる！
* しかし、この「分割」があるからこそ、**最後に繋ぎ合わせる職人（リンカ）** が必要になる！

# 5. オブジェクトファイル（`.obj`）の正体

## 単なる機械語ではない。「まだ完成していないプログラム部品」

コンパイラが出力する `.obj`（Linux等では `.o`）の中身を覗くと:

```text
【オブジェクトファイル（.obj）の構造概念】

1. 機械語コード（.textセクション）
   - コンパイルされたCPU命令列（関数の処理）
2. データ（.data / .rdataセクション）
   - 文字列リテラルやグローバル定数など
3. シンボルテーブル（Symbol Table）
   - 提供シンボル（エクスポート）: 「自分の中に main という関数があります」
   - 未解決参照（インポート）    : 「ProcessImage という関数を呼び出したいです」
4. 再配置情報（Relocation Table）
   - 「ProcessImage の飛び先アドレスは、あとでリンカに書き込んでもらう場所」のリスト
```

* `.obj` 単体では実行できない。
  外部へのジャンプ先番地が **空欄（未解決）のまま残された組み立て部品** なのです。

---

# シンボル（Symbol）：リンカが部品を結ぶための「目印」

## 人間が書いた「関数名」が、部品同士の結合ピンになる

機械語レベルでは、関数呼び出しは最終的に **「メモリ番地 `0x00401234` へ飛べ（CALL）」** という数値になります。
しかし、コンパイル時点では相手がどこに配置されるか分からない！

そこで、コンパイラは関数名や変数名を目印（**シンボル**）として残します。

```text
【main.obj】
main関数の機械語:
  CALL [ ?????? ]  ← 「まだ飛び先が分からない！」
  未解決シンボル参照: "ProcessImage" を探してくれ

【Process.obj】
ProcessImage関数の機械語:
  [ 0x55 0x8B 0xEC ... ] ← 実際のCPU命令
  提供シンボル: ここに "ProcessImage" の実体があるぞ
```

* シンボルとは、**「部品同士をカチッと繋ぐためのオスメスの端子」** のようなもの！
* ※C++では引数の型違い（オーバーロード）を区別するため、関数名に引数情報などを付加したシンボル名が生成されます。そのため型が1文字でも異なると「別のシンボル」と見なされます。

---

# 6. リンカの仕事：シンボルを結合し、アドレスを確定させる

## バラバラの部品を1本の完成品（EXE）に組み上げる

リンカ（Linker）は、すべての `.obj` を集めて以下の大仕事をします。

```text
ステップ 1: 全部品の機械語をメモリ空間に並べる
  [ main関数の機械語 ] [ ProcessImage関数の機械語 ] ...

ステップ 2: 名前の照合（シンボル解決）
  main.obj の「ProcessImage を探して」──> Process.obj の「ここにある」を発見！

ステップ 3: アドレスの書き込み（再配置 / Relocation）
  main関数の CALL [ ?????? ] の空欄に、
  配置された ProcessImage の実際のメモリ番地（例: 0x00401050）を書き込む！
```

* 空欄だった呼び出し先がすべて埋まり、**1本の実行可能ファイル（`.exe`）が完成する！**

---

# 7. 静的ライブラリ（`.lib`）の正体

## 便利な部品（.obj）を1つの箱に詰めたアーカイブ集

毎回 `foo.obj`, `bar.obj`, `baz.obj` ... と何十個ものファイルをリンカに渡すのは大変です。
そこで、よく使う部品をまとめたものが **静的ライブラリ（`.lib` / Linuxでは `.a`）** です。

```text
【静的ライブラリ（Utility.lib）】
┌──────────────────────────────────────┐
│  Math.obj   Image.obj   File.obj ... │ （.obj の詰め合わせパック）
└──────────────────────────────────────┘
                  │
                  ↓ リンカに渡す
リンカ「お、main.obj が必要としているシンボルが Image.obj に入っているな。
       Image.obj だけを取り出して EXE に埋め込もう！」
```

```text
※重要な技術的注記（Windowsの二面性）:
Windowsでは「静的ライブラリ」の拡張子も .lib ですが、
第6回で学ぶ「DLL用のインポートライブラリ」も同じ .lib という拡張子を使います。
そのため「.lib は必ず .obj のアーカイブである」とは断定できません。
まずは「複数のオブジェクトコードを再利用しやすくまとめた箱」として理解しましょう。
```

# 8. なぜ LNK2019（未解決の外部シンボル）が起きるのか？

## 「宣言を信じて部品を作ったが、実体が見つからなかった」

ここで最初の謎に戻りましょう。なぜ赤線が出ないのに `LNK2019` が出るのか？

```text
【コンパイラの視点（main.cpp のみを見る）】
「Process.h に ProcessImage の宣言があるな。約束手形があるからOK！
 CALL [ ??? ] という空欄を残して main.obj を作ったぞ。私の仕事は終わり！」
      ↓ （文法的に完璧なのでエラーは出ない）

【リンカの視点（プロジェクト全体を見る）】
「よし、main.obj を開いたぞ。ProcessImage というシンボルの実体を探そう。
 ……あれ？ プロジェクト内の .obj や .lib を全部探したが、
 ProcessImage の実体（定義）がどこにも見当たらないぞ？
 空欄を埋められないから、EXE を作れない！」
      ↓
error LNK2019: 未解決の外部シンボル "ProcessImage" が関数 _main で参照されました
```

* **「コンパイラは宣言（約束手形）でパスするが、リンカは実体（定義）が見つからなければエラーにする」**

---

# 現場で多発する LNK2019 の代表的な原因

## 原因は1つではない！ 現場の定番トラブル集

`LNK2019` は、コード内で参照されたシンボルの実体をリンカが解決できなかったことを示しています。
その裏には様々な原因があります。

* **① `.cpp` ファイルをプロジェクトに追加し忘れている（超定番！）**
  * ヘッダ（`.h`）だけプロジェクトに入れて、実装の `.cpp` がビルド対象に入っていない
* **② 関数の宣言と定義で型や名前が微妙に一致していない**
  * 引数の型違い（`int` と `size_t`）、`const` の有無、クラス名（`MyClass::`）の付け忘れ
  * リンカにとっては1文字でも違えば「別のシンボル」に見える！
* **③ 宣言だけ書いて、定義（中身のコード）を書き忘れている**
* **④ 名前空間（`namespace`）が宣言と定義でズレている**
* **⑤ 必要な外部ライブラリ（`.lib`）をリンカの設定に指定していない**
* **⑥ 条件付きコンパイル（`#ifdef` 等）で実体のコードが無効化されている**

---

# もう一つの定番：LNK1169「多重定義されたシンボル」

## 逆に「同じ名前の実体が2つ見つかった」ときのパニック

ヘッダファイルに、通常の関数の **定義（中身のコード）** を直接書いてしまうと？

```cpp
// Common.h に中身を直接書いてしまった！
int Add(int a, int b) {
    return a + b;
}
```

```text
main.cpp ──(#include "Common.h")──> main.obj に Add の機械語が生成される
foo.cpp  ──(#include "Common.h")──> foo.obj  にも Add の機械語が生成される
                 │
                 ↓ リンカが合体しようとすると……
リンカ「おい！ main.obj にも foo.obj にも Add の実体があるぞ！
       どっちのアドレスを書き込めばいいんだ！？」
                 ↓
error LNK1169: 1 つ以上の複数回定義されているシンボルが見つかりました
```

* `#include` はテキスト展開なので、両方の `.obj` に同じ実体が生まれてしまう！
* **だからこそ「ヘッダには宣言、cppに定義」という住み分けが基本になる！**

# 現場のトラブルシューティング：リンカエラー解決フロー

## `LNK2019` が出たときの確実なチェックリスト

```text
error LNK2019: 未解決の外部シンボル "ProcessImage" が _main で参照されました
  │
  ├─ 【チェック 1: ファイルの登録】
  │   その関数を書いた .cpp ファイルは、プロジェクト（ビルド対象）に入っているか？
  │   （ファイルを移動したときや、新規作成時にプロジェクトから漏れるミス）
  │
  ├─ 【チェック 2: シグネチャの完全一致】
  │   .h の宣言と .cpp の定義で、関数名・引数の型・const・namespace は完全一致しているか？
  │   （クラス関数の場合、void MyClass::Func() の「MyClass::」を忘れていないか？）
  │
  └─ 【チェック 3: ライブラリのリンク指定】
      外部ライブラリの関数なら、対応する .lib ファイルが
      リンカの「追加の依存ファイル」に正しく指定されているか？
```

* 「赤線がないからコードは合っているはず」という思い込みを捨てる！
* **エラーメッセージに書かれたシンボル名を手がかりに、実体の居場所を捜索する**

# 今回学んだ「静的リンク」と、外の世界への境界

## ビルド時にすべてを埋め込む方式の強みと、その先の世界

今回学んだのは、すべての部品をビルド時に1つのEXEに結合する **「静的リンク（Static Link）」** です。

```text
【静的リンク（今回学んだ世界）】
main.obj + Process.obj + Utility.lib ──(リンカ)──> App.exe（単体で完結！）
```

* **静的リンクの大きなメリット**:
  * 必要なコードがEXEの中に埋め込まれるため、EXE単体で自己完結して動作する
  * リンカが未解決シンボルをビルド時にすべて解決するため、実行前の安全性が高い
* **しかし、実務では次のような要求も生まれる**:
  * 「巨大なEXEを再ビルドせず、部品の差し替えだけでアップデートしたい」
  * 「C++で作った高速処理を、C# や Python などの別言語から呼び出したい」
* これらを可能にする「実行時に結合する仕組み（動的リンク・DLL）」の土台にも、今回学んだ「シンボル」の概念が生きてきます。

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① ビルドは単一の作業ではなく「工程のバケツリレー」**
  * プリプロセス（展開） ──> コンパイル（機械語化） ──> リンク（結合）
* **② `#include` はリンクではなく「テキスト展開」**
  * ヘッダの中身をその場に貼り付けるだけ。実体を探すのはリンカの仕事
* **③ コンパイラとリンカは「別人」である**
  * コンパイラは「宣言（約束手形）」を信じる。リンカは「定義（実体）」を探して結合する
* **④ `.obj` は未完成の部品、シンボルは結合用の目印**
  * 機械語だけでなく、未解決の参照と提供シンボル、再配置情報を持つ
* **⑤ `LNK2019` は「リンカがシンボルの実体を見つけられなかった」叫び**
  * cppの追加漏れ、シグネチャの不一致、libのリンク漏れなどを順に疑う
