# 1. 現場の2つの疑問（Why）

## アドレスとマルチスレッドにまつわる現場トラブル

システム開発やトラブルシューティングで、多くのエンジニアが直面する2つの疑問があります。

```text
【疑問 1: アドレスが同じなら読めるのか？】
アプリAでポインタの数値を調べたら「0x0000012345678000」だった。
アプリBのメモリにも、同じ数値「0x0000012345678000」のアドレスが存在する。
では、アプリBからそのポインタを使えば、アプリAのデータを読み書きできるのか？
──> 通常、そうはならない！ まったく別のデータになるかクラッシュする！

【疑問 2: なぜ単純な足し算が狂うのか？】
counter = 0 に対して、
スレッドAが100万回「counter++」し、スレッドBも100万回「counter++」した。
最終的な結果は「200万」になるはずなのに、毎回140万などの変な値になってしまう！
```

* なぜアドレス番号が同じなのに互いにアクセスできないのか？
* なぜ同じメモリを複数の処理で触ると計算が狂うのか？

---

# その疑問の根本原因：プロセスは「箱」、スレッドは「流れ」！

## コンピュータシステムが持つ2大実行単位

この2つの疑問を解く鍵が、**プロセス（Process）** と **スレッド（Thread）** の境界線です。

```text
Process（実行環境の箱 / 独立した仮想アドレス空間）
┌─────────────────────────────────────────────────────────┐
│ 仮想アドレス空間（コード、静的データ、動的メモリ...）   │
│                                                         │
│   Thread A                      Thread B                │
│   ├ スタック領域                ├ スタック領域          │
│   └ 実行状態（レジスタ・PC等）  └ 実行状態（レジスタ・PC等）
└─────────────────────────────────────────────────────────┘
```

* **プロセス（Process）＝ 独立したメモリ空間（箱）**:
  * アプリAとアプリBは「別の箱（独立した仮想アドレス空間）」なので、通常のポインタで直接相手のメモリに触れることはできない！
* **スレッド（Thread）＝ 箱の中を走る実行の流れ**:
  * スレッドAとスレッドBは「同じ箱（同一のアドレス空間）」のメモリを共有しているため競合が起こる！

# 2. プログラム（Program）と プロセス（Process）を分ける

## 「ディスク上の静止ファイル」と「メモリ上の実行インスタンス」

エンジニアの間で混同されやすい2つの言葉を明確に区別しましょう。

```text
【プログラム（Program: 静物）】
・ストレージ（SSD/HDD）に保存された実行ファイル（.exe など）
・CPU命令列や初期データが仕様に従って記録された byte列（第4回の世界！）

【プロセス（Process: 生物）】
・OSがプログラムをメモリへ展開し、CPU時間などのリソースを割り当てて実行している
  「1つの実行インスタンス」
```

* **具体例**:
  * デスクトップ上の「メモ帳（notepad.exe）」のアイコンは **プログラム**
  * メモ帳をダブルクリックして2つ立ち上げると、**1つのプログラムから2つの独立したプロセス** が起動する！
* プロセスとは、単なるメモリ空間だけでなく、OSリソース（ファイルハンドル等）やスレッドを収容する **「OS管理の実行環境の箱」** です。

# 3. 仮想アドレス（Virtual Address）の正体

## アプリから見えているアドレスは「物理メモリの番地」ではない！

第1回で「アドレスとはメモリ上のロッカー番号」と学びました。
しかし現代のOSにおいて、アプリから見えている番地は **仮想アドレス（Virtual Address）** です。

```text
[ プロセス A の仮想アドレス空間 ]   [ 物理メモリ（RAM） ]   [ プロセス B の仮想アドレス空間 ]
仮想番地 0x1000 ──────(ページ表A)──────> [ 物理ページ X ]
                                         [ 物理ページ Y ] <──────(ページ表B)────── 仮想番地 0x1000
```

* **なぜ疑問1で「同じアドレス値なのに相手のデータを読めない」のか？**:
  * Aの `0x1000` と Bの `0x1000` が同じ物理メモリを指す保証はない！
  * 通常、それぞれのプロセスのページ表等のマッピング文脈（Context）に従って解釈されるから。
* **重要**:
  * **「同じ仮想アドレス値 ＝ 同じメモリ」ではない！**
  * プロセスごとに「その仮想アドレスを何へ対応づけるか」という文脈が異なる。
  * そのため、プロセス境界を越えて通常のポインタ値をそのまま渡しても相手にとっては無意味！
  * ※注: 共有メモリ等の明示的な仕組みを使えば、別プロセスの仮想アドレスが同一の物理ページを参照する構成も可能です。

# 4. プロセスの隔離（Process Isolation）

## 互いのメモリを侵食させないOSの防壁

現代のOSは、各プロセスに対して独立した仮想アドレス空間を割り当て、互いにメモリを直接読み書きできないよう **隔離（Isolation）** しています。

```text
プロセス A （Webブラウザ）        プロセス B （画像処理ソフト）
┌─────────────────────────┐      ┌─────────────────────────┐
│ 仮想アドレス空間 A      │      │ 仮想アドレス空間 B      │
│ [ ポインタ 0x1000 ]     │      │ [ ポインタ 0x1000 ]     │
└────────────┬────────────┘      └────────────┬────────────┘
             │                                │
             └─── 相手のメモリ領域には ───────┘
                  通常のポインタで直接触れない！
```

* **なぜ隔離するのか？**:
  * 1つのアプリがバグで暴走・不正メモリアクセスでクラッシュしても、
    他のアプリやOS全体を巻き添えにせず、そのプロセスだけを安全に終了させるため！
* ※技術的注記: 共有メモリ（Shared Memory）やプロセス間通信（IPC）、メモリマップトファイルなど、OSが提供する明示的な仕組みと権限を使えばプロセス間でデータを共有できます。

# 第6回 DLL の伏線回収：プロセス境界 vs モジュール境界

## なぜ第6回ではポインタを渡して直接メモリを扱えたのか？

第6回で学んだ DLL と、今回の「プロセス隔離」を頭の中で接続しましょう！

```text
【プロセス境界（今回のテーマ）】
・アプリA と アプリB は、別々のプロセス（別々の仮想アドレス空間）
・通常のポインタを渡しても相手には通用しない！

【モジュール境界（第6回のテーマ）】
・App.exe と ImageCore.dll は、同じプロセス（同じ仮想アドレス空間）に同居！
・だから C# と C++ DLL の間でポインタを渡して直接メモリを読み書きできた！
```

```text
【1つのプロセスの内部】
┌───────────────────────────────────────────────┐
│ App.exe                                       │
│   ProcessImage(ptr, width) を呼ぶ             │
│       │（同じアドレス空間内なのでそのまま渡せる！） │
│       ↓                                       │
│   ImageCore.dll                               │
│       ptr が指す共有バッファを直接加工！      │
└───────────────────────────────────────────────┘
```

* **「プロセス境界（空間が違う）」と「モジュール境界（同じ空間の別部品）」は全く別物！**

# 5. スレッド（Thread）とは何か？

## プロセスという箱の中を走る「実行の流れ」

プロセスという箱が作られても、それだけではコードは1行も動きません。
箱の中で命令を1つずつ辿って実行していく実体が **スレッド（Thread）** です。

```text
プロセス（箱）が立ち上がると、
OSによって「最初の1本のスレッド（メインスレッド）」が作られ、
エントリポイント（main関数等）を実行し始めます。
必要に応じて、処理を分担する追加のスレッド（ワーカースレッド）を起動できます。
```

```text
【スレッド（Thread）が保持する固有の情報】

1. プログラムカウンタ（PC / Instruction Pointer）
   - 「今、コードの何行目（どの番地の機械語）を実行しているか」
2. レジスタコンテキスト（Register Context）
   - 計算途中の値やフラグを保持するCPUレジスタの状態
3. スタック領域（Stack）
   - 現在実行中の関数呼び出し履歴や、ローカル変数を格納するメモリ領域
```

* スレッドとは、**「1つの独立した実行コンテキスト（実行状態）」** のことです。

---

# 6. スレッド と CPUコア を分ける

## 「論理的な実行の流れ」と「物理的な計算機」

初学者が最も混同しやすいのが、「スレッド」と「CPUコア」の関係です。

```text
【スレッド（Thread: ソフトウェア側の概念）】
・OSがスケジューリングする「論理的な実行の流れ」
・OSやシステムリソース（スタックメモリ等）の許す範囲で、多数（何百本単位など）を作成できる

【CPUコア / 論理プロセッサ（ハードウェア側の概念）】
・実際に物理的に機械語命令を実行する「物理的な演算ユニット」
・4コア、8コア、16コアなど、物理的に有限な個数しか存在しない
```

```text
【OSスケジューラによる時分割（タイムスライス）】
何百本ものスレッド  ───(OSスケジューラが高速に切り替え)───>  少数のCPUコア
Thread A (1ミリ秒実行) ──> 一時停止 ──> Thread B (1ミリ秒実行) ──> 一時停止 ──> ...
```

* スレッドが100本あっても、CPUが100個あるわけではありません！
* **OSスケジューラがスレッドをCPUコアへ目まぐるしく割り当てている** のです。

---

# 7. 並行（Concurrency）と 並列（Parallelism）

## 「同時に進んでいるように見える」と「物理的に同時に動く」

マルチスレッドを語る上で欠かせない2つの概念を整理しましょう。

```text
【並行（Concurrency / コンカレンシー）】
・複数の処理が「時間的に重なって進行している」状態
・1つのCPUコア上でも、交互に切り替えて実行すれば並行処理になる
・例: 1人のシェフが、2つのコンロの鍋を交互にかき混ぜて料理を進める

【並列（Parallelism / パラレリズム）】
・複数の処理が「複数のCPUコア上で物理的に同時に実行されている」状態
・複数のコアが同時に異なる命令を実行する
・例: 2人のシェフが、それぞれのコンロで同時に料理を作る
```

* **重要**:
  * **「マルチスレッド ＝ 必ず並列（Parallel）に同時実行される」とは限らない！**
  * 1コア環境でもマルチスレッド（並行）は動きますし、OSの都合で切り替わりながら進みます。

# 8. プロセス内でスレッドが共有するもの・異なるもの

## 箱（プロセス）の資源と、流れ（スレッド）の資源

同じプロセス内で動く複数のスレッドは、何を共有し、何が独立しているのか？

```text
1つのプロセス（仮想アドレス空間）
┌──────────────────────────────────────────────────────────┐
│ 機械語コード（.textセクション）                ← 全スレッドで共有│
│ 静的データ / グローバル変数                    ← 全スレッドで共有│
│ 動的に確保されたメモリ（ヒープ領域など）       ← 共有可能        │
│ オープンされたファイル等のOSリソース           ← 全スレッドで共有│
│                                                          │
│   Thread A                      Thread B                 │
│   ├ スタック A（ローカル変数）  ├ スタック B（ローカル変数）│
│   └ レジスタ状態 A (PC等)       └ レジスタ状態 B (PC等)  │
└──────────────────────────────────────────────────────────┘
```

* **各スレッドは「自分専用のスタック」を持ち、独立して関数を呼び出せる**
* 一方で、**「コード・静的変数・ヒープメモリ」は同じ箱の中にあるため、他スレッドからもアクセス可能な状態にある！**
* ※注意: スレッドのスタックも同じ仮想空間内にあるため、ポインタを渡せば他スレッドから技術的に参照可能な場合があります（不可侵の物理壁ではない）。

# 【C++で観察】スレッドごとのスタックの違い

## ローカル変数のアドレスを表示して「別々のスタック」を実感する

C++を観察レンズとして、2つのスレッドのスタック位置を覗いてみましょう。

```cpp
// ※文法は覚えなくてOK！ 「スレッドごとに変数のアドレスが違う」様子を見る
#include <iostream>
#include <thread>

void WorkerFunction() {
    int workerLocal = 10;
    std::cout << "[Worker] Thread ID: " << std::this_thread::get_id()
              << " | localVar アドレス: " << &workerLocal << "\n";
}

int main() {
    int mainLocal = 20;
    std::cout << "[Main  ] Thread ID: " << std::this_thread::get_id()
              << " | localVar アドレス: " << &mainLocal << "\n";

    std::thread t(WorkerFunction);
    t.join();
}
```

```text
【出力結果の例（64bit環境）】
[Main  ] Thread ID: 140735 | localVar アドレス: 0x7ffee3bbf7bc
[Worker] Thread ID: 140736 | localVar アドレス: 0x70000dc4afbc
```

* スレッドごとにローカル変数の異なるアドレスが観察できる！
* これは、スレッドごとにスタック領域が割り当てられる一般的な実装を観察する一例です。
* ※注意: アドレスが離れていること自体が「別スタックであることの規格上の証明」ではありませんが、スレッドが独立した領域を使って動いている様子を実感できます。

# スレッド固有のデータ：Thread Local Storage

## 「グローバル変数だけど、スレッドごとに独立させたい」ときは？

グローバル変数は通常全スレッドで共有されますが、例外的にスレッドごとに独立した記憶域を持たせる仕組みもあります。

```cpp
// thread_local を付けると、スレッドごとに別々のインスタンスが作られる
thread_local int threadSpecificCounter = 0;
```

```text
Thread A が threadSpecificCounter++ しても、
Thread B の threadSpecificCounter には一切影響しない！
```

* 「グローバル変数や静的変数は、全スレッドで例外なく1個共有される」
  と決めつける必要はありません。
* スレッドごとに独立した状態（エラー情報や乱数シード等）を保持する実務的な道具として活用されます。

# 9. なぜ `counter++` は壊れるのか？（疑問2の解剖）

## `counter++` を概念的な Read-Modify-Write として分解すると

ここで最初の疑問2に戻りましょう。
なぜ複数のスレッドで同じ `counter++` を実行すると値が狂うのか？

```cpp
counter++; // この1行は、不可分な（アトミックな）1つの操作ではない！
```

```text
【概念的な 3つの複合操作（Read-Modify-Write）】

ステップ 1: [Read]   メモリ上の counter の値を読み込む
ステップ 2: [Modify] 読み込んだ値を +1 する
ステップ 3: [Write]  計算後の値を、メモリの counter へ書き戻す

※コンパイラや最適化により、実際の機械語が必ず3命令になるわけではありません
```

* スレッドAとスレッドBが、この複合操作を **互いに割り込みながら並行実行** すると何が起きるでしょうか？

---

# Lost Update（更新の取りこぼし）の再現図

## 2回足したのに、1回分しか増えない瞬間

```text
初期状態: メモリ上の counter = 10

【Thread A】                                 【Thread B】
1. Read: 10 を読み込む
                                             1. Read: 10 を読み込む（Aの書き戻し前！）
2. Modify: 10 + 1 = 11
                                             2. Modify: 10 + 1 = 11
3. Write: 11 をメモリへ書き込む！
   （メモリの counter は 11 になる）
                                             3. Write: 11 をメモリへ書き込む！
                                               （Aの結果を 11 で上書き！）

最終結果: counter = 11 （期待値は 12 なのに、1回分の加算が消滅した！）
```

* Thread B は、Thread A が計算結果を書き戻す前の「古い値（10）」を読んだため、
  Thread A の更新内容を丸ごと上書きして消し去ってしまった！
* これを **Lost Update（更新の取りこぼし）** と呼びます。

# 10. C++における本質：Data Race は「未定義動作」！

## 「計算結果が少しズレるだけ」と思ってはいけない

単なる計算結果の誤差だと思ったら大間違いです。
C++言語規格には、マルチスレッドに関する極めて厳しいルールが存在します。

```text
【Data Race（データ競合）の発生条件】
異なるスレッドから同一のメモリ位置へ競合するアクセスがあり、

・少なくとも1つが「書き込み（Write）」
・少なくとも一方が「non-atomic（非アトミック操作）」
・適切な happens-before 関係（同期による順序付け）がない

場合、C++規格上 Data Race となり未定義動作を引き起こす！
```

```text
【C++規格の鉄則】
Data Race（データ競合）が発生したプログラムは、
言語仕様上「未定義動作（Undefined Behavior）」となる！
```

* **未定義動作が引き起こす恐怖**:
  * コンパイラの最適化によってループ処理が丸ごと消滅する
  * メモリアクセス順序が入れ替わり、想定外のクラッシュを引き起こす
  * 「たまに計算がズレる」程度で済む保証すら、C++規格上は一切ありません！

---

# 用語の整理：Race Condition vs Data Race

## 現場で混同しやすい2つの「競合」を区別する

```text
【Race Condition（競合状態: 広義の論理的問題）】
・処理のタイミングや実行順序によってプログラムの最終結果が変わってしまう状態
・ビジネスロジックの不具合（例: 在庫確認と注文処理の間に他人が購入して在庫がマイナスになった）
・同期や排他制御のタイミング設計ミス全般を指す広い概念

【Data Race（データ競合: 厳密なメモリ違反）】
・同一メモリ位置に対する「同期なし並行アクセス ＋ 少なくとも1つが書き込み」という物理的状態
・C++の言語仕様上、直接の「未定義動作（Undefined Behavior）」を引き起こす違反行為
```

* 「仕様・ロジック上の競合（Race Condition）」と、
  「メモリ規約違反の未定義動作（Data Race）」を冷静に切り分けることが実務では重要です。

# 11. どう防ぐのか？：同期（Synchronization）という契約

## ❌ やってはいけないこと：「volatile」で直そうとする！

ネットの記事などで「`volatile int counter;` にすれば直る」と書かれていることがありますが、**これは標準C++において、マルチスレッド同期の解決策としては誤りです！**

```text
C++規格において、volatile は主に特殊なメモリアクセス（MMIO等）に対する最適化抑止を意図したものであり、
言語規格上、スレッド間の同期（Synchronization）や不可分性（Atomicity）を保証する機能はありません。
（※特定環境の独自拡張を除き、マルチプラットフォームで可搬なスレッド同期には使えません）
```

```text
【正しい処方箋①：std::mutex（排他制御）】
・クリティカルセクション（共有メモリを触る区間）に「鍵」をかける
・Thread A が処理している間、Thread B は待たされ、同時に触れなくする

【正しい処方箋②：std::atomic<int>（不可分操作）】
・対象の操作を C++ memory model 上、atomic な操作として扱う
・他スレッドから「操作の途中の状態」が観測されないようにする
・※必ず1本のCPU命令になるわけではない（ロックフリーでない実装もあり得る）
・※「スレッドが途中で一切停止（プリエンプト）されない」という意味でもない
```

* **中心メッセージ**:
  * 共有メモリを複数スレッドから安全に触るなら、**「同期（Synchronization）」という別の契約** を結ばなければならない！

# プログラム実行基盤の全体像（第2部の統合）

## ソースコードが OS 上で動くまでの構造マップ

第5回〜第7回を通じて、プログラムが実行される基盤の仕組みが1つの絵に繋がりました！

```text
[ 第5回: ビルド境界 ]
ソースコード ──(コンパイル・リンク)──> 静的な実行可能ファイル（EXE / DLL）
                                            │
[ 第6回: モジュール境界 ]                  │
DLLモジュール ──(動的ロード)───────────────┼──> 同一プロセスのアドレス空間へ
                                            │
[ 第7回: 実行境界と実行の流れ ]             ↓
プロセス（OSが管理する独立した箱）の空間内で、
スレッド（CPUを動かす実行の流れ）が並行・並列に命令を実行していく！
```

* **静止したファイルから、動くシステムへ**:
  * ソースコードはバイナリになり、OSにロードされてプロセスとなり、スレッドによって実行される。
* **境界線の整理**:
  * **プロセス境界**: 仮想アドレス空間とメモリ保護（Memory Protection）による隔離。
  * **モジュール境界**: 同じ空間内の部品の壁（バイナリ契約を守れば直接連携できる）。
  * **スレッド境界**: 同じ空間内を走る複数の足並み（適切な同期がなければ Data Race が起きる）。

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① プログラムは静止ファイル、プロセスは実行環境の箱**
  * 同じEXEからでも、起動するたびに独立したプロセス（箱）が立ち上がる
* **② 見えているのは仮想アドレス（Virtual Address）である**
  * プロセスごとに文脈が異なるため、同じ番地数値でも同じ物理メモリとは限らない
* **③ スレッドはプロセス内を走る「実行の流れ」である**
  * CPUコア数とは異なり、OSスケジューラがコアへ割り当てて並行・並列に実行する
* **④ スレッド間では多くのメモリ（コード・静的・ヒープ）が共有される**
  * スタックとレジスタはスレッド固有だが、同じ箱の中のデータは共有され得る
* **⑤ 同期されていない競合する non-atomic アクセスは Data Race になり得る**
  * `volatile` では直らない。`std::mutex` や `std::atomic` 等による適切な同期契約が不可欠
