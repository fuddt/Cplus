# 1. なぜ「名前も引数も同じ」なのにクラッシュするのか？

## C# から C++ DLL を呼び出したときの現場トラブル集

C++ で書いた高速画像処理DLLを、C# から呼び出してみた。
コンパイルは成功し、DLLファイルも見つかった。なのに実行した瞬間……

```text
【現場で頻発する阿鼻叫喚】
・画像処理関数を呼んだら、数値がゴミデータに化ける
・構造体の途中にあるフィールドから、値がガタガタにズレる
・関数を呼び出した瞬間に AccessViolationException でアプリが即死する
・32bit環境の開発PCでは動いたのに、64bit環境に持っていくと動かない
```

* **受講者の疑問**:
  * 「C++のヘッダを見ながら、C#側にも全く同じ関数名と引数を書いたのに！」
  * 「文法も型名も合っているのに、なぜメモリが壊れるの？」

---

# その疑問の根本原因：DLL境界とは「バイナリ契約」である！

## ソースコード上で「似た型」を書くだけでは安全に動かない

DLLを呼び出す側（Caller）と呼ばれる側（Callee）の間には、
コンパイル後の機械語レベルで **4つのバイナリ契約** が完全に一致している必要があります。

```text
【DLL境界で成立させるべき 4大バイナリ契約】

契約① 関数をどう探すか？
      └── Symbol / Export Name （名前の契約）

契約② どう引数・戻り値を渡すか？
      └── Calling Convention / ABI （レジスタ・スタックの契約）

契約③ 何byteとして解釈するか？
      └── Size / Struct Layout / Alignment （メモリ配置の契約）

契約④ 誰がそのメモリを管理するか？
      └── Ownership / Lifetime （寿命と解放の契約）
```

* 1つでも契約が食い違っていれば、メモリ破壊や即死クラッシュが起きます！

# 2. DLLとは何か？：プロセスとモジュールの関係

## よくある誤解：「DLLは裏で動く別のプログラム（別プロセス）？」

DLL（Dynamic-Link Library）は、独立した別プログラムではありません。
**実行時に、呼び出し元プロセスの仮想アドレス空間へロードされる共有モジュール** です。

```text
【1つのプロセス（仮想アドレス空間）】
┌───────────────────────────────────────────────┐
│ App.exe                                       │
│   ProcessImage() を呼び出す                   │
│       │                                       │
│       ↓（同じメモリ空間内の番地へジャンプ！） │
│   ImageCore.dll                               │
│   ProcessImage() の機械語コード               │
│                                               │
│ 共有バッファ [ 0x1000: 画素データ byte列 ]    │
└───────────────────────────────────────────────┘
```

* **EXEとDLLは、同じプロセスのメモリ空間を共有して動いている！**
* だからこそ、ポインタを渡して直接生メモリを読み書きできるのです。

# 3. 静的リンク vs 動的リンク：第5回の復習

## オブジェクトコードを取り込むか、別ファイルとしてロードするか

第5回で学んだ「静的リンク」と、今回の「動的リンク（DLL）」の違いを整理しましょう。

```text
【静的ライブラリ（Static Library: .lib）】
・ビルド時に、必要なオブジェクトコード（.obj）を最終成果物（EXE側）へ取り込む
・その静的ライブラリ自体を実行時に別ファイルとして配布・配置する必要は基本的にない

【動的リンクライブラリ（Dynamic-Link Library: .dll）】
・DLL本体（.dll）は独立したファイルとして存在し、実行時にメモリへロードされる
・複数のアプリケーションから同じDLLモジュールを利用できる場合がある
```

```text
※注意（過度な一般化を避ける）:
「動的リンクなら必ずメモリが節約できる」「DLLを差し替えれば必ず本体の再ビルドが不要」
と過信してはいけません。後述するABI互換性が1箇所でも壊れれば、
DLLだけを差し替えてもプログラムは正常に動作しなくなります。
```

# インポートライブラリ（.lib）の正体

## 第5回で触れた「Windowsにおける .lib の二面性」を回収！

WindowsでDLLをビルドすると、`.dll` と一緒に **`ImageCore.lib`** が出力されます。
この `.lib` は、第5回で学んだ「オブジェクトコードのアーカイブ」ではありません。

```text
【インポートライブラリ（Import Library）の正体】
DLL本体の機械語コードを含んでいるのではなく、
リンカに対して「この関数は実行時に ImageCore.dll からロードされる」
という外部参照解決のための情報（引き換え券）だけを納めた小さなファイル！
```

```text
[ ビルド時（リンカの仕事） ]
App.obj ＋ ImageCore.lib（引き換え券） ──(リンク)──> App.exe
（「起動時に ImageCore.dll から ProcessImage を探せ」という情報をEXEに埋め込む）

[ 実行時（OSローダーの仕事） ]
App.exe を起動 ──> OSが ImageCore.dll を探し、プロセス空間へロードして結合！
```

* **`.lib` はビルド時の道標、`.dll` は実行時の実体！**

# DLLのシンボル公開：Export と Import

## 外界に向けて関数を公開する仕組み

DLL内の関数は、デフォルトでは外部から見えません（非公開）。
公開したい関数には、コンパイラに対して明示的な指示を与えます。

```cpp
// ImageCore.h
#ifdef BUILD_DLL
    // DLLを作る側：関数を外部に公開（Export）する
    #define DLL_API __declspec(dllexport)
#else
    // DLLを使うC++側：外部DLLからインポートすることを明示する
    #define DLL_API __declspec(dllimport)
#endif

// 公開する関数
DLL_API int ProcessImage(uint8_t* buffer, int lineSpan);
```

```text
※技術的注記:
・__declspec(dllexport) はシンボルをエクスポートする代表的な方法の1つです。
  モジュール定義ファイル（.def）を使ってエクスポート名を指定する方法もあります。
・第5回の「定義済みシンボル/未定義シンボル」と、DLLの「Export/Import」を混同しないようにしましょう。
```

# 4. 契約① 関数をどう探すか？：名前マングリングの壁

## C++コンパイラが裏で生成する「修飾名」

第5回で学んだ通り、多くのC++処理系では同名関数の多重定義（オーバーロード）を実現するため、
関数名に引数の型情報などを付加したシンボル名（マングル名）を生成します。

```text
人間が書いたC++コード:
int ProcessImage(uint8_t* buffer, int lineSpan);

多くのMSVC環境で生成されるシンボル名（マングル名）:
?ProcessImage@@YAHPAEH@Z
```

* このままDLLをビルドすると、DLLの公開シンボル名は暗号のような文字列になる！
* C# や Python から「`ProcessImage` という関数を呼んでくれ！」と頼んでも、
  **「そんな名前の関数は存在しない（?ProcessImage@@YAHPAEH@Z ならあるが）」**
  となって名前の照合に失敗します。

# `extern "C"` の正体と、現場の重大な誤解

## 「extern "C" を付ければすべて解決する」は危険な嘘！

そこで、C++コードに関数の結合規則を指定します。

```cpp
// C language linkage（C言語の結合規則）で関数を定義
extern "C" DLL_API int ProcessImage(uint8_t* buffer, int lineSpan);
```

* **`extern "C"` の本質は「C language linkage（C結合規則）」の指定**
  * 多くの処理系において、C++固有の名前修飾（マングリング）を避け、
    関数名をそのままに近い形でシンボルとして公開しやすくする
* **【現場で多発する極めて危険な思い込み！】**:
  * ❌「`extern "C"` を付ければ、別言語との互換性がすべて解決する魔法」──> **大間違い！**
  * `extern "C"` が整えるのは、主に **「名前の探し方（契約①）」** だけ！
  * 引数の渡し方、構造体の並び順、メモリの所有権といった **残りの契約（契約②〜④）は何も保証してくれません！**

# 5. 契約② どう引数・戻り値を渡すか？：API と ABI

## ソースコードの約束（API）と、バイナリの約束（ABI）

```text
【API（Application Programming Interface）: ソースコード世界の約束】
・人間がソースコードを書くための約束（関数名、引数の型、戻り値の型）
・「ProcessImage(buffer, lineSpan) と書けば画像処理が走る」

【ABI（Application Binary Interface）: コンパイル後・バイナリ世界の約束】
・機械語・CPU・メモリレベルで守るべき厳密な規約全体
・引数はどのレジスタ（またはスタックのどの位置）に積むか？
・戻り値はどのレジスタに置いて返すか？
・呼び出しに使ったスタック領域は誰が巻き戻して掃除するか？
・構造体の各フィールドは何バイトで、パディングはどう入るか？
```

* **ABIは、単なる「呼び出し規約」よりもはるかに広い概念！**

---

# 呼び出し規約（Calling Convention）と x86 / x64

## 引数の受け渡しとスタックの掃除ルール

関数の機械語呼び出しにおいて、「引数をどう並べ、スタックを誰が掃除するか」の約束を **呼び出し規約（Calling Convention）** と呼びます。

```text
【Windows x86（32bit時代）の代表例】
__cdecl   : C言語の標準。呼び出し側（Caller）がスタックを掃除する
__stdcall : Win32 APIの標準。呼び出された関数側（Callee）がスタックを掃除する
※ここが食い違うと、関数から戻った瞬間にスタックが壊れて即死クラッシュした！
```

```text
【超重要：現代の Windows x64 における統一規約】
Windows x64 では、基本的に単一の標準呼び出し規約（Microsoft x64 calling convention）
に統一されています。最初の4つの整数/ポインタ引数はレジスタ（RCX, RDX, R8, R9）で渡されます。
32bit時代のような __cdecl / __stdcall のスタック不整合事故は大幅に減りましたが、
引数の型サイズや構造体レイアウトの不一致による破壊は依然として発生します！
```

# 6. C# P/Invoke（プラットフォーム呼び出し）

## C# からネイティブDLLを呼び出す宣言

C# から C++ DLL を呼び出すには、`[DllImport]` 属性を使用します。

```csharp
using System;
using System.Runtime.InteropServices;

internal static class NativeMethods {
    // DLLファイル名と、合致させる呼び出し規約を指定
    [DllImport("ImageCore.dll", CallingConvention = CallingConvention.Cdecl)]
    public static extern int ProcessImage(IntPtr buffer, int lineSpan);
}
```

* **P/Invoke における最重要ルール**:
  * C++側の宣言と、C#側の宣言が、**バイナリ契約として完全に一致していること！**
  * 関数名だけでなく、引数の順序、バイトサイズ、メモリ配置を1つずつ検証する必要がある

# 7. 契約③ 何byteとして解釈するか？：型のバイト表現

## 第1回〜第4回がすべて繋がる！「型名」ではなく「byte幅」を見よ

C++とC#で同じ名前の型を書いたとしても、メモリ上のバイト表現が同じとは限りません！

```text
【型サイズと表現の確認チェックリスト】

・ポインタ / アドレス:
  - 32bit環境では 4バイト、64bit環境では 8バイト！
  - C# の IntPtr も実行環境のビット数に合わせて 4B または 8B に変動する

・整数型:
  - int32_t / int は通常4バイトで一致するが、符号（signed/unsigned）の扱いに注意
  - C++ の long は Windows（4バイト）と Linux 64bit（8バイト）でサイズが異なる！

・bool 型の罠（現場定番！）:
  - C++ の bool は通常 1バイト
  - Windows API の BOOL は 4バイト整数（int）
  - C# の bool は P/Invoke 時、デフォルトで 4バイト（Win32 BOOL）として扱われやすい！
```

# 構造体レイアウトとアライメント（第1回の伏線回収！）

## 「見た目が同じ構造体」がメモリ上で壊れる瞬間

第1回で学んだ **「アライメントとパディング」** を覚えているでしょうか？

```cpp
// C++ DLL側の構造体
struct SensorData {
    uint8_t  id;      // 1バイト
    // ──> ここに 3バイトのパディング（隙間）が入る！（第1回）
    int32_t  value;   // 4バイト（オフセット 4 から配置）
}; // 全体サイズは 8バイト
```

```text
もしC#側でアライメントを考慮せず、メモリ上に隙間なく詰めて解釈したら？
C++側のメモリ : [ id(1B) ][ pad ][ pad ][ pad ][ value (4バイト) ]
C#側の読み取り: [ id(1B) ][ value (4バイト)?????? ] ──> 3バイトずれて値が完全破壊！
```

* **第3回・第4回の教訓そのもの！**
  * 「構造体の各メンバが、先頭から何バイト目のオフセットにあるか」が両者で一致していなければ、値が正常に読み取れず破壊が起きます！

# C# の StructLayout と `Pack` の真実

## `Pack = 1` は万能安全スイッチではない！

C# の構造体は、デフォルトでは実行時（CLR）がメモリ効率のために並び順を変更することがあります。
ネイティブとやり取りするには、**「宣言通りの順序で並べよ」** と明示します。

```csharp
[StructLayout(LayoutKind.Sequential)] // 宣言通りの順序で配置
public struct SensorData {
    public byte id;
    public int value;
}
```

```text
【超重要：Pack = 1 の危険な誤用！】
ネット上の記事で「困ったら Pack = 1 を付けろ」と書かれていることがありますが、大変危険です！
Pack = 1 は「パディングを一切入れずに 1バイト境界で詰めろ」という特殊な指定です。
もしC++側が標準のアライメント（4バイト境界等）でビルドされていた場合、
C#側に Pack = 1 を付けると、かえってパディングが消えてオフセットがズレてしまいます！

★本質は「C++側の offset と sizeof に、C#側のメモリ配置を正確に一致させること」！
```

# マーシャリング（Marshaling）と Blittable 型

## 「そのまま渡せる型」と「変換が挟まる型」

P/Invoke では、ランタイム（CLR）がマネージドとネイティブの間でデータを中継します。

```text
【Blittable（ブリッタブル）型: 変換コストゼロ】
・マネージド（C#）とネイティブ（C++）で、メモリ上のバイナリ表現が完全に同一の型
・例: byte, int, double, IntPtr、およびBlittable型だけで構成された連続配置構造体
・ポインタをそのまま渡して、超高速に直接読み書きできる！

【Non-Blittable 型: 変換（マーシャリング）が必要】
・文字列（string）、配列、クラス参照、bool など
・言語間でメモリ管理や文字コード（UTF-8, UTF-16, ANSI等）の内部表現が異なる
・P/Invokeの呼び出し時に、ランタイムが裏でメモリ変換やコピーを行う
```

* 「P/Invoke ＝ 単にポインタを素通りさせているだけ」ではないと認識しましょう。

# 8. 契約④ 誰がそのメモリを管理するか？：所有権と Pinning

## 「確保した者」と「解放する者」の厳格な境界線

メモリを安全に受け渡すには、**ライフタイム（寿命）と所有権（誰が解放するか）** の契約が不可欠です。

```text
【推奨パターン：C#側でバッファを確保し、C++に加工させる】
C#で配列を確保 ──(ポインタを渡す)──> C++ DLLがその場で画素処理 ──(return)──> C#側で使い続ける
```

* **ここで立ちはだかる C# の壁：ガベージコレクション（GC）！**
  * C#のGCは、メモリの断片化を防ぐため、オブジェクトのメモリ番地を勝手に動かすことがある！
  * C++がポインタを読み書きしている最中に、C#が勝手にアドレスを移動させたら大惨事！
* **処方箋：Pinning（ピン留め）**
  * ネイティブコードにポインタを渡している間、GCに対して **「このメモリを動かすな！」** と固定する。

---

# C# での安全な Pinning 実装

## `fixed` 文による確実なアドレス固定と解放

C# では `fixed` 文を使うことで、スコープ内だけ安全にメモリをピン留めできます。

```csharp
byte[] pixelBuffer = new byte[width * height];

// fixedスコープを抜けると、自動的にピン留めが解除される
fixed (byte* p = pixelBuffer) {
    // ネイティブ関数へ安全にポインタを渡す
    NativeMethods.ProcessImage((IntPtr)p, width);
}
```

```text
※技術的注記（C++側でメモリを確保して返す場合）:
どうしても C++ 側でメモリを確保して C# に返したい場合は、
DLL側にペアとなる解放関数（例: FreeBuffer(IntPtr p)）を用意し、
使い終わったら C# からそれを呼び出して解放するのが定石の1つです。
モジュールをまたいで異なるメモリアロケータ（new / malloc / Marshal.AllocHGlobal等）を
混同して直接解放しようとすると、ヒープ破壊の原因になります。
```

# 9. DLLのロード方法と検索の現実

## プログラム実行時にDLLはどうやって読み込まれるのか？

DLLをプロセスへ読み込む方式には、大きく2つの方法があります。

```text
【Load-time Dynamic Linking（暗黙的ロード）】
・EXEのインポート情報（.lib由来）に基づき、プログラム起動時にOSローダーが自動でDLLをロードする方式
・C# の [DllImport] も通常、最初の関数呼び出し時にランタイムが自動ロードする

【Run-time Dynamic Linking（明示的ロード）】
・プログラム内で LoadLibrary() や GetProcAddress() を呼び出し、必要なDLLを実行時にコードから取得する方式
・プラグイン構造などで「存在するか分からないDLLを後から読み込む」場合に多用される
```

* **【実務の注意：DLL検索順序は固定ではない！】**:
  * 「常にEXEと同じフォルダ ──> カレント ──> System32 ──> PATH の順で探す」という固定的な思い込みは禁物！
  * Windowsのセキュリティ設定（Safe DLL Search Mode）やマニフェスト、ディレクトリ設定等により検索規則は変動します。
  * トラブル時は「想定と違う場所の古いDLLがロードされていないか？」をツール等で確認する姿勢が大切です。

# 10. 実行基盤の罠：32bit / 64bit 不一致

## ビルドは通るのに、起動した瞬間に即死する最大の原因

```text
32bit（x86）のプロセスに、64bit（x64）のDLLをロードすることはできない！
（逆も同様：通常、64bitプロセスに 32bit DLLを直接ロードすることはできない）
```

* **C# 開発で最も多発するトラブル**:
  * C# のプロジェクト設定が **`Any CPU`** になっている
  * 64bit Windows 上で実行すると、C# アプリは自動的に **64bit プロセス** として起動する
  * そこへ 32bit でビルドされた C++ DLL を読もうとすると……
  * ──> **`BadImageFormatException`** が発生して起動直後にクラッシュ！
* **解決策**:
  * C# 側のビルドターゲットを `x64` または `x86` に明示的に固定し、
    **「プロセスとDLLのアーキテクチャを完全に一致させる」** こと！

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① DLL境界とは「バイナリ契約」である**
  * ソースコードで似た型を書くだけでは動かない。4つの契約（名前・呼び出し・配置・所有権）を一致させる
* **② DLLは別プロセスではなく「同じプロセス内の別モジュール」**
  * 同じ仮想アドレス空間でメモリを共有して動くからこそ、ポインタを渡して高速処理できる
* **③ `extern "C"` は魔法ではない**
  * C linkage（名前の探し方）を整えるだけであり、残りのABIや構造体レイアウトの契約は別途合わせる必要がある
* **④ 構造体は「名前」ではなく「byte配置（offset / sizeof）」を合わせる**
  * 第1回のアライメント・パディングを意識し、安易に `Pack = 1` を使わず両側の配置を検証する
* **⑤ メモリの所有権と寿命を曖昧にしない**
  * C#のバッファは `fixed` 等でピン留めして渡し、C++側で確保したメモリは対応する解放関数で片付ける
