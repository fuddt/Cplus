カメラSDKから、次のような生データが届いたとします。


* 画面に画像文字や表は存在しません。あるのはただの **生byte列** だけ

# 01の復習：byte境界 と データ境界 は一致しない！

## アドレスの境界と、意味上の境界のズレ

第1回で、メモリは「8bit（1byte）のロッカー街」だと学びました。

```text
アドレスの境界（物理的な番地）:
|   byte (8bit)   |   byte (8bit)   |   byte (8bit)   |

意味上の境界（データの仕様）:
|       12 bit 画素 A        |       12 bit 画素 B        |
```

* 一般的な現代の環境では、メモリは **1byte（8bit）単位でアドレスが付けられている**
* しかし、画像や通信のデータは **12bitや10bit** など、バイト境界を無視して詰め込まれることがある
* アドレスの境界と意味の境界がズレるからこそ、**「生byte列を操る技術」** が不可欠になります

# 1. bitを切り出す：12bit Packed画素の復元

## 2つの画素（計24bit）を「3バイト」に詰め込んだ実例

第1回で予告した「12bit画像」の救出に挑みましょう！

```text
画素A (12bit): AAAAAAAAAAAA      画素B (12bit): BBBBBBBBBBBB

3バイトのメモリ配置例:
[ byte 0 (8B) ]    [ byte 1 (8B) ]    [ byte 2 (8B) ]
  AAAAAAAA           AAAA BBBB          BBBBBBBB
  └─ 画素Aの上8bit ─┘  └A下4┘ └B上4┘    └─ 画素Bの下8bit ─┘
```

* 2画素（12bit × 2 = 24bit）が、無駄なくちょうど3バイト（24bit）に収まる
* ※重要：この詰め込み順（Packing）は一例であり、カメラやセンサの仕様書によって異なります

---

# まずゴールを確認：Packedデータを何に戻すのか？

## 「詰め込まれた24bit」を「2つの計算しやすい16bit整数」へ戻す

bit演算のテクニックに入る前に、**「最終的にどんな形のデータに変換したいのか」** ゴールを明確にしましょう。

```text
【入力: カメラから届く状態（Packed 3バイト）】
3 byte の連続メモリ
┌──────────┬──────────┬──────────┐
│ byte 0   │ byte 1   │ byte 2   │
│ AAAAAAAA │ AAAABBBB │ BBBBBBBB │
└──────────┴──────────┴──────────┘

              ↓ 復元（Unpack）

【ゴール: プログラムで計算したい状態（Unpacked 16bit整数 × 2）】
uint16_t pixelA
┌─────────┬──────────────┐
│  0000   │ AAAAAAAAAAAA │  ──> 1つの独立した数値（0〜4095）
└─────────┴──────────────┘
  上位4bit   画素Aの12bit

uint16_t pixelB
┌─────────┬──────────────┐
│  0000   │ BBBBBBBBBBBB │  ──> 1つの独立した数値（0〜4095）
└─────────┴──────────────┘
  上位4bit   画素Bの12bit
```

* **Packing（パッキング）**：複数データを隙間なくバイト列へ詰め込むこと
* **Unpacking（アンパッキング）**：詰め込まれたバイト列から、計算しやすい整数型へ復元すること
* **今回のゴール**：12bit画素値を `uint16_t` の **「下位12bit」へ右詰め（上位4bitは0）** して復元する。これにより、`pixelA` は `0〜4095` の普通の整数値としてそのまま計算できるようになります！

# なぜ16bitの器を使うのか？（余る4bitの正体）

## 通信・保存の効率 vs プログラムでの扱いやすさ

受講者の方から自然に湧く2つの疑問を整理しましょう。

```text
疑問①「12bit型ではなく、なぜ uint16_t（16bit）を使うの？」
疑問②「16bitに入れると上位4bitが余るけど、なぜ右詰めでいいの？」
```

* **① 12bitを収容できる標準整数型を使う**:
  * 標準C++には `uint12_t` のような一般的な12bit整数型はありません。
  * 12bitの値域は `0 〜 4095` です。8bit（最大255）には収まらないため、**12bitの情報を欠落なく収められる `uint16_t`（16bit幅）** を使います。
* **② なぜ「下位12bitへ右詰め」にするのか？（余る4bitの役割）**:
  * 例えば12bit最大値 `1111 1111 1111`（4095）を `uint16_t` で表す場合、**`0000 1111 1111 1111` と下位12bitへ右詰め（上位4bit=0）にすれば、整数値がそのまま「4095」** になります。
  * もし左詰め（`1111 1111 1111 0000`）にしてしまうと、整数値が 65520 に化けてしまいます。
  * **「上位4bitを0にして下位12bitに右詰めする」からこそ、0〜4095の普通の数値として自然に計算できる** のです！
* **③ なぜ一度Packedにして、また広げるのか？（役割分担）**:
  * **通信・保存時**：コンパクトさ優先（Packed）。※外部フォーマットの配置は仕様書に従う。
  * **プログラム計算時**：扱いやすさ優先（Unpacked）。下位12bitへ正規化して計算する。
* ※注記：ここでいう「右詰め」は整数値のbit表現で下位12bitを使うという意味であり、メモリ上のbyte順（エンディアン）とは別の概念です。

# bitを操る3つの基本技：シフト・マスク・OR

## 12bit画素を16bit整数へ再構成するための「3つの道具」

バイトの箱から特定bitを取り出し、新しい16bitの器へ組み立てる道具です。

```text
① シフト（>> / <<）: 位置合わせのピンセット
   欲しいbitを、最終的な16bit整数の「正しい位置」へ移動する
   1011 0101 >> 4  ──>  0000 1011 （上位4bitを右端へずらす）

② マスク（& / AND）: 余分なbitを切り落とすハサミ
   同じbyte内に混ざっている「不要なbit」をゼロにして消す
   1011 0101
 & 0000 1111  ──>  0000 0101 （下位4bitだけを残す！）

③ 結合（| / OR）: パーツを接着するのり
   別々のbyteから切り出したbitパーツを、1つの整数値として合体する
   1010 0000
 | 0000 0101  ──>  1010 0101 （2つのパーツを1つの値に合成！）
```

* この3つの道具を組み合わせることで、バイト境界をまたいだどんなbitも自由自在に再構成できます！

# 02の伏線回収：なぜ「0x0F」でマスクできるのか？

## 16進数は「bit列との対応が最も見やすい記法」

第2回で **「16進数 2桁 ＝ ちょうど1バイト（8bit）」** と学びました。

```text
16進数の1桁 ＝ 4 bit、 16進数の2桁 ＝ 8 bit (1 byte)

16進数:   0     x     0           F
2進数:              [ 0 0 0 0 ] [ 1 1 1 1 ]
                     上位4bit消す  下位4bit残す
```

* `byte & 0x0F` と書くだけで、**「下位4bitだけを抽出するマスク」** になる！
* 2進数で `0b00001111` と書くよりも、16進数 `0x0F` の方が圧倒的に短く見やすい
* **「16進数が低レイヤでよく使われる大きな理由の1つ」** が、このbit列との対応の良さにあります

# 図解：画素A（12bit）はどうやって組み立てる？

## 2つのバイトからパーツを集めて、1つの16bit値へ合体！

```text
目標: uint16_t の中に「0000 AAAAAAAA AAAA」（12bit値）を作る

① byte0（AAAAAAAA）を 16bitの器の中で左へ4bitシフトする:
   AAAAAAAA ──(<< 4)──> 0000 AAAAAAAA 0000
                        ↑上位8bitを配置   ↑下位4bitに空き地ができる！

② byte1（AAAABBBB）を 右へ4bitシフトして、上4bit（AAAA）を取り出す:
   AAAABBBB ──(>> 4)──> 0000 0000 0000 AAAA
                        （不要なBBBBが押し出されて落ちる）

③ 二つのパーツを OR（|）で合体！
     0000 AAAAAAAA 0000  (ステップ①の上位パーツ)
   | 0000 0000 0000 AAAA  (ステップ②の下位パーツ)
   ────────────────────────────────────────────
     0000 AAAAAAAA AAAA  (12bitの画素Aが完成！)
```

* 計算式を丸暗記するのではなく、**「目的の位置へずらして、重ねる」** という図解で掴む！

# 実際の数値で追ってみよう！（0xB3 / 0xD5 ──> 0xB3D）

## 実際のbit列がどう動いて1つの数値になるのか

具体的な数値を入れて、12bit画素Aが復元される様子を1回だけ追ってみましょう。

```text
【カメラから届いた生データ（3バイト）】
byte0 = 0xB3 (1011 0011)  ──> 画素Aの上位8bit
byte1 = 0xD5 (1101 0101)  ──> 上位4bit(1101=D)が画素A、下位4bit(0101=5)が画素B
byte2 = 0x67 (0110 0111)  ──> 画素Bの下位8bit
```

```text
【画素Aの組み立てプロセス】

① byte0 (0xB3) を 16bit幅で左へ4bitシフト:
     0000 0000 1011 0011  ──(<< 4)──>  0000 1011 0011 0000  (0x0B30)

② byte1 (0xD5) を 右へ4bitシフト:
     1101 0101  ──(>> 4)──>  0000 1101  (0x0D)

③ 二つを OR（|）で合体:
     0000 1011 0011 0000  (0x0B30)
   | 0000 0000 0000 1101  (0x000D)
   ────────────────────────────────
     0000 1011 0011 1101  (0x0B3D ＝ 10進数で 2877)
```

* **0x0B3D の内訳**:
  * 先頭の `0`（`0000`）はただの飾りではなく、**16bitの器で余った上位4bit** です。
  * 続く `B3D`（`1011 0011 1101`）が、**下位12bitへ右詰めされた画素Aの値（2877）** です！
* 2つのバイトに泣き別れになっていたデータが、`0x0B3D`（2877）という1つの普通の整数値に復元されました！

# コードで見る：12bit復元の実践

## 図と数値の流れをそのままC++で書くだけ！

```cpp
// 12bitを収めるため、16bitの整数型（uint16_t）に復元する
// ※文法は覚えなくてOK！ 図・数値との対応を見る

// 画素A: byte0を左へ4 + byte1の上位4bit
uint16_t a = (static_cast<uint16_t>(byte0) << 4) | (byte1 >> 4);

// 画素B: byte1の下位4bitを左へ8 + byte2
uint16_t b = (static_cast<uint16_t>(byte1 & 0x0F) << 8) | byte2;
```

* **`static_cast<uint16_t>(byte0)` と書く理由**:
  * 最終的に16bit値を作ることをコード上で明示し、意図通りの型でシフトを扱うためです
* **bit操作の真の役割**:
  * 「難しい算数のパズル」ではなく、**「バイト境界をまたいだ生データを、プログラムで計算しやすい整数へアンパックする道具」** なのです！

# 2. byteを移す：std::memcpy

## bit単位ではなく「連続するbyteの塊」をそのまま動かす

```text
bit操作  ──> 「必要なbitを切り出す」（バイト境界を分解する）
memcpy   ──> 「必要なbyteの塊をそのまま移す」（バイトの並びを保つ）
```

```cpp
// メモリの塊を一括コピーする標準関数
std::memcpy(コピー先アドレス, コピー元アドレス, コピーするバイト数);
```

* 「高速化の裏技」ではなく、**「連続するbyte列をそのままコピーする標準的な基本道具」**
* ただし、画像処理では第2回で学んだ **Stride（行の歩幅）の違い** が立ちふさがります

# 02の復習：なぜStrideが違うと、一発のmemcpyでは足りないのか？

## 行ごとに余白が異なるため、一括コピーすると絵が崩れる！

```text
コピー元画像（有効幅 100 byte, srcStride = 104 byte）:
[ 画素 100 byte ][ 余白 4 byte ]
[ 画素 100 byte ][ 余白 4 byte ]

コピー先バッファ（有効幅 100 byte, dstStride = 300 byte）:
[ コピー先 100 byte ][ 余白 200 byte ]
[ コピー先 100 byte ][ 余白 200 byte ]
```

* 同じStride同士なら一括コピーできますが、**Stride（余白）が異なる場合は一括コピーできない！**
* 余白のサイズが違うため、丸ごと移すとコピー先で行の先頭がズレて絵が斜めに崩壊する
* だから **「1行ずつ、欲しい画素部分（100 byte）だけをコピーする」** 必要があります

---

# 実践：安全な矩形コピーの実装

## 1行ごとに LineSpan でジャンプしながら memcpy

```cpp
void CopyRect(const uint8_t* src, int srcLineSpan,
              uint8_t* dst, int dstLineSpan,
              int copyWidthBytes, int copyHeight) {
    for (int y = 0; y < copyHeight; ++y) {
        // 各行の先頭アドレスへワープ（第2回の知識！）
        const uint8_t* srcRow = src + (y * srcLineSpan);
        uint8_t* dstRow = dst + (y * dstLineSpan);

        // 有効データ幅だけを安全にコピー
        std::memcpy(dstRow, srcRow, copyWidthBytes);
    }
}
```

* 各行のジャンプには **必ず LineSpan（Stride）** を使う
* 余白を綺麗に飛び越えながら、欲しい矩形部分だけを確実に移せる！

# 現場の注意：境界外アクセスは「未定義動作」

## 「即クラッシュ」よりも恐ろしい、サイレントなメモリ破壊

もしコピー先の枠よりも大きいデータをコピーしてしまったら？

```text
コピー先バッファの枠:       コピーしようとしたデータ（はみ出し！）:
┌──────────────────┐      ┌──────────────────────┐
│                  │      │                      │
│                  │      │                      │### 枠外（未定義動作！）
└──────────────────┘      └──────────────────────┘
```

* 1バイトでも領域外に書き込むと **未定義動作（UB）** になる
* 即座にクラッシュすればまだマシで、**「隣にある別の変数を静かに破壊し、数分後に別の場所で謎の不具合が起きる」** のが一番怖い！
* ※小さな注意：コピー元とコピー先が重なる場合は `memmove` を使う（重複時の `memcpy` は未定義動作）

# 3. byte列を読む：意味を与える

## メモリ上のバイト列だけ見ても、数値は絶対に分からない！

メモリ上に、次の4バイトが並んでいたとします。

```text
[ 0x78 ][ 0x56 ][ 0x34 ][ 0x12 ]  （アドレス 0x1000 〜 0x1003）
```

* このデータは、10進数で「いくつ」でしょうか？
* **答えは「仕様が分からない限り、絶対に分からない」です！**
* 第1回の重要原則：**「byte列 ＋ 解釈ルール（仕様） ＝ 意味あるデータ」**
  * Little-Endian の 32bit 整数？ ──> `0x12345678`（305,419,896）
  * Big-Endian の 32bit 整数？    ──> `0x78563412`（2,018,915,346）
  * 1バイトの数値が4つ？          ──> `120, 86, 52, 18`

# 読み方A：明示的に組み立てる（安全・確実）

## 4つのロッカーから1つの値を作る、最も教育的な基本形

仕様書が「リトルエンディアンの 32bit 符号なし整数」と指定している場合:

```cpp
// 4つのバイトから、1つの uint32_t（32bit）を合成する
uint32_t val = static_cast<uint32_t>(p[0])
             | (static_cast<uint32_t>(p[1]) << 8)
             | (static_cast<uint32_t>(p[2]) << 16)
             | (static_cast<uint32_t>(p[3]) << 24);
```

* 下位バイトから順に、8bitずつ左へずらして OR で合体！
* **「4つのbyteから1つの32bit値を作っている」** 様子が誰の目にも明らか
* 実行環境（ホストCPU）のエンディアンに左右されず、常に安全で移植性が高い

# 読み方B：std::memcpy による値の取り出し

## 変数にバイト列を写し取って読む手法

```cpp
uint32_t val;
std::memcpy(&val, p, sizeof(val)); // 4バイトを変数にそのまま写す
```

* シフト演算を書かずに、手軽に値を取り出せる
* メモリコピー可能な単純な型（Trivially Copyable）に対して安全に使える
* **ただし大前提がある！**
  * 外部データのエンディアンと、自分のPCのエンディアンが一致している必要がある
  * もし外部がBig-EndianでPCがLittle-Endianなら、値が完全にひっくり返る！

# 4. 「構造体ビュー」という実務コードの誘惑

## 生バッファに構造体を被せて直接読む書き方を見かけるが……

実務のC++コードでは、次のような記述を見かけることがあります。

```cpp
struct Header {
    uint32_t width;
    uint32_t height;
};

// 生バッファに直接 Header* を被せて読む（ゼロコピー？）
const Header* header = reinterpret_cast<const Header*>(buffer);
std::cout << header->width;
```

* コピーを一切せず、構造体のメンバ名で生メモリを読めて便利に見える……
* **しかし、C++の規格上、これは何でも自由に被せてよいわけではありません！**

# なぜ安易な reinterpret_cast は危険なのか？

## 「便利な技」ではなく「確認すべき5つの条件がある」と読む！

`reinterpret_cast` を使ったアクセスが合法になるには、厳しい関門があります。

* **① オブジェクトの寿命（Lifetime）**:
  * そこに本当にその型のオブジェクトが存在しているか？
* **② 型アクセス規則（Aliasing / Strict Aliasing）**:
  * そのポインタ型を通して生メモリを読み書きしてよいか？
* **③ アドレス境界（Alignment）**:
  * 要求されるバイト境界（4バイト、8バイト等）に正しく揃っているか？
* **④ 構造体の配置（Padding / Offset）**:
  * メンバの並びや余白が、外部フォーマットの仕様と完全に一致しているか？
* **⑤ バイト順（Endianness）**:
  * データの並び順（リトル/ビッグ）がホストCPUと一致しているか？
* **このコードを見たら「これら5つの前提をすべて満たしているか？」を疑うこと！**

# 補足：std::bit_cast（C++20）は何をするものか？

## 構造体ビューの代替ではない！「ビット表現の安全な転換」

```cpp
// 例: float（32bit）のビット並びを、そのまま uint32_t（32bit）として観察する
float f = 1.0f;
uint32_t bits = std::bit_cast<uint32_t>(f);
```

* `std::bit_cast<To>(from)` は、**同じサイズで、どちらも trivially copyable な型同士** で、ビット表現をもとに「新しい値を作る」機能（コピーの一種）
* ※ここでは「メモリ表現をそのまま扱える単純な型」くらいの理解でOK
* 生バッファの上に構造体を被せる「ゼロコピービュー」とは全く別の道具です

# 実務の健全なアプローチ：コードではなく「仕様」を見る

## 01〜03の総決算：byte列 ＋ 詳細仕様 ＝ 意味のあるデータ

生byte列を扱うとき、コードを先に見るのではなく **「仕様書」** を見ます。

```text
生 byte 列
    ＋
仕様書（解釈ルール）
 ├─ bit位置   （どこに何ビットあるか？）
 ├─ offset    （何バイト目から始まるか？）
 ├─ size      （何バイトのデータか？）
 ├─ endian    （下位から並ぶか、上位からか？）
 └─ stride    （次の行まで何バイトあるか？）
    │
    ↓ 初めて値として復元できる！
意味のあるデータ
```

* **第1回の「bit列 ＋ 解釈ルール ＝ 意味あるデータ」が、ここで完全な実務の姿になる！**
* 構造体を使う場合は `static_assert`（サイズ・オフセット検証）で仕様との一致を保証する

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① bit単位で欲しい部分を取る ──> shift / mask / OR**
  * 12bit Packed画素のように、バイト境界をまたぐデータも自在に復元できる
* **② byte単位で塊を移す ──> memcpy**
  * Strideが異なる画像間では、LineSpanを考慮して1行ずつコピーする
* **③ byte列を値にするときは ──> 「フォーマット仕様」が必須**
  * bit位置・offset・size・endian・strideが揃って初めて意味のあるデータになる
* **④ エンディアン・サイズ・オフセット・アライメントを勝手に仮定しない**
  * 外部データと内部メモリの前提を必ず確認する
* **⑤ reinterpret_cast を見たら ──> 「5つの条件を満たすか？」を確認できる人になる**
  * Lifetime・Aliasing・Alignment・Padding・Endianness を冷静にチェックする
