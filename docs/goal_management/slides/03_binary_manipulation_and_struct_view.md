# なぜ、生メモリを扱う技術が必要なのか？

## 「この生byte列から、画素値を取り出してください」と言われたら？

カメラSDKから、次のような生データが届いたとします。

```text
A3 5C 7F 12 84 09 B2 ...
```

* 「この中から、各画素の明るさ（値）を取り出してください」
* ……どこからどこまでが1つの値でしょうか？
* 画面に画像文字や表は存在しません。あるのはただの **生byte列** だけ
* **「このbyte列から、欲しい情報をどう取り出し、どう動かし、どう意味付けするか」**
  これが低レイヤ・システム開発の日常です

# 01の復習：byte境界 と データ境界 は一致しない！

## メモリの都合と、データの都合のズレ

第1回で、メモリは「8bit（1byte）のロッカー街」だと学びました。

```text
メモリ側の仕切り（物理）:
|   8 bit (1 byte)   |   8 bit (1 byte)   |   8 bit (1 byte)   |

データの仕様（論理）:
|       12 bit 画素 A        |       12 bit 画素 B        |
```

* コンピュータは **8bit（1byte）単位** でしかメモリを区切れない
* しかし、画像や通信のデータは **12bitや10bit** で詰め込まれることがある
* byteの境界とデータの意味がズレているからこそ、**「生byte列を操る技術」** が不可欠になります

# 1. bitを切り出す：12bit Packed画素の復元

## 2つの画素（計24bit）を「3バイト」に詰め込んだ実例

第1回で予告した「12bit画像」の救出に挑みましょう！

```text
画素A (12bit): AAAAAAAAAAAA      画素B (12bit): BBBBBBBBBBBB

3バイトのメモリ配置例:
[ byte 0 (8B) ]    [ byte 1 (8B) ]    [ byte 2 (8B) ]
  AAAAAAAA           AAAA BBBB          BBBBBBBB
  └─ 画素Aの上8bit ─┘  └A下4┘ └B上4┘    └─ 画素Bの下8bit ─┘
```

* 2画素（12bit × 2 = 24bit）が、無駄なくちょうど3バイト（24bit）に収まる
* ※重要：この詰め込み順（Packing）は一例であり、カメラやセンサの仕様書によって異なります

# bitを操る3つの基本技：シフト・マスク・OR

## 欲しいビットを狙い撃ちにする「ハサミとピンセット」

```text
① シフト（>> / <<）: bit列を左右にずらす
  1011 0101 >> 4  ──>  0000 1011  （下位4bitを捨て、上位4bitを右端へ）

② マスク（& / AND）: 欲しいbitだけ残して、不要なbitをゼロにする
  1011 0101
& 0000 1111  ──>  0000 0101  （下位4bitだけを取り出す！）

③ 結合（| / OR）: 分かれたbitを1つに合体させる
  1010 0000
| 0000 0101  ──>  1010 0101  （2つのパーツを1つの値に合成！）
```

* この3つの組み合わせだけで、どんな位置のbitでも自由に取り出せます

# 02の伏線回収：なぜ「0x0F」でマスクできるのか？

## 16進数は「ビットマスクを書くための道具」だった！

第2回で **「16進数 2桁 ＝ ちょうど1バイト（8bit）」** と学びました。

```text
16進数:   0     x     0           F
2進数:              [ 0 0 0 0 ] [ 1 1 1 1 ]
                     上位4bit消す  下位4bit残す
```

* `byte & 0x0F` と書くだけで、**「下位4bitだけを抽出するマスク」** になる！
* 2進数で `0b00001111` と書くよりも、16進数 `0x0F` の方が圧倒的に短く見やすい
* プログラマが16進数を好む最大の理由は、このビットマスクの書きやすさにあります

---

# 図解：画素A（12bit）はどうやって組み立てる？

## 2つのバイトからパーツを集めて、1つの値へ合体！

```text
画素Aを作りたい: 目標は「AAAAAAAA AAAA」（12bit）

① byte0（AAAAAAAA）を 左へ4bitシフト する:
   AAAAAAAA ──(<< 4)──> AAAAAAAA 0000  （16bitの箱に左詰め）

② byte1（AAAABBBB）を 右へ4bitシフト して、上4bitを取り出す:
   AAAABBBB ──(>> 4)──> 0000AAAA      （不要なBBBBを捨てる）

③ 二つを OR（|）で合体！
   AAAAAAAA 0000  |  0000AAAA  ──>  AAAAAAAA AAAA（完成！）
```

* 計算式を丸暗記するのではなく、**「ずらして、重ねる」** という図解で掴む！

---

# コードで見る：12bit復元の実践

## 図の通りにそのままC++で書くだけ！

```cpp
// 12bitを収めるため、16bitの整数型（uint16_t）に復元する
// ※文法は覚えなくてOK！ 図との対応を見る

// 画素A: byte0を左へ4 + byte1の上4bit
uint16_t a = (static_cast<uint16_t>(byte0) << 4) | (byte1 >> 4);

// 画素B: byte1の下4bitを左へ8 + byte2
uint16_t b = (static_cast<uint16_t>(byte1 & 0x0F) << 8) | byte2;
```

* 第1回で「どうやって取り出すの？」と疑問だった12bitが、見事に復元できた！
* **bit操作の役割 ＝ 「バイト境界を越えて、必要なbitを切り出すこと」**

# 2. byteを移す：std::memcpy

## bit単位ではなく「連続するbyteの塊」をそのまま動かす

```text
bit操作  ──> 「必要なbitを切り出す」（バイト境界を分解する）
memcpy   ──> 「必要なbyteの塊をそのまま移す」（バイトの並びを保つ）
```

```cpp
// メモリの塊を一括コピーする標準関数
std::memcpy(コピー先アドレス, コピー元アドレス, コピーするバイト数);
```

* 「高速化の裏技」として使うのではなく、**「連続するバイト列を安全に動かす基本道具」**
* ただし、画像処理では第2回で学んだ **LineSpan（余白）** が立ちふさがります

---

# 02の復習：なぜ画像を一発でmemcpyできないのか？

## LineSpan（余白）があるため、一括コピーすると絵が崩れる！

```text
コピー元画像（幅 100 byte）      コピー先バッファ（幅 300 byte）
[ 有効 100 ][ 余白 4 ]          [ コピー先 100 ][ 余白 200 ]
[ 有効 100 ][ 余白 4 ]   ───>   [ コピー先 100 ][ 余白 200 ]
[ 有効 100 ][ 余白 4 ]          [ コピー先 100 ][ 余白 200 ]
```

* 画像全体を一括で `memcpy` すると、**「行末の余白ゴミ」まで一緒にコピーされる！**
* コピー先とコピー元で行の歩幅（LineSpan）が違うため、絵が斜めに崩壊する
* **「1行ずつ、有効幅のバイト数だけをコピーして次行へ進む」** 必要があります

---

# 実践：安全な矩形コピーの実装

## 1行ごとに LineSpan でジャンプしながら memcpy

```cpp
void CopyRect(const uint8_t* src, int srcLineSpan,
              uint8_t* dst, int dstLineSpan,
              int copyWidthBytes, int copyHeight) {
    for (int y = 0; y < copyHeight; ++y) {
        // 各行の先頭アドレスへワープ（第2回の知識！）
        const uint8_t* srcRow = src + (y * srcLineSpan);
        uint8_t* dstRow = dst + (y * dstLineSpan);

        // 有効データ幅だけを安全にコピー
        std::memcpy(dstRow, srcRow, copyWidthBytes);
    }
}
```

* 各行のジャンプには **必ず LineSpan（Stride）** を使う
* 余白を綺麗に飛び越えながら、欲しい矩形部分だけを確実に移せる！

# 現場の注意：境界外アクセスは「未定義動作」

## 「即クラッシュ」よりも恐ろしい、サイレントなメモリ破壊

もしコピー先の枠よりも大きいデータをコピーしてしまったら？

```text
コピー先バッファの枠:       コピーしようとしたデータ（はみ出し！）:
┌──────────────────┐      ┌──────────────────────┐
│                  │      │                      │
│                  │      │                      │### 枠外（未定義動作！）
└──────────────────┘      └──────────────────────┘
```

* 1バイトでも領域外に書き込むと **未定義動作（UB）** になる
* 即座にクラッシュすればまだマシで、**「隣にある別の変数を静かに破壊し、数分後に別の場所で謎の不具合が起きる」** のが一番怖い！
* ※小さな注意：コピー元とコピー先が重なる場合は `memmove` を使う（重複時の `memcpy` は未定義動作）

# 3. byte列を読む：意味を与える

## メモリ上のバイト列だけ見ても、数値は絶対に分からない！

メモリ上に、次の4バイトが並んでいたとします。

```text
[ 0x78 ][ 0x56 ][ 0x34 ][ 0x12 ]  （アドレス 0x1000 〜 0x1003）
```

* このデータは、10進数で「いくつ」でしょうか？
* **答えは「仕様が分からない限り、絶対に分からない」です！**
* 第1回の重要原則：**「byte列 ＋ 解釈ルール（仕様） ＝ 意味あるデータ」**
  * Little-Endian の 32bit 整数？ ──> `0x12345678`（305,419,896）
  * Big-Endian の 32bit 整数？    ──> `0x78563412`（2,018,915,346）
  * 1バイトの数値が4つ？          ──> `120, 86, 52, 18`

---

# 読み方A：明示的に組み立てる（安全・確実）

## 4つのロッカーから1つの値を作る、最も教育的な基本形

仕様書が「リトルエンディアンの 32bit 符号なし整数」と指定している場合:

```cpp
// 4つのバイトから、1つの uint32_t（32bit）を合成する
uint32_t val = static_cast<uint32_t>(p[0])
             | (static_cast<uint32_t>(p[1]) << 8)
             | (static_cast<uint32_t>(p[2]) << 16)
             | (static_cast<uint32_t>(p[3]) << 24);
```

* 下位バイトから順に、8bitずつ左へずらして OR で合体！
* **「4つのbyteから1つの32bit値を作っている」** 様子が誰の目にも明らか
* 実行環境（ホストCPU）のエンディアンに左右されず、常に安全で移植性が高い

---

# 読み方B：std::memcpy による値の取り出し

## 変数にバイト列を写し取って読む手法

```cpp
uint32_t val;
std::memcpy(&val, p, sizeof(val)); // 4バイトを変数にそのまま写す
```

* シフト演算を書かずに、手軽に値を取り出せる
* メモリコピー可能な単純な型（Trivially Copyable）に対して安全に使える
* **ただし大前提がある！**
  * 外部データのエンディアンと、自分のPCのエンディアンが一致している必要がある
  * もし外部がBig-EndianでPCがLittle-Endianなら、値が完全にひっくり返る！

# 4. 「構造体ビュー」という実務コードの誘惑

## 生バッファに構造体を被せて直接読む書き方を見かけるが……

実務のC++コードでは、次のような記述を見かけることがあります。

```cpp
struct Header {
    uint32_t width;
    uint32_t height;
};

// 生バッファに直接 Header* を被せて読む（ゼロコピー？）
const Header* header = reinterpret_cast<const Header*>(buffer);
std::cout << header->width;
```

* コピーを一切せず、構造体のメンバ名で生メモリを読めて便利に見える……
* **しかし、C++の規格上、これは何でも自由に被せてよいわけではありません！**

---

# なぜ安易な reinterpret_cast は危険なのか？

## 「便利な技」ではなく「確認すべき条件がある」と読む！

`reinterpret_cast` を使ったアクセスが合法になるには、厳しい関門があります。

* **① そこにそのオブジェクトの実体はあるか？**
  * メモリ上にその型の寿命（Lifetime）が正しく始まっている必要がある（Aliasing規則）
* **② アライメントは合っているか？**
  * 奇数アドレスに `uint32_t*` を被せて読むと、ハードウェア例外や未定義動作になる
* **③ パディングは仕様と一致しているか？**
  * 構造体メンバ間の余白が、外部データの仕様と1バイトでもズレたら破綻する
* **④ エンディアンは一致しているか？**
* **このコードを見たら「本当にすべての前提条件を満たしているか？」を疑うこと！**

---

# 補足：std::bit_cast（C++20）は何をするものか？

## 構造体ビューの代替ではない！「ビット表現の型変換」

```cpp
// 例: float（32bit）のビット並びを、そのまま uint32_t（32bit）として観察する
float f = 1.0f;
uint32_t bits = std::bit_cast<uint32_t>(f);
```

* `std::bit_cast<To>(from)` は、同サイズの単純な型同士で、ビット表現をもとに **「新しい値を作る」** 機能（コピーの一種）
* 生バッファの上に構造体を被せる「ゼロコピービュー」とは全く別の道具
* 「memcpyより速い代替品」として並べて覚えるものではありません

---

# 実務の健全なアプローチ：仕様のオフセットから読む

## 構造体の形を過信せず、仕様書に従って安全に取り出す

外部データ（通信パケットやファイル）を扱うプロの基本姿勢:

```text
外部仕様書:
offset 0:  sensor_id  (1 byte)
offset 1:  reserved   (3 byte)
offset 4:  raw_value  (4 byte, little-endian)
```

* **基本**: 仕様書のオフセットに従って、明示的にシフト合成するか `memcpy` で読む
* **構造体を使う場合**:
  * `static_assert(sizeof(Packet) == 8);`
  * `static_assert(offsetof(Packet, raw_value) == 4);`
  * コンパイル時にサイズとオフセットが仕様通りか厳密に検証する！

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① bit単位で欲しい部分を取る ──> shift / mask / OR**
  * 12bit Packed画素のように、バイト境界をまたぐデータも自在に復元できる
* **② byte単位で塊を移す ──> memcpy**
  * 画像コピーでは LineSpan を考慮して1行ずつジャンプする
* **③ byte列を値にするときは ──> 「フォーマット仕様」が必須**
  * byte列だけでは意味がない。仕様と合わせて初めて値になる
* **④ エンディアン・サイズ・オフセット・アライメントを勝手に仮定しない**
  * 外部データと内部メモリの前提を必ず確認する
* **⑤ reinterpret_cast を見たら ──> 「本当に合法か？」を確認できる人になる**
  * ゼロコピーの安易な多用は未定義動作の温床。条件を冷静にチェックする
