# 1. バイナリを操作する「2大アプローチ」

## 「コピーするか」「その場で見るか」の二者択一

メモリ上にある生バイト列（バッファ）を扱う方法は、
大きく分けて **2つの流派** しかありません。

```text
【アプローチA: コピー方式（memcpy）】
元バッファ [ 01 02 03 04 ] ──(複製)──> 別の変数 [ 01 02 03 04 ]
安全・確実だが、メモリとCPU時間を消費する

【アプローチB: ゼロコピー参照（構造体ビュー）】
元バッファ [ 01 02 03 04 ]
           ↑
           このアドレスに構造体の「型」を直接被せて読む
複製ゼロ・超高速だが、アライメントやパディングの罠がある
```

* まずは基本となる **「安全なコピー（アプローチA）」** から攻略する

---

# 2. 実践：画像の一部をコピーする（矩形コピー）

## なぜ `memcpy` 一発でコピーできないのか？

第2回で学んだ通り、画像には **LineSpan（余白付きの歩幅）** があります。

```text
コピー元画像（幅 100）           コピー先バッファ（幅 300）
[ 有効 100 ][ 余白 ]            [ コピー先 100 ][ 余白 200 ]
[ 有効 100 ][ 余白 ]    ───>    [ コピー先 100 ][ 余白 200 ]
[ 有効 100 ][ 余白 ]            [ コピー先 100 ][ 余白 200 ]
```

* メモリ全体を一気に `memcpy` すると、**余白ゴミまで一緒にコピーされる**
* 余白のサイズが違うため、コピー先で絵がぐちゃぐちゃに崩れる！
* **「1行ずつ、有効幅だけをコピーして次行へスキップ」** しなければならない

---

# 矩形コピーの実装コード

## 1行ごとに LineSpan でポインタを進めながら memcpy

```cpp
void CopyRect(const uint8_t* src, int srcLineSpan,
              uint8_t* dst, int dstLineSpan,
              int copyWidthBytes, int copyHeight) {
    for (int y = 0; y < copyHeight; ++y) {
        // 各行の先頭アドレスを計算
        const uint8_t* srcRow = src + (y * srcLineSpan);
        uint8_t* dstRow = dst + (y * dstLineSpan);

        // 有効データ幅だけを安全にコピー
        std::memcpy(dstRow, srcRow, copyWidthBytes);
    }
}
```

* `for` ループで1行ずつ処理する
* アドレスの移動には **必ず LineSpan を掛ける**

---

# 現場の落とし穴：境界外アクセス（クラッシュ）

## はみ出し判定（Clipping）のないコピーは即死する

もしコピー先の枠よりも大きい画像をコピーしようとしたら？

```text
コピー先バッファの枠:       コピーしようとした画像（はみ出し！）:
+──────────────────+      +──────────────────────+
|                  |      |                      |
|                  |      |                      |### バッファ外！
+──────────────────+      +──────────────────────+ (メモリ破壊)
```

* 1バイトでもメモリの領域外に `memcpy` すれば **即クラッシュ（未定義動作）**
* 実務コードでは、ループの前に必ず **「枠内に収まっているか」のクランプ処理** を挟む
* `actualWidth = std::min(copyWidth, maxWidth - dstX);`

---

# 3. でも、毎回コピーするのは「無駄」ではないか？

## 通信パケットや巨大データで問題になるコピーのコスト

コピーは安全ですが、大きな代償があります。

```text
4K画像（約 33MB）のコピー:
CPU「33MBをまるごと別の場所に書き写します...」（数ミリ秒の遅延）

通信パケットの受信（毎秒数万回）:
パケットが届くたびに memcpy で構造体にコピー...（CPUがコピーだけで圧迫）
```

* **「データを別の場所に流し込まず、その場にある生データを直接読めないのか？」**
* この切実な要求から生まれたのが **「構造体ビュー（ゼロコピー参照）」**

---

# 4. 構造体ビューの思想

## 「流し込む」のではない。「型というレンズを変える」

```text
メモリ上の12バイト:
アドレス:  0x1000  0x1004  0x1008
生データ: [ 4バイト ][ 4バイト ][ 4バイト ]

見方A（uint8_t* として見る）:
buffer[0] 〜 buffer[11] の 12個のバイトに見える

見方B（HorseRecord* として見る）:
record->birthday (4B), record->owner (4B), record->jockey (4B) に見える！
```

* メモリは1つしか存在しない
* **`reinterpret_cast` はメモリの中身を1ビットも動かさない**
* ポインタの「解釈の型」をすり替えるだけの操作

---

# 構造体ビューの実装コード

## 生バッファに構造体を「被せる」

```cpp
struct HorseRecord {
    uint8_t birthday[4]; // 生年月日 (offset 0〜3)
    uint8_t owner[4];    // 馬主コード (offset 4〜7)
    uint8_t jockey[4];   // 騎手コード (offset 8〜11)
};

uint8_t buffer[12] = { /* 12バイトのバイナリ */ };

// バッファの先頭アドレスを HorseRecord* として見る
HorseRecord* rec = reinterpret_cast<HorseRecord*>(buffer);

// コピーなしで直接アクセスできる！
std::cout << (int)rec->owner[0]; // buffer[4] を直接読んでいる
```

* コピー時間ゼロ、追加メモリ消費ゼロ

---

# 「見る」と「書き換える」は同じこと

## 構造体経由で代入すると、生バッファが書き換わる

```cpp
rec->owner[0] = 99; // 構造体のメンバに代入したつもり

std::cout << (int)buffer[4]; // → なんと「99」になっている！
```

```text
実体は 1つのメモリ領域:
          [ 0 ] [ 1 ] [ 2 ] [ 3 ] [ 4 ] [ 5 ] ...
buffer:                            ↑
rec->owner:                       [ 0 ]
どちらからアクセスしても、書き換わるのは同一のアドレス！
```

### 一行で言えば
**構造体ビューとは「生メモリにリモコンのボタンを割り当てる行為」である**

---

# 5. 強力すぎる武器の代償：未定義動作（UB）

## `reinterpret_cast` が安全に使える厳格な条件

この技は極めて危険で、以下の条件を破ると即座にプログラムが死にます。

* **① バッファサイズ不足**: 構造体のサイズより小さいバッファに被せると領域外アクセス
* **② パディングの混入**: コンパイラが勝手に余白を入れるとオフセットが全壊
* **③ アライメント違反**: CPUが要求する境界アドレスに揃っていない
* **④ 複雑なクラスの禁止**: `std::string` や仮想関数（virtual）を持つ型は絶対不可

---

# 現場の鉄則①：パディングを殺す設計

## なぜプロのバイナリ構造体は `uint8_t` 配列だらけなのか？

```cpp
// 【危険な構造体】
struct BadPacket {
    uint8_t id;   // 1バイト
    int     data; // 4バイト → 間に勝手に3バイトのパディングが入る！
};

// 【現場の安全な構造体】
struct SafePacket {
    uint8_t id[1];   // 1バイト
    uint8_t data[4]; // 4バイト配列として定義する！
};
```

* 全フィールドを `uint8_t` 配列で定義すれば、**パディングは 100% 混入しない**
* `uint8_t` にはアライメント制約がないため、何番地から始まっても安全
* 現場の低レイヤコードが `uint8_t field[4]` だらけなのは、これが理由

---

# 現場の鉄則②：アライメント違反のクラッシュ

## 奇数アドレスを 4バイト整数として読んではいけない

```text
バッファのアドレス: 0x1001 （奇数番地！）
ここに uint32_t* （4バイト境界が必須）を被せて読むと:

x86（PCなど）: 速度が低下するが何とか動いてしまう（気づきにくい罠！）
ARM（スマホ・Switch・組み込み等）: CPU例外（バスエラー）で一発クラッシュ！
```

* **「自分のPCで動いたから大丈夫」は通用しない**
* アライメントが保証できない生バッファから数値を取り出すときは、
  無理にキャストせず **`std::memcpy` で変数に移すのが一番安全**

---

# 結論：3つのアプローチの使い分け基準

## 現場で迷ったときの判断フローチャート

```text
Q1. パフォーマンスが極限まで求められるか？
  ├─ No  → 【std::memcpy】（一番安全。コンパイラが最適化してくれる）
  └─ Yes → Q2 へ

Q2. バッファのアライメントは完全に保証されているか？
  ├─ No  → 【std::memcpy】（無理にキャストするとクラッシュする）
  └─ Yes → Q3 へ

Q3. C++20 以降が使える環境か？
  ├─ Yes → 【std::bit_cast】（型安全・ゼロオーバーヘッドな最新標準）
  └─ No  → 【reinterpret_cast】（パディングを完全排除した構造体で使用）
```

---

# 本日のまとめ

## 持ち帰ってほしい 4つの重要ポイント

* **① 矩形コピーは 1行ずつ LineSpan を掛けて行う**
  * 余白（Padding）を巻き込まないための必須ループ
* **② 構造体ビューの本質は「見方を変える」こと**
  * コピーせず生バッファを直接読み書きできる超高速イディオム
* **③ パディング混入を防ぐなら `uint8_t` 配列**
  * コンパイラによる隙間挿入を物理的に阻止する設計パターン
* **④ 迷ったら `memcpy`**
  * 現代の最適化コンパイラは `memcpy` を極限までインライン展開してくれる
