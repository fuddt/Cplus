# 1. 現場の2つの疑問（Why）

## ポインタとメモリ解放にまつわる現場の定番バグ

C/C++での開発やシステムトラブルにおいて、誰もが遭遇する2大トラブルがあります。

```cpp
// 【疑問 1: なぜアドレスがあるのに使ってはいけないのか？】
int* GetValue() {
    int value = 42;
    return &value; // ローカル変数のアドレスを返す
}
// 呼び出し元で受け取ったポインタは 0x7ffd... という数値を持ち、
// メモリ上を覗くと「42」っぽい値がそのまま残っていることもある。
// なのに、なぜこのポインタを使ってはいけないのか？
```

```text
【疑問 2: なぜOSが勝手に片付けてくれないのか？】
ループ処理を動かすたびに、アプリのメモリ使用量が少しずつ増えていく。
数時間後には数GBに達してアプリが突然強制終了した（メモリリーク）。
「プログラムが使わなくなったメモリ」くらい、なぜOSが自動で回収してくれないのか？
```

* なぜアドレスの数値やbyteが残っているのに触ると壊れるのか？
* なぜ使わなくなった動的メモリは自然消滅しないのか？

# 中心メンタルモデル

## 「アドレスが存在すること」と「オブジェクトが生きていること」は別！

この2大トラブルを解明する鍵は、**メモリの住所（アドレス）** と **データの命（寿命）** を切り離して考えることです。

```text
【住所（アドレス）と 住人（オブジェクト）の例え】

・アパートの「301号室」という住所（アドレス値 0x1000）はずっと存在する。
・しかし、そこに住んでいた住人（オブジェクト）はすでに退去（寿命終了）している！
・退去後、部屋を覗いたら前の住人の荷物（byte列）がたまたま残っているかもしれない。
・だが、勝手にその部屋を使って手紙を送れば、不法侵入（未定義動作）になる！
```

* **重要**:
  * **ポインタ値（アドレス）が存在していても、その場所にオブジェクトが生きている保証はない！**
  * メモリ事故の多くは、「もう死んでいるオブジェクト」を触るか、「片付ける責任」を見失ったときに起きる！

---

# 2. 混乱を防ぐ3つの軸：Storage, Lifetime, Ownership

## データが持つ「場所」「命」「責任」を厳密に区別する

メモリを安全に扱うために、次の3つの問いを明確に切り分けましょう。

```text
┌─────────────────────────────────────────────────────────────┐
│ ① どこにある？     ──>  Storage / Location（配置場所）      │
│                          物理的・論理的にどの記憶域を使うか │
│                                                             │
│ ② いつ生きている？ ──>  Object Lifetime（オブジェクトの寿命）│
│                          生成されてから破棄されるまでの期間 │
│                                                             │
│ ③ 誰が後始末する？ ──>  Ownership（所有権）                 │
│                          そのリソースの後始末に責任を持つ主体│
└─────────────────────────────────────────────────────────────┘
※「Storage Duration」は別途、記憶域そのものの存続期間を分類するC++の正式用語です
```

* **現場の混乱の元凶**:
  * 「スタックにあるから寿命はここまで」「ポインタを持っているから自分が解放する」と、3つの軸を混同してしまうこと！
  * この3つを独立した契約として捉えることが、低レイヤのメモリ事故を防ぐ基礎となります。

# 3. Scope（見える範囲）と Lifetime（生存期間）を分ける

## 「名前が使えるコード上の範囲」と「メモリ上に実体が存在する期間」

初学者が混同しやすい「スコープ」と「ライフタイム」を整理します。

```text
【Scope（スコープ: コード・コンパイラの世界）】
・ソースコード上で、その「変数名」を参照できる有効範囲
・波括弧 { } で囲まれたブロックなど、静的なテキスト上の境界

【Lifetime（ライフタイム: 実行時・メモリの世界）】
・プログラム実行時に、そのオブジェクトがメモリ上に構築され、
  破棄されるまでの動的な時間的区間
```

```cpp
void Example() {
    int* p = nullptr;
    {
        int x = 10; // x のスコープはこの { } の中だけ
        p = &x;     // x のライフタイムはこのブロックを抜けると終了する
    }
    // ここでは変数名 x はスコープ外で使えない
    // さらに p が指す先の x のライフタイムも終了している！
}
```

* この例のような **automatic storage duration を持つローカルオブジェクト `x` は、ブロックを抜けると Lifetime が終了** します。
* ※注意: 「スコープを抜けるとメモリ領域そのものが消滅する」わけではありません。また、`static` 変数のようにスコープ外でも生存し続けるオブジェクトもあります（Scope と Lifetime の独立性）。

---

# 4. Storage Duration（記憶域期間）の4分類

## オブジェクトが確保・保持される「4つの時間的ルール」

C++規格では、オブジェクトの記憶域のあり方を4つの **Storage Duration（記憶域期間）** として定めています。

```text
【1. Automatic Storage Duration（自動記憶域期間）】
・ブロック（複合文）等の実行に対応して記憶域が存続する（ローカル変数など）
・※一般的な実装では、スレッドごとのスタック領域を使って配置されることが多い

【2. Static Storage Duration（静的記憶域期間）】
・プログラムの実行全体（開始から終了まで）にわたり記憶域が存続する（グローバル変数等）

【3. Thread Storage Duration（スレッド記憶域期間）】
・対応するスレッドの実行期間全体にわたり記憶域が存続する（thread_local 変数）

【4. Dynamic Storage Duration（動的記憶域期間）】
・明示的な要求（new 式等）と解放処理によって記憶域の期間が決まる
```

* **ポイント**:
  * 「メモリはスタックとヒープの2種類しかない」と単純化してはいけません。
  * 規格が保証するのは **「記憶域（Storage）そのものが存続する期間」の分類** です。
  * ※注意: 記憶域の存続期間と、その中で「オブジェクトがいつ構築・破棄されるか（Lifetime）」は別の概念です（例: 関数内 static 変数は初回到達時に初期化される等）。

# 5. Automatic Storage とローカル変数の寿命

## 関数実行とともに生まれ、スコープを抜けると寿命を終える

最も日常的に使うローカル変数の振る舞いを観察します。

```cpp
void Process() {
    int counter = 0; // counter のオブジェクトが生成される（Lifetime 開始）
    counter += 5;
    // ...
} // スコープの終端：counter のオブジェクトの Lifetime が終了する
```

```text
【一般的な実装（スタック領域）でのイメージ】

Process() 呼び出し ──> スタックポインタを進めて領域を確保（counter配置）
                   │
counter の読み書き │
                   ↓
Process() 終了     ──> スタックポインタを巻き戻す（counter の寿命終了）
```

* **重要**:
  * スタックポインタが巻き戻されるだけで、**その番地の byte 列がゼロクリアされるわけではありません！**
  * メモリ領域としてはそのまま残っていても、**「counter というオブジェクトはもう死んでいる」** のです。

# 6. Dangling Pointer（ダングリングポインタ）の解剖

## 疑問1の答え：寿命が終わった場所を指す「幽霊ポインタ」

ここで最初の疑問1「ローカル変数のアドレスを返したらどうなるか」に戻ります。

```cpp
int* GetValue() {
    int value = 42;
    return &value; // value のアドレス（例: 0x7ffd0001）を返す
} // ← ここで value の Lifetime は終了した！

void Caller() {
    int* ptr = GetValue();
    std::cout << *ptr << std::endl; // 危険！ Dangling Pointer の参照（Use After Free）！
}
```

```text
GetValue() 実行中:     [ 0x7ffd0001 : 42 (value 生存中) ]
                               │
GetValue() 終了後:     [ 0x7ffd0001 : 42 (寿命終了！再利用待ち領域) ]
                               ↑
Caller() の ptr:       0x7ffd0001 （アドレス数値だけが手元に残っている）
```

* ポインタ変数 `ptr` には確かにアドレス `0x7ffd0001` が入っています。
* しかし、**そのアドレスに存在したオブジェクト `value` は既に寿命を終えています！**

---

# なぜ「byteが残っている」のに触ってはいけないのか？

## 偶然動いているように見えても、C++規格上は「未定義動作」！

「でも、実行してみたら画面に 42 って表示されたよ？ 動くじゃん！」──これこそが最大の罠です。

```text
【なぜ動いたように見えるのか？】
スタックが巻き戻された直後、たまたま別の関数呼び出しが行われておらず、
メモリ上の byte（42）が上書きされずに残っていただけ！
```

```text
【別の関数を1つ呼んだだけで世界が一変する】
int* ptr = GetValue();
DoSomethingElse(); // 別の関数を呼ぶと、同じスタック領域が別のデータで上書きされる！
std::cout << *ptr << std::endl; // 突然ゴミデータが出力されるか、クラッシュする！
```

* **C++規格上の事実**:
  * 寿命が終了したオブジェクトへのポインタの逆参照（アクセス）は **未定義動作（Undefined Behavior）**！
  * 「たまたま動いた」は「正しい」ではありません。コンパイラ最適化でコードが消去されたり、実行時に怪現象を引き起こす原因になります。

---

# 7. 動的確保（Dynamic Allocation）の観察

## スコープを越えて生き続けるメモリの要求

関数の終了後もデータを生き続けさせたい場合、**動的記憶域期間（Dynamic Storage Duration）** を使います。

```cpp
// ※C++での概念観察用コード
int* p = new int(42); // 1. メモリを確保し、int オブジェクトを構築（Lifetime 開始）

// ... 複数の関数やスレッドをまたいで利用できる ...

delete p;             // 2. オブジェクトを破棄し、メモリをアロケータへ返却（Lifetime 終了）
```

* **誤解を解く注意点**:
  * `new` ＝ 単なるヒープ確保ではありません。「メモリ領域の確保 ＋ オブジェクトの構築（初期化）」を行っています。
  * `delete` ＝ メモリの完全消去（0クリア）ではありません。「オブジェクトの破棄 ＋ メモリ領域をアロケータへ再利用可能として返却」する処理です。
* 明示的に `delete` を呼ぶまで、オブジェクトは **スコープを抜けても生き続けます**。

---

# 疑問：`delete p;` のあと、ポインタ変数 `p` はどうなる？

## ポインタは自動で nullptr にはならない！

初心者が最も勘違いしやすいポイントの1つです。

```cpp
int* p = new int(42);

delete p;    // オブジェクトを破棄し記憶域を返却した
             // ※注意: delete は「p = nullptr;」を実行する操作ではない！

p = nullptr; // 安全のため、必要なら明示的にポインタ変数の状態を変える
```

* **「ポインタ変数そのもの」と「指している先のオブジェクト」は別物！**:
  * `delete p;` は、指している先のオブジェクトを破棄する命令です。
  * ポインタ変数 `p` の中身を自動的に `nullptr` に書き換えてくれるわけではありません。
* **Dangling Pointer（状態）と Use After Free（行為・未定義動作）の区別**:
  * `delete p;` の直後、`p` は「寿命が終わった場所を指したポインタ」＝ **Dangling Pointer（状態）** になる！
  * そのポインタを使って `*p` を実際に読み書きする行為・バグを **Use After Free（UAF / 未定義動作）** と呼ぶ！

---

# 8. Memory Leak と Dangling Pointer の対比図

## 寿命とポインタの「交差点の事故」を整理する

メモリ事故の2大巨頭は、Lifetime と Pointer の関係が正反対に狂った状態です。

```text
【Memory Leak（メモリリーク）】
・状態: 確保したリソースが不要になった後も解放されない／解放できない状態
・典型例: アクセスするポインタを途中で失い、二度と解放経路に到達できない
──> 疑問2の答え：OSはC++プログラム内の「どの動的メモリがもう不要か」という
    意図（所有権）を理解できないため、勝手に片付けることはできない！
    （※プロセス終了時にOSがアドレス空間ごと回収するが、それまでメモリは増え続ける）

【Dangling Pointer（ダングリングポインタ：状態）】
・状態: オブジェクトの寿命が終了したのに、ポインタ（住所）だけが手元に残っている
・危険: そのポインタを使ってアクセスする行為（Use After Free）が未定義動作を招く！
──> もう存在しないオブジェクトの場所を触ってしまい、重大なバグ・脆弱性を引き起こす！
```

* **Lifetime / Ownership の失敗を理解する代表的な対照例**:
  * リソースが不要になったのに解放されない ──> **Memory Leak**
  * オブジェクトの寿命が切れたのにポインタが残っている ──> **Dangling Pointer**
  * 手動で `new` / `delete` を管理していると、こうした管理ミスを起こしやすくなります。

# 9. Ownership（所有権）とは何か？

## 「そのリソースの後始末に責任を持つのは誰か」という設計の契約

こうした管理ミスを防ぎ、リソースを安全に扱うための鍵が **Ownership（所有権）** という設計概念です。

```cpp
void ProcessData(Widget* p) {
    // この関数は p を使って処理を行う
    // ...
    // ここで delete p; を呼ぶべきか？？
    // それとも呼び出し元が後で解放してくれるのか？？
}
```

* 生ポインタ（`Widget*`）を見ても、次のことが一切分かりません：
  * ① このメモリは誰が確保したのか？
  * ② 誰が `delete`（後始末）をする責任を持つのか？
  * ③ この関数は「一時的に借りているだけ」なのか？
* **Ownership とは**:
  * **「そのリソースを破棄・解放する責任と権利を持つ主体」** を明確にする設計概念です。

---

# 生ポインタ（Raw Pointer）の限界

## ポインタを持っていること ＝ 所有者（Owner）ではない！

日常の世界に例えると、生ポインタの危険性がよく分かります。

```text
【図書館の本と生ポインタの例え】

・図書館から本を借りて読んでいる人（借り手）
・本のアドレス（場所）は知っているし、中身を読むこともできる。
・しかし、その人は「本の所有者（Owner）」ではない！
・借り手が勝手に本をゴミ箱に捨てたら（二重解放・誤解放）、大問題になる！
・逆に、本を返却したのに（寿命終了）、手元にコピーがあると思い込んで読もうとしても読めない！
```

* 生ポインタ（`T*`）は「アドレスを指す」ことしか表現できません。
* **「所有者（Owner）」なのか「ただの参照者（Borrower）」なのかが型に現れない** ため、実務で二重解放（Double Free）やメモリリークが多発するのです。

---

# 10. RAII（リソース取得＝初期化）の思想

## オブジェクトの寿命（Lifetime）とリソースの寿命を結びつける

C++で広く使われる重要なリソース管理手法が **RAII** です。

```text
【RAII の基本サイクル】

1. オブジェクト生成（コンストラクタ） ──> リソースを取得・確保する
                                          │
2. オブジェクトを利用                     │ 通常のスコープ終了や例外発生時、
                                          │ オブジェクトの破棄に伴って
3. オブジェクト破棄（デストラクタ）   ──> デストラクタがリソースを自動解放！
```

* **なぜ安全なのか？**:
  * 人間がコードのすべての出口（return、エラー分岐、例外など）に `delete` を書く必要がない！
  * **通常のスコープ終了や例外送出時、オブジェクトの破棄に伴ってデストラクタが片付けを担当してくれる** からです。
* ※注意: `std::abort` や強制終了などの異常終了時を除き、通常のスコープ終了や例外によるスタック巻き戻し（Stack Unwinding）でデストラクタが実行されます。

---

# RAII は「メモリ専用」ではない！

## ファイル、ロック、ソケット通信…メモリ以外のリソース管理にも適用できる

RAII を「単なるスマートポインタの仕組み」と狭く捉えてはいけません。
メモリ以外の多くのリソース管理にも適用できる重要な考え方です。

```text
【RAII が管理する代表的なリソース】

・メモリ領域      : new で確保 ──> delete で解放
・ファイル        : open で開く ──> close で閉じる（std::ifstream）
・ミューテックス  : lock で鍵をかける ──> unlock で鍵を開ける（std::lock_guard）
・ソケット通信    : socketハンドルを取得 ──> close / closesocket で返却
・OSハンドル      : CreateFile 等で取得 ──> CloseHandle で返却
```

* 「関数が途中でエラー終了したため、ファイルの `close()` を忘れてロックされたままになった」
* 「例外で抜けたため、`mutex` の `unlock()` を忘れてデッドロックした」
* ──> **これら現場の管理ミスの多くを、RAII（寿命による自動解放）の設計によって根本から防ぐことができます！**

---

# 11. `std::unique_ptr`：所有権を型で表現する

## 単独所有権（Exclusive Ownership）を型として表現する

現代のC++では、手動の `new` / `delete` を書かず、**`std::unique_ptr`** を使って所有権を表現します。

```cpp
#include <memory>

void Example() {
    // 領域を確保し、所有権を持つ unique_ptr を生成
    auto p = std::make_unique<Widget>();

    p->DoSomething();
    // delete を呼ぶ必要はない！
} // ← スコープを抜けると p の Lifetime が終了し、管理していた Widget が自動解放される！
```

* **`std::unique_ptr` の3大ルール**:
  * ① **コピー禁止（No Copy）**: `unique_ptr` 自体をコピーできず、意図せず所有権が複製される事故を防ぐ。
  * ② **移動可能（Move）**: `std::move` を使って、所有権を別の変数や関数へ明示的に「譲渡」できる。
  * ③ **自動解放**: 所有者の寿命が尽きたとき、管理下のリソースを解放する。

# 12. `std::vector` によるストレージ管理とポインタ無効化

## 第3回バッファの正体と、「内部アドレスが変わる」現実

第3回・第4回で使った `std::vector<uint8_t> buffer;` も、内部ストレージを管理する RAII コンテナです。

```text
vector オブジェクト（ローカル変数等）        動的ストレージ（内部バッファ）
┌───────────────────────────┐                ┌───────────────────────┐
│ [データ先頭ポインタ] ─────┼───────────────>│ 0x1000 : byte列...   │
│ [サイズ / キャパシティ]   │                └───────────────────────┘
└───────────────────────────┘
このローカルな vector オブジェクトが破棄されると、管理していた内部ストレージも解放される！
```

* **実務の超重要注意：ポインタの無効化（Pointer Invalidation）**:
  * 「vector を使っているからポインタはずっと安全」と思い込んではいけません！
  * 要素を追加（`push_back` 等）してメモリ再確保（Reallocation）が起きると、
    **内部ストレージが別の場所へ引っ越す（アドレスが変わる）** ことがあります。
  * 以前取得していたポインタや参照は、**「引っ越し前の古い場所を指した Dangling Pointer」** に化けてしまいます！

# 13. `std::shared_ptr`（共有所有権）の存在と循環参照

## 「複数の所有者」を許す仕組みと、その落とし穴

どうしても複数の場所でリソースを共同所有したい場合に、**`std::shared_ptr`** が使われます。

```text
【参照カウント（Reference Counting）による管理】
・何人がそのリソースを所有しているか（カウンタ）を保持する。
・所有者が増えると +1、スコープを抜けて減ると -1。
・カウンタが「0」になった瞬間に、最後の一人がリソースを自動解放する。
```

* **「shared_ptr を使えば何でも安全」という誤解の排除**:
  * カウンタの管理コスト（不可分操作等）が発生し、設計が曖昧になりやすい。
  * **循環参照（Reference Cycle）の罠**:
    * オブジェクトAがBを所有し、BもAを所有すると、互いにカウントが0にならず **メモリリークが発生する！**
* **基本指針**:
  * まずは明確な単独所有権を表す `std::unique_ptr` を基本とし、共有所有権（`std::shared_ptr`）は真に必要な場合に限定して用います。

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① アドレスが存在すること ≠ オブジェクトが生きていること**
  * メモリ番地やbyteが残っていても、Lifetime が終了した場所にアクセスすれば未定義動作
* **② 3つの軸を区別する：Storage, Lifetime, Ownership**
  * どこにあるか、いつまで生きるか、誰が後始末するかの契約を混同しない
* **③ Memory Leak と Dangling Pointer は対照的な失敗例**
  * リソースが不要なのに解放されない（Leak） vs 寿命が切れたのにポインタが残る（Dangling）
  * ポインタが残る「状態（Dangling）」と、それを参照する「行為（Use After Free）」を峻別する
* **④ 生ポインタは所有権を語らない**
  * ポインタを持っているだけで所有者とは限らない。後始末の責任（Ownership）を型で明示する
* **⑤ RAII はメモリ専用ではない、リソース管理の重要な手法**
  * オブジェクトの寿命にリソース解放を結びつける。`std::unique_ptr` や `std::vector` を活用する
