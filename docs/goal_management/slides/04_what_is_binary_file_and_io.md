# なぜ、テキスト（JSON/CSV）ではなくバイナリで保存するのか？

## 「とりあえずJSONで保存」が現場で大炎上した日

普段のWeb開発や業務アプリでは、JSONやCSVでデータを保存するのが一般的です。
しかし、画像やセンサログ、計測データを同じノリで保存すると……

```text
・ファイルサイズが数十MB〜数十GBに膨れ上がり、ディスクを圧迫！
・保存ボタンを押してから、ファイル出力が終わるまで数秒フリーズ！
・ロード時もテキストのパース（文字→数値の変換）でCPUが手一杯！
```

* テキスト形式は **「人間が読みやすい」** 代わりに、コンピュータにとっては **「無駄が多く重い」**
* 巨大なデータを高速かつコンパクトに保存するために、**バイナリ形式** の出番となります
* 今日は「ファイルとは何か」から解き明かし、保存されたbyte列の扱い方を学びましょう

# 1. そもそも「ファイル」とは何か？

## メモリ（RAM）とストレージ（SSD/HDD）の決定的な違い

```text
【メモリ（RAM）】
・電源を切ると中身が消える（揮発性）
・CPUが直接超高速にアクセスできる（ロッカー街）
・容量が限られている（数GB〜数十GB）

        │ 電源を切っても残したい！
        ↓ OS（ファイルシステム）を通してディスクへ書き込む
【ストレージ（SSD / HDD）】
・電源を切ってもデータが残り続ける（不揮発性）
・容量が非常に大きい（数百GB〜数TB）
```

* **ファイルの本質**: ストレージ上に、OSの管理のもと永続化された **「1本の長いbyte列」** である！
* メモリのロッカー街と同じく、ファイルも本質は **「0番地から始まる1次元のbyteテープ」** です

---

# 注意：「拡張子」がデータの意味を決めるわけではない

## `.png` や `.dat` は、人間に向けた「看板」にすぎない

受講者が最初につまずきやすい誤解が **「拡張子」** です。

```text
photo.png ──(名前を変更)──> photo.txt
```

* 拡張子を `.txt` に変えても、**ファイルの中身（byte列）は1ビットも変わりません**
* テキストエディタで開くと、文字コードとして解釈できないため **激しく文字化け** します
* OSやアプリは「拡張子」を見て開くアプリを推測しますが、
  **「そのbyte列をどう解釈すべきか」は、ファイルの中身と仕様が決める！**

# 2. テキストファイル vs バイナリファイル

## どちらもディスク上の実態は「ただのbyte列」である！

「テキストファイル」と「バイナリファイル」に物理的な違いはありません。

```text
【テキストファイル（txt, json, csv）】
中身のbyte列を「文字コード（UTF-8やShift-JIS）」のルールで解釈する約束のファイル
例: 1000000 という数値 ──> "1000000"（'1','0','0','0','0','0','0' の7バイト消費）

【バイナリファイル（png, mp4, 独自形式）】
中身のbyte列を「決められたフォーマット仕様」のルールで解釈するファイル
例: 1000000（0x000F4240） ──> [ 40 42 0F 00 ]（32bit整数なら 4バイトで完結！）
```

* **第1回の重要原則がここでもそのまま成立する！**
  * **「byte列 ＋ 解釈ルール（文字コードか、バイナリ仕様か） ＝ 意味あるデータ」**

# 3. 単純なバイナリ形式でよく見られる基本構造

## 「ヘッダー（固定長メタデータ）」＋「データ部（ペイロード）」

多くの単純なバイナリ形式では、次のような2層レイアウトがよく使われます。

```text
┌─────────────────────────────────────┬─────────────────────────────────────┐
│      ヘッダー部（固定サイズ）        │       データ部（ペイロード）        │
├─────────────────────────────────────┼─────────────────────────────────────┤
│ ・マジックナンバー (2〜4 byte)       │ 実際の画像ピクセル配列              │
│ ・フォーマットのバージョン (2 byte)  │ センサの測定値ログ配列              │
│ ・データの幅・高さ・要素数 (8 byte)  │ 音声波形データ                      │
│ ・後続するデータ部の長さ (4 byte)    │ 本体の可変長データ...               │
└─────────────────────────────────────┴─────────────────────────────────────┘
```

* **ヘッダー**: 「このファイルは何者か？ どんな設定か？ データは何バイトあるか？」
* **データ部**: ヘッダーの案内に従って読み進める、本体の巨大なbyte列

---

# フォーマット仕様書の例（独自画像ファイル）

## 仕様書を読んで初めて、ファイルの中身が意味を持つ

```text
【独自画像フォーマット（.mypimg）仕様書】
offset 0  (2B) : マジックナンバー 'M', 'G'（0x4D, 0x47）
offset 2  (2B) : バージョン番号（uint16_t, little-endian）
offset 4  (4B) : 画像の幅 Width（uint32_t, little-endian）
offset 8  (4B) : 画像の高さ Height（uint32_t, little-endian）
offset 12 (4B) : データ部のバイト長 DataSize（uint32_t, little-endian）
──────────────────────────────────────────────────────────── (ここまでヘッダー 16B)
offset 16 〜   : 画素データ（8bitグレースケールなら Width × Height バイト）
```

* 第3回で学んだ通り、**「offset」「size」「endian」** が厳密に定義されている！
* この仕様書があるからこそ、異なるプログラム同士でファイルを正しく受け渡せます

# 4. メモリ上のstructをそのまま保存してはいけない！

## 「file.write(&myStruct, sizeof(myStruct))」が招く悲劇

「構造体をそのまま `write` すれば簡単だし速いのでは？」 と思うかもしれません。

```cpp
// 【現場で大惨事を招くコード】
struct Header {
    uint8_t  id;    // 1バイト
    uint32_t size;  // 4バイト → 間に勝手に3バイトのパディングが入る！
};
file.write(reinterpret_cast<char*>(&header), sizeof(header));
```

* **第1回・第3回の復習：構造体にはパディングやエンディアンの罠がある！**
  * コンパイラやCPUアーキテクチャが違うと、パディングの入り方が変わる
  * 自分のPCで書き出したファイルを、別の環境で読むとオフセットがズレて壊れる！
* **内部メモリの構造体配置と、外部ファイルフォーマットを絶対に同一視しないこと！**

# シリアライズ と デシリアライズ

## メモリ上の値と、ファイルbyte列の相互変換

```text
【シリアライズ（Serialization / 直列化・保存）】
メモリ上の変数（Width, Height, PixelData...）
      │
      ↓ 仕様書に従って、決まった順番・サイズ・エンディアンでbyte列を組み立てる
ファイル仕様通りのbyte列 [ 'M' 'G' 01 00 64 00 00 00 ... ] ──> ディスクへ書き出す

【デシリアライズ（Deserialization / 復元・読み込み）】
ディスクから読み込んだファイルbyte列 [ 'M' 'G' 01 00 64 00 00 00 ... ]
      │
      ↓ 仕様書のオフセット位置から、各値を安全に取り出す（第3回の技術！）
メモリ上の変数（Width = 100, Height = 100, PixelBuffer...）
```

* 構造体を丸投げするのではなく、**「仕様に沿って1つずつ変換する」** のが確実な設計！

# 5. C++でのファイルオープン：std::ios::binary の意味

## なぜバイナリファイルを開くときに binary フラグが必要なのか？

C++でファイルを開くとき、次のように指定します。

```cpp
std::ifstream file("input.bin", std::ios::binary);   // 読み込み
std::ofstream outFile("output.bin", std::ios::binary); // 書き込み
```

* **なぜ `std::ios::binary` を指定するのか？**
  * テキストモードでは、プラットフォーム（特にWindows）によって、
    改行コード（`\n` と `\r\n`）の自動変換が行われる場合がある
  * バイナリデータの中にたまたま改行と同じ値（`0x0A`）が含まれていると、
    勝手にバイトが挿入・置換されてデータ全体が破壊されてしまう！
* **「書いたbyte列を1ビットも変えずに、そのまま扱いたい」から binary を明示する！**

# ファイルサイズを取得してバッファを用意する

## ファイル末尾へ移動して「何バイトあるか」を測るイディオム

バイナリファイルを読み込むには、まず全体を受け止めるバッファの大きさを知る必要があります。

```cpp
// ※文法は覚えなくてOK！ 「位置を動かして長さを測る」様子を見る
std::ifstream file("data.bin", std::ios::binary);

file.seekg(0, std::ios::end);            // 1. ファイルの末尾へシーク（移動）
std::streamsize fileSize = file.tellg(); // 2. 現在の読み取り位置（=ファイルサイズ）を取得
file.seekg(0, std::ios::beg);            // 3. 読み取り位置を先頭に戻す

// 4. ファイル全体のbyteを受け止める正確なバッファを確保！
std::vector<uint8_t> buffer(static_cast<size_t>(fileSize));
```

* `seekg`（seek get: 読み取り位置の移動）と `tellg`（tell get: 現在位置の報告）
* テープの長さを測ってから、ぴったりサイズのバッファを用意する

# ファイルからバッファへ一括読み込み

## 1バイトずつ読むのではなく、メモリへ一気に流し込む

バッファが用意できたら、`file.read` で一括ロードします。

```cpp
// buffer.data() の先頭アドレスへ、fileSize バイト分を一気に流し込む
if (!file.read(reinterpret_cast<char*>(buffer.data()), fileSize)) {
    throw std::runtime_error("ファイル読み込みに失敗しました");
}
```

```text
ディスク上のファイル (10 MB)
      │
      │ OSのファイルシステム経由で一括転送
      ↓
メモリ上の std::vector<uint8_t> buffer (10 MB)
[ 0x4D ][ 0x47 ][ 0x01 ][ 0x00 ][ 0x64 ] ...
```

* メモリ上に、**ファイルと寸分違わぬ生byte列** が丸ごと展開された！
* ここから、第3回で学んだ「byte列を読む技術」が始まります

# 6. 実践：仕様オフセットに従って値を復元する

## 構造体を無理にキャストせず、仕様書通りに安全に読む

読み込んだバッファから、仕様書に従ってヘッダー情報を復元します。

```cpp
// offset 0: マジックナンバー（2バイト）
char magic[2] = { static_cast<char>(buffer[0]), static_cast<char>(buffer[1]) };

// offset 4: Width（4バイト, little-endian）を第3回の方法で安全に合成！
uint32_t width = static_cast<uint32_t>(buffer[4])
               | (static_cast<uint32_t>(buffer[5]) << 8)
               | (static_cast<uint32_t>(buffer[6]) << 16)
               | (static_cast<uint32_t>(buffer[7]) << 24);
```

* 構造体を直接被せる（`reinterpret_cast`）誘惑に負けず、
  **仕様のオフセットから明示的に組み立てる** のが最も安全で移植性が高い！
* エンディアンやパディングに悩まされる心配がゼロになります

# 7. 現場の防衛設計① マジックナンバーの検証

## 「違うファイルを読み込んだ事故」を水際で阻止する

ユーザーが誤ってテキストファイルやPDFの拡張子を `.mypimg` に変えて開いたら？

```cpp
if (magic[0] != 'M' || magic[1] != 'G') {
    throw std::runtime_error("不正なファイル形式です（マジックナンバー不一致）");
}
```

```text
【実在する代表的なファイルのマジックナンバー（先頭バイト）】
PNGファイル : 先頭 8バイトが必ず [ 89 50 4E 47 0D 0A 1A 0A ]（"\x89PNG..."）
BMPファイル : 先頭 2バイトが必ず [ 42 4D ]（"BM"）
PDFファイル : 先頭 4バイトが必ず [ 25 50 44 46 ]（"%PDF"）
ZIPファイル : 先頭 4バイトが必ず [ 50 4B 03 04 ]（"PK.."）
```

* 拡張子は誰でも偽装できますが、**先頭のマジックナンバーは嘘をつけない！**
* ファイルを開いたら、何よりもまずマジックナンバーを確認するのが実務の鉄則

# 現場の防衛設計② ファイルサイズと境界の検証

## 「途中で切れたファイル」によるメモリ破壊を防ぐ

ネットワーク通信の中断などで、ファイルが途中で切れていることがあります。

```cpp
// ① 最小限のヘッダーサイズ（16バイト）があるか？
if (fileSize < 16) {
    throw std::runtime_error("ファイルサイズがヘッダー未満です");
}

// ② ヘッダーに書かれた画像サイズから、期待される全体サイズを計算
size_t expectedSize = 16 + (static_cast<size_t>(width) * height);

// ③ 実際のファイルサイズが足りているか？
if (static_cast<size_t>(fileSize) < expectedSize) {
    throw std::runtime_error("データ部が途中で切れています（破損ファイル）");
}
```

* 外部からやってくるファイルは **「壊れているかもしれない」** と疑う
* サイズ検証を挟んでからアクセスすることで、領域外アクセス（未定義動作）を完全に防止する

# 8. 実践：バイナリパッチ（一部の書き換えと上書き保存）

## メモリ上のbyte列を書き換えて、再びディスクへ出力する

```text
[ ステップ 1: 一括ロード ]
ファイル ──(file.read)──> std::vector<uint8_t> buffer に展開
                                │
[ ステップ 2: byte列を書き換え（パッチ） ]
buffer[4] = 200; // offset 4（Width）の下位バイトを 200 に書き換える！
                                │
[ ステップ 3: 一括書き出し ]
buffer ──(outFile.write)──> ファイルへ一括書き戻し！
```

```cpp
// 書き戻しコード（※文法は覚えなくてOK！）
std::ofstream outFile("patched.mypimg", std::ios::binary);
outFile.write(reinterpret_cast<const char*>(buffer.data()), buffer.size());
```

* メモリ上のbyte列をそのまま `write` すれば、変更がディスクへ永続化される
* これがゲームのセーブデータ編集やファームウェア更新の原理です！

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① ファイルとは、ストレージ上に永続化された「1本の長いbyte列」**
  * テキストもバイナリも実態は同じ。違いは「文字コードで読むか、独自仕様で読むか」
* **② メモリ上の構造体をそのまま write してはいけない**
  * パディングやエンディアンのズレを防ぐため、仕様に沿ってシリアライズする
* **③ `std::ios::binary` は「勝手な改行変換を防ぐ」ために付ける**
  * プラットフォームの自動変換を抑制し、byte列を1ビットも変えずに扱う
* **④ マジックナンバーとサイズ検証で、破損ファイルを水際で防ぐ**
  * 拡張子は看板にすぎない。先頭シグネチャとファイルサイズを必ず確認する
* **⑤ ファイルも結局「byte列 ＋ 仕様（解釈ルール）」で意味を持つ**
  * 第1回〜第4回まで、メモリでもファイルでも貫かれている本質は全く同じ！
