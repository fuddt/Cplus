# 1. そもそも、私たちはどうして色が見えるのか？

## 光の波長の違いを、目が感知して脳が色として認識する

物体やディスプレイから届く情報、それはすべて **「光（電磁波）」** です。

```text
物体やディスプレイから「光」が届く
        │
        ↓
目（網膜）に入る
        │
        ↓ 明るい場所での色の知覚には、主に「3種類の錐体細胞」が関わる
        │ （それぞれ光の波長に対する感度が異なる）
脳へ信号が送られる
        │
        ↓ 反応の組み合わせから「赤っぽい」「緑っぽい」と判断
脳が「色」として認識する！
```

* 人間の目は、無限にある光の波長を **「3種類の反応の組み合わせ」** に要約して知覚している
* **「少数の異なる光を組み合わせれば、多くの色を感じさせられる」** という性質が、コンピュータの色作りの土台になります

# 光と数値の循環：カメラとディスプレイ

## 「表示」と「撮影」は、互いに真逆の変換を行っている

```text
【現実世界】
    │ 光
    ↓
【カメラ】          光をセンサーで捉え、電気信号を経て「数値」にする
    │ 数値データ
    ↓
【画像データ】       圧縮保存（PNG/JPEG等） or メモリ上の生配列（Pixel Buffer）
    │ 展開（RGB値）
    ↓
【ディスプレイ】     数値を受け取り、対応する「RGBの光」を出す
    │ 光
    ↓
【人間の目】        網膜（錐体細胞）で受け取り、脳が色を感じる
```

* ディスプレイは **「数値 → 光」**、カメラは **「光 → 数値」** の変換器
* **実務のカメラでは、最初からRGB（8bit×3）とは限らない！**
  * 第1回で登場した「12bit RAWデータ」のように、センサーの生数値をそのまま扱う現場もあります

# 2. ディスプレイはどうやって色を作るのか？

## 一般的なディスプレイも「3つの光（RGB）」を混ぜて色を作る

```text
R ＝ 赤（Red）     G ＝ 緑（Green）     B ＝ 青（Blue）
```

```text
・R だけ光らせる      ──> 赤
・G だけ光らせる      ──> 緑
・B だけ光らせる      ──> 青
・R ＋ G を混ぜる     ──> 黄色
・R ＋ B を混ぜる     ──> マゼンタ（赤紫）
・G ＋ B を混ぜる     ──> シアン（水色）
・R ＋ G ＋ B 全部光る ──> 白！
・全部消す（光ゼロ）   ──> 黒！
```

* **加法混色（光の三原色）**: 光を足すほど明るくなり、全部合わさると白になる
* ※絵の具（混ぜるほど暗くなる「減法混色」）とは全く逆の仕組み！

# 3. 1つのピクセルの中にもRGBがある

## 画面を極限まで拡大すると現れる「小さな発光要素」

ディスプレイの最小単位である **1ピクセル（画素）** を拡大すると:

```text
1 ピクセル (Pixel) の構造例（※一般的なRGBストライプ配列の場合）
┌──────────────┐
│  R │  G │  B │  ← 3つの小さな発光要素（サブピクセル）が並んでいる
└──────────────┘
```

* コンピュータは、各ピクセルに対して次の数値を指定します
  * **「R をどれくらい強く光らせるか？」**
  * **「G をどれくらい強く光らせるか？」**
  * **「B をどれくらい強く光らせるか？」**
* **では、この「光の強さ（明るさ）」はどうやって数値化されているのか？**

---

# 24bit RGBでは、1ピクセルを「1byte × 3個」で表す

## 今回は最も標準的で分かりやすい「24bit RGB」の例で考える

各色の明るさを、それぞれ **0（消灯）〜 255（最大発光）** の数値で表します。

```text
R の明るさ : 0 〜 255 (1 byte)
G の明るさ : 0 〜 255 (1 byte)
B の明るさ : 0 〜 255 (1 byte)

1ピクセル ＝ 合計 3 byte（24bit カラー）
[ R (1B) ][ G (1B) ][ B (1B) ]
```

```text
・真っ赤なピクセル : R = 255, G =   0, B =   0
・真っ白なピクセル : R = 255, G = 255, B = 255
・真っ暗なピクセル : R =   0, G =   0, B =   0
```

* **第1回で勉強した「256通りの状態が入る箱（1byte）」を3個並べれば、1677万色（256×256×256）を表現できる！**
* ※用途によって8bitグレースケール（1byte）や透過付き（4byte）、12bit RAW等も存在します

# 4. 「画像ファイル」と「展開後のPixel Buffer」

## ディスク上のファイルと、メモリ上の生データは別物！

「画像データ」という言葉には、実は2つの状態があります。

```text
【ディスク上の画像ファイル（PNG, JPEG, etc.）】
・ファイルサイズを小さくするため「圧縮」されている
・中身はそのままではピクセルの並び順になっていない

        │ プログラムで読み込む（デコード・展開）
        ↓
【メモリ上の生バッファ（Pixel Buffer / 生ピクセル配列）】
・1画素ずつの数値が、ルール通りに並んだ「生データの表」
・画面に描画したり、画像処理フィルタをかけるのはこの状態！
```

* **本研修で扱うのは、メモリ上に展開された「Pixel Buffer」です！**
* 画像処理プログラミングの核心は、この展開後の生メモリをどう歩くかにあります

---

# Pixel Buffer とは「RGBの数字が並んだ表」である

## ディスプレイが光を出すための「数値の2次元テーブル」

たとえば、2×2ピクセルの小さな画像を考えてみます。

```text
【人間の目に見える絵】
[ 赤 ][ 緑 ]
[ 青 ][ 白 ]

【メモリ上の生データ（数値の表）】
(0,0) 赤: (255,   0,   0)    (1,0) 緑: (  0, 255,   0)
(0,1) 青: (  0,   0, 255)    (1,1) 白: (255, 255, 255)
```

* **Pixel Buffer とは、突き詰めれば「色を表す数値の2次元テーブル」である！**
* ファイルが光っているのではなく、**展開後の数値を受け取ったディスプレイが光を出している**
* そして、ここからプログラマ最大の課題が始まります

# 5. 疑問：画像は「2次元の表」なのに、メモリは1次元？

## 2次元の平面を「1本の長いテープ」にどう収めるか？

第1回で学んだ通り、**メモリは1バイトの箱が一列に並んだロッカー街（1次元）** です。
メモリ側に「縦と横」という概念はありません。

```text
画面上の見え方（2次元・行と列の表）:
[ (0,0) ][ (1,0) ][ (2,0) ]  ← 0行目
[ (0,1) ][ (1,1) ][ (2,1) ]  ← 1行目
[ (0,2) ][ (1,2) ][ (2,2) ]  ← 2行目

メモリ上の実態（1次元・1本の長いテープ）:
[ 0行目全部 ][ 1行目全部 ][ 2行目全部 ] ...
```

* 2次元の表を1次元メモリに並べるには **「折りたたむルール」** が必要
* 最も標準的なルールが **「左から右へ読み、端まで行ったら次の行へ改行する」**

---

# 【二段構え①】まずは8bitグレースケールで考える

## 1画素＝1バイト（0〜255の濃淡）なら、話は驚くほどシンプル！

幅（Width）= 3、高さ = 2 の小さな8bitグレースケール画像を、メモリに並べてみます。

```text
【2次元の絵】
     x=0    x=1    x=2
y=0 [ A ]  [ B ]  [ C ]   (0行目)
y=1 [ D ]  [ E ]  [ F ]   (1行目)
        │
        ↓ 「1行ごとに改行して、後ろへ繋げる」
【1次元のメモリ（ロッカー街）】
index:  0      1      2      3      4      5
     [ A ][ B ][ C ]  [ D ][ E ][ F ]
      └── 0行目 ──┘    └── 1行目 ──┘
```

* 0行目が終わったら、すぐ後ろに1行目がペタッと連結される
* **では、座標 (x=2, y=1) にある「F」をメモリから探すにはどう計算する？**

---

# なぜ `y * Width + x` なのか？

## 「y行分丸ごとスキップして、x歩進む」という身体感覚

```text
探したい場所: y=1行目、x=2列目 の「F」

① y=1行目に行くには？
   手前にある「0行目（Width = 3個分）」を丸ごと飛び越える必要がある！
   ──> 1 × Width ＝ 3個スキップ！

② そこから x=2列目 に進むには？
   行の先頭から「+ 2歩」進む！
   ──> + x ＝ 2歩！

結果: index = (1 × 3) + 2 = 5番地 ──> 見事に「F」に到達！
```

* **基本計算式: `index = y * Width + x`**
* `y * Width` は「上の行をすべて飛び越えるためのジャンプ台」である

---

# 【二段構え②】カラー（RGB 3バイト）へ拡張する

## 1ピクセルが3バイトになっても、考え方はまったく同じ！

カラー画像では、1つのマスの中に「R, G, B」の3バイトが入ります。

```text
1ピクセル = 3バイト（bytesPerPixel = 3）:
[ px(0,0) (3B) ][ px(1,0) (3B) ][ px(2,0) (3B) ] ...
[ R G B ][ R G B ][ R G B ] ...
```

* 飛び越えるロッカーの数が、すべて **「3倍」** になるだけ！
  * 1行スキップするバイト数: `Width × 3` バイト
  * x画素進むバイト数: `x × 3` バイト
* **バイト位置（オフセット） = `(y * Width + x) * 3`**
* グレースケールの式に「1画素あたりのバイト数」を掛け算しただけ！

---

# 6. なぜカラーコードは `#FF0000` なのか？

## 16進数は「人間が1バイトを最も読みやすくする記法」

Webやデザインツールでおなじみのカラーコード: **`#FF 00 00`（赤）**

```text
16進数は「0〜9」の後に「A〜F」を使って、1桁で16通りの状態を表す
0, 1, 2 ... 9, A(10), B(11), C(12), D(13), E(14), F(15)

16進数の 2桁 ＝ 16 × 16 ＝ 256通り！
00 ──> 0
FF ──> 255
```

* **16進数の2桁は、ちょうど「1バイト（8bit = 256状態）」にジャストフィットする！**
* だからプログラマは、バイト値を書くときに `0xFF` や `0x00` を使う
* `#FF 00 00` とは、単に「赤=255, 緑=0, 青=0」を1バイトずつ書いただけ！

---

# 実務の注意①：カラーコードとメモリ配置は別物！

## 「#FF0000」がそのままメモリに「FF 00 00」と並ぶとは限らない

ここにも第1回で学んだ「解釈ルール（仕様）」の壁が存在します。

```text
カラーコード（表記上のルール）:
# [ R ][ G ][ B ]  ──> 赤なら #FF0000

実際のメモリ配置（ハードウェアやOSの仕様依存）:
・一般的な形式（RGB）      : [ R (FF) ][ G (00) ][ B (00) ]
・Windows標準（BGR形式）   : [ B (00) ][ G (00) ][ R (FF) ] ← 逆順！
・透過付き（BGRA形式）     : [ B (00) ][ G (00) ][ R (FF) ][ A (FF) ]
```

* Windowsの描画やOpenCVでは、歴史的経緯により **BGR順** で並ぶことが多い
* **色コードは「色の表現」。メモリ上の並び順は「仕様（フォーマット）」が決める！**

---

# 実務の注意②：Top-down と Bottom-up

## 「画面の上が先頭か、下が先頭か？」 歴史が生んだ上下逆さまの罠

冒頭で触れた「画像が上下逆さまになる現象」の正体がこれです。

```text
【Top-down（左上原点）】※現代の主流（PNG, OpenCV, 多くのWeb規格）
メモリ先頭: 0行目（一番上） ──> 下に向かって 1行目、2行目... と進む

【Bottom-up（左下原点）】※Windows標準（BMPファイル, Windows DIB）
メモリ先頭: 最終行（一番下）──> 上に向かって進む（原点が「左下」！）
```

* Windowsの歴史的なBitmap形式（DIB）は、グラフの座標系のように **左下原点（Bottom-up）** を採用
* Top-down の感覚でそのまま画面に流し込むと、**「上下が綺麗に逆さま」** に表示されてしまう！
* ※C#の `BitmapData.Stride` が負の値（マイナス）になることがあるのも、このBottom-upに由来します

# 7. 現場で起きる大事件：「画像が斜めに崩れる！」

## 新人エンジニアが必ず一度は遭遇する恐怖のバグ

画像処理アプリを作っていて、生バッファを表示した瞬間:

```text
本来の絵:               実際に表示された絵（斜め崩れ）:
[ ■ ■ ■ ■ ]            [ ■ ■ ■ ]
[ ■ ■ ■ ■ ]     →      [ ■ ■ ■ ■ ]
[ ■ ■ ■ ■ ]            [   ■ ■ ■ ■ ]
                       [     ■ ■ ■ ]
```

* 画像全体が **右や左に斜めに引き裂かれ、砂嵐ノイズまみれ** になる！
* 計算ミス？ メモリ破壊？
* **いいえ、原因は「Width をそのまま使って行ジャンプしたこと」にあります。**

---

# なぜ斜めに流れてしまうのか？

## 「わずか数バイトのズレ」が、行を追うごとに累積する

1行あたり、たった **1バイトだけ認識がズレていた** とします。

```text
1行目のズレ: +1 byte （見た目はほぼ気づかない）
2行目のズレ: +2 byte （右へ 1〜2ピクセルずれる）
3行目のズレ: +3 byte （右へ 3ピクセルずれる）
...
100行目のズレ: +100 byte （画面が完全に崩壊！）
```

* メモリは1本のテープなので、行末の解釈がずれると **次行の先頭がずれる**
* 行が進むほどズレが掛け算で増えていき、綺麗な平行四辺形に歪んでしまう
* これを防ぐための合言葉が **LineSpan（ストライド）** です。

---

# 8. 核心概念：LineSpan（ストライド）とは何か？

## 「画素データの幅」と「次の行までの歩幅」は一致するとは限らない

```text
画像（Width = 101 ピクセル、LineSpan = 104 バイト）のメモリ配置例:

row 0: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
row 1: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
row 2: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
       |<-------------- LineSpan = 104 byte -------------->|
```

* **Width（有効幅）**: 人間が見る画像の横幅（有効なピクセル数）
* **LineSpan（ストライド / ピッチ）**: メモリ上で「次の行の先頭へ行くための実際のバイト数」
* **注意**: 余白（Padding）が含まれる場合、`Width分のバイト数 ≠ LineSpan` となる！

---

# なぜ行末に「余白（Padding）」が入るのか？

## ハードウェアやAPIの都合で「行の先頭を特定の境界に揃える」仕様がある

「なぜわざわざ余白を詰めるのか？」 その理由は **データ転送や処理の効率化** です。

```text
幅 101 ピクセルの8bitグレースケール画像（余白なしの場合）:
row 0 の先頭: アドレス 0x0000 （4の倍数・綺麗）
row 1 の先頭: アドレス 0x0065 = 101番地 （4の倍数ではない！中途半端！）

余白を 3バイト足して 1行を 104バイト（4の倍数）に揃えたフォーマットの場合:
row 1 の先頭: アドレス 0x0068 = 104番地 （4の倍数・一括読み出ししやすい！）
```

* 画像フォーマット、GPU、画像処理API、キャプチャボード等には、**「各行の開始位置を 4バイトや 16バイト等の境界に揃える」** 仕様がよくある
* 第1回で学んだ **「アライメント（境界を揃えて効率化する）」という思想** が、ここでも形を変えて登場している！

---

# 行先頭への正しいアクセス

## 仕様から「行の実際の歩幅」を確認し、提供されている歩幅を使う

画像処理でピクセル `(x, y)` のメモリアドレスを計算するとき:

```text
【やってはいけない思い込み】
「1行のバイト数 ＝ Width × bytesPerPixel」だと決めつけること

【実務での正しい姿勢】
画像の仕様やAPIから「行の歩幅（Stride / LineSpan）」を確認してジャンプする！
```

```cpp
// C++ でのアドレス計算例（※文法は覚えなくてOK！ 歩幅の概念を見る）
const uint8_t* rowStart = srcBuffer + y * lineSpan;       // まず行先頭へジャンプ
const uint8_t* pixelPtr = rowStart + x * bytesPerPixel;   // そこからx画素進む
```

### 一行で言えば
**LineSpanとは「次の行の先頭へ正しくワープするための実際の歩幅」である**

# 9. 普段のC#では？

## C# の BitmapData.Stride の正体はこれだった！

C# で `Bitmap` を高速処理するとき、次のようなコードを書きます。

```csharp
// C# の高速画像処理コード
BitmapData bmpData = bmp.LockBits(rect, ImageLockMode.ReadWrite, pixelFormat);
IntPtr ptr = bmpData.Scan0;      // メモリ先頭アドレス
int stride = bmpData.Stride;    // ← これがまさに LineSpan（行の歩幅）！
```

* C# ではこれを **`Stride`** と呼ぶ（中身は LineSpan と同じ概念）
* 画像処理ライブラリに渡すときも、`Width` ではなく `Stride` を渡さないと崩れる
* **言語が高水準になっても、裏側のメモリの物理構造（Stride）は全く同じ！**

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① 画像ファイル（圧縮）と Pixel Buffer（展開後の生メモリ）を区別する**
  * カメラは光→数値、ディスプレイは数値→光。メモリ上では「数値の2次元テーブル」
* **② 24bit RGBなら1ピクセルは 1byte（0〜255）× 3個**
  * グレースケールなら1byte。ジャンプの基本式は `y * width + x`
* **③ 画面上の配置とメモリ配置は「仕様」に従う**
  * RGB/BGRの並び順や、Top-down/Bottom-up（上下の向き）に注意
* **④ 「画素データの幅」と「行の歩幅（LineSpan）」は別物**
  * 境界揃えの余白（Padding）があると、Widthのバイト数と歩幅が食い違う
* **⑤ 行のアクセスには「仕様で定められた歩幅（Stride）」を使う**
  * 歩幅を無視してWidthで決めつけると、画像が斜めに崩壊する
