# 1. そもそも、私たちはどうして色が見えるのか？

## 「光」の違いを、目が感知して脳が色と判断している

物体やディスプレイから届く情報、それはすべて **「光（電磁波）」** です。

```text
物体やディスプレイから「光」が届く
        │
        ↓
目（網膜）に入る
        │
        ↓ 人間の目は、光の波長の違いを主に「3種類の感度」で捉える
脳へ信号が送られる
        │
        ↓
脳が「赤っぽい」「緑っぽい」などの「色」として認識する！
```

* 人間の目は、無限にある光の波長を **「おおよそ3つの成分」** に要約して感じ取っている
* この人体の特性が、コンピュータの色作りの大ヒントになります

---

# 2. ディスプレイはどうやって色を作るのか？

## 一般的なディスプレイも「3つの光（RGB）」を混ぜて色を作る

```text
R ＝ 赤（Red）     G ＝ 緑（Green）     B ＝ 青（Blue）
```

```text
・R だけ光らせる      ──> 赤
・G だけ光らせる      ──> 緑
・B だけ光らせる      ──> 青
・R ＋ G を混ぜる     ──> 黄色
・R ＋ B を混ぜる     ──> マゼンタ（赤紫）
・G ＋ B を混ぜる     ──> シアン（水色）
・R ＋ G ＋ B 全部光る ──> 白！
・全部消す（光ゼロ）   ──> 黒！
```

* **加法混色（光の三原色）**: 光を足すほど明るくなり、全部合わさると白になる
* ※絵の具（混ぜるほど暗くなる「減法混色」）とは全く逆の仕組み！

---

# 3. 1つのピクセルの中にもRGBがある

## 画面を極限まで拡大すると現れる「小さな発光要素」

ディスプレイの最小単位である **1ピクセル（画素）** を拡大すると:

```text
1 ピクセル (Pixel)
┌──────────────┐
│  R │  G │  B │  ← 3つの小さな発光要素（サブピクセル）が並んでいる
└──────────────┘
```

* コンピュータは、各ピクセルに対して次の数値を指定します
  * **「R をどれくらい強く光らせるか？」**
  * **「G をどれくらい強く光らせるか？」**
  * **「B をどれくらい強く光らせるか？」**
* **では、この「光の強さ（明るさ）」はどうやって数値化されているのか？**

---

# 1ピクセルは「1byteの箱 × 3個」で表す

## 第1回で学んだ「1byte ＝ 0〜255」の箱がここで大活躍！

各色の明るさを、それぞれ **0（消灯）〜 255（最大発光）** の数値で表します。

```text
R の明るさ : 0 〜 255 (1 byte)
G の明るさ : 0 〜 255 (1 byte)
B の明るさ : 0 〜 255 (1 byte)

1ピクセル ＝ 合計 3 byte（24bit カラー）
[ R (1B) ][ G (1B) ][ B (1B) ]
```

```text
・真っ赤なピクセル : R = 255, G =   0, B =   0
・真っ白なピクセル : R = 255, G = 255, B = 255
・真っ暗なピクセル : R =   0, G =   0, B =   0
```

* **第1回で勉強した「256通りの状態が入る箱（1byte）」を3個並べれば、1677万色（256×256×256）を表現できる！**

---

# 4. 画像とは「RGBの数字が並んだ表」である

## 画像ファイル自体が光っているのではなく、ただの数値の集まり

たとえば、2×2ピクセルの小さな画像を考えてみます。

```text
【人間の目に見える絵】
[ 赤 ][ 緑 ]
[ 青 ][ 白 ]

【コンピュータが持っているデータ（数値の表）】
(0,0) 赤: (255,   0,   0)    (1,0) 緑: (  0, 255,   0)
(0,1) 青: (  0,   0, 255)    (1,1) 白: (255, 255, 255)
```

* **画像データとは、突き詰めれば「色を表す数値の2次元テーブル」である！**
* 画像ファイルが光っているのではなく、**数値を受け取ったディスプレイが光を出している**
* そして、ここからプログラマ最大の課題が始まります

# 5. 疑問：画像は「2次元の表」なのに、メモリは1次元？

## 2次元の平面を「1本の長いテープ」にどう収めるか？

第1回で学んだ通り、**メモリは1バイトの箱が一列に並んだロッカー街（1次元）** です。
メモリ側に「縦と横」という概念はありません。

```text
画面上の見え方（2次元・行と列の表）:
[ (0,0) ][ (1,0) ][ (2,0) ]  ← 0行目
[ (0,1) ][ (1,1) ][ (2,1) ]  ← 1行目
[ (0,2) ][ (1,2) ][ (2,2) ]  ← 2行目

メモリ上の実態（1次元・1本の長いテープ）:
[ 0行目全部 ][ 1行目全部 ][ 2行目全部 ] ...
```

* 2次元の表を1次元メモリに並べるには **「折りたたむルール」** が必要
* 最も標準的なルールが **「左から右へ読み、端まで行ったら次の行へ改行する」**

---

# 【二段構え①】まずは白黒画像で考える

## 1画素＝1バイトなら、話は驚くほどシンプル！

幅（Width）= 3、高さ = 2 の小さな白黒画像を、メモリに並べてみます。

```text
【2次元の絵】
     x=0    x=1    x=2
y=0 [ A ]  [ B ]  [ C ]   (0行目)
y=1 [ D ]  [ E ]  [ F ]   (1行目)
        │
        ↓ 「1行ごとに改行して、後ろへ繋げる」
【1次元のメモリ（ロッカー街）】
index:  0      1      2      3      4      5
     [ A ][ B ][ C ]  [ D ][ E ][ F ]
      └── 0行目 ──┘    └── 1行目 ──┘
```

* 0行目が終わったら、すぐ後ろに1行目がペタッと連結される
* **では、座標 (x=2, y=1) にある「F」をメモリから探すにはどう計算する？**

---

# なぜ `y * Width + x` なのか？

## 「y行分丸ごとスキップして、x歩進む」という身体感覚

```text
探したい場所: y=1行目、x=2列目 の「F」

① y=1行目に行くには？
   手前にある「0行目（Width = 3個分）」を丸ごと飛び越える必要がある！
   ──> 1 × Width ＝ 3個スキップ！

② そこから x=2列目 に進むには？
   行の先頭から「+ 2歩」進む！
   ──> + x ＝ 2歩！

結果: index = (1 × 3) + 2 = 5番地 ──> 見事に「F」に到達！
```

* **基本計算式: `index = y * Width + x`**
* `y * Width` は「上の行をすべて飛び越えるためのジャンプ台」である

---

# 【二段構え②】カラー（RGB 3バイト）へ拡張する

## 1ピクセルが3バイトになっても、考え方はまったく同じ！

カラー画像では、1つのマスの中に「R, G, B」の3バイトが入ります。

```text
1ピクセル = 3バイト（bytesPerPixel = 3）:
[ px(0,0) (3B) ][ px(1,0) (3B) ][ px(2,0) (3B) ] ...
[ R G B ][ R G B ][ R G B ] ...
```

* 飛び越えるロッカーの数が、すべて **「3倍」** になるだけ！
  * 1行スキップするバイト数: `Width × 3` バイト
  * x画素進むバイト数: `x × 3` バイト
* **バイト位置（オフセット） = `(y * Width + x) * 3`**
* 白黒の式に「1画素あたりのバイト数」を掛け算しただけ！

---

# 6. なぜカラーコードは `#FF0000` なのか？

## 16進数は「人間が1バイトを最も読みやすくする記法」

Webやデザインツールでおなじみのカラーコード: **`#FF 00 00`（赤）**

```text
16進数は「0〜9」の後に「A〜F」を使って、1桁で16通りの状態を表す
0, 1, 2 ... 9, A(10), B(11), C(12), D(13), E(14), F(15)

16進数の 2桁 ＝ 16 × 16 ＝ 256通り！
00 ──> 0
FF ──> 255
```

* **16進数の2桁は、ちょうど「1バイト（8bit = 256状態）」にジャストフィットする！**
* だからプログラマは、バイト値を書くときに `0xFF` や `0x00` を使う
* `#FF 00 00` とは、単に「赤=255, 緑=0, 青=0」を1バイトずつ書いただけ！

---

# 実務の注意：カラーコードとメモリ配置は別物！

## 「#FF0000」がそのままメモリに「FF 00 00」と並ぶとは限らない

ここにも第1回で学んだ「解釈ルール（仕様）」の壁が存在します。

```text
カラーコード（表記上のルール）:
# [ R ][ G ][ B ]  ──> 赤なら #FF0000

実際のメモリ配置（ハードウェアやOSの仕様依存）:
・一般的な形式（RGB）      : [ R (FF) ][ G (00) ][ B (00) ]
・Windows標準（BGR形式）   : [ B (00) ][ G (00) ][ R (FF) ] ← 逆順！
・透過付き（BGRA形式）     : [ B (00) ][ G (00) ][ R (FF) ][ A (FF) ]
```

* Windowsの描画やOpenCVでは、歴史的経緯により **BGR順** で並ぶことが多い
* **色コードは「色の表現」。メモリ上の並び順は「仕様（フォーマット）」が決める！**

# 7. 現場で起きる大事件：「画像が斜めに崩れる！」

## 新人エンジニアが必ず一度は遭遇する恐怖のバグ

画像処理アプリを作っていて、画面を表示した瞬間:

```text
本来の絵:               実際に表示された絵（斜め崩れ）:
[ ■ ■ ■ ■ ]            [ ■ ■ ■ ]
[ ■ ■ ■ ■ ]     →      [ ■ ■ ■ ■ ]
[ ■ ■ ■ ■ ]            [   ■ ■ ■ ■ ]
                       [     ■ ■ ■ ]
```

* 画像全体が **右や左に斜めに引き裂かれ、砂嵐ノイズまみれ** になる！
* 計算ミス？ メモリ破壊？
* **いいえ、原因は「Width をそのまま使って行ジャンプしたこと」にあります。**

---

# なぜ斜めに流れてしまうのか？

## 「わずか1バイトのズレ」が、行を追うごとに累積する

1行あたり、たった **1バイトだけ認識がズレていた** とします。

```text
1行目のズレ: +1 byte （見た目はほぼ気づかない）
2行目のズレ: +2 byte （右へ 2ピクセルずれる）
3行目のズレ: +3 byte （右へ 3ピクセルずれる）
...
100行目のズレ: +100 byte （画面が完全に崩壊！）
```

* メモリは1本のテープなので、行末の解釈がずれると **次行の先頭がずれる**
* 行が進むほどズレが掛け算で増えていき、綺麗な平行四辺形に歪んでしまう
* これを防ぐための合言葉が **LineSpan（ストライド）** です。

---

# 8. 核心概念：LineSpan（ストライド）とは何か？

## 「有効幅（Width）」と「LineSpan」は絶対に別物である

```text
画像（Width = 101 ピクセル、LineSpan = 104 バイト）のメモリ配置:

row 0: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
row 1: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
row 2: [ 有効データ 101 byte ][ 余白（Padding） 3 byte ]
       |<-------------- LineSpan = 104 byte -------------->|
```

* **Width（有効幅）**: 人間が見る画像の横幅（有効なピクセル数）
* **LineSpan（ストライド / ピッチ）**: メモリ上で「次の行の先頭へ行くための実際のバイト数」
* **重要**: `Widthのバイト数 ≤ LineSpan` は常に成り立つ（同じ場合もある）

---

# なぜ行末に「余白（Padding）」が入るのか？

## 第1回で学んだ「CPUのアライメント要求」がここでも登場！

第1回で **「CPUは4バイト境界を好み、中途半端なアドレスを嫌う」** と学びました。
まさにその理由が、画像の行末にも働いています。

```text
幅 101 ピクセルの白黒画像（余白なしの場合）:
row 0 の先頭: アドレス 0x0000 （4の倍数・綺麗）
row 1 の先頭: アドレス 0x0065 = 101番地 （4の倍数ではない！中途半端！）

余白を 3バイト足して 104バイト（4の倍数）に揃えると:
row 1 の先頭: アドレス 0x0068 = 104番地 （4の倍数・CPUが一撃で読める！）
```

* GPUやCPU、描画APIは **「各行の先頭が 4バイトや 16バイトの倍数に揃っていること」** を要求する
* その高速化のために、コンパイラやグラフィックチップが行末に余白を詰める！

# 正しいアドレス計算式

## Width ではなく、必ず LineSpan でジャンプする！

画像処理でピクセル `(x, y)` のメモリアドレスを指すときは:

```text
【やってはいけない間違い（大惨事）】
アドレス = 先頭 + y * (Width * 3) + x * 3

【正しい計算式】
アドレス = 先頭 + y * LineSpan + x * bytesPerPixel
```

```cpp
// C++ 実装コード（※文法は覚えなくてOK！ 考え方を見る）
const uint8_t* rowStart = srcBuffer + y * lineSpan;       // まず行先頭へジャンプ
const uint8_t* pixelPtr = rowStart + x * bytesPerPixel;   // そこからx画素進む
```

### 一行で言えば
**LineSpanとは「次の行へワープするための実際の歩幅」である**

---

# 9. 普段のC#では？

## C# の BitmapData.Stride の正体はこれだった！

C# で `Bitmap` を高速処理するとき、次のようなコードを書きます。

```csharp
// C# の高速画像処理コード
BitmapData bmpData = bmp.LockBits(rect, ImageLockMode.ReadWrite, pixelFormat);
IntPtr ptr = bmpData.Scan0;      // メモリ先頭アドレス
int stride = bmpData.Stride;    // ← これがまさに LineSpan！
```

* C# ではこれを **`Stride`** と呼ぶ（中身は LineSpan と完全同一）
* C# で画像処理ライブラリに渡すときも、`Width` ではなく `Stride` を渡さないと壊れる
* **言語が高水準になっても、裏側のメモリの物理構造（LineSpan）は全く同じ！**

# 本日のまとめ

## 持ち帰ってほしい 5つの重要ポイント

* **① ディスプレイはRGBの光を混ぜ、画像データはその数値を保持する**
  * 1ピクセルは「1byte（0〜255）の箱 × 3個」。画像は「数値の2次元テーブル」
* **② ジャンプの基本式は `y * width + x`**
  * 1行進むごとに width 個スキップして、x 歩進む感覚を掴む
* **③ 16進数2桁は「1バイト（0〜255）」を表す道具**
  * ただしカラーコードの並び（RGB）とメモリ配置（BGR等）は仕様による
* **④ Width と LineSpan は別物**
  * Width は画素数、LineSpan は「次の行の先頭までの実際の歩幅（バイト数）」
* **⑤ 行ジャンプには必ず LineSpan を使う**
  * アライメントによる行末パディングを無視すると、画像が斜めに崩れる
