# 1. 画像を極限まで拡大すると何が見えるか？

## 画像の正体は「色のついたタイルの格子（グリッド）」

スマホやPCの画面に映る鮮やかな写真も、
極限まで拡大すると **小さな正方形（ピクセル）** の集まりです。

```text
拡大図（3×3ピクセルの世界）:
[ (0,0) 赤 ][ (1,0) 緑 ][ (2,0) 青 ]
[ (0,1) 白 ][ (1,1) 黒 ][ (2,1) 黄 ]
[ (0,2) 灰 ][ (1,2) 橙 ][ (2,2) 紫 ]
```

* 横のピクセル数を **幅（Width）** と呼ぶ
* 縦のピクセル数を **高さ（Height）** と呼ぶ
* 画面とは、この正方形タイルを縦横に並べた **2次元平面**

---

# 1ピクセルは何バイトなのか？

## モノクロなら1バイト、カラーなら3〜4バイト

第1回で「1バイトは 0〜255」と学びました。
画像の色も、この **0〜255** の組み合わせで表現されます。

```text
【モノクロ（グレースケール）】 1ピクセル = 1 byte (uint8_t)
0（真っ黒） 〜 255（真っ白）

【カラー（24bit RGB）】 1ピクセル = 3 byte
[ R (0〜255) ][ G (0〜255) ][ B (0〜255) ]

【カラー（32bit RGBA）】 1ピクセル = 4 byte
[ R ][ G ][ B ][ A（透明度 0〜255） ]
```

### 一行で言えば
**1ピクセルとは「1個〜4個の byte の箱」の集まりにすぎない**

---

# 2. 疑問：メモリは1次元なのに、画像はどう入るのか？

## 2次元の平面を「1本の長いテープ」にどう収めるか？

第1回で学んだ通り、**メモリは1列に並んだロッカー街（1次元）** です。
メモリ側に「2次元」という概念はありません。

```text
画面上の見え方（2次元）:
[ px(0,0) ][ px(1,0) ][ px(2,0) ]  ← 1行目
[ px(0,1) ][ px(1,1) ][ px(2,1) ]  ← 2行目
[ px(0,2) ][ px(1,2) ][ px(2,2) ]  ← 3行目

メモリ上の実態（1次元）:
[ 1行目全部 ][ 2行目全部 ][ 3行目全部 ] ...
```

* 2次元のデータを1次元に並べるには **「折りたたむルール」** が必要
* 最も標準的なのが **「左から右へ読み、端まで行ったら次の行へ」**（ラスタースキャン順）

---

# 座標 (x, y) からアドレスを求める計算式

## 「y行スキップして、x個進む」という単純な足し算

モノクロ画像（1ピクセル＝1バイト、幅＝Width）の場合:

```text
先頭アドレス (0,0)
  ↓
[ row 0 (Widthバイト) ][ row 1 (Widthバイト) ][ row 2 (Widthバイト) ] ...
|<--- y行分のスキップ --->|<- xバイト進む ->|
```

* **先頭からのオフセット = y × Width + x**
* 例：幅 100ピクセルの画像で、座標 (10, 5) のアドレスは？
* `offset = 5 × 100 + 10 = 510` 番地
* プログラムはこの数式を使って、2次元座標をメモリアドレスに変換している

# 3. 現場で起きる大事件：「画像が斜めに崩れる！」

## 新人エンジニアが必ず一度は遭遇する恐怖のバグ

画像処理アプリを作っていて、画面を表示した瞬間:

```text
本来の絵:               実際に表示された絵（斜め崩れ）:
[ ■ ■ ■ ■ ]            [ ■ ■ ■ ]
[ ■ ■ ■ ■ ]     →      [ ■ ■ ■ ■ ]
[ ■ ■ ■ ■ ]            [   ■ ■ ■ ■ ]
                       [     ■ ■ ■ ]
```

* 画像全体が **右や左に斜めに引き裂かれ、ノイズまみれ** になる！
* 計算ミス？ メモリ破壊？
* **いいえ、原因は「Width をそのまま使って計算したこと」にあります。**

---

# なぜ斜めに流れてしまうのか？

## 「わずか1バイトのズレ」が、行を追うごとに累積する

1行あたり、たった **1バイトだけ認識がズレていた** とします。

```text
1行目のズレ: +1 byte （見た目はほぼ気づかない）
2行目のズレ: +2 byte （右へ 2ピクセルずれる）
3行目のズレ: +3 byte （右へ 3ピクセルずれる）
...
100行目のズレ: +100 byte （画面が完全に崩壊！）
```

* メモリは1本のテープなので、行末の解釈がずれると **次行の先頭がずれる**
* 行が進むほどズレが掛け算で増えていき、綺麗な平行四辺形に歪んでしまう
* これを防ぐための合言葉が **LineSpan（ストライド）** です。

---

# 4. 核心概念：LineSpan（ストライド）とは何か？

## 「有効幅（Width）」と「LineSpan」は絶対に別物である

```text
画像（Width = 100 ピクセル、LineSpan = 128 バイト）のメモリ配置:

row 0: [ 有効データ 100 byte ][ 余白（Padding） 28 byte ]
row 1: [ 有効データ 100 byte ][ 余白（Padding） 28 byte ]
row 2: [ 有効データ 100 byte ][ 余白（Padding） 28 byte ]
       |<-------------- LineSpan = 128 byte -------------->|
```

* **Width（有効幅）**: 人間が見る画像の横幅（有効なピクセル数）
* **LineSpan（ストライド / ピッチ）**: メモリ上で「次の行の先頭まで行くための実際のバイト数」
* **重要**: `Width ≤ LineSpan` は常に成り立つ（同じ場合もある）

---

# なぜ行末に「余白（Padding）」が入るのか？

## 第1回で学んだ「CPUのアライメント要求」がここでも登場

なぜわざわざ無駄なゴミデータ（余白）を挟むのでしょうか？

```text
幅 101 ピクセルの画像（1ピクセル=1バイト）:
row 0 の先頭: アドレス 0x0000 （4の倍数・綺麗）
row 1 の先頭: アドレス 0x0065 = 101番地 （4の倍数ではない！中途半端！）

余白を 3バイト足して 104バイト（4の倍数）に揃えると:
row 1 の先頭: アドレス 0x0068 = 104番地 （4の倍数・CPUが一撃で読める！）
```

* GPUやCPU、高速な描画API（DirectX, Windows GDI, SIMD演算）は、
  **「各行の先頭が 4バイトや 16バイトの境界に揃っていること」** を要求する
* そのために、行末に自動的にパディングが詰められる

# 正しいアドレス計算式

## Width ではなく、必ず LineSpan を掛ける！

画像処理でピクセル `(x, y)` のメモリアドレスを指すときは:

```text
【やってはいけない間違い（大惨事）】
アドレス = 先頭 + y * Width + x

【正しい計算式】
アドレス = 先頭 + y * LineSpan + x * bytesPerPixel
```

```cpp
// C++ 実装コード
const uint8_t* rowStart = srcBuffer + y * lineSpan;
const uint8_t* pixelPtr = rowStart + x * bytesPerPixel;
```

### 一行で言えば
**LineSpanとは「次の行へワープするための歩幅」である**

# 5. 座標系の落とし穴：左上原点 vs 左下原点

## 数学の教科書と、コンピュータの画面は天地が逆

原点 `(0, 0)` の位置にも流派が存在します。

```text
【左上原点（画面の標準）】      【左下原点（数学・Windows BMP）】
(0,0) ───────→ x               y ↑
  │                             │
  │   yが増えると「下」に進む      │   yが増えると「上」に進む
  ↓ y                           (0,0) ───────→ x
```

* **左上原点**: Windows/MacのUI、Web、DirectX、OpenCVなどほぼ全て
* **左下原点**: 数学のグラフ、**Windows標準のBMPファイル（歴史的遺産）**
* BMPファイルをそのまま読み込むと、**上下逆さま（倒立）** になる原因はこれ

# 実務での共通認識：C# と C++ の連携

## 言語が変わっても「メモリの掟」は全く同じ

C# の `Bitmap` を C++ ネイティブに渡して高速処理するとき:

```csharp
// C# 側のコード
BitmapData bmpData = bmp.LockBits(rect, ImageLockMode.ReadWrite, pixelFormat);
IntPtr ptr = bmpData.Scan0;      // 先頭メモリアドレス
int stride = bmpData.Stride;    // これがまさに LineSpan！
```

* C# ではこれを **`Stride`** と呼ぶ（中身は LineSpan と完全同一）
* `Width` と `Stride` の両方を C++ に渡さないと、ネイティブ側で処理できない
* **言語が高レベルになっても、メモリの物理構造からは逃れられない**

# 本日のまとめ

## 持ち帰ってほしい 4つの重要ポイント

* **① 画像はメモリ上では「1本の長いバイト列」**
  * 2次元の絵を、行ごとに折りたたんでメモリに収納している
* **② Width と LineSpan は別物**
  * Width は画素数、LineSpan は「次の行の先頭までの歩幅（バイト数）」
* **③ パディングの理由はアライメント**
  * 各行の先頭を 4の倍数や 16の倍数番地に揃えて高速化するため
* **④ 行ジャンプには必ず LineSpan を使う**
  * Width でジャンプするとズレが累積して「画像が斜めに崩れる」
