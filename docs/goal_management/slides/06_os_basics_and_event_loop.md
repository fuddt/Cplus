# 1. コンソールアプリとGUIアプリの決定的な違い

## 「上から下へ走る」プログラムは、GUIでは通用しない

```text
【コンソールアプリ（手続き型）】
main() 開始 ──> 入力を待つ ──> 計算する ──> 結果を表示 ──> 終了
※ プログラム側が主導権を握り、一本道で進む

【GUIアプリ（イベント駆動型）】
アプリ起動 ──> 【？？？】
※ ユーザーがいつボタンを押すか、いつ画面を閉じるかは予測不能！
```

* GUIアプリは **「いつ来るかわからない外からの刺激（イベント）」** を待ち続ける
* この仕組みを支えるのが **「OSとのメッセージング」** です。

# 2. Windowsアプリの起動：`WinMain`

## `main` の代わりに呼び出されるエントリポイント

```cpp
int WINAPI WinMain(
    HINSTANCE hInstance,     // このアプリ自身の識別番号（ハンドル）
    HINSTANCE hPrevInstance, // （昔の名残：常に nullptr）
    LPSTR     lpCmdLine,     // コマンドライン引数
    int       nCmdShow       // ウィンドウの初期表示状態
) {
    // ここからアプリが始まる！
}
```

* コンソールが `main` から始まるように、Windows GUI は `WinMain` から始まる
* 引数の `hInstance` は **「OSがこのアプリを識別するための番号札」**

# ウィンドウを表示する 3ステップ

## 「設定書きを登録し、実体化し、画面に出す」

```text
[ ステップ 1: ウィンドウクラスの登録 (RegisterClassEx) ]
「こういう見た目で、メッセージはこの関数に送ってくれ」という設定書きをOSに提出

[ ステップ 2: ウィンドウの生成 (CreateWindowEx) ]
設定書きをもとに、OSのメモリ上に実際のウィンドウオブジェクトを作成（HWND取得）

[ ステップ 3: ウィンドウの表示 (ShowWindow / UpdateWindow) ]
ディスプレイ画面にウィンドウを描画する
```

* この3行を書いただけでは、まだウィンドウは動きません
* 心臓を動かすために **「メッセージループ」** を開始します。

# 3. メッセージループの心臓部

## OSからの手紙を無限に待ち受けるループ処理

```cpp
MSG msg = {};
// OSのメッセージキューから「手紙（メッセージ）」を取り出す
while (GetMessage(&msg, nullptr, 0, 0)) {
    TranslateMessage(&msg); // キー入力を文字に変換
    DispatchMessage(&msg);  // 窓口（WndProc）へ手紙を配達！
}
return (int)msg.wParam;
```

```text
Windows OS のメッセージキュー
[ クリック手紙 ][ キー入力手紙 ][ 描画手紙 ]
       │ (GetMessage で1つ取り出す)
       ↓
DispatchMessage ──(配達)──> 担当のウィンドウプロシージャへ！
```

* `GetMessage` は手紙が来るまで **CPUを使わずに待機（スリープ）** する

# 4. イベントを処理する窓口：`WndProc`

## 届いたメッセージを `switch` 文で仕分ける

```cpp
LRESULT CALLBACK WndProc(HWND hwnd, UINT msg, WPARAM wParam, LPARAM lParam) {
    switch (msg) {
    case WM_CREATE:  // 画面が作られた瞬間（ボタン等の部品を配置）
        return 0;
    case WM_COMMAND: // ボタンが押された！
        OnButtonClicked(LOWORD(wParam));
        return 0;
    case WM_DESTROY: // 閉じるボタンが押された！
        PostQuitMessage(0); // メッセージループを終わらせる
        return 0;
    }
    // 自分で処理しないメッセージは OS の標準処理に丸投げする！
    return DefWindowProc(hwnd, msg, wParam, lParam);
}
```

# ボタンがクリックされたときの完全な旅

## マウスからあなたのコードへ届くまでの全ステップ

```text
1. ユーザーがマウスをクリック！
     ↓
2. マウスドライバ経由で Windows(OS) がクリックを検知
     ↓
3. OSが「WM_COMMAND」というメッセージを作ってアプリのキューに入れる
     ↓
4. whileループの GetMessage がキューからメッセージを拾い上げる
     ↓
5. DispatchMessage がウィンドウの WndProc を直接呼び出す
     ↓
6. あなたが書いたボタン処理関数が実行される！
```

### 一行で言えば
**GUIアプリとは「OSから次々に投げ込まれる手紙をさばく配達員」である**

# 5. 実務最大の疑問：なぜ画面が「応答なし」になるのか？

## 誰がアプリをフリーズさせているのか？

ボタンを押した処理の中に、重い処理を書くと:

```cpp
case WM_COMMAND:
    // 巨大な画像処理（30秒かかる重い計算）
    ProcessHugeImage(); 
    return 0;
```

```text
ボタン押下 ──> ProcessHugeImage() が 30秒間 CPUを占有！
                 │
                 ├── その間、メッセージループ（while）に帰ってこない！
                 ├── OS「次の描画メッセージを送りたいんだけど...」
                 ├── OS「マウスクリックの手紙も溜まってるんだけど...」
                 ↓
OS「全然手紙を受け取らないな。よし、白く曇らせて【応答なし】を出そう」
```

* **画面をフリーズさせている真犯人は、メッセージループを止めた開発者自身**

# 解決策：UIスレッドとワーカースレッドの分離

## 「接客係（UI）」と「調理係（処理）」を分ける

```text
【UIスレッド（接客係）】
while(GetMessage) を絶対に止めない！
ボタンが押されたら「注文書」だけ作って、裏方に投げて即座にレジに戻る。

【ワーカースレッド（調理係 / バックグラウンド）】
裏でじっくり巨大画像処理や通信を行う。
終わったら UIスレッドに「できたよ」とメッセージ（PostMessage）を送る。
```

* C# の `async / await` や `Task.Run` も、裏ではこの分離を行っている
* **OSのメッセージループを理解して初めて、非同期処理の必然性が腹落ちする**

# 6. 他のフレームワークとの普遍的な共通点

## 言語やプラットフォームが変わっても、本質は変わらない

```text
Win32 API:
while (GetMessage) { DispatchMessage }

C# (WinForms / WPF):
Application.Run() の内部で、全く同じメッセージループがグルグル回っている

Webブラウザ (JavaScript):
「シングルスレッド ＋ イベントループ」という完全同一の思想
重いループを書くとブラウザが「ページが応答しません」と警告を出す
```

* 現代のあらゆるUIフレームワークは、この **「イベント駆動モデル」** の上に建っている

# 本日のまとめ

## 持ち帰ってほしい 4つの重要ポイント

* **① GUIアプリの本質は「イベント駆動」**
  * 予測不能なユーザー操作を待ち受けるアーキテクチャ
* **② 心臓部は `GetMessage` と `DispatchMessage`**
  * OSのキューから手紙を取り出し、WndProc へ配達し続ける
* **③ UIフリーズの原因はメッセージループの停止**
  * 重い処理は別スレッドに逃がし、UIループを絶対にブロックしない
* **④ すべての現代UIはイベントループの上に成り立っている**
  * WinForms, WPF, Web frontend すべてに共通する普遍原理
