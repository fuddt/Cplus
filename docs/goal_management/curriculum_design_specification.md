## 1. 受講者ペルソナと到達目標

### 【受講者ペルソナ（起点）】
* **経験言語**: Python や C# の実務経験者。これから C++ や低レイヤを学ぶ人。
* **メンタルモデルの特性**:
  * メモリやアドレスを普段意識せずにプログラミングしてきた。
  * データを **「表（行と列、DataTable、2次元配列 `arr[y, x]`）」** として捉えており、その裏でメモリが一列の1次元テープ（ロッカー街）に並んでいる感覚がまだ身体化されていない。
* **低レイヤ基礎知識の初期状態**:
  * **16進数**: 概念は知っている、見れば思い出せるが、即座に読み書きはできない。
  * **ポインタ**: 「番地」という言葉は知っているが、ポインタ加算（`p + offset`）や参照外し（`*p`）は書けない。
  * **2次元インデックス**: `y * width + x` の計算が「なぜそう動くのか」ピンとこない。

### 【到達目標（ゴール）】
> **「画像処理や通信パケットの C++ コードを読んだときに、頭の中に byte 列（メモリの物理的な並び）を描ける人」**

* 自分で低レイヤコードをゼロからスラスラ書けること（コーダー）を目指すのではない。
* **実務コードを読んだとき、デバッガのメモリダンプを見たとき、仕様書を開いたときに、「あ、メモリ上では今こう並んでいるんだな」と頭の中で図解・トラブル診断できる状態** を目指す。

## 4. 各回の詳細設計仕様

### 第1回：データとは何か？――ビット・バイトから始まるメモリの正体
* **役割**: すべての土台。「bitは状態」「型は解釈ルール」「メモリはロッカー街」を確立する。
* **導入（Why）**: 普段は高水準言語が隠してくれているが、壊れた理由（画像崩れ、12bitが入らない、数値化け）を知るために必要になる。
* **核心内容**:
  * 1bitは状態（0/1そのものに意味はない）
  * bit列 ＋ 解釈ルール ＝ 意味あるデータ（CPU命令もbit列）
  * 1byte＝8bit（256状態の箱）
  * C++は観察顕微鏡、型も解釈ルールの一つ（uint8_t vs int）
  * メモリは1バイトの箱が一列に並んだ「ロッカー街」、アドレスは「番号札」
  * 【応用】12bit Packed画像：ロッカーの仕切り（8bit）と画素の区切り（12bit）がズレる！ ──> ビット操作が必要（詳細は第3回へ）
  * リトルエンディアンの罠（人間の直感と逆、下位バイトから配置）
  * 【実験】`unsigned char*` で2バイト目を書き換えると `100 ──> 356`（+256）に化ける！
  * バッファ（生メモリに型のレンズを当てる）
  * アライメントとパディング：`SensorRecord`（データは5byteなのに、なぜ8byte？）
  * 実務の処方箋：内部メモリ配置と外部データフォーマットは別物。ファイル・通信はシリアライズする。

---

### 第2回：画像データの正体――「2次元の絵」を「1次元メモリ」にどう並べるか？
* **役割**: 「表形式（2次元）」から「1次元メモリテープ」へのパラダイムシフト。LineSpanの解明。
* **導入（Why）**: カメラやファイルから読み込んだ画像を表示したら、**「なぜか全体が斜めに崩れてノイズになった」** 現場の絶望から入る。
* **核心内容**:
  * **二段構えのインデックス解説（超重要）**:
    1. まず **「1画素＝1バイトの白黒画像」** で、2次元の表を改行して1列のテープにする図解。
       `y=1, x=2` ──> `index = y * width + x`（1行進むごとにwidth個のロッカーを丸ごとスキップして `+ x` 歩進む）。
    2. その後で **「1画素＝3バイト（RGBカラー）」** へ拡張する。
       `offset = (y * width + x) * 3`。
  * **16進数（hex）の自然な導入**:
    * カラーコード `#FF0000` はなぜ赤か？
    * 16進数の2桁（`00`〜`FF`）は、ちょうど「1バイト（0〜255）」を表すのに人間にとって最も都合がいいから！
    * ※注意：「カラーコードは色を記述する記法であり、メモリ上にそのまま `FF 00 00` と並ぶとは限らない（RGB/BGR等の仕様依存）」と釘を刺す。
  * **核心：LineSpan（ストライド/ピッチ）の解剖**:
    * 第1回で学んだ **「アライメント（CPUは4バイト境界を好む）」** を伏線回収！
    * 画像の横幅の末尾に、なぜパディング（余白）が入るのか？
    * 正しいジャンプの歩幅：`offset = y * lineSpan + x * bytesPerPixel`。
    * 余白を無視して `width` で飛ぶと、1行ごとに数バイトずつズレて全体が斜めに流れる！
  * **【普段のC#では？】**:
    * C#の `BitmapData.Stride` の正体はこれだったのか！

---

### 第3回：生メモリを操る3つの技術――ビット操作・コピー・構造体ビュー
* **役割**: メモリ上の生バイト列を自由自在にハンドリングする実践技法。
* **導入（Why）**: 「byte配列から値を取り出すのに、毎回手動計算や無駄なコピーを書いていて処理が追いつかない」から入る。
* **核心内容（生メモリを操る3つの流派）**:
  1. **切り抜く（ビット操作）**:
     * 第1回で予告した **12bit Packed画素の救出コード** をここで本格実践！
     * シフト（`>>`, `<<`）、マスク（`&`）、結合（`|`）で、バイト境界をまたぐ12bit画素を復元する。
     * 【実務鉄則】符号拡張バグを防ぐため、ビット操作は必ず `uint8_t` 等の unsigned 型で行う。
  2. **移す（バイトコピー）**:
     * LineSpanを考慮した安全な矩形コピー（`memcpy` の行ループ）。
     * バッファオーバーランを防ぐ境界チェックガード。
  3. **レンズを変える（構造体ビュー）**:
     * コピーせず、生メモリのアドレスに直接構造体の型を被せるゼロコピー参照（`reinterpret_cast`）。
     * 【技術的負債の排除】「ゼロコピーなら何でもキャストしていいわけではない」。アライメント違反（SIGBUS）や Strict Aliasing Rule の制約を正しく伝える。

### 第4回：バイナリファイルの仕組み――メモリのデータをそのままディスクに保存する
* **役割**: メモリとストレージの架け橋。ファイルフォーマットの共通構造の理解。
* **導入（Why）**: 「テキスト形式（JSON/CSV）で画像やセンサーデータを保存したら、数十MB〜数GBに膨れ上がり、ロードに数秒かかって現場で怒られた」から入る。
* **核心内容**:
  * テキスト形式 vs バイナリ形式（数値1000000を "1000000" の7文字で書くか、4バイトで書くか）。
  * **フォーマットの黄金律：ヘッダー（固定長）＋ データ部（可変長）**。
    * BMP等の実例（マジックナンバー、画像サイズ、オフセット）。
  * C++バイナリI/Oの鉄板作法：
    * なぜ `std::ios::binary` を忘れると改行コード自動変換（`0x0A`）でファイルが即死するのか。
    * ファイルサイズを取得し、`std::vector<uint8_t>` に一撃でバッファロードする。
  * 実践：バイナリパッチ（ファイルをメモリに読み込み、第3回の構造体ビューで一部を書き換えて保存）。
  * 第1回の教訓の回収：構造体を丸ごと書き込まず、ヘッダー仕様に合わせてシリアライズする。

---

### 第5回：DLLとリンカ――プログラムが部品として結合する仕組み
* **役割**: ソースコードが機械語になり、別言語と連携する実行基盤の解明。
* **導入（Why）**: 「#include も通って文法エラーもないのに、謎の **`LNK2019`** でビルドが止まって帰れない」「別言語にDLLを渡したらクラッシュした」現場トラブルから入る。
* **核心内容**:
  * ビルドの2大フェーズ：**コンパイル（文法検査）** と **リンク（実体の結合）** の分離。
    * `#include` は宣言を信じるだけ。リンカが初めて実体（.obj）を探しに行く。
  * 静的リンク（.lib）と動的リンク（.dll）の違い。
  * DLLの関数公開と `extern "C"` の正体（C++の名前マングリングを無効化する理由）。
  * **【普段のC#では？】P/Invoke による C# 連携**:
    * C#の `[DllImport]` で C++ DLL を呼び出すときのメモリの受け渡し。
    * 構造体を渡したときにパディングやアライメントでデータがズレる現場の地雷。
  * **【データの置かれる場所と寿命（スタックと動的メモリ）】**:
    * 二分法講座にはせず、**「データにはスコープと寿命がある」** と1枚で整理。
    * ローカル変数は関数を抜けると消える（戻り値でポインタを返すと即死）。
    * 動的に確保したメモリと、C++のRAIIによる自動管理の恩恵。

### 第6回：OSの基本動作――メッセージループとイベント駆動アーキテクチャ
* **役割**: 全6回の集大成。OSがプログラムをどう制御し、なぜ画面が動くのかの解明。
* **導入（Why）**: 「ボタンを押して重い画像処理を走らせたら、**画面が白くなって『応答なし』でフリーズした**」トラブルから入る。
* **核心内容**:
  * コンソールアプリ（手続き型：上から下へ走って終了）vs GUIアプリ（イベント駆動：外からの刺激を待ち続ける）。
  * Windowsアプリの心臓部：**メッセージループ（`GetMessage` ──> `DispatchMessage`）**。
  * 窓口関数 `WndProc`（ウィンドウプロシージャ）によるイベント分岐。
  * **「応答なし（フリーズ）」の真犯人**:
    * メッセージループが重い処理でブロックされる ──> OSからの生存確認に応答できなくなる！
    * UIスレッドとワーカースレッドの分離（非同期処理）の物理的必然性。
  * **全6回の総括（コンピュータシステム基礎の全体地図）**:
    * bit/byte ──> メモリ ──> 2次元画像 ──> バイナリ操作 ──> ファイル ──> DLL ──> OSイベントループ
    * 受講生の頭の中に、完全な「メモリとプログラムの地図」が完成する。
