# コンピュータシステム基礎研修 教材設計仕様書

本ドキュメントは、「コンピュータシステム基礎研修」を一貫した教育ストーリーとして構築するための**教材設計仕様書（マスタープラン）**である。

## 1. 受講者ペルソナと到達目標

### 【受講者ペルソナ（起点）】
* **経験言語**: Python や C# の実務経験者。これから C++ や低レイヤを学ぶ人。
* **メンタルモデルの特性**:
  * メモリやアドレスを普段意識せずにプログラミングしてきた。
  * データを **「表（行と列、DataTable、2次元配列 `arr[y, x]`）」** として捉えており、その裏でメモリが一列の1次元テープ（ロッカー街）に並んでいる感覚がまだ身体化されていない。
* **低レイヤ基礎知識の初期状態**:
  * **16進数**: 概念は知っている、見れば思い出せるが、即座に読み書きはできない。
  * **ポインタ**: 「番地」という言葉は知っているが、ポインタ加算（`p + offset`）や参照外し（`*p`）は書けない。
  * **2次元インデックス**: `y * width + x` の計算が「なぜそう動くのか」ピンとこない。

### 【到達目標（ゴール）】
> **「画像処理や通信パケット、ファイル入出力、DLL境界、マルチスレッドの C++ コードを読んだときに、頭の中に byte 列（メモリの物理的な並び）と実行状態を描ける人」**

* 自分で低レイヤコードをゼロからスラスラ書けること（コーダー）を目指すのではない。
* **実務コードを読んだとき、デバッガのメモリダンプを見たとき、仕様書を開いたときに、「あ、メモリ上では今こう並んでいるんだな」「裏でOSがこう動いているんだな」と頭の中で図解・トラブル診断できる状態** を目指す。

* **講義スタイル**: **スタイルA（座学講義型・1回30〜45分程度）**

## 4. 各回の詳細設計仕様

### 第1回：データとメモリの正体――ビット・バイトから始まるメモリの物理モデル
* **役割**: すべての土台。「bitは状態」「型は解釈ルール」「メモリはロッカー街」を確立する。
* **導入（Why）**: 普段は高水準言語が隠してくれているが、壊れた理由（画像崩れ、12bitが入らない、数値化け）を知るために必要になる。
* **核心内容**:
  * 1bitは状態（0/1そのものに意味はない）
  * bit列 ＋ 解釈ルール ＝ 意味あるデータ（CPU命令もbit列）
  * 1byte＝8bit（256状態の箱）
  * C++は観察顕微鏡、型も解釈ルールの一つ（uint8_t vs int）
  * メモリは1バイトの箱が一列に並んだ「ロッカー街」、アドレスは「番号札」
  * 【応用】12bit Packed画像：ロッカーの仕切り（8bit）と画素の区切り（12bit）がズレる！ ──> ビット操作が必要（詳細は第3回へ）
  * リトルエンディアンの罠（人間の直感と逆、下位バイトから配置）
  * 【実験】`unsigned char*` で2バイト目を書き換えると `100 ──> 356`（+256）に化ける！
  * バッファ（生メモリに型のレンズを当てる）
  * アライメントとパディング：`SensorRecord`（データは5byteなのに、なぜ8byte？）
  * 実務の処方箋：内部メモリ配置と外部データフォーマットは別物。ファイル・通信はシリアライズする。

---

### 第2回：画像データの正体――「2次元の絵」を「1次元メモリ」にどう並べるか？
* **役割**: 「表形式（2次元）」から「1次元メモリテープ」へのパラダイムシフト。LineSpanの解明。
* **導入（Why）**: カメラやファイルから読み込んだ画像を表示したら、**「なぜか全体が斜めに崩れてノイズになった」** 現場の絶望から入る。
* **核心内容**:
  * 光と色の仕組み（3種類の錐体細胞による知覚、RGB加法混色、ディスプレイとカメラの逆方向循環）。
  * 24bit RGB（1画素＝3バイト、サブピクセル）と Pixel Buffer（圧縮ファイルと展開後メモリの明確な区別）。
  * **二段構えのインデックス解説（超重要）**:
    1. まず **「1画素＝1バイトの8bitグレースケール画像」** で、2次元の表を改行して1列のテープにする図解。
       `y=1, x=2` ──> `index = y * width + x`（1行進むごとにwidth個のロッカーを丸ごとスキップして `+ x` 歩進む）。
    2. その後で **「1画素＝3バイト（RGBカラー）」** へ拡張する。
       `offset = (y * width + x) * 3`。
  * **16進数（hex）の自然な導入**:
    * カラーコード `#FF0000` はなぜ赤か？
    * 16進数の2桁（`00`〜`FF`）は、ちょうど「1バイト（0〜255）」を表すのに人間にとって最も都合がいいから！
    * ※注意：「カラーコードは色を記述する記法であり、メモリ上にそのまま `FF 00 00` と並ぶとは限らない（RGB/BGR等の仕様依存）」と釘を刺す。
  * **実務の罠：Top-down と Bottom-up**:
    * 左上原点（現代標準）と左下原点（Windows DIB/BMP）の座標系の違い。なぜ画像が上下逆さまになるのか？
  * **核心：LineSpan（ストライド/ピッチ）の解剖**:
    * 第1回で学んだ **「アライメント（境界を揃えて効率化する）」** の思想を伏線回収！
    * 画像フォーマットやハードウェアの要求で、なぜ行末にパディング（余白）が入るのか？
    * 仕様から行の歩幅を確認してジャンプする：`offset = y * lineSpan + x * bytesPerPixel`。
    * 余白を無視して `width` で飛ぶと、1行ごとに数バイトずつズレて全体が斜めに流れる！
  * **【普段のC#では？】**:
    * C#の `BitmapData.Stride` の正体はこれだったのか！（負のStrideの意味）。

### 第3回：生メモリを操る3つの技術――bitを切り出す・byteを移す・byte列を読む
* **役割**: メモリ上の生バイト列から必要な情報を正しく取り出し、動かし、意味付けする情報工学の基礎。
* **導入（Why）**: カメラSDK等から「`A3 5C 7F 12 84 ...`」という謎の生byte列を渡され、「画素値を取り出せ」と言われたが、どこが1つの値か全く分からない現場トラブルから入る。
  * 第1回の復習：一般的な現代の環境ではメモリは1byte単位でアドレス付けされるが、データの意味は12bit区切りなど、アドレス境界と意味境界は一致しない！
* **核心内容（生メモリを操る3本柱）**:
  1. **切り出す（bit操作）**:
     * 第1回で予告した **12bit Packed画素の復元** を本格実践（伏線回収）。
     * 仕様例：`byte0: AAAAAAAA`, `byte1: AAAABBBB`, `byte2: BBBBBBBB`（※これが全12bit画像の仕様ではないと明記）。
     * シフト（ずらす）、マスク（欲しいbitだけ残す）、OR（分かれたbitを結合する）を図解から導く。
     * 第2回の16進数（`0x0F = 0000 1111`）を回収してビットマスクを解説（16進数が低レイヤで使われる大きな理由の1つ）。
     * コードをいきなり出さず、「図で組み立ててからコードを見せる」。
  2. **移す（byteコピー）**:
     * 高速化のためではなく、「bit単位ではなく、連続するbyte列をそのままコピーする標準的な基本道具」としての `std::memcpy`。
     * 第2回のLineSpanを復習：Strideの異なる画像間では一発コピーできず、パディング余白をスキップして有効画素だけを移す「行ごとの矩形コピー」が必要。
     * 【安全性の注意】：領域外アクセスは「即クラッシュ」ではなく「未定義動作（気づかずメモリ破壊することもある）」と解説。領域の重複時は `memmove` を使う注記。
  3. **読む（byte列に意味を与える）**:
     * byte列だけでは意味がない。フォーマット仕様（bit位置・offset・size・endian・stride）と組み合わせて初めて意味あるデータになる（第1回の結実）。
     * 方法A（明示的な合成）：シフトとORで4バイトから1つの `uint32_t` を組み立てる（4つの箱から1つの値を作るのが見える安全・移植性の高い基本形）。
     * 方法B（`std::memcpy` による値の取り出し）：trivially copyableな型を安全に読み出す。ただしホストとデータのエンディアン一致が必要。
     * 【実務で見かけるコードへの健全な警戒心】：
       * `reinterpret_cast<const Header*>(buffer)` を見かけることがあるが、「安全なゼロコピー技」として推奨しない。
       * 確認すべき5大条件（①Lifetime、②Aliasing、③Alignment、④Padding/Offset、⑤Endianness）を冷静にチェックできる人になる。
       * `std::bit_cast` は同サイズのtrivially copyable型間でビット表現を転換するものであり、ゼロコピーviewではないことを正しく理解する。
       * 外部データ仕様上のoffsetから明示的に読む姿勢を基本とし、構造体を使う場合は `static_assert`（サイズ・オフセット）で検証する。

### 第4回：バイナリファイルとフォーマット――byte列を決められた仕様で保存する
* **役割**: メモリとストレージの架け橋。保存されたbyte列にも「仕様」が必要であることの理解。
* **導入（Why）**: 「テキスト形式（JSON/CSV）で画像やセンサーデータを保存したら、ファイルサイズが数十倍に膨れ上がり、ロードに数秒かかって現場で怒られた」トラブルから入る。
* **核心内容**:
  * テキスト形式 vs バイナリ形式（数値1000000を "1000000" の7文字で書くか、4バイトで書くか）。
  * **単純なバイナリ形式でよく見られる基本構造：ヘッダー（固定長メタデータ）＋ ペイロード（データ部）**。
    * BMP等の実例（マジックナンバー、画像サイズ、データ開始オフセット）。
  * **C++バイナリI/Oの鉄板作法**:
    * テキストモードではプラットフォーム（Windows等）によって改行コードなどの自動変換が起こり得るため、書いたbyteをそのまま保存・読み込みできるよう `std::ios::binary` を明示する。
    * ファイルサイズを取得し、`std::vector<uint8_t>` に一括バッファロードする。
  * 実践：バイナリパッチ（ファイルをメモリに読み込み、第3回の仕様オフセットに従って一部を書き換えて保存）。
  * 第1回・第3回の教訓の回収：構造体を丸ごと書き込まず、ヘッダー仕様に合わせてシリアライズする。

---

### 第5回：ソースコードから実行ファイルができるまで――コンパイラとリンカの仕事
* **役割**: 「書いたコードがどう機械語の部品になるか」。「コンパイラとリンカは別人」というメンタルモデルの確立。
* **導入（Why）**: 「#include も通って文法エラーもないのに、ビルドボタンを押したら謎の **`LNK2019: 未解決の外部シンボル`** が大量に出てビルドが通らない」「ヘッダに何でも書けばいいと思ってたら多重定義エラーが出た」現場トラブルから入る。
* **核心内容**:
  * ビルドの4大フェーズ：プリプロセス（`#include` 展開） ──> コンパイル（文法検査・機械語化） ──> アセンブル ──> リンク（実体の結合）。
  * オブジェクトファイル（`.obj`）の正体：関数の機械語と「シンボルテーブル（外部参照の未解決リスト）」。
  * **コンパイラとリンカは別人！**:
    * コンパイラは「宣言」を信じるだけ（`#include` は約束手形）。
    * リンカが初めて実体（`.obj`）を探しに行き、約束を果たしに行く。
  * 静的ライブラリ（`.lib`）の正体：`.obj` ファイルをまとめたアーカイブ集。
  * **`LNK2019` の解剖**:
    * なぜ起きるのか？（宣言はあるのに、リンク対象の .obj/.lib に実体がない）。
    * エラーメッセージから「足りない関数」を特定し、プロジェクト設定で解決する手順。

### 第6回：DLLとプログラム境界――別モジュール・別言語の境界を越えて関数とデータを受け渡す
* **役割**: 動的リンクの仕組みと、「DLL境界とはバイナリ契約である」というメンタルモデルの確立。
* **導入（Why）**: 「C++で作った高速画像処理DLLを C# から呼び出したら、**データが化ける・structの途中から値がズレる・突然アプリが即死クラッシュする**」「32bitでは動いたのに64bitで動かない」現場トラブルから入る。
  * 受講者の疑問：「関数名も引数も同じように書いたのに、なぜ壊れるの？」
* **核心内容（DLL境界という4つのバイナリ契約）**:
  * **DLLの実態**: 別プロセスではなく、呼び出し元プロセスの仮想アドレス空間へロードされる共有モジュール。
  * **静的リンク vs 動的リンク**:
    * 静的ライブラリ（必要なコードを取り込む）vs DLL（別ファイルとして存在し実行時にロード）。
    * Import Library（`.lib`：DLL内の公開シンボル情報）と DLL本体（`.dll`：実行コード）の分離（第5回の伏線回収）。
  * **契約① 関数をどう探すか？（Symbol / `extern "C"`）**:
    * C++の名前マングリングと、C linkage を指定する `extern "C"` の正体。
    * 「`extern "C"` だけでABI互換がすべて解決するわけではない」という本質。
  * **契約② どう引数・戻り値を渡すか？（Calling Convention / ABI）**:
    * API（ソースコードの約束）vs ABI（バイナリ・機械語の約束）。
    * 呼び出し規約（`__cdecl`, `__stdcall` 等）と、x86とx64での扱いの違い（x64の統一規約）。
  * **契約③ 何byteとして解釈するか？（型サイズ・Struct Layout・Alignment）**:
    * 第1回のアライメント・パディング、第3回のオフセット、第4回の仕様解釈を全面回収！
    * C# P/Invoke（`[DllImport]`）での構造体受け渡し：C# `[StructLayout]` によるレイアウトの一致確認（`Pack = 1` は万能安全スイッチではない）。
    * 言語間のマーシャリング（bool, string, 配列, blittable型）。
  * **契約④ 誰がそのメモリを管理するか？（Ownership / Lifetime / Pinning）**:
    * 確保と解放の責任境界（同一モジュールで解放するAPI設計）。
    * C#バッファを渡す際のガベージコレクション対策（`fixed` / pinning によるアドレス固定）。
  * **実行基盤の罠**:
    * 32bit（x86）プロセスと 64bit（x64）DLLの不一致問題。
    * DLL検索順序（固定リストではなくOS設定・規則により変動する現実）。

### 第7回：プロセスとスレッド――プログラムが実行される空間と処理の流れ
* **役割**: OSが提供する仮想アドレス空間と、並行して動く処理の流れ（スレッド）の解明。
* **導入（Why）**: 「ポインタのアドレス値が全く同じなのに、別のプログラムからは相手のデータを読み書きできない」「2つのスレッドで同じ数値をカウントアップしたら、計算結果が毎回狂う」トラブルから入る。
* **核心内容**:
  * **プロセス（Process）**: OSがプログラムごとに割り当てる独立した「仮想アドレス空間（箱）」。
    * 互いのメモリ空間はOSによって隔離・保護されている。
  * **スレッド（Thread）**: CPUが実際に命令を実行していく「処理の流れ」。
  * **1つのプロセスに複数のスレッドが存在する**:
    * スレッドごとに独立しているもの：**スタック領域（Stack）**、プログラムカウンタ。
    * スレッド間で共有されるもの：**仮想アドレス空間（ヒープ、静的領域、コード）**。
  * スレッドセーフティの萌芽：同じメモリを複数スレッドが同時に書き換えると破壊が起きる。

---

### 第8回：メモリの寿命と所有権――データはどこに生まれ、いつ消えるのか？
* **役割**: オブジェクトの生存期間（Lifetime）と後始末の責任（Ownership）の解明。メモリ事故（Dangling Pointer / Memory Leak）の撲滅。
* **導入（Why）**:
  * 「関数からローカル変数のアドレスを返したら、値が残っているのに使ってはいけないと言われた（Dangling Pointer）」
  * 「処理を繰り返すとメモリ使用量が増え続け、数GBに達する（Memory Leak）──なぜOSが勝手に片付けてくれないのか？」
* **核心内容**:
  * **「アドレスの存在」と「オブジェクトの生存」の分離**:
    * どこにあるか（Storage）、いつまで生きるか（Lifetime）、誰が後始末するか（Ownership）の3軸。
  * **Storage Duration（記憶域期間）とスコープ・寿命の違い**:
    * Automatic Storage Duration（ローカル変数等：一般的な実装ではスレッドのスタックが使われることが多い）。
    * スコープを抜けるとオブジェクトの寿命（Lifetime）は終了する（※byteが即座にゼロ消去されるわけではない）。
    * 4つの記憶域期間（automatic / static / thread / dynamic）の存在把握。
  * **Dangling Pointer と Memory Leak の対比**:
    * Dangling Pointer: 寿命が終了したのにポインタが残っている（Use After Free）。
    * Memory Leak: オブジェクト/ストレージは生きているのにOwnerへの道を失い解放できなくなった状態。
  * **Ownership（所有権）と RAII（Resource Acquisition Is Initialization）**:
    * 生ポインタ（raw pointer）は所有権を明示しない。所有権＝「そのリソースの後始末に責任を持つのは誰か」。
    * RAII: メモリ専用ではなく、あらゆるリソース（メモリ、ファイル、mutex、OSハンドル等）の取得・解放をオブジェクト寿命に結びつける思想。
    * 通常のスコープ終了やスタック巻き戻しでデストラクタが解放を担う（※プロセス異常終了等の例外を除く）。
    * 所有権を型で表現する：`std::unique_ptr`（単独所有権・move可能）と、リソース管理コンテナ `std::vector`（内部ストレージの再配置によるポインタ無効化の注意）。共有所有権としての `std::shared_ptr` の存在と循環参照リスクの注記。

---

### 第9回：イベント駆動とGUIアプリの仕組み――なぜ重い処理で画面が白くフリーズするのか？
* **役割**: カリキュラム全体の集大成。OSがプログラムをどう制御し、なぜ画面が動くのかの解明。
* **導入（Why）**: 「ボタンを押して重い画像処理やファイルロードを走らせたら、**画面が白くなって『応答なし』でフリーズした**」トラブルから入る。
* **核心内容**:
  * コンソールアプリ（手続き型：上から下へ走って終了）vs GUIアプリ（イベント駆動：外からの刺激を待ち続ける）。
  * Windowsアプリの心臓部：**メッセージキュー** と **メッセージループ（`GetMessage` ──> `DispatchMessage`）**。
  * 窓口関数 `WndProc`（ウィンドウプロシージャ）によるイベント分岐。
  * **「応答なし（フリーズ）」の真犯人**:
    * UIスレッドが重い処理でブロックされる ──> メッセージキューの処理が滞り、描画や入力などのメッセージに応答できなくなる！
  * **処方箋：UIスレッドとワーカースレッドの分離（マルチスレッド・非同期処理）**:
    * 第7回で学んだ「スレッド」を使い、重い処理をワーカースレッドに逃がすことで、UIスレッドが常にメッセージループを回し続けられるようにする。
  * **全9回の総括（コンピュータシステム基礎の完全な地図）**:
    * bit/byte ──> メモリ ──> 2次元画像 ──> 生メモリ操作 ──> ファイル ──> ビルド・リンク ──> DLL境界 ──> プロセス・スレッド ──> 寿命・RAII ──> イベントループ
    * 受講生の頭の中に、完全な「メモリとプログラムの地図」が完成する。
