# コンピュータシステム基礎研修 スライド教材設計ガイドライン

本ドキュメントは、研修資料（`docs/goal_management/slides/`）全6回（01〜06）を作成・改訂する際に、すべてのスライドで厳格に遵守すべき「教育資料作成ルール」をまとめた設計規範である。

スライド01（データとメモリ）のレビューと改善を通じて得られた、**「初学者が躓かず、かつ現場で通用する技術力を確実に獲得するための原則」** を体系化している。

---

## 1. 導入の原則：Whyファーストと実務課題からの出発

### 原則1-1：いきなり内部原理や定義から入らない
* 「コンピュータは0と1」「DLLとは動的リンクライブラリである」といった理論や用語定義から始めない。
* 高水準言語（C#, Python, Java等）が普段それらを覆い隠してくれている恩恵をまず認める。

### 原則1-2：現場のトラブル・痛点（困りごと）から入る
* 「普段は隠されているものが、トラブルの現場では必ず姿を現す」という構図を作る。
* **「壊れた理由を理解するために、低レイヤの基礎が必要になる」** という納得感を受講生に最初に与える。
* 導入で提示するトラブル例の基準：
  * 「画像がなぜか斜めに崩れてノイズになる」（02 LineSpan）
  * 「12bitデータが1byteに入らない」（01 メモリ/03 ビット操作）
  * 「バイナリを読んだら数値が激しく化ける」（01 エンディアン/04 ファイルIO）
  * 「DLLに渡した構造体がズレてクラッシュする」（01 パディング/05 DLL）
  * 「画面がフリーズして応答なしになる」（06 イベントループ）

## 2. 認知負荷と難易度曲線の原則：既習事項による新概念の駆動

### 原則2-1：既習の概念を使って、新しい問題を説明する（前提の飛躍防止）
* **新しい難所（応用）は、必ず受講者が「直前に理解したメンタルモデル」を使って説明する。**
* *悪い例*: メモリ空間（ロッカー街）の並びを知らない受講生に、いきなり「12bitの境界ズレ」を説明する。
* *良い例*: 「メモリは1byteのロッカーが一列に並んだもの」と理解させた直後に、「では12bitの値はロッカーにどう入る？ ──> 仕切り（8bit）と画素（12bit）が合わない！」と見せる。受講生は「さっき習ったロッカーの境界と合わないのか！」と直感的に腹落ちする。

### 原則2-2：1スライドで複数の新概念を同時に出さない（過積載の防止）
* 1つのスライドで「bit」「byte」「packed」「16進数（hex）」「bit shift」「bit mask」を同時に教えようとすると受講生はパンクする。
* **第1回で必要なのは「なぜその操作が必要なのか」という理由・概念まで** に留める。
* 具体的な実装やテクニック（`>>`, `&`, `0x0F` 等）は、適切な回のスライド（第3回など）へ意図して委譲する。

## 3. 専門用語・構文の導入原則：「理解対象」と「観察道具」の分離

### 原則3-1：難解な構文を出すときは「文法は覚えなくてOK」と明言する
* `reinterpret_cast<unsigned char*>(&x)` やポインタ操作のような複雑なC++コードを提示する際は、冒頭に **「※今は文法を覚えなくてOK」** と明記し、構文アレルギーによる心理的シャッターを下ろさせない。
* そのコードが何をしているのかを、概念レベルで一言で要約する。
  * 例：「やっていること：intを1バイトずつ観察するための見方に切り替える」

### 原則3-2：身体的・視覚的メタファーを首尾一貫して使用する
* 抽象的なコンピュータの振る舞いには、常に一貫した日常の比喩を当てる。
  * **メモリ** ＝ 1バイトの箱が一列に並んだ「ロッカー街」
  * **アドレス・ポインタ** ＝ ロッカーの「番号札」
  * **C++** ＝ 低レイヤを直接覗き込む「顕微鏡」
  * **型** ＝ bit列を見る「レンズ」
  * **ビット操作** ＝ 境界をまたぐbitを救出する「ハサミとピンセット」

## 4. 主従関係の原則：情報工学が「主」、C++は「観察の道具（従）」

### 原則4-1：C++講座に見せない（言語の文法習得を主目的にしない）
* 本研修シリーズの主軸は、あくまで **「コンピュータシステム基礎・情報工学（メモリ、OS、バイナリ）」** である。
* C++を学ぶためにbitやメモリを説明するのではない。**bitやメモリを理解するためにC++を使う** という主従関係を徹底する。

### 原則4-2：C++を「低レベル言語」と決めつけない
* C++を単に「低レベル言語」と断定しない。
* **「C++は高水準な記述もできる一方で、低水準なメモリ操作まで扱えるシステムプログラミング言語」** と表現し、ハードウェアやメモリの姿をごまかさずに直接観察できる「最高の顕微鏡」として位置づける。

### 原則4-3：プログラミング言語の「型」も情報工学の枠組みに回収する
* 「型とは何か？」を構文論ではなく、情報工学の視点で定義する。
* **「プログラミング言語の『型』も、メモリ上のbit列をどう解釈するかを決めるルール（レンズ）の一つに過ぎない」** と教えることで、前半の「bit列 ＋ 解釈ルール ＝ データ」という思想と完璧に同期させる。

## 5. 実務例の選択原則：「意味のノイズ」の排除と論点の絞り込み

### 原則5-1：ゲーム風の題材を排し、実務文脈に統一する
* `PlayerData`、`hp`、`mp` といったRPG風の識別子・題材は、シリアスな実務研修（画像処理、通信、計測バイナリ等）において受講者に「なぜ急にゲーム？」という**意味のノイズ**を生むため使用しない。
* 現場で日常的に扱うデータ構造（`SensorRecord`, `ImageHeader` 等）を一貫して使用する。

### 原則5-2：論点が広がりすぎる実務例を避ける
* パディングを説明したい場面で `struct PacketHeader { int length; };` のように通信パケットを持ち出すと、「通信でint？」「エンディアンは？」「固定幅整数型は？」と別の論点が大量に湧いて話が発散する。
* その章で伝えたい本質（パディングならパディング）だけに集中できるよう、**「プログラム内部で保持するシンプルな構造体（例：`SensorRecord`）」** を選定する。

### 原則5-3：「内部メモリの都合」と「外部データフォーマット」を明確に区別させる
* CPUの都合でアライメント・パディングされた「内部メモリ配置」と、ファイルやネットワークに流す「外部データフォーマット」は全く別物であることを繰り返し強調する。
* 問題（パディングで大惨事）を提示した後は、必ず **実務での処方箋（シリアライズの推奨、pack指示の注意点）** までセットで着地させる。

## 6. 技術的正確性と初心者向け単純化の両立原則（技術的負債の排除）

### 原則6-1：嘘をつかない単純化（将来のバグ源を残さない）
* 初心者向けに噛み砕くが、受講者が将来現場に出たときに「スライドと違う」「バグになった」となるような技術的負債（嘘）を残さない。
* 処理系依存がある場合は「※一般的な環境では4byte」のように必ず正確な注記を添える。
* 規格上の地雷（Strict Aliasing、未定義動作、符号拡張、アライメント違反）には深入りしすぎずとも、**最初から規格安全なコードパターン（`unsigned char*` による観察、符号なし型でのビット操作など）** を自然に提示する。

## 7. スライド構成・運用ルール

1. **1スライド1メッセージの徹底**: 長文を避け、ASCII図・矢印・対比表（textブロック）を多用する。
2. **「次回予告」スライドは含めない**: 各スライドは「本日のまとめ（5つの重要ポイント）」でスマートに完結させる（※プロジェクト規約）。
3. **作業完了時のコミット＆プッシュの徹底**: スライドや関連ドキュメントの作業完了時は、必ず最後に `git commit` および `git push origin main` を実行する。
