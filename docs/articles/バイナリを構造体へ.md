バイナリ / buffer / struct / reinterpret_cast）で実際に起きる事故に近い話。

# 1. padding事故の実例

まずこれ。

```cpp
#include <iostream>
#include <cstdint>

struct Header
{
    uint8_t  type;   // 1byte
    uint32_t size;   // 4byte
};
```

初心者予想：

```text
type = 1byte
size = 4byte

合計5byte
```

実際に確認。

```cpp
std::cout << sizeof(Header) << std::endl;
```

結果（多くの環境）：

```text
8
```

え？5じゃない。

---

理由。

CPUは4byte整数を4byte境界に置きたがる。

なのでコンパイラが勝手に隙間を入れる。

メモリ配置：

```text
Address

1000: type
1001: padding
1002: padding
1003: padding
1004: size byte0
1005: size byte1
1006: size byte2
1007: size byte3
```

図。

```text
Header

[type][PAD][PAD][PAD][size size size size]

 1B    3B            4B
```

---

# 2. 実際にバイナリ流し込みすると何が起きるか

ここが怖い。

バイナリファイル側がこうだったとする。

```text
01 78 56 34 12
```

設計者の意図：

```text
type = 0x01

size = 0x12345678
```

5byte構造だと思っている。

だから：

```cpp
Header h;

memcpy(&h, bytes, 5);
```

した。

---

しかし構造体は8byte。

メモリはこうなる。

```text
コピー後

1000: 01
1001: 78
1002: 56
1003: 34
1004: 12
1005: ??
1006: ??
1007: ??
```

対応。

```text
type = 01

padding = 78 56 34

size = 12 ?? ?? ??
```

size が壊れる。

つまり。

**padding領域にデータが吸われた。**

---

実際の値：

```cpp
std::cout << std::hex << h.size;
```

↓

```text
??????12
```

みたいな謎値になる可能性。

---

# 3. offsetofで真実を見る

実務ではこれを確認する。

```cpp
#include <cstddef>

std::cout
    << offsetof(Header, type)
    << std::endl;

std::cout
    << offsetof(Header, size)
    << std::endl;
```

結果：

```text
type : 0
size : 4
```

つまり。

```text
offset 0 → type

offset 1〜3 → padding

offset 4 → size
```

---

これはあなたの

> LayoutTable
> offset + memcpy

の設計と直結する。

offsetを知らずにやると事故る。

# 4. ネスト構造体 + padding事故

さらに怖いやつ。

```cpp
struct Inner
{
    uint8_t  a;
    uint32_t b;
};

struct Outer
{
    uint16_t id;
    Inner    data;
    uint8_t  flag;
};
```

見た目：

```text
Outer
 ├ id
 ├ data
 │   ├ a
 │   └ b
 └ flag
```

初心者脳内：

```text
2 + (1+4) +1

=8byte
```

違う。

実際。

---

Inner。

```text
[a][PAD PAD PAD][b]

1 +3 +4

=8byte
```

Outer。

```text
[id][PAD PAD]
[data 8byte]
[flag]
[PAD PAD PAD]
```

図。

```text
Outer

[id][PP]
[a][PPP][b]
[flag][PPP]
```

サイズ：

```text
2 +2 +8 +1 +3

=16byte
```

---

確認コード。

```cpp
std::cout
    << sizeof(Inner)
    << std::endl;

std::cout
    << sizeof(Outer)
    << std::endl;
```

↓

```text
8
16
```

になる可能性が高い。

# 5. reinterpret_cast案件で起きる事故

あなたの案件に近づける。

例えば。

```cpp
struct Record
{
    uint16_t frameNo;
    uint32_t value;
};
```

buffer：

```cpp
uint8_t buffer[6];
```

で、

```cpp
Record* rec =
    reinterpret_cast<Record*>(buffer);
```

した。

問題。

`Record` は多くの環境で

```text
8byte
```

になる。

しかしbufferは6byte。

結果。

```text
frameNo OK

value読みに行くと
buffer外参照
```

未定義動作。

これは実際かなり危険。

# 6. pack(1) でpaddingを殺す方法

バイナリ解析ではこれを使うことがある。

MSVC。

```cpp
#pragma pack(push,1)

struct Header
{
    uint8_t type;
    uint32_t size;
};

#pragma pack(pop)
```

今度。

```text
[type][size]
```

になる。

sizeof：

```text
5
```

になる。

---

でも注意。

paddingを消すとCPUの自然アラインメントが崩れる。

性能低下や環境依存が出ることがある。

だから実務では、

**「本当にバイナリ仕様と一致させたいときだけ使う」**

ことが多い。

---

# 7. バイナリ解析の王道確認コード

実務ならこれを書く。

```cpp
#include <iostream>
#include <cstddef>

struct Header
{
    uint8_t  type;
    uint32_t size;
};

int main()
{
    std::cout
        << "sizeof(Header)="
        << sizeof(Header)
        << '\n';

    std::cout
        << "type offset="
        << offsetof(Header, type)
        << '\n';

    std::cout
        << "size offset="
        << offsetof(Header, size)
        << '\n';
}
```

これで、

**「コンパイラが実際どう並べたか」**

を確認する。

推測しない。

---

要約すると。

| 概念               | 実務上の意味          |
| ---------------- | --------------- |
| structネスト        | メモリでは平坦化される     |
| padding          | コンパイラが勝手に隙間を入れる |
| offsetof         | 本当のoffset確認     |
| sizeof           | 本当のサイズ確認        |
| reinterpret_cast | サイズ不一致事故に注意     |
| pack(1)          | バイナリ仕様合わせ用      |

これ、かなり重要な理解ポイント。

特にあなたの案件だと、

> 「struct定義を信じてbufferへreinterpret_cast」

している箇所があるなら、

**sizeof / offsetof をログ出力して仕様書と突き合わせる**

のはかなり有効。
