```text
        ↓

        ↓

実装
「コードを書く」
```

---

## この整理で一番良いと思った点

実は、一般的な教科書では **「基本設計」「詳細設計」** のようなフェーズ名は載っていますが、「その前に何を整理すると設計が進めやすいか」はあまり体系立てて説明されていません。

今回の流れで特に価値があるのは、**「ドメイン分析」を独立したフェーズとして意識していること**です。

* 要求分析で「何を作るか」を決める。
* ドメイン分析で「何を扱うか」を理解する。
* その後に初めてシステムや機能を設計する。

この順番は、データ中心のツール開発やAI駆動開発とも相性が良く、後続の設計や実装が進めやすくなります。これは一般的な工程と矛盾するものではなく、設計工程をより実践的に分解した考え方として使えると思います。

# ソフトウェア開発フェーズ・プレイブック

このドキュメントは、開発作業中に「今どのフェーズにいるのか」「次に何を作るべきか」を確認するための作業用メモである。

一般的な開発工程をそのまま覚えるための資料ではなく、実務で迷ったときに現在地を確認し、次の作業へ進むためのナビゲーションとして使う。

---

# 0. まず現在地を確認する

作業中に迷ったら、最初にこのチェックを見る。

```text
□ 何を作りたいのかがまだ曖昧である
  → Phase1 要求分析へ

□ お客様の要望はあるが、扱うデータや用語が整理できていない
  → Phase2 ドメイン分析へ

□ データは整理できたが、システム全体の構成が見えていない
  → Phase3 アーキテクチャ設計へ

□ 全体構成は見えたが、必要な機能が整理できていない
  → Phase4 基本設計へ

□ 機能は整理できたが、コードに落とせる粒度になっていない
  → Phase5 詳細設計へ

□ 実装方法まで決まっている
  → Phase6 実装へ
```

---

# 1. 開発フェーズ全体像

このドキュメントでは、開発の流れを以下の6段階で整理する。

```text
Phase1 要求分析
「何を作る？」

        ↓

Phase2 ドメイン分析
「何を扱う？」

        ↓

Phase3 アーキテクチャ設計
「全体はどう動く？」

        ↓

Phase4 基本設計
「どんな機能が必要？」

        ↓

Phase5 詳細設計
「どう実装する？」

        ↓

Phase6 実装
「コードを書く」
```

重要なのは、いきなり基本設計や詳細設計を書こうとしないこと。

特に補助ツール開発では、以下の順で整理すると進めやすい。

```text
データ
  ↓
関係
  ↓
動き
  ↓
画面
  ↓
仕様
```

---

# 2. Phase1 要求分析

## 目的

「何を作るのか」を明確にする。

お客様の要望をそのまま仕様にするのではなく、以下を整理する。

- 何に困っているのか
- 何を実現したいのか
- 現在はどう作業しているのか
- ツール化後にどうなってほしいのか

---

## 開始条件

以下のような状態なら、Phase1から始める。

- お客様から「こういうことをしたい」という要望だけ受け取っている
- 実現方法がまだ曖昧である
- どこまで作ればよいかが決まっていない
- 現状業務と理想業務の差分が整理できていない

---

## 成果物

### 2.1 要求一覧

システムに求められる要求を一覧化する。

| No | 要求 | 種別 | 優先度 | 備考 |
|---|---|---|---|---|
| 1 | 〇〇したい | 機能要求 | 高 | |
| 2 | ローカル環境で動かしたい | 制約 | 高 | |
| 3 | 手作業を減らしたい | 業務改善 | 中 | |

整理する内容の例。

- 作りたい機能
- 制約事項
- お客様の要望
- 解決したい課題
- やらないこと

---

### 2.2 As-Is（現状業務）

現在どのような手順で業務を行っているかを整理する。

```text
手作業でbatを探す
  ↓
Folderを開く
  ↓
Version確認
  ↓
Color設定
  ↓
手作業でデータ作成
```

ここでは、システムの話よりも「人が今どう動いているか」を書く。

---

### 2.3 To-Be（理想業務）

ツール導入後の理想的な業務フローを整理する。

```text
batを指定
  ↓
色を選択
  ↓
データ生成
```

As-IsとTo-Beを並べることで、ツール化によって何を減らすのか、何を自動化するのかが見える。

---

## 終了条件

以下が説明できる状態になれば、Phase1は一旦完了とする。

- [ ] 何を作るのか説明できる
- [ ] 何のために作るのか説明できる
- [ ] 現状業務の流れを説明できる
- [ ] ツール導入後の理想業務を説明できる
- [ ] やること・やらないことの境界がある程度見えている

---

## 次に進む判断

要求は見えているが、扱うデータや用語が曖昧なら、Phase2 ドメイン分析へ進む。

---

# 3. Phase2 ドメイン分析

## 目的

「何を扱うシステムなのか」を理解する。

ここでは、処理ではなくデータに注目する。

補助ツール開発では、このフェーズが特に重要になる。

お客様はドメイン知識を持っていても、プログラム内部のデータ取得経路までは整理できていないことが多い。
そのため、まずは「どこに何のデータがあり、何をキーに次のデータへ辿るのか」を整理する。

---

## 開始条件

以下のような状態なら、Phase2を行う。

- お客様の要望はある程度分かっている
- 必要そうなファイルやデータが存在する
- ただし、データ同士の関係が曖昧である
- どのデータを使えば実現できるか確認したい

---

## 成果物

### 3.1 データ一覧

システムで扱うデータを洗い出す。

| データ名 | 種別 | 所在 | 取得方法 | 用途 | 備考 |
|---|---|---|---|---|---|
| batファイル | 入力 | ユーザー指定 | ファイル選択 | フォルダパス取得 | |
| フォルダパス | 中間データ | batファイル内 | bat解析 | FileA検索 | |
| FileA | 入力 | フォルダ配下 | ファイル検索 | Version取得、新データ生成 | |
| Version | 中間データ | FileA内 | ファイル解析 | ColorFile特定 | |
| ColorFile | 入力 | Versionに対応するパス | 対応表から取得 | カラー一覧表示 | |
| Color設定 | ユーザー入力 | 画面 | ON/OFF選択 | 新データ生成 | |
| FileB | 入力 | フォルダ配下 | 条件検索 | 新データ生成 | |
| Output | 出力 | 出力先フォルダ | 生成 | 最終成果物 | |

この資料では、「何が存在するか」を広く洗い出す。
まだ処理順を細かく決めすぎない。

---

### 3.2 データ辞書

各データや項目の意味を定義する。

| データ | 項目名 | 型 | 説明 | 使用有無 | 使用目的 | 備考 |
|---|---|---|---|---|---|---|
| FileA | Version | string | バージョン番号 | 使用 | ColorFile特定 | |
| FileA | ParamA | int | 〇〇の値 | 使用 | Output生成 | |
| FileA | ParamB | int | 〇〇の値 | 使用 | Output生成 | |
| FileA | ParamC | int | 〇〇の値 | 使用 | Output生成 | |
| FileA | ParamX | string | 予備情報 | 未使用 | - | 今回は使わない |

データ辞書では、「ファイルの中にどんなパラメータがあるか」と「そのうち何を使うか」を明確にする。

---

### 3.3 データマップ

データがどこに存在するかを整理する。

```text
batファイル
  └─ フォルダパス

フォルダ
  ├─ FileA
  ├─ FileB
  └─ その他ファイル

Version
  └─ ColorFileを特定するキー

ColorFile
  └─ カラー一覧
```

データマップは、処理順ではなく「データの所在」を見るための図である。

---

### 3.4 データ取得ルール

各データを、どこから、どう取得するかを整理する。

| 欲しいデータ | 取得元 | キー | 取得条件・方法 | 取得できない場合 |
|---|---|---|---|---|
| フォルダパス | batファイル | - | bat内の指定行を解析 | エラー表示 |
| FileA | フォルダパス | フォルダパス | 指定条件で検索 | エラー表示 |
| Version | FileA | - | FileA内のVersion項目を読み取り | エラー表示 |
| ColorFile | Version | Version | Version対応表からパスを特定 | エラー表示 |
| FileB | フォルダパス、FileA、Color設定 | 複数条件 | 条件に一致するファイルを検索 | エラー表示 |

この表では、「取得する順番」よりも「何を根拠に取得するのか」を明確にする。

---

### 3.5 データ依存図

どのデータを使って次のデータを取得するかを図示する。

```text
batファイル
  ↓
フォルダパス
  ↓
FileA
  ↓
Version
  ↓
ColorFile
  ↓
Color設定

フォルダパス + FileA + Color設定
  ↓
FileB

FileA + FileB + Color設定
  ↓
Output
```

この図では、「何がないと次へ進めないか」を確認する。

---

## 終了条件

以下が説明できる状態になれば、Phase2は一旦完了とする。

- [ ] 扱うデータを一覧化できている
- [ ] 各データの意味を説明できる
- [ ] データの所在を説明できる
- [ ] データ取得ルールを説明できる
- [ ] どのデータをキーに次のデータを取得するか説明できる
- [ ] 使用するパラメータと使用しないパラメータを区別できている

---

## 次に進む判断

データは整理できたが、ユーザー・補助ツール・ファイル・出力先の関係がまだ曖昧なら、Phase3 アーキテクチャ設計へ進む。

---

# 4. Phase3 アーキテクチャ設計

## 目的

「システム全体がどう動くか」を決める。

ここでは、細かい機能ではなく、以下を整理する。

- 誰が操作するか
- どのシステムが処理するか
- どのファイルを読むか
- どこに出力するか

---

## 開始条件

以下のような状態なら、Phase3を行う。

- 扱うデータが整理できている
- データの取得元が分かっている
- ただし、システム全体の構成がまだ見えていない
- ユーザー操作とシステム処理の境界を整理したい

---

## 成果物

### 4.1 システム構成図

システム全体の構成を整理する。

```text
ユーザー
  │ bat選択 / Color設定
  ▼
補助ツール
  │ 読み取り
  ▼
ローカルフォルダ
  │ bat / FileA / FileB / ColorFile
  ▼
出力フォルダ
  │ Output
```

小規模ツールでは、システム構成図と業務フロー図を兼ねてもよい。
その場合は「利用フロー兼システム構成図」のような名前にすると分かりやすい。

---

### 4.2 業務フロー

ユーザーとシステムがどのように動くかを整理する。

| No | 主体 | 操作・処理 | 入力 | 出力 |
|---|---|---|---|---|
| 1 | ユーザー | batファイルを選択 | batファイル | batパス |
| 2 | 補助ツール | フォルダパス取得 | batファイル | フォルダパス |
| 3 | 補助ツール | FileA取得 | フォルダパス | FileA |
| 4 | 補助ツール | Version取得 | FileA | Version |
| 5 | 補助ツール | ColorFile取得 | Version | カラー一覧 |
| 6 | ユーザー | Color ON/OFF設定 | カラー一覧 | Color設定 |
| 7 | 補助ツール | FileB取得 | フォルダパス、FileA、Color設定 | FileB |
| 8 | 補助ツール | 新データ生成 | FileA、FileB、Color設定 | Output |

---

### 4.3 データフロー

データが、どこから来て、どこへ流れ、どこで加工されるかを整理する。

```text
batファイル
  ↓
補助ツールで解析
  ↓
フォルダパス
  ↓
FileA取得
  ↓
Version取得
  ↓
ColorFile取得
  ↓
ユーザーがColor設定
  ↓
FileB取得
  ↓
Output生成
```

---

### 4.4 画面遷移図（必要な場合）

複数画面がある場合は、画面同士の遷移を整理する。

```text
開始画面
  ↓
bat選択画面
  ↓
Color設定画面
  ↓
生成完了画面
```

画面が1つだけの場合は、無理に画面遷移図を作らなくてもよい。

---

## 終了条件

以下が説明できる状態になれば、Phase3は一旦完了とする。

- [ ] ユーザー、補助ツール、ファイル、出力先の関係を説明できる
- [ ] ユーザー操作とシステム処理の境界を説明できる
- [ ] データがどこからどこへ流れるか説明できる
- [ ] 画面が必要か、必要なら何画面か説明できる

---

## 次に進む判断

システム全体の動きは見えたが、具体的な機能単位や画面項目が整理できていないなら、Phase4 基本設計へ進む。

---

# 5. Phase4 基本設計

## 目的

システムが持つ機能を決める。

ここでは、実装方法ではなく「外から見たシステムの振る舞い」を整理する。

---

## 開始条件

以下のような状態なら、Phase4を行う。

- システム全体の構成が整理できている
- ユーザー操作とシステム処理の境界が見えている
- ただし、機能単位や画面項目がまだ整理できていない

---

## 成果物

### 5.1 機能一覧

システムが提供する機能を一覧化する。

| 機能ID | 機能名 | 入力データ | 処理概要 | 出力データ | 呼び出し元 | 備考 |
|---|---|---|---|---|---|---|
| F01 | bat読込 | batファイル | batを解析してフォルダパスを取得 | フォルダパス | メイン処理 | |
| F02 | FileA取得 | フォルダパス | 条件に一致するFileAを検索 | FileA | F01 | |
| F03 | Version取得 | FileA | FileAからVersionを取得 | Version | F02 | |
| F04 | Color一覧取得 | Version | 対応するColorFileを取得 | カラー一覧 | F03 | |
| F05 | Color設定 | カラー一覧 | ユーザーがON/OFFを設定 | Color設定 | 画面 | |
| F06 | FileB取得 | フォルダパス、FileA、Color設定 | 条件に一致するFileBを取得 | FileB | F05 | |
| F07 | Output生成 | FileA、FileB、Color設定 | 新データを生成 | Output | F06 | |

機能は「データに対して何をするか」で考えると洗い出しやすい。

# 9. このドキュメントの使い方

このドキュメントは、上から順番に必ず埋めるものではない。

作業中に迷ったときに、以下を確認するために使う。

- 今どのフェーズにいるか
- 次に作るべき成果物は何か
- そのフェーズは何が終われば完了なのか
- お客様と何を認識合わせすべきか
- AIに何を渡せばよいか

特に補助ツール開発では、いきなり基本設計や詳細設計に入るよりも、先にドメイン分析でデータを整理した方が進めやすい。

```text
データを洗い出す
  ↓
データの意味を決める
  ↓
データの取得元を決める
  ↓
データ同士の関係を決める
  ↓
システム全体の動きを決める
  ↓
機能を決める
  ↓
実装方法を決める
```

迷ったら、処理ではなくデータに戻る。

処理はデータを動かすためのものだからである。
