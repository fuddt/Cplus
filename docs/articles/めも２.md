
```text
位置と幅が同じ
でも高さだけズレる
```

なら、原因は **X方向の対応は合っているが、Y方向の対応だけがズレている** 可能性が高いです。

つまり、今回疑うべきはこれです。

```text
左右方向の配置ではなく、
上下方向の座標系・開始Y・高さ換算・原点解釈
```

です。

---

## まず、この結果から分かること

### 位置と幅が同じ

黒くした場所の **横位置と幅が同じ** なら、少なくとも以下は合っていそうです。

```text
x方向のコピー位置
x方向のLineSpan解釈
x方向の有効幅
ベイヤー面の横方向対応
```

なので、`x` 方向の処理はかなり正しそうです。

---

### 高さだけズレる

一方で、高さがズレるなら、問題はほぼ `y` 側です。

候補はこれです。

```text
1. 左下原点の開始Yが微妙に違う
2. テーブル高さと画像高さの対応倍率がYだけ違う
3. 上下方向だけcrop / offset / 有効領域開始位置がある
4. Bayerの2行周期の影響でYだけ丸めが入っている
5. 再生ツール側で表示領域の上端・下端が違う
6. シェーディング補正テーブルのheightと画像heightが1対1ではない
```

---

## 一番ありそうな原因

一番ありそうなのは、**Y方向にだけ有効領域オフセットがある** ことです。

つまり、あなたは今、

```cpp
dstStartY = dstHeight - srcHeight;
```

で左下配置している。

でも実際には、再生ツールや補正適用側が見ている有効領域が、

```text
dst全体の左下
```

ではなく、

```text
有効画像領域の左下
```

かもしれません。

その場合、本当はこうかもしれません。

```cpp
dstStartY = dstHeight - srcHeight - offsetY;
```

または、

```cpp
dstStartY = validAreaBottomY - srcHeight + 1;
```

のような形です。

---

## なぜXは合うのにYだけズレるのか

画像処理では、横方向より縦方向の方が「余白」「有効領域」「読み出し開始位置」が入りやすいです。

たとえばセンサーや動画バッファでは、

```text
上側に黒帯・無効行・OB領域がある
下側に余白がある
有効画像領域だけ切り出して表示している
補正処理はセンサー座標、再生表示は表示座標
```

みたいなことがあります。

その場合、X方向は同じでも、Y方向だけズレます。

---

## もう1つ怪しい原因：テーブルと画像のY倍率

前に出ていた話で、

```text
補正テーブル上の空欄: 654行
画像側の空欄: 1304行くらい
```

という観察がありました。

これは、

```text
補正テーブル1行 ≒ 画像2行
```

を示している可能性がありました。

今回も高さだけズレるなら、補正適用側で、

```c
tableY = imageY / 2;
```

または、

```c
tableY = imageY >> 1;
```

のような処理が入っている可能性があります。

この場合、テーブル上で `N行` 黒くしたものが、画像上では `約2N行` になる。
逆に、Y開始位置のズレも2倍近くに見えることがあります。

---

## 「位置と幅が同じ」なら、左下配置は間違いではなさそう

ここは大事です。

もし左下原点配置そのものが完全に間違っていたら、黒い場所はもっと大きくズレるはずです。

例えば、

```text
左上に出るはずが左下に出る
上下反転する
別の位置に出る
横方向もズレる
```

みたいになります。

でも今回は、

```text
横位置と幅は同じ
高さだけズレる
```

なので、**配置方向そのものは大筋合っていて、Y方向のオフセットだけが未解決** という見方が自然です。

---

## 次に確認すべきこと

次は、黒くした範囲を「テーブル座標」と「画像座標」で対応表にした方がいいです。

例えば、こうです。

```text
補正テーブルで0にした範囲:
x = 0〜99
y = 0〜99

小さい再生ツールで黒くなった範囲:
x = ?
y = ?
width = ?
height = ?

大きい再生ツールで黒くなった範囲:
x = ?
y = ?
width = ?
height = ?
```

目視で厳密なピクセル数を出せないなら、まずは「上端位置」と「下端位置」の傾向だけでもよいです。

見るべきはこれです。

```text
黒領域の上端がズレているのか
黒領域の下端がズレているのか
黒領域の高さだけ伸び縮みしているのか
黒領域全体が上下に平行移動しているのか
```

この4つで原因が変わります。

---

## パターン別の見方

### 1. 黒領域全体が上下に移動している

例えば、

```text
幅は同じ
高さもほぼ同じ
ただし上にズレる / 下にズレる
```

なら、原因は **Yオフセット** です。

疑うもの：

```text
有効領域開始Y
crop offset
dstStartYの計算
左下基準の位置
```

---

### 2. 黒領域の高さが違う

例えば、

```text
幅は同じ
位置は近い
でも高さが大きい / 小さい
```

なら、原因は **Y方向のスケール倍率** です。

疑うもの：

```text
tableY = imageY / 2
tableY = imageY >> 1
2行周期のBayer処理
補正テーブル1行が画像複数行に対応
```

---

### 3. 黒領域の上端は同じで、下端だけ違う

これは、**高さ方向の伸び方** の問題です。

疑うもの：

```text
Y倍率
表示スケール
補正テーブルと画像の縦方向対応
```

---

### 4. 黒領域の下端は同じで、上端だけ違う

これは、**左下原点の底合わせは合っているが、高さ換算が違う** 可能性が高いです。

つまり、

```text
下端基準は合っている
でもテーブルN行が画像N行ではない
```

です。

これはかなり「補正テーブル1行 = 画像2行」仮説に近いです。

---

## いま一番見るべきコード

`Fn_U32_Clip_SHADE` より、その前です。

探すべきは、補正テーブルを読むところです。

```c
shade = shading_table[...];
```

または、

```c
coef = ...
```

または、

```c
*(shade + ...)
```

みたいなところ。

そこで見たいのは、

```text
画像のyをそのまま使っているか
y / 2 しているか
y >> 1 しているか
別のoffsetYを足しているか
```

です。

特にこの形があればかなり重要です。

```c
tableY = y >> 1;
```

または、

```c
tableY = y / 2;
```

または、

```c
tableIndex = (y >> 1) * tableStride + x;
```

## 今の仮説

現時点では、私はこう見ます。

```text
左下原点配置そのものは大筋合っている。
X方向も合っている。
ただし、Y方向では補正テーブル座標と画像座標の間に、
倍率またはオフセットが存在している。
```

特に、以前の `654` と `1304` の関係を考えると、

```text
Y方向だけ 2行単位で対応している
```

可能性が高いです。

## 次の一手

次は、黒くする範囲を変えて、Y方向の対応を測るのがよいです。

たとえば、補正テーブルで黒くする範囲を3パターン作ります。

```text
テスト1: 左上から 50行だけ0
テスト2: 左上から 100行だけ0
テスト3: 左上から 200行だけ0
```

もし画像上の黒高さが、

```text
100行相当
200行相当
400行相当
```

のように約2倍で変わるなら、

```text
補正テーブル1行 = 画像2行
```

がほぼ確定します。

この検証はかなり強いです。

今回の結果は、むしろ良い情報です。

です。
