
```text
位置と幅が同じ
でも高さだけズレる
```

なら、原因は **X方向の対応は合っているが、Y方向の対応だけがズレている** 可能性が高いです。

つまり、今回疑うべきはこれです。

```text
左右方向の配置ではなく、
上下方向の座標系・開始Y・高さ換算・原点解釈
```

です。

---

## まず、この結果から分かること

### 位置と幅が同じ

黒くした場所の **横位置と幅が同じ** なら、少なくとも以下は合っていそうです。

```text
x方向のコピー位置
x方向のLineSpan解釈
x方向の有効幅
ベイヤー面の横方向対応
```

なので、`x` 方向の処理はかなり正しそうです。

---

### 高さだけズレる

一方で、高さがズレるなら、問題はほぼ `y` 側です。

候補はこれです。

```text
1. 左下原点の開始Yが微妙に違う
2. テーブル高さと画像高さの対応倍率がYだけ違う
3. 上下方向だけcrop / offset / 有効領域開始位置がある
4. Bayerの2行周期の影響でYだけ丸めが入っている
5. 再生ツール側で表示領域の上端・下端が違う
6. シェーディング補正テーブルのheightと画像heightが1対1ではない
```

---

## 一番ありそうな原因

一番ありそうなのは、**Y方向にだけ有効領域オフセットがある** ことです。

つまり、あなたは今、

```cpp
dstStartY = dstHeight - srcHeight;
```

で左下配置している。

でも実際には、再生ツールや補正適用側が見ている有効領域が、

```text
dst全体の左下
```

ではなく、

```text
有効画像領域の左下
```

かもしれません。

その場合、本当はこうかもしれません。

```cpp
dstStartY = dstHeight - srcHeight - offsetY;
```

または、

```cpp
dstStartY = validAreaBottomY - srcHeight + 1;
```

のような形です。

---

## なぜXは合うのにYだけズレるのか

画像処理では、横方向より縦方向の方が「余白」「有効領域」「読み出し開始位置」が入りやすいです。

たとえばセンサーや動画バッファでは、

```text
上側に黒帯・無効行・OB領域がある
下側に余白がある
有効画像領域だけ切り出して表示している
補正処理はセンサー座標、再生表示は表示座標
```

みたいなことがあります。

その場合、X方向は同じでも、Y方向だけズレます。

---

## もう1つ怪しい原因：テーブルと画像のY倍率

前に出ていた話で、

```text
補正テーブル上の空欄: 654行
画像側の空欄: 1304行くらい
```

という観察がありました。

これは、

```text
補正テーブル1行 ≒ 画像2行
```

を示している可能性がありました。

今回も高さだけズレるなら、補正適用側で、

```c
tableY = imageY / 2;
```

または、

```c
tableY = imageY >> 1;
```

のような処理が入っている可能性があります。

この場合、テーブル上で `N行` 黒くしたものが、画像上では `約2N行` になる。
逆に、Y開始位置のズレも2倍近くに見えることがあります。

---

## 「位置と幅が同じ」なら、左下配置は間違いではなさそう

ここは大事です。

もし左下原点配置そのものが完全に間違っていたら、黒い場所はもっと大きくズレるはずです。

例えば、

```text
左上に出るはずが左下に出る
上下反転する
別の位置に出る
横方向もズレる
```

みたいになります。

でも今回は、

```text
横位置と幅は同じ
高さだけズレる
```

なので、**配置方向そのものは大筋合っていて、Y方向のオフセットだけが未解決** という見方が自然です。

---

## 次に確認すべきこと

次は、黒くした範囲を「テーブル座標」と「画像座標」で対応表にした方がいいです。

例えば、こうです。

```text
補正テーブルで0にした範囲:
x = 0〜99
y = 0〜99

x = ?
y = ?
width = ?
height = ?

大きい再生ツールで黒くなった範囲:
x = ?
y = ?
width = ?
height = ?
```

目視で厳密なピクセル数を出せないなら、まずは「上端位置」と「下端位置」の傾向だけでもよいです。

見るべきはこれです。

```text

黒領域の下端がズレているのか
黒領域の高さだけ伸び縮みしているのか
黒領域全体が上下に平行移動しているのか
```

この4つで原因が変わります。

---

## パターン別の見方

### 1. 黒領域全体が上下に移動している


---

### 4. 黒領域の下端は同じで、上端だけ違う

これは、**左下原点の底合わせは合っているが、高さ換算が違う** 可能性が高いです。

つまり、

```text
下端基準は合っている
でもテーブルN行が画像N行ではない
```

です。

これはかなり「補正テーブル1行 = 画像2行」仮説に近いです。

# 仮説1：補正テーブル1行が画像2行に対応している

## 理屈

以前、

```text
補正テーブル側の空欄高さ ≒ 654
画像側の空欄高さ ≒ 1304
```

のような話がありました。

```text
1304 / 654 ≒ 1.99
```

なので、

```text
補正テーブル1行 ≒ 画像2行
```

の可能性があります。

ベイヤー画像は基本的に2行周期です。

```text
R G
G B
```

なので、縦方向に2行単位で処理していても不自然ではありません。

## 何を調べればよいか

補正適用コードで、補正テーブルのY座標を求める部分を見る。

探すべき式：

```c
tableY = imageY / 2;
tableY = y / 2;
tableY = imageY >> 1;
tableY = y >> 1;
```

またはポインタ演算で、

```c
tableIndex = (y >> 1) * tableStride + x;
tableIndex = (y / 2) * tableStride + x;
```

のようなもの。

## 検証方法

補正テーブル側で、黒くする高さを変える。

```text
テスト1: 補正テーブル上で50行だけ0
テスト2: 補正テーブル上で100行だけ0
テスト3: 補正テーブル上で200行だけ0
```

画像側の黒高さが、

```text
約100行
約200行
約400行
```

のように出るなら、この仮説はかなり強いです。

# 仮説2：補正テーブルと画像のY座標に固定オフセットがある

## 理屈

小さいテーブルを大きいテーブルの左下に置くとき、今はおそらくこうしています。

```c
dstStartY = dstHeight - srcHeight;
```

でも本当に必要なのは、

```c
dstStartY = dstHeight - srcHeight + offsetY;
```

または、

```c
dstStartY = 有効領域の下端 - srcHeight + 1;
```

かもしれません。

つまり、「大きいテーブル全体の左下」ではなく、**有効画像領域の左下** が基準かもしれない。

## 何を調べればよいか

以下の情報を見る。

```text
大きい画像の有効領域開始Y
小さい画像の有効領域開始Y
クロップ開始Y
センサー有効領域のtop/bottom
black margin / optical black 領域
表示対象領域
```

コード上ではこういう名前が怪しいです。

```text
offsetY
startY
validY
activeY
cropY
top
bottom
roiY
imageOffsetY
```

## 検証方法

黒領域の「高さ」ではなく、「上端・下端の位置」を見る。

```text
黒領域全体が上下に平行移動している
→ 固定オフセット仮説が強い

黒領域の下端は同じで上端だけ違う
→ 倍率・高さ換算仮説が強い
```

# 仮説3：左下原点の解釈が「配置」ではなく「上下反転」だった

## 理屈

左下原点には2つの意味があり得ます。

### 意味A：左下に配置する

```text
src row 0 → dst の下側ブロックの先頭
src row 1 → その次
```

### 意味B：Y軸の向きが逆なので上下反転する

```text
src row 0 → dst の最下行
src row 1 → dst の下から2行目
```

もし相手が「左下原点」と言った意味がBだった場合、単純な左下配置ではY方向だけズレます。

## 何を調べればよいか

以下を確認する。

```text
value[0] の行は、画像上の上端を表すのか？
value[0] の行は、画像上の下端を表すのか？
```

コードで見るなら、補正テーブル参照時に、

```c
tableY = height - 1 - y;
```

のような上下反転式があるか確認します。

## 検証方法

補正テーブルの上端と下端に別々のマーカーを入れる。

```text
上端だけ0
下端だけ別の値
```

再生結果でどちらが画像の上に出るかを見る。

# 仮説4：補正テーブル側と画像側のheightが同じ意味ではない

## 理屈

「height」と言っても、同じ意味とは限りません。

```text
補正テーブルのheight
= 補正値テーブルとしての行数

画像のheight
= 実画像の画素行数

表示ツールのheight
= 表示対象になっている行数

センサーheight
= センサー全体の行数
```

これらが一致しない可能性があります。

つまり、

```text
補正テーブルの654行差
```

と、

```text
画像上の1304行差
```

は、そもそも違う座標系で測っている可能性がある。

## 何を調べればよいか

次を表にして整理する。

```text
小さい補正テーブル height
大きい補正テーブル height

小さい画像 height
大きい画像 height

小さい再生ツール表示 height
大きい再生ツール表示 height

補正適用対象の有効 height
実際にdumpした画像 height
```

特に重要なのは、

```text
補正処理が使っているheight
再生ツールが表示しているheight
dumpした画像のheight
```

が同じかどうか。

# 仮説5：画像側のLineSpanまたはstrideの解釈がY方向でズレている

## 理屈

U32画像なら、1画素4byteです。

```text
U32 = 4byte
```

画像をCSV化するときに、1行のサイズを間違えると、行の区切りがズレます。

例えば、本当は、

```text
lineSpanBytes = 16000
```

なのに、

```text
width × 4 = 15360
```

で読んでいたら、行の途中から次の行として読んでしまいます。

この場合、黒領域の高さやY位置がズレて見えます。

## 何を調べればよいか

画像データの実際のlineSpanを確認する。

探すべき変数名：

```text
lineSpan
stride
pitch
lineSize
bytesPerLine
widthStep
```

さらに、それが、

```text
byte単位なのか
U32要素数単位なのか
```

を確認する。

## 検証方法

binファイルサイズを確認します。

```text
期待サイズ = height × lineSpanBytes
```

PowerShellなら、

```powershell
(Get-Item out_img_u32.bin).Length
```

CSV化するときも、

```text
row_start = y * lineSpanBytes
byte_index = row_start + x * 4
```

で読めているか確認します。

# 仮説6：黒くした補正テーブル範囲と、画像に効く範囲が1対1ではない

## 理屈

シェーディング補正テーブルは、画像の1画素ごとに補正値を持っているとは限りません。

あり得るパターン：

```text
補正テーブル1マス = 画像1画素
補正テーブル1マス = 画像2画素
補正テーブル1マス = 画像2×2画素
補正テーブルが内部で補間されて画像に適用される
```

この場合、黒くしたテーブル範囲の高さと、画像上の黒高さが一致しません。

## 何を調べればよいか

補正適用コードで、補正テーブルのindexをどう作っているかを見る。

探すもの：

```c
tableX = imageX / 2;
tableY = imageY / 2;

tableX = imageX >> 1;
tableY = imageY >> 1;
```

または補間らしき処理：

```text
x0, x1, y0, y1
ratio
weight
interpolation
bilinear
```

## 検証方法

補正テーブルに1行だけ0を入れる。

```text
table row 100 だけ0
```

画像側で何行に黒が出るかを見る。

```text
1行だけ黒くなる → 1対1
2行黒くなる → 1対2
複数行にぼやける → 補間されている
```

# 仮説7：Bayerの2行周期で、片方の行だけに補正が効いている

## 理屈

ベイヤー配列は2行周期です。

補正処理が色面ごとに分かれている場合、Y方向の偶数行・奇数行で参照する面が違います。

そのため、黒くした範囲が、実際には、

```text
偶数行だけ強く効く
奇数行だけ強く効く
2行単位で効く
```

のように見える可能性があります。

## 何を調べればよいか

補正適用コードで、Yの偶奇を見ていないか確認する。

探す式：

```c
y % 2
y & 1
i % 2
i & 1
```

または、

```text
bayer
phase
R
Gr
Gb
B
```

のような変数。

## 検証方法

補正後画像のCSVで、偶数行と奇数行を分けて見る。

```text
row 0, 2, 4...
row 1, 3, 5...
```

黒くなる強さや範囲が違うなら、Bayer周期が絡んでいる可能性があります。

# 仮説8：再生ツール側で表示時にスケーリングまたはクロップしている

## 理屈

再生ツールが表示しているのは、画像バッファそのものではなく、表示用に加工された結果かもしれません。

例えば、

```text
上部数行を表示しない
表示用に縦だけ縮小/拡大している

小さい動画ツールと大きい動画ツールで表示スケールが違う
```

この場合、バイナリ上では同じでも、画面上の高さがズレて見えます。

## 何を調べればよいか

再生ツール側の表示処理を見る。

探すもの：

```text
displayWidth
displayHeight
scaleX
scaleY
crop
viewport
render
draw
stretch
```

## 検証方法

```text
再生ツール表示ではなく、
補正直後のout_imgで黒領域を測る
```

これで、表示ツール由来のズレか、補正処理由来のズレかを分離できます。

# 仮説9：小さい動画を大きい再生ツールで読むときに、内部で画像バッファの配置が変わっている


ような処理が入っている可能性があります。

# 仮説10：空欄部分の値が0であり、黒領域として観測されている

## 理屈

シェーディング補正テーブルの余った領域を0で埋めている場合、

```text
補正後 = 入力値 × 0
```

になって、その範囲が黒くなる可能性があります。

本来、余白部分は0ではなく、

```text
補正なし基準値
```

で埋めるべきかもしれません。

ただし今回の「意図的に左上を0にしたテスト」では、0で黒くなること自体は想定通りです。

でも、意図していない上部空欄が黒に見えるなら、この仮説は重要です。

## 何を調べればよいか

補正なしを意味する値を確認する。

候補：

```text
1
256
1024
4096
65535
```

固定小数点なら、`1` ではなく `1024` や `4096` が1.0倍の可能性があります。

## 検証方法

余白部分を0ではなく、既存テーブルの平均値または補正なし基準値で埋める。

黒領域が消えるか確認する。

# 仮説11：U32の補正後画像が24bitクリップされていて、高さ判定が歪んでいる

## 理屈

`クリップ関数` が24bitクリップしているなら、補正後値は上限で丸められる可能性があります。

ただし、今回の0化テストでは主に黒方向なので、上限クリップはあまり関係しません。

でも、黒領域を「しきい値」で測る場合、途中の計算やクリップで境界がぼやける可能性はあります。

## 何を調べればよいか

`クリップ関数` の前後の値をdumpする。

```text
clip前の値
clip後の値
```

ただし優先度は低めです。
0化テストの高さズレ原因としては弱いです。

# 仮説12：黒くしたつもりの範囲が、実際には想定した範囲と違う

## 理屈

シェーディング補正テーブルがU16なのに、byte単位で範囲を書いていると、想定と違う範囲を0にしている可能性があります。

例えば、U16テーブルなら、

```text
1値 = 2byte
```

です。

なのに、

```text
100ピクセル分を0にしたつもりで100byteだけ0にした
```

なら、実際には50値分しか0になっていません。

あるいは、U32なら1値4byteです。

## 何を調べればよいか

0にした処理が、

```text
何byteを0にしているのか
何要素を0にしているのか
U16/U32の型単位で0にしているのか
```

を確認する。

## 検証方法

0にした後の補正テーブルをbin出力し、CSV化して確認する。

```text
本当に x=0〜N, y=0〜M の範囲が0になっているか
```

ここは必須です。

# 仮説13：小さい再生ツールと大きい再生ツールで、同じ「小さい動画」でも異なる補正テーブルを使っている

## 理屈

小さい動画を再生していても、再生ツールが違うと、

```text
小さい用補正テーブル
大きい用補正テーブル
変換後補正テーブル
```

のどれを使っているかが違うかもしれません。

その場合、同じ場所を0にしたつもりでも、実際に画像へ効いているテーブルのサイズや参照方法が違います。

## 何を調べればよいか

再生時に実際に使われる補正テーブルのポインタ・サイズ・height・lineSpanをログに出す。

```text
再生ツール名
使用テーブルwidth
使用テーブルheight
使用テーブルlineSpan
補正適用直前テーブルの先頭アドレス
```

## 検証方法

補正適用直前のテーブルを、両方の再生ツールでbin出力する。

CSV化して、0化範囲が同じか比較する。

# 仮説14：黒領域の「高さがズレた」のは、表示上の主観で、実データ上は同じ

## 理屈

目視では「高さが違う」と見えても、実際の画像データ上では同じ可能性があります。

表示倍率、画面サイズ、アンチエイリアス、ビューアのスケーリングで違って見えることがあります。

## 何を調べればよいか

画面ではなく、補正後 `out_img` のbin/CSVを見る。

## 検証方法

U32の補正後画像から、黒画素をしきい値で判定する。

```text
小さい再生ツールのout_img
大きい再生ツールのout_img
```

それぞれで、

```text
黒領域の上端
黒領域の下端
黒領域の高さ
```

を数値化する。

# 仮説15：横方向は同じだが、縦方向だけ別の縮尺を持つテーブル仕様

## 理屈

補正テーブルが、

```text
横方向は画像と1対1
縦方向は画像と1対2
```

のような仕様の可能性があります。

画像処理やセンサー処理では、横方向と縦方向でサンプリング密度が違うことがあります。

今回、

```text
位置と幅は同じ
高さだけズレる
```

なら、これもかなり候補です。

## 何を調べればよいか

補正テーブルの仕様または生成元を見る。

```text
tableWidth と imageWidth の比
tableHeight と imageHeight の比
```

を出す。

例えば、

```text
imageWidth / tableWidth = 1
imageHeight / tableHeight = 2
```

なら、この仮説が強いです。

# 一番ありそうな仮説

現時点で一番強いのは、この2つです。

```text
仮説A:
補正テーブルY座標と画像Y座標が1対1ではなく、
Y方向だけ2倍対応している。

仮説B:
補正テーブルの左下配置は大筋合っているが、
有効領域のYオフセットが別に存在している。
```

そして、それを分けるには、

```text
黒領域が上下に平行移動しているのか
黒領域の高さそのものが変わっているのか
```

を見る必要があります。

---



やることは、補正テーブル側を画像座標に合わせて無理に拡大することではなく、まずは 「画像座標 → 補正テーブル座標」の対応式に合わせて、補正テーブル内のどこを変更すべきか逆算する ことです。

今回 >> 1 が見つかったなら、補正適用側はたぶんこう読んでいます。

shadeY = imageY >> 1;  // imageY / 2

つまり、

画像 row 0, 1   → 補正テーブル row 0
画像 row 2, 3   → 補正テーブル row 1
画像 row 4, 5   → 補正テーブル row 2
...

です。

なので、画像上の同じ位置に補正をかけたいなら、画像Yをそのまま補正テーブルYに使ってはいけません。

⸻

結論：画像Y座標を >> 1 した位置に補正値を置く

たとえば、画像のこの範囲を黒くしたいとします。

画像側で黒くしたい範囲:
x = 0〜99
y = 100〜199

補正適用側が、

shadeY = imageY >> 1;

しているなら、補正テーブル側ではこうなります。

shadeY開始 = 100 >> 1 = 50
shadeY終了 = 199 >> 1 = 99

つまり、補正テーブルでは、

補正テーブル側:
x = 0〜99
y = 50〜99

を変更する必要があります。

画像側で100行ぶん黒くしたいなら、補正テーブル側では約50行ぶん変更する、ということです。

⸻

対応式

基本はこれです。

補正テーブルY = 画像Y >> 1

逆に言うと、

画像Y = 補正テーブルY × 2

です。

だから、補正テーブルの1行を変更すると、画像では2行ぶんに効きます。

shade row 50
↓
image row 100, 101 に効く

⸻

同じ位置に効かせるための考え方

「画像のどこに効かせたいか」を基準に考えます。

画像で効かせたい範囲を決める
↓
その画像Yを >> 1 して補正テーブルYに変換する
↓
補正テーブルのその範囲を書き換える

つまり、処理順はこうです。

画像座標で考える
↓
補正テーブル座標へ変換する
↓
補正テーブルを書き換える

⸻

C++で書くならこう

画像上の指定範囲に対応する補正テーブル範囲を0にするサンプルです。

#include <cstdint>
#include <algorithm>
using U16 = std::uint16_t;
// ------------------------------------------------------------
// 画像座標で指定した範囲に対応する補正テーブル領域を0にする
//
// shadeTable:
//   U16のシェーディング補正テーブル
//
// shadeWidth / shadeHeight:
//   補正テーブルの有効幅・高さ
//
// shadeLineSpanBytes:
//   補正テーブル1行あたりのbyte数
//
// imageX0, imageY0:
//   画像上で補正を効かせたい左上座標
//
// imageWidth, imageHeight:
//   画像上で補正を効かせたい範囲
//
// 注意:
//   補正適用側で imageY >> 1 している前提。
//   つまり、画像2行に対して補正テーブル1行が対応する。
// ------------------------------------------------------------
void markShadeAreaByImageAreaYShift1(
    U16* shadeTable,
    int shadeWidth,
    int shadeHeight,
    int shadeLineSpanBytes,
    int imageX0,
    int imageY0,
    int imageWidth,
    int imageHeight
)
{
    if (shadeTable == nullptr)
    {
        return;
    }
    // U16*としてアクセスするため、byte単位のLineSpanをU16要素数に変換する
    int shadeLineSpanElements =
        shadeLineSpanBytes / static_cast<int>(sizeof(U16));
    // ------------------------------------------------------------
    // 画像Y座標を、補正テーブルY座標へ変換する
    //
    // 補正適用側が shadeY = imageY >> 1 しているため、
    // ここでも同じ変換を使う。
    // ------------------------------------------------------------
    int shadeY0 =
        imageY0 >> 1;
    int imageY1 =
        imageY0 + imageHeight - 1;
    int shadeY1 =
        imageY1 >> 1;
    // X方向に >> 1 がない前提なら、Xはそのまま
    int shadeX0 =
        imageX0;
    int shadeX1 =
        imageX0 + imageWidth - 1;
    // 範囲外アクセス防止
    shadeX0 = std::max(0, shadeX0);
    shadeY0 = std::max(0, shadeY0);
    shadeX1 = std::min(shadeWidth - 1, shadeX1);
    shadeY1 = std::min(shadeHeight - 1, shadeY1);
    if (shadeX0 > shadeX1 || shadeY0 > shadeY1)
    {
        return;
    }
    // ------------------------------------------------------------
    // 変換後の補正テーブル範囲を0にする
    // ------------------------------------------------------------
    for (int y = shadeY0; y <= shadeY1; ++y)
    {
        U16* row =
            shadeTable + y * shadeLineSpanElements;
        for (int x = shadeX0; x <= shadeX1; ++x)
        {
            row[x] = 0;
        }
    }
}

⸻

ただし、X方向にも >> 1 があるなら話が変わる

もし補正適用コードで、

shadeX = imageX >> 1;
shadeY = imageY >> 1;

のように、X方向にも >> 1 があるなら、補正テーブルは画像に対して縦横どちらも1/2解像度です。

その場合は、

補正テーブルX = 画像X >> 1
補正テーブルY = 画像Y >> 1

になります。

つまり、画像上の100×100範囲に効かせたいなら、補正テーブルでは約50×50範囲を書き換えます。

コードではXもこうします。

int shadeX0 = imageX0 >> 1;
int shadeX1 = (imageX0 + imageWidth - 1) >> 1;

⸻

X方向に >> 1 がないなら

今回、黒くした「位置と幅」は小さいツール・大きいツールで同じだったんですよね。

それなら、現時点ではこう見ます。

X方向:
画像Xと補正テーブルXはほぼ1対1対応
Y方向:
画像Yと補正テーブルYは >> 1 で1/2対応

つまり、補正テーブル側の調整は、

Xはそのまま
Yだけ半分に換算

の可能性が高いです。

⸻

左下配置との関係

ここで混乱しやすいですが、2段階に分けてください。

1. 小さい補正テーブルを大きい補正テーブルへ配置する

これは今までの話。

src補正テーブルをdst補正テーブルの左下に置く

式はこれ。

dstY = dstHeight - srcHeight + srcY;

2. 画像に補正を適用するときの対応

これは今回見つけた >> 1 の話。

shadeY = imageY >> 1;

この2つは別レイヤーです。

補正テーブルをどこに置くか
≠
画像Yから補正テーブルYをどう参照するか

今回「同じ位置に補正をかける」には、補正適用側の参照式に合わせる必要があります。

⸻

今の結論

やるべきことはこれです。

1. 補正適用コードで確認する
   shadeY = imageY >> 1 なのか
   shadeX も >> 1 なのか
2. 画像上で効かせたい範囲を決める
3. その範囲を補正テーブル座標に変換する
   Yは imageY >> 1
   Xはコード次第
4. 変換後の補正テーブル範囲を書き換える
5. 出力画像で、期待位置に効いたか確認する

今の段階で安易に、

補正テーブルを2倍に引き伸ばす
補正テーブルを上下反転する
左下配置を変える

はやらない方がいいです。

>> 1 があるなら、補正適用側がすでにスケール変換している可能性が高いです。

だから、こちらがやるべきなのは、補正テーブルの配置をいじることではなく、

画像座標から補正テーブル座標への換算を理解して、
狙った画像位置に対応する補正テーブル位置を書き換える

ことです。
