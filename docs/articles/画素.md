# 画素

ここはかなり大事なので、いったん画像処理用語を抜いて説明します。

結論から言うと、

```text
補正テーブルのheight
= 補正値が何行ぶん並んでいるか

画像のheight
= 画像の画素が何行あるか
```

です。

この2つは **同じとは限りません**。

---

## 1. まず「画像のheight」

画像のheightは、普通に言えば **画像の縦の画素数** です。

例えば画像が、

```text
幅 3840
高さ 2160
```

なら、画像はこういう表です。

```text
画像データ

row 0
row 1
row 2
...
row 2159
```

つまり、画像のheightは、

```text
2160行ぶんの画素がある
```

という意味です。

U32画像なら、各画素がU32で入っている可能性があります。

```text
1画素 = U32 = 4byte
```

なので、画像は概念的にはこうです。

```text
image[2160][3840]
```

---

## 2. 次に「補正テーブルのheight」

シェーディング補正テーブルは、画像に対して、

```text
この場所は少し明るくする
この場所はそのまま
この場所は暗くする
```

みたいな補正値を持つ表です。

だから、補正テーブルも表です。

例えば、

```text
補正テーブル幅 3840
補正テーブル高さ 1860
```

なら、概念的にはこうです。

```text
shade[1860][3840]
```

つまり、

```text
補正値が1860行ぶんある
```

という意味です。

---

## 3. なぜ画像heightと補正テーブルheightが違うことがあるのか

ここが混乱の本体です。

直感的には、

```text
画像が2160行あるなら、
補正テーブルも2160行あるべきでは？
```

と思います。

これは自然です。

でも実際には、補正テーブルが画像と完全に1対1対応していないことがあります。

例えばこうです。

```text
画像 height = 2160
補正テーブル height = 1080
```

この場合、補正テーブルは画像の半分の行数しかありません。

ではどう使うか。

例えば、

```text
補正テーブルの1行を、画像の2行に使う
```

という使い方をします。

---

## 4. 例：画像6行、補正テーブル3行

画像が6行あるとします。

```text
画像

image row 0
image row 1
image row 2
image row 3
image row 4
image row 5
```

補正テーブルが3行しかないとします。

```text
補正テーブル

shade row 0
shade row 1
shade row 2
```

このとき、対応をこうすることがあります。

```text
image row 0, 1 → shade row 0
image row 2, 3 → shade row 1
image row 4, 5 → shade row 2
```

つまり、

```text
補正テーブル1行 = 画像2行
```

です。

コードではこうなります。

```c
shadeY = imageY / 2;
```

例えば、

```text
imageY = 0 → shadeY = 0
imageY = 1 → shadeY = 0

imageY = 2 → shadeY = 1
imageY = 3 → shadeY = 1

imageY = 4 → shadeY = 2
imageY = 5 → shadeY = 2
```

---

## 5. だから「height差」が同じになるとは限らない

あなたが見ていた話に戻すと、

```text
補正テーブル側の空欄高さ = 654行
画像側で見える空欄高さ = 1304行くらい
```

でした。

もし、

```text
補正テーブル1行 = 画像2行
```

なら、

```text
654 × 2 = 1308
```

になります。

これは `1304` にかなり近いです。

つまり、

```text
補正テーブルでは654行ぶん空いている
でも画像上では約2倍の1304行ぶんに見える
```

ということが起きても不自然ではありません。

---

## 6. なぜ「補正テーブル1行 = 画像2行」みたいなことをするのか

理由はいくつかあります。

### 理由1：補正テーブルを画像より粗く持つため

画像1画素ごとに補正値を持つとデータ量が大きくなります。

なので、

```text
補正値は少し粗い表で持つ
画像に適用するときに対応させる
```

という設計があります。

### 理由2：ベイヤー画像が2行周期だから

ベイヤー配列は、

```text
R G
G B
```

の2行周期です。

そのため、処理によっては縦方向を2行単位で扱うことがあります。

### 理由3：センサー領域・有効領域・表示領域が違うため

画像処理では、

```text
センサー全体の高さ
有効画像の高さ
表示される画像の高さ
補正テーブルの高さ
```

が全部違うことがあります。

---

## 7. 今回の文脈での見方

今回のデータを、仮にこう置きます。

```text
大きい補正テーブル height = 1860
小さい補正テーブル height = 1206
```

すると、左下に置いた場合、

```text
上側の空欄 = 1860 - 1206 = 654
```

です。

これは **補正テーブル上の行数** です。

でも画像側がもし2倍対応なら、

```text
画像上の空欄相当 = 654 × 2 = 1308
```

です。

だから、画像側で `1304` くらいに見えるのは、

```text
補正テーブル行数と画像行数が1対1ではない
```

と考えると説明できます。

---

## 8. コードで確認すべき場所

本当にそうかは、補正適用コードを見る必要があります。

探すべきはこういう処理です。

```c
shadeY = imageY / 2;
```

または、

```c
shadeY = imageY >> 1;
```

`>> 1` は、整数を2で割るのに近い処理です。

例えば、

```c
shadeY = y >> 1;
```

があれば、

```text
画像の2行に対して、補正テーブルの1行を使っている
```

可能性が高いです。

---

## 9. 逆に、1対1ならこう

もし補正適用コードがこうなら、

```c
shadeY = imageY;
```

つまり、

```c
shade = shadeTable[imageY * shadeLineSpan + imageX];
```

なら、

```text
補正テーブル1行 = 画像1行
```

です。

この場合は、補正テーブルの空欄654行が、画像側でも654行相当として出るはずです。

---

## 10. 一番簡単な理解

こう覚えていいです。

```text
画像height
= 画像そのものの縦の画素数

補正テーブルheight
= 補正値表の縦の行数

この2つは同じとは限らない
```

そして、

```text
補正テーブル1行が、画像何行ぶんに対応するか
```

は、補正適用コードが決めます。

---

## 11. 今のあなたの検証に当てはめると

今、黒くした範囲の「幅」は同じで、「高さ」だけズレた。

これは、

```text
X方向は、補正テーブルと画像がほぼ1対1対応している

Y方向は、補正テーブルと画像が1対1ではない可能性がある
```

という見方ができます。

だから、疑うべきは、

```text
shadeY = imageY / 2
shadeY = imageY >> 1
Y方向のoffset
Y方向の有効領域
```

です。

---

## まとめ

今回の一番重要な整理はこれです。

```text
補正テーブルのheightは「補正値表の行数」
画像のheightは「実画像の画素行数」

補正テーブルの1行が、画像の1行に対応するとは限らない。
補正テーブル1行が画像2行に対応するなら、
補正テーブル上の654行は、画像上では約1308行に見える。
```

なので、あなたが今すべき確認はこれです。

```text
画像Y座標から補正テーブルY座標をどう計算しているか
```

ここが分かれば、かなり整理できます。
