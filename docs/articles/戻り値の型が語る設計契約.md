# 戻り値の型が語る設計契約

C++ では、戻り値の型は「実装の都合」ではなく「設計上の約束」を伝えるものだ。

関数シグネチャを読むだけで、呼び出し側が
「null チェックが必要か」「コピーが発生するか」「所有権が移るか」
を判断できる。

この記事では、`T` / `T&` / `T*` の3つの戻り値型が何を意味するかを整理する。

---

## 第1章：3つの戻り値型と設計上の意味

| 戻り値型 | 意味 | 呼び出し側の責務 |
| :--- | :--- | :--- |
| `T` | 値のコピーを返す。呼び出し側が所有する | null チェック不要。コピーを受け取る |
| `T&` | 参照を返す。**必ず存在する** | null チェック不要。借りて使う |
| `T*` | ポインタを返す。**存在しない可能性がある** | **null チェックが必要** |

これは単なる記法の違いではない。
**「この関数は失敗する可能性があるか」という設計意図を型で宣言している。**

---

## 第2章：`T&` を返す場合 ―― 「必ず存在する」という契約

### 典型例：static 変数の返却

```cpp
class Config
{
public:
    // 設定は必ず存在する → T& で返す
    static Config& instance()
    {
        static Config config;
        return config;
    }

    int maxRetry = 3;
};

// 呼び出し側
Config& cfg = Config::instance();
// null チェックは不要。型が「必ず存在する」を保証している
cout << cfg.maxRetry << endl;
```

`T&` を返す関数は「この関数は失敗しない」という宣言だ。
呼び出し側は null チェックなしで使ってよい。

### `T&` を返すと何が起きるか

```cpp
// 関数の中の static 変数のアドレスが返る
// static なのでプログラム終了まで生きている → ダングリングしない
static Config config;
return config;   // config の参照を返す（コピーではない）
```

`T&` を返す場合、呼び出し側が受け取るのは「元の変数そのもの」だ。
コピーは発生しない。

---

## 第3章：`T*` を返す場合 ―― 「存在しない可能性」という契約

### 典型例：検索処理

```cpp
class Inventory
{
public:
    // 見つかるとは限らない → T* で返す
    Item* find(const std::string& name)
    {
        for (auto& item : items_)
        {
            if (item.name == name)
            {
                return &item;  // 見つかったらアドレスを返す
            }
        }
        return nullptr;  // 見つからなければ nullptr
    }

private:
    std::vector<Item> items_;
};

// 呼び出し側
Item* result = inventory.find("Potion");

if (result != nullptr)  // ← null チェックが必須
{
    result->use();
}
```

`T*` を返す関数は「この関数は失敗する可能性がある」という宣言だ。
呼び出し側は null チェックの責任を負う。

---

## 第4章：2つの実装を並べて比較する

同じロジックを `T&` と `T*` で書いた場合の違い。

```cpp
// バージョン1: T& を返す（必ず存在する前提）
Config& getConfig()
{
    static Config config;
    return config;
}

// バージョン2: T* を返す（存在しない可能性を含む）
Config* getConfig()
{
    static Config config;
    return &config;
}
```

どちらも `static` なので寿命は問題ない。
しかし設計の意味が違う。

```cpp
// T& の場合
Config& cfg = getConfig();
cfg.maxRetry = 5;  // null チェック不要。シンプル

// T* の場合
Config* cfg = getConfig();
if (cfg)           // null チェックが必要
{
    cfg->maxRetry = 5;
}
```

`static` 変数を返す場合は `T&` が自然だ。
「設定は必ずある」ことが実装上の事実なら、それを型で表現するのが正しい。

---

## 第5章：「型で嘘をつかない」という設計原則

### 悪い設計の例

```cpp
// 内部では必ず存在するのに T* を返している
Config* getConfig()
{
    static Config config;
    return &config;  // null になることは絶対にない
}
```

これは嘘だ。
`T*` を見た呼び出し側は「null かもしれない」と思い、
不要な null チェックを書くか、あるいは「null チェックしなくていいだろう」と
誤った判断をする。

### 型は「呼び出し側への約束」

```
T&  を返す  →「絶対に存在する。失敗しない。」
T*  を返す  →「存在しないことがある。チェックしてくれ。」
```

この約束を守るだけで、呼び出し側のコードが設計上正しい形になる。

---

## 第6章：戻り値型の選択基準

```
この関数は失敗する可能性があるか？
│
├── No（必ず返せる）
│   ├── コピーでよい？       → T
│   └── コピーしたくない？   → T&
│
└── Yes（返せないことがある）
    └── nullptr で表現する  → T*
        または
        std::optional<T>   → 存在しない可能性を型で明示（モダンC++）
```

---

## 理解度チェック

次の3つの関数について、それぞれ「呼び出し側は null チェックが必要か」と
「そのシグネチャは設計として適切か」を答えてほしい。

```cpp
// 1. ゲームのプレイヤーは常に1人存在する
Player* getPlayer();

// 2. 名前でアイテムを検索する（見つからない場合がある）
Item& findItem(const std::string& name);

// 3. ログファイルは起動時に必ず初期化される
Logger& getLogger();
```

---

**正解：**

**1. `Player* getPlayer();`**
- 呼び出し側：null チェックが必要（型がそう言っている）
- 設計として：**不適切**。「常に1人存在する」なら `Player&` が正しい。
  `T*` を返すことで「存在しない可能性がある」と嘘をついている。

**2. `Item& findItem(const std::string& name);`**
- 呼び出し側：null チェックが不要（型が「必ず存在する」を保証）
- 設計として：**不適切**。見つからないことがあるなら `Item*` か
  `std::optional<std::reference_wrapper<Item>>` が正しい。
  見つからなかったとき何を返すか定義できない。

**3. `Logger& getLogger();`**
- 呼び出し側：null チェック不要
- 設計として：**適切**。「必ず存在する」ことを型で正直に表現している。

> **重要な視点：**
> シグネチャを読んだだけで「この関数は失敗する可能性があるか」が分かる。
> それが C++ の型システムによる設計表現だ。
