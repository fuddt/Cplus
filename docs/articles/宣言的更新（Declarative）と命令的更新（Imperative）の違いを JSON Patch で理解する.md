# 宣言的更新と命令的更新の違いを、JSON Patch で理解する

データを更新するとき、あなたはどちらのやり方をとりますか？

> 「こうなってほしい」という **最終状態** を伝える
> 「これをこう変えてほしい」という **手順** を伝える

実はこの違いに、プログラム設計の重要な考え方が隠れています。

この記事では **JSON**（データの書き方の一種）を使って、その違いをやさしく解説します。  
プログラミング初心者でも読めるよう、具体的な例をたくさん使いながら説明します。

---

## まず「JSON」ってなんだろう？

JSON（ジェイソン）は、データをテキストで表すための書き方です。  
アプリやウェブサービスがデータをやりとりするときによく使われています。

たとえば、こんな形で書きます。

```json
{
  "name": "山田太郎",
  "age": 17,
  "done": false
}
```

`{}`の中に、`キー: 値` の形でデータを並べるだけ。  
英語でも日本語でも読みやすく、プログラマーに広く使われています。

---

## 今回の例：Todoリストアプリ

この記事では **Todoリストアプリ** を例に考えます。  
「やること」を管理するアプリです。

次のようなデータがあるとします。

```json
{
  "todos": [
    { "id": 1, "text": "牛乳を買う",  "done": false },
    { "id": 2, "text": "メール返信", "done": false }
  ]
}
```

`"done": false` は「まだ完了していない」という意味です。

ここで「1番のタスク（牛乳を買う）を完了にしたい」とします。  
このデータをどうやって更新すればいいでしょうか？

実は、大きく **2つのやり方** があります。

---

## やり方① 宣言的更新（Declarative）― 「こうなってほしい」を書く

**宣言的（Declarative）** とは、**最終的にどういう状態になってほしいか** を伝えるやり方です。

「どうやって変えるか」は伝えません。  
「変えたあとのかたちはこれです」とだけ伝えます。

JSON では **JSON Merge Patch** という方法がこれにあたります。

```json
{
  "todos": [
    { "id": 1, "text": "牛乳を買う", "done": true }
  ]
}
```

これは「`todos` をこの内容にしてほしい」という宣言です。  
変更後の状態をそのまま書いています。

### わかりやすいたとえ

> 「部屋をきれいな状態にしてください」
> （どうやって片付けるかは任せる）

これが宣言的な伝え方です。

---

## やり方② 命令的更新（Imperative）― 「これをこう変えてほしい」を書く

**命令的（Imperative）** とは、**具体的な操作の手順** を伝えるやり方です。

「どこを」「どう変えるか」を細かく指定します。

JSON では **JSON Patch** という方法がこれにあたります。

```json
[
  {
    "op": "replace",
    "path": "/todos/0/done",
    "value": true
  }
]
```

少し見慣れない形ですね。それぞれの意味はこうです。

| フィールド | 意味 |
| --------- | ---- |
| `"op"` | 操作の種類（今回は `replace`＝置き換え） |
| `"path"` | どこを変えるか（`todos` の0番目の `done`） |
| `"value"` | どんな値にするか（`true`） |

「`todos[0].done` を `true` に置き換えてください」という命令です。

### わかりやすいたとえ

> 「まず床の物を拾って、次に掃除機をかけて、最後に拭き掃除してください」
> （手順を一つひとつ指定する）

これが命令的な伝え方です。

---

## 2つのやり方を比べてみよう

| 観点 | 宣言的（Declarative） | 命令的（Imperative） |
| --- | -------------------- | ------------------- |
| 何を書くか | 最終状態 | 操作の手順 |
| 読みやすさ | わかりやすい | やや難しい |
| 順番の管理 | 不要 | 必要 |
| 部分的な更新 | 苦手 | 得意 |
| 代表的な方法 | JSON Merge Patch | JSON Patch |

---

## 宣言的更新のいいところ・弱いところ

### いいところ
- 直感的でわかりやすい
- 書くコードが少なくてすむ
- 「最後にどうなってほしいか」が一目でわかる

### 弱いところ
**配列（リスト）の一部だけを変えることができません。**

たとえば先ほどの例：

```json
{
  "todos": [
    { "id": 1, "text": "牛乳を買う", "done": true }
  ]
}
```

これを適用すると、`todos` リストが **丸ごと** このデータに置き換わります。  
2番目のタスク「メール返信」が **消えてしまいます**。

---

## 命令的更新のいいところ・弱いところ

### いいところ
**リストの一部だけを変えることが得意です。**

```json
[
  {
    "op": "replace",
    "path": "/todos/0/done",
    "value": true
  }
]
```

これなら「0番目のタスクの `done` だけ変える」と指定できるので、  
他のタスクはそのまま残ります。

また、操作を **順番に並べられる** のも強みです。

```json
[
  { "op": "remove", "path": "/todos/0" },
  { "op": "add",    "path": "/todos/-", "value": { "id": 3, "text": "散歩する", "done": false } }
]
```

「0番を削除してから、新しいタスクを追加する」という順番が重要な場合にも対応できます。

### 弱いところ
- 読みにくい
- 「最終的にどんな状態になるのか」がパッと見てわからない

---

## どちらを使えばいい？

シンプルな判断基準はこれです。

**「最終的な状態を書けばすむ場合」→ 宣言的（JSON Merge Patch）**

- ユーザーの設定を変える
- 単純な値の書き換え
- 人間が直接編集するファイル

**「手順や順番が大事な場合」→ 命令的（JSON Patch）**

- リストの一部だけを変える
- 変更の履歴を残したい
- 削除→追加のように順序が意味を持つ

---

## 実は、両方を組み合わせることもできる

少し発展的な話です。

実際のアプリでは、**宣言的と命令的を組み合わせて使う** こともあります。

たとえば、こんな構造のデータ：

```json
{
  "filepath": "todos.json",
  "operations": [
    {
      "op": "replace",
      "path": "/todos/0/done",
      "value": true
    },
    {
      "op": "add",
      "path": "/todos/-",
      "value": { "id": 3, "text": "散歩する", "done": false }
    }
  ]
}
```

| フィールド | やり方 | 意味 |
| ---------- | ------ | ---- |
| `filepath` | 宣言的 | 保存先のファイル名（最終状態） |
| `operations` | 命令的 | 実行する変更の手順 |

「どのファイルを使うか」は状態として書き、  
「どんな変更をするか」は手順として書く、という役割分担です。

「状態として書けるものは宣言的に、操作として書く必要があるものは命令的に」  
これが自然な設計です。

---

## まとめ

| やり方 | キーワード | 得意なこと |
| ------ | ---------- | ---------- |
| 宣言的（Declarative） | 「こうなってほしい」 | 読みやすさ・シンプルな更新 |
| 命令的（Imperative） | 「これをこうして」 | 細かい操作・順序の管理 |

**どちらが正しい、というわけではありません。**  
「何を更新したいのか」によって、使い分けることが大切です。

この「状態を書く」か「手順を書く」かという考え方は、  
JSON に限らずプログラミング全般でとても重要な概念です。  
ぜひ意識してみてください。
