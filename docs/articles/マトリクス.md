座標や領域でMatrixデータが切り替わっている
小さい動画と大きい動画でゲインレベルの対応が違う
入力bit深度が違う
LUT index の作り方が違う
scale が違う


Matrixデータ が配列になっているか？
MatrixLut の value の次元は本当に [ゲインレベル][LUTサイズ] だけか？
r0〜b2 を読むときに x, y, block, area が絡んでいないか？
scale は何か？ 1024か？ 4096か？

できる。
ただし、「何を証明したいか」を分けないと、弱い証明になる。

結論はこれです。

小さい動画ツール・大きい動画ツールのそれぞれで、
「補正前 bin」と「補正後 bin」を CSV 化して比較すれば、
マトリクス補正が実際に画像へ効いていること は確認できる。

でも、それだけではまだ、

小さい動画用キャリブレーションテーブルをコピーしたことが、大きい動画ツールで正しく解釈されている

という証明としては少し弱いです。

⸻

何が証明できるか

今回の比較で証明できることは主に3つあります。

1. 補正が実際に適用されていること

補正前と補正後を比べて、RGB値が変わっていれば、

マトリクス補正処理が動いている

とは言えます。

たとえば、

補正前: R=1000, G=800, B=600
補正後: R=950,  G=830, B=620

なら、色が変換されています。

⸻

2. 小さい動画ツールと大きい動画ツールで同じ傾向の補正がされていること

小さい動画側でも、

Rが少し下がる
Gが少し上がる
Bが少し上がる

大きい動画側でも、

Rが少し下がる
Gが少し上がる
Bが少し上がる

なら、補正の方向性は一致しています。

これは「コピーしたマトリクスが似た働きをしている」証拠になります。

⸻

3. 同じ入力RGBに対して同じ出力RGBになること

ここまでできると強いです。

たとえば、小さい動画側と大きい動画側で、同じ補正前RGBがあるとする。

入力RGB = R=1000, G=800, B=600

そのとき補正後も同じなら、

小さい動画側の補正後: R=950, G=830, B=620
大きい動画側の補正後: R=950, G=830, B=620

これはかなり強い。

つまり、

同じ入力に対して、同じマトリクス補正がかかっている

と言える。

⸻

ただし、補正前画像が違うなら単純比較はできない

ここが大事です。

小さい動画ツールと大きい動画ツールでは、アフィン後の画像サイズや画素配置が違う可能性があります。

つまり、

小さい動画の x=100, y=50
大きい動画の x=100, y=50

が、同じ内容の画素とは限らない。

だから、単純にCSVの同じ行・同じ列を比較して、

値が違うからNG

とは言えません。

前回のシェーディング補正は「黒塗り領域のセル位置」を見たので、座標比較が主役でした。
でも今回のマトリクス補正は「色変換」なので、見るべきなのは座標そのものより、

補正前RGB → 補正後RGB の変化

です。

⸻

今回の正しい検証単位

見るべき単位はこれです。

補正前RGB
↓
マトリクス補正
↓
補正後RGB

つまり、CSV比較ではこういう行を作るべきです。

x,y,R_before,G_before,B_before,R_after,G_after,B_after,dR,dG,dB

ここで、

dR = R_after - R_before
dG = G_after - G_before
dB = B_after - B_before

を見る。

⸻

最低限の検証

最低限なら、これでよいです。

小さい動画ツール:
  補正前CSV
  補正後CSV
  差分CSV
大きい動画ツール:
  補正前CSV
  補正後CSV
  差分CSV

そして確認する。

1. 補正前と補正後で値が変わっているか
2. 小さい側と大きい側で、変化方向が一致しているか
3. 異常値が出ていないか
4. クリップ、0埋め、最大値張り付きが増えていないか

⸻

ただし「証明」として強くするなら

もっと強くするなら、マトリクス係数から期待値を計算します。

たとえば係数がこうだったとする。

r0 r1 r2
g0 g1 g2
b0 b1 b2

補正前RGBが、

R_before, G_before, B_before

なら、期待値はこう。

R_expected = r0*R_before + r1*G_before + r2*B_before
G_expected = g0*R_before + g1*G_before + g2*B_before
B_expected = b0*R_before + b1*G_before + b2*B_before

固定小数点なら、最後に /1024 や >>10 が入る。

そして、

R_after == R_expected
G_after == G_expected
B_after == B_expected

を見る。

これが一番強いです。

⸻

検証レベルでいうと3段階ある

レベル1: 補正前後の差分を見る

補正前CSV vs 補正後CSV

これは、

補正が効いている

の確認。

ただし、正しい係数で効いているかまでは弱い。

⸻

レベル2: 小さい側と大きい側の差分傾向を見る

小さい側の dR,dG,dB
大きい側の dR,dG,dB

これで、

同じような補正傾向になっている

が確認できる。

ただし、入力画像が違うなら完全一致は期待できない。

⸻

レベル3: 係数から期待値を再計算する

補正後CSV == Pythonで計算した期待値CSV

これが一番強い。

この検証なら、

マトリクス情報が正しくコピーされ、
大きい動画ツール側で正しく適用されている

にかなり近い証明になります。

⸻

Pythonでやるならこういう比較

前提として、CSVがこういう形式だとする。

x,y,R_before,G_before,B_before,R_after,G_after,B_after

マトリクス係数が固定で、scale が 1024 だと仮定すると、検証コードはこう。

import pandas as pd
# 例: MatrixData
# scale=1024 のとき、1024 が 1.0倍を意味する想定
matrix = {
    "r0": 900,  "r1": 80,   "r2": 40,
    "g0": 30,   "g1": 1000, "g2": 20,
    "b0": 10,   "b1": 50,   "b2": 1100,
}
SCALE = 1024
MAX_VALUE = 4095  # 12bit想定。10bitなら1023、8bitなら255。
def clamp(value, min_value=0, max_value=MAX_VALUE):
    """
    画素値が範囲外に出た場合、画像フォーマットの範囲内に収める。
    """
    return max(min_value, min(value, max_value))
def calc_expected(row):
    """
    CSVの1行から、マトリクス補正後の期待RGBを計算する。
    """
    r = int(row["R_before"])
    g = int(row["G_before"])
    b = int(row["B_before"])
    # 3x3マトリクスでRGBを混ぜ直す
    r_exp = (
        matrix["r0"] * r +
        matrix["r1"] * g +
        matrix["r2"] * b
    ) // SCALE
    g_exp = (
        matrix["g0"] * r +
        matrix["g1"] * g +
        matrix["g2"] * b
    ) // SCALE
    b_exp = (
        matrix["b0"] * r +
        matrix["b1"] * g +
        matrix["b2"] * b
    ) // SCALE
    # 画素値範囲にクリップ
    r_exp = clamp(r_exp)
    g_exp = clamp(g_exp)
    b_exp = clamp(b_exp)
    return pd.Series({
        "R_expected": r_exp,
        "G_expected": g_exp,
        "B_expected": b_exp,
    })
# 補正前後をまとめたCSVを読む
df = pd.read_csv("matrix_debug.csv")
# 期待値を計算
expected = df.apply(calc_expected, axis=1)
df = pd.concat([df, expected], axis=1)
# 実際の補正後値との差分
df["R_error"] = df["R_after"] - df["R_expected"]
df["G_error"] = df["G_after"] - df["G_expected"]
df["B_error"] = df["B_after"] - df["B_expected"]
# 完全一致しているか確認
ok_rows = (
    (df["R_error"] == 0) &
    (df["G_error"] == 0) &
    (df["B_error"] == 0)
)
print("total rows:", len(df))
print("ok rows:", ok_rows.sum())
print("ng rows:", len(df) - ok_rows.sum())
# NGだけ出力して、どこがズレたか確認できるようにする
df_ng = df[~ok_rows]
df_ng.to_csv("matrix_check_ng.csv", index=False)
# 全体も保存
df.to_csv("matrix_check_result.csv", index=False)

サンプルコード。

#include <cstdint>
#include <fstream>
using U16 = std::uint16_t;
enum class BayerPattern {
    RGGB,
    BGGR,
    GRBG,
    GBRG
};
enum class BayerColor {
    R,
    G,
    B
};
BayerColor getBayerColor(int x, int y, BayerPattern pattern)
{
    const bool evenX = (x % 2 == 0);
    const bool evenY = (y % 2 == 0);
    if (pattern == BayerPattern::RGGB) {
        if ( evenY &&  evenX) return BayerColor::R;
        if ( evenY && !evenX) return BayerColor::G;
        if (!evenY &&  evenX) return BayerColor::G;
        return BayerColor::B;
    }
    if (pattern == BayerPattern::BGGR) {
        if ( evenY &&  evenX) return BayerColor::B;
        if ( evenY && !evenX) return BayerColor::G;
        if (!evenY &&  evenX) return BayerColor::G;
        return BayerColor::R;
    }
    if (pattern == BayerPattern::GRBG) {
        if ( evenY &&  evenX) return BayerColor::G;
        if ( evenY && !evenX) return BayerColor::R;
        if (!evenY &&  evenX) return BayerColor::B;
        return BayerColor::G;
    }
    // GBRG
    if ( evenY &&  evenX) return BayerColor::G;
    if ( evenY && !evenX) return BayerColor::B;
    if (!evenY &&  evenX) return BayerColor::R;
    return BayerColor::G;
}
const char* toString(BayerColor color)
{
    if (color == BayerColor::R) return "R";
    if (color == BayerColor::G) return "G";
    return "B";
}
void writeBayerCsv(
    const U16* image,
    int width,
    int height,
    int lineSpanBytes,
    BayerPattern pattern,
    const char* outputPath
) {
    std::ofstream ofs(outputPath);
    // 検証用なので列名をつけた方がよい。
    ofs << "x,y,color,value\n";
    for (int y = 0; y < height; ++y) {
        // 1行の先頭アドレスを byte 単位で移動する。
        const auto* row = reinterpret_cast<const U16*>(
            reinterpret_cast<const std::uint8_t*>(image) + y * lineSpanBytes
        );
        for (int x = 0; x < width; ++x) {
            U16 value = row[x];
            BayerColor color = getBayerColor(x, y, pattern);
            ofs << x << ","
                << y << ","
                << toString(color) << ","
                << value << "\n";
        }
    }
}

または、

ApplyMatrix(U16* rPlane, U16* gPlane, U16* bPlane, ...)

3. r0〜b2 を使う直前

ここを見るのが一番早い。

outR = r0 * R + r1 * G + r2 * B;

この R, G, B がどこから来ているかを追う。

もしこうならRGB化済み。

R = rgbBuffer[index].r;
G = rgbBuffer[index].g;
B = rgbBuffer[index].b;

もしこうならBayerから周辺画素を拾っている。

R = src[y * stride + x];
G = src[y * stride + x + 1];
B = src[(y + 1) * stride + x + 1];

この場合、Bayerパターンが絡んでいます。

今の質問への短い答え

どういうコードを見ればRGBがどういう順番で並んでいるのかわかりそうですか？

ベイヤー画像なら、見るべきはこの3つです。

1. Bayerパターン定義
   RGGB / BGGR / GRBG / GBRG のどれか
2. x,yの偶奇でR/G/Bを判定している処理
   x % 2, y % 2, x & 1, y & 1 が出てくる場所
3. r0〜b2を使う直前に、R/G/Bをどの画素から取っているか

特に3番が一番強いです。

r0〜b2に渡しているR/G/Bがどこから来ているか

を追えば、実際の処理上の色の扱いがわかります。
