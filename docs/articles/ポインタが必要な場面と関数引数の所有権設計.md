# ポインタが必要な場面と関数引数の所有権設計

> **前提：** この記事は `参照とポインタの使い分け.md` の続きとして読む。
> 「参照 vs ポインタの基本比較」はそちらで扱っている。
> ここでは「**なぜポインタが必要になるのか**」と「**関数引数の型選択**」に絞る。

---

## この記事が扱う問い

> 「参照のほうが安全で可読性が高い。
>  ポインタで指す先をコロコロ変えることに何のメリットがある？
>  可読性の低下とバグのリスクだけじゃないのか？」

この直感は正しい。
だからモダン C++ の原則は「**参照で足りるなら参照を使え**」だ。

しかし、参照では **物理的に不可能** なことが5つある。
そのときだけポインタが正当化される。

---

## 第1章：ポインタが必要な5つの場面

### 場面1：「まだ何も選んでいない」状態を表現する

```cpp
// 参照では書けない
int& current = ???;  // 参照は宣言時に必ず何かを指していないといけない

// ポインタなら書ける
int* current = nullptr;  // 「まだ何も指していない」
```

`nullptr` は「存在しない」または「未選択」を表現する手段だ。
参照にはこれがない。

**具体例：** ゲームで「現在選択中のアイテム」を持つ変数。
何も選んでいない状態が存在するため、`nullptr` が必要。

```cpp
class Player
{
    Item* selectedItem = nullptr;  // 未選択状態を表現できる
};
```

---

### 場面2：指す対象を動的に切り替える

```cpp
// 木構造の探索
Node* current = root;  // root から始める

while (current != nullptr)
{
    if (target < current->value)
        current = current->left;   // 左の子に移動
    else
        current = current->right;  // 右の子に移動
}
```

`current` は「今どのノードを見ているか」という**状態**だ。
ループのたびに指す先が変わる。

参照は再束縛できない。だからこのコードは参照では書けない。

**ポインタが得るもの：** 「今どれを指しているか」という状態を持てること。

---

### 場面3：ノードがアドレスで繋がるデータ構造

```cpp
struct Node
{
    int value;
    Node* left  = nullptr;  // 左の子ノード（なければ nullptr）
    Node* right = nullptr;  // 右の子ノード（なければ nullptr）
};
```

連結リスト・木・グラフは「ノード同士がアドレスで繋がっている」構造だ。
参照で繋ごうとすると、再束縛できないため構造を変更できない。
これらはポインタなしには実現できない。

---

### 場面4：所有と観測を分離する

```cpp
std::unique_ptr<Node> owner;   // owner が Node を所有する
Node* observer = owner.get();  // observer は Node を観測するだけ（所有しない）
```

`unique_ptr` は所有権を持つ。
しかし同じオブジェクトを「ただ見たい」だけの場合、
`unique_ptr` では2つが同時に所有できない（unique = 唯一の所有者）。

`Node*`（生ポインタ）は「所有権なしの借用」だ。
所有権を主張せず、指す先を読むだけの役割を担う。

---

### 場面5：C API との接続

```cpp
// OS・ネットワーク・組み込みの API はポインタ前提
void process(int* buffer, std::size_t size);

std::vector<int> data{1, 2, 3};
process(data.data(), data.size());  // data() は int* を返す
```

C言語で書かれた API（OS、デバイスドライバ、外部ライブラリ）は
ポインタを引数・戻り値として使う。
これとの接続でポインタは避けられない。

---

## 第2章：トレードオフの整理

| | 参照 `T&` | ポインタ `T*` |
| :--- | :--- | :--- |
| **得るもの** | 安全性・可読性 | 状態保持・null表現・動的切り替え |
| **失うもの** | null表現・再束縛 | 安全性・可読性 |
| **使う場面** | 普通の引数・借用 | 上記5場面のいずれか |

> **結論：** ポインタは「危険を扱う能力」だ。
> 必要でないときに使うのは危険を招くだけ。
> 必要な5場面でのみ使う。

---

## 第3章：関数引数の所有権設計

関数を定義するとき、引数の型で「この引数をどう扱うか」を宣言する。

### 5パターンの比較

| 型 | 意味 | 使う場面 |
| :--- | :--- | :--- |
| `T` | コピーして所有する | 引数が小さい型、または所有したいとき |
| `const T&` | 借りる（読み取り専用） | **基本形。重いオブジェクトを読むだけ** |
| `T&` | 借りる（書き換えあり） | 呼び出し元の変数を直接書き換えたいとき |
| `T&&` | 所有権を受け取る（ムーブ） | 呼び出し元がもう使わないオブジェクトを渡すとき |
| `T*` | 借りる（null あり得る） | null を渡す可能性があるとき |

---

### `const T&`：普通の借用（最も使う）

```cpp
void print(const std::string& s)
{
    cout << s << endl;
}

std::string name = "Alice";
print(name);  // コピーせず name そのものを渡す
```

- コピーコストなし
- 呼び出し元の変数は変わらない
- null にならない

**重いオブジェクトを「読むだけ」なら常にこれ。**

---

### `T&`：書き換えを伴う借用

```cpp
void heal(Player& player, int amount)
{
    player.hp += amount;  // 呼び出し元の player を直接書き換える
}

Player hero;
heal(hero, 30);  // hero.hp が増える
```

呼び出し元の変数が変わることを意図するときに使う。
関数シグネチャを見た人が「呼び出し元に影響する」と分かる。

---

### `T&&`：ムーブセマンティクス

```cpp
void store(std::string&& name)
{
    stored_ = std::move(name);  // 所有権を受け取る
}

std::string s = "hello";
store(std::move(s));  // s の所有権を store に渡す
// この後 s は空になる可能性がある
```

`T&&` は「呼び出し元はもうこの値を使わない」という宣言だ。
`std::move()` は「所有権を渡すこと」に同意する合図。

コピーが不要になるため、巨大なオブジェクトを渡すときにコストが下がる。

---

### `T*`：null ありの借用

```cpp
void logIfEnabled(Logger* logger, const std::string& message)
{
    if (logger != nullptr)  // ← null チェックが必要
    {
        logger->write(message);
    }
}

logIfEnabled(nullptr, "message");  // null を渡せる
logIfEnabled(&myLogger, "message");
```

`nullptr` を渡すことを許容したいときに使う。
呼び出し側に null チェックの責任を求めるのではなく、
関数内部で null を扱う設計にすることが多い。

## 第4章：判断フローチャート

```
関数に何かを渡したい
│
├── null を渡す必要がある？
│   └── Yes → T*
│
├── 呼び出し元の変数を書き換えたい？
│   └── Yes → T&
│
├── 所有権ごと渡したい（移動後は使わない）？
│   └── Yes → T&&（+ std::move で呼び出す）
│
└── ただ使ってもらうだけ（所有も書き換えも不要）
    ├── 型が小さい（int, bool など）
    │   └── T（コピーで十分）
    └── 型が重い（string, vector など）
        └── const T&（基本形）
```

## 理解度チェック

以下の3つの関数定義について、引数の型が設計として適切かを判断してほしい。

```cpp
// 1. 文字列の長さを返す（文字列は変更しない）
size_t length(std::string s);

// 2. プレイヤーの HP を回復する
void heal(Player player, int amount);

// 3. アイテムを探す（見つからないことがある）
Item& findItem(std::vector<Item>& items, const std::string& name);
```

---

**正解：**

**1. `size_t length(std::string s)`**
- **不適切**。`s` は値渡しなのでコピーが発生する。
- 文字列を変更しないなら `const std::string&` が正しい。
  ```cpp
  size_t length(const std::string& s);
  ```

**2. `void heal(Player player, int amount)`**
- **不適切**。`player` はコピーされるため、呼び出し元の `player` の HP は変わらない。
- 呼び出し元の Player を書き換えるなら `Player&` が必要。
  ```cpp
  void heal(Player& player, int amount);
  ```

**3. `Item& findItem(std::vector<Item>& items, const std::string& name)`**
- **不適切**。見つからないことがあるのに `T&` を返すと、
  見つからなかったとき何を返すか定義できない（無効な参照は作れない）。
- `Item*` を返すのが正しい。
  ```cpp
  Item* findItem(std::vector<Item>& items, const std::string& name);
  ```

> **まとめ：**
> 関数シグネチャは「仕様書」だ。
> 引数の型・戻り値の型を見るだけで、関数の振る舞いと責任が分かるように設計する。
