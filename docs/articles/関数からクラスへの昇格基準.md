# 関数で始めて、いつクラスへ昇格させるべきか

## 先回りの抽象化を避けるための判断基準

ソフトウェア設計をしていると、よく出てくる悩みがあります。

「この処理、最初からクラスにした方がいいのだろうか？」
「それとも、まずは関数で十分なのだろうか？」

特にデザインパターンを学んだ直後は、見たことのある形に寄せたくなります。
インターフェースを切って、具象クラスを作って、管理クラスを作って……という構成は、たしかにそれっぽく見えます。

ただ、そこで一度立ち止まった方がいいです。
なぜなら、**「クラスにすること」自体には価値がない**からです。価値があるのは、**クラスにすることで得られる設計上の利益**です。

状態も持たない。外部依存もない。差し替え予定もない。
そのような処理まで最初からクラスにしてしまうと、設計が立派になるどころか、むしろ重くなります。

この記事では、**まずは関数で始めて、必要になったらクラスへ昇格させる**という考え方を整理します。
「どのタイミングでクラス化すべきか」を判断するための基準も、実例つきでまとめます。

---

## まず結論

最初に結論を書くと、基本方針は次の通りです。

* **状態を持たない処理**は、まず関数でよい
* **状態・依存関係・初期化責務**が出てきたら、クラス化を検討する
* 「将来使うかもしれない」だけでは、クラス化の理由にはならない

つまり、最初からクラスを作るのではなく、**必要が発生した時に昇格させる**のが自然です。

---

## なぜ最初は関数でよいのか

関数で十分な処理は、意外と多いです。

たとえば次のような処理です。

* 文字列を整形する
* 値を変換する
* 条件に応じて何かを更新する
* 入力を受けて、その場で結果を返す

このような処理に共通しているのは、**関数自身が状態を持たない**ことです。
引数を受け取り、その場で処理して、結果を返すだけです。

この段階では、クラス化しても得られる利益があまりありません。
それどころか、次のようなコストが増えることがあります。

* クラス定義が増える
* ファイル数が増える
* 抽象インターフェースが増える
* 理解コストが上がる
* 依存関係が増える

ここで重要なのは、**「メモリがもったいないからクラスにしない」ではない**ということです。
もちろん、オブジェクト化すれば多少のメモリや生成コストは増えますが、本質はそこではありません。

本当に痛いのは、**抽象化のコストに対して、利益が薄いこと**です。

---

## クラス化しすぎると何が起こるか

たとえば、ただの短い処理をこんなふうにクラス化したとします。

```cpp
class NormalizeTextProcessor : public IProcessor {
public:
    void process(std::string& text) override {
        // 文字列整形処理
    }
};
```

このコード自体は間違いではありません。
しかし、ここで考えるべきは「**なぜクラスである必要があるのか**」です。

もしこの処理が、

* 状態を持たない
* コンストラクタ引数もない
* 差し替え要件もない
* 単発の処理として完結する

のであれば、実質的には**「関数をクラスで包んだだけ」**です。

その場合、こう突っ込まれた時に苦しくなります。

> 状態を持たないのに、なぜクラスにしているのですか？

この問いに明確に答えられないなら、そのクラス化は早すぎる可能性が高いです。

---

## まずは関数で始める例

ここでは、題材として「テキスト整形処理」を使います。
特定の業務知識に依存しない、一般的な例です。

たとえば、入力文字列に対して次のような処理をしたいとします。

* 前後の空白を削除する
* 小文字化する
* 禁止語を伏せ字にする

この段階では、関数で十分です。

```cpp
#include <algorithm>
#include <cctype>
#include <string>
#include <vector>

// 前後の空白を除去する関数
// 状態を持たず、入力文字列を受けて結果を返すだけ
std::string trim(const std::string& input)
{
    std::size_t start = 0;
    while (start < input.size() && std::isspace(static_cast<unsigned char>(input[start]))) {
        ++start;
    }

    std::size_t end = input.size();
    while (end > start && std::isspace(static_cast<unsigned char>(input[end - 1]))) {
        --end;
    }

    return input.substr(start, end - start);
}

// 文字列を小文字化する関数
// これも状態を持たない純粋な変換処理
std::string toLower(const std::string& input)
{
    std::string result = input;

    std::transform(
        result.begin(),
        result.end(),
        result.begin(),
        [](unsigned char c) {
            return static_cast<char>(std::tolower(c));
        }
    );

    return result;
}

// 禁止語を置換する関数
// 置換対象の単語一覧は引数で受けるので、関数自体は状態を持たない
std::string replaceForbiddenWords(
    const std::string& input,
    const std::vector<std::string>& forbiddenWords
)
{
    std::string result = input;

    for (const auto& word : forbiddenWords) {
        std::size_t pos = 0;

        while ((pos = result.find(word, pos)) != std::string::npos) {
            result.replace(pos, word.size(), "***");
            pos += 3; // "***" の長さだけ進める
        }
    }

    return result;
}
```

この段階でクラス化する理由は薄いです。
なぜなら、どの処理も「引数を受け取って結果を返すだけ」だからです。

---

## クラスへ昇格すべきタイミング

では、いつクラス化を考えるべきなのでしょうか。

答えは、**関数では表現しづらい責務が出てきた時**です。

具体的には、次のような状況です。

* 処理ごとに設定値を保持したい
* 毎回同じ依存関係を渡すのがつらい
* 初期化と後始末が必要になった
* 外部サービスや Logger などを抱える
* テストで差し替えたい
* 関数が長くなり、補助関数が増え始めた

このような状態になると、「ただの関数」では責務のまとまりが悪くなってきます。
そこで初めて、クラス化の利益がはっきりしてきます。

---

## クラスへ昇格した方がよい例

同じテキスト整形処理でも、次のような要求が追加されたとします。

* 禁止語辞書を毎回引数で渡したくない
* ログを出したい
* 置換ポリシーを切り替えたい
* テストでは Logger を偽物にしたい

こうなると、クラスの方が自然です。

```cpp
#include <algorithm>
#include <cctype>
#include <iostream>
#include <memory>
#include <string>
#include <vector>

// ログ出力のためのインターフェース
// 実運用ではファイル出力や別のLogger実装に差し替え可能
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& message) = 0;
};

// 単純なコンソール出力Logger
class ConsoleLogger : public ILogger {
public:
    void log(const std::string& message) override {
        std::cout << message << std::endl;
    }
};

// テキスト整形器
// 禁止語辞書やLoggerを「状態」として持つ
class TextSanitizer {
public:
    // コンストラクタで必要な依存関係を受け取る
    TextSanitizer(
        std::vector<std::string> forbiddenWords,
        std::shared_ptr<ILogger> logger
    )
        : forbiddenWords_(std::move(forbiddenWords))
        , logger_(std::move(logger))
    {
    }

    // 文字列を整形するメイン処理
    std::string sanitize(const std::string& input)
    {
        logger_->log("sanitize start");

        std::string result = trim(input);
        result = toLower(result);
        result = replaceForbiddenWords(result);

        logger_->log("sanitize end");
        return result;
    }

private:
    // このクラス専用の内部状態
    std::vector<std::string> forbiddenWords_;

    // このクラス専用の依存関係
    std::shared_ptr<ILogger> logger_;

    // クラス内部専用の補助処理
    std::string trim(const std::string& input)
    {
        std::size_t start = 0;
        while (start < input.size() && std::isspace(static_cast<unsigned char>(input[start]))) {
            ++start;
        }

        std::size_t end = input.size();
        while (end > start && std::isspace(static_cast<unsigned char>(input[end - 1]))) {
            --end;
        }

        return input.substr(start, end - start);
    }

    std::string toLower(const std::string& input)
    {
        std::string result = input;

        std::transform(
            result.begin(),
            result.end(),
            result.begin(),
            [](unsigned char c) {
                return static_cast<char>(std::tolower(c));
            }
        );

        return result;
    }

    // forbiddenWords_ を内部状態として使うので、関数群よりクラスの方が自然になる
    std::string replaceForbiddenWords(const std::string& input)
    {
        std::string result = input;

        for (const auto& word : forbiddenWords_) {
            std::size_t pos = 0;

            while ((pos = result.find(word, pos)) != std::string::npos) {
                result.replace(pos, word.size(), "***");
                pos += 3;
            }
        }

        return result;
    }
};
```

このケースなら、クラス化の理由をきちんと説明できます。

* 禁止語辞書という**状態**を持つ
* Logger という**依存関係**を持つ
* 内部 helper を **private** に閉じ込められる
* 差し替え可能な Logger を使うことで、テストしやすくなる

つまり、**クラスにしたことで明確な利益が生まれている**のです。

## 関数のままでよいケースと、クラスへ昇格すべきケース

判断基準を表にすると、次のようになります。

| 状況                     | 関数のままでよい | クラスへ昇格した方がよい | 理由                                  |
| ---------------------- | -------- | ------------ | ----------------------------------- |
| 処理が短い                  | ○        | -            | 1関数1責務で完結するなら関数で十分                  |
| 内部状態を持たない              | ○        | -            | 入力を受けて出力するだけならオブジェクト性が薄い            |
| 設定値が毎回引数で渡せる           | ○        | -            | 保持すべき値がない                           |
| 共通シグネチャで統一できる          | ○        | -            | 関数として扱いやすい                          |
| 処理を差し替える予定がまだない        | ○        | -            | 抽象インターフェースの利益がまだ薄い                  |
| 処理ごとに設定を持ちたい           | -        | ○            | 閾値やモードなどを保持したくなる                    |
| 外部依存を抱える               | -        | ○            | Logger、DB、Clock、APIクライアントなどを注入したくなる |
| 初期化と後始末が必要             | -        | ○            | ライフサイクル管理が出るとクラスが自然                 |
| 同じ処理群で内部 helper を共有したい | -        | ○            | private メソッドでまとめやすい                 |
| 実装差し替えを本気でやりたい         | -        | ○            | A/B実装や Mock 差し替えがしやすい               |
| テストで依存を偽物にしたい          | -        | ○            | DIしやすくなる                            |
| 関数が肥大化してきた             | -        | ○            | 長大化した関数は分解・責務整理が必要になる               |
| 単にパターン本で見た             | ○        | -            | それはクラス化の理由にならない                     |
| 将来使うかもしれない             | ○        | -            | “かもしれない”だけで抽象化すると外しやすい              |
| クラスの方が本格的に見える          | ○        | -            | これは設計理由ではない                         |

---

## 迷った時の判断フロー

迷ったら、次の順番で考えると整理しやすいです。

1. **その処理は状態を持つか**
2. **外部依存を抱えるか**
3. **初期化や後始末が必要か**
4. **差し替えや Mock 化が必要か**
5. **関数1本で読み切れるか**

このどれにも当てはまらないなら、まずは関数で始める方が安全です。

---

## レビューで使いやすい言い方

設計レビューで「なぜクラスなのか」「なぜ関数で十分なのか」を聞かれた時は、次のように言えると強いです。

### 関数のままにする理由

* この処理は状態を持たない
* 外部依存もない
* 1関数1責務で閉じている
* 差し替え要件もまだない
  → だから関数で十分

### クラスへ昇格する理由

* この処理は設定値や依存関係を保持する必要がある
* 初期化時に必要なものを受け取りたい
* 実装差し替えやテスト差し替えが必要
* 関数群として散らすより、1責務としてまとめた方が読みやすい
  → だからクラス化する

このように説明できれば、クラス化が「なんとなく」ではなく、**設計上の判断**になります。

---

## 一番避けたいこと

一番避けたいのは、次のような理由で先にクラス化してしまうことです。

* デザインパターンで見たことがある
* 将来必要になるかもしれない
* クラスの方が本格的に見える
* なんとなく設計っぽい

これらは、どれもクラス化の理由として弱いです。

そうやって作られたクラスは、たいてい次のようになります。

* 状態を持たない
* 依存も持たない
* 1メソッドしかない
* 実質ただの関数ラッパー

これでは、クラスにしたこと自体が目的化しています。

設計とは、形をなぞることではありません。
**必要な責務が出た時に、それを自然な形へまとめ直すこと**です。

---

## まとめ

最初から立派なクラスを作る必要はありません。
むしろ、最初は関数で始めた方が、コードは軽く、意図も明確になります。

そして次のような条件が揃ってきたら、そこで初めてクラスへの昇格を考えればよいです。

* 状態を持ちたい
* 外部依存を持ちたい
* 初期化や後始末が必要
* 差し替えやテストが必要
* 1つの責務として独立させた方が自然

つまり原則はシンプルです。

**関数で始めて、必要になったらクラスへ昇格させる。**

この順序を守るだけで、先回りの抽象化はかなり防げます。
Und結果として、コードは軽く、理由のある設計になります。
