# Part2. 全体再評価という考え方

前回、状態は`PathGenerationStatus`という列挙型で持つことにした。今回は「その状態を、いつ・どの範囲で計算し直すか」を考える。

## お題の確認

FolderA〜Eは自由な順番で入力できる。例えば、こんな順番もありうる。

```text
1. Bを入力
2. Dを入力
3. Aを入力
```

## 質問1

素直に考えると、「入力欄が変更されたら、その入力欄の生成処理を呼ぶ」という設計になりそうだ。

```csharp
private void TextBoxB_Leave(object sender, EventArgs e)
{
    TryGenerateFilePath(FolderKey.B);
}
```

この設計で、上の「B→D→A」という順番の入力を追いかけてみてほしい。それぞれのタイミングで何が起きるか、そしてAを入力し終わった時点でBとDの生成結果はどうなっているか、考えてみよう。

---

1. Bを入力 → `TryGenerateFilePath(B)`が呼ばれる。しかしAがまだ空なので生成できない。Bは「A待ち」のまま
2. Dを入力 → `TryGenerateFilePath(D)`が呼ばれる。同様に「A待ち」のまま
3. Aを入力 → `TryGenerateFilePath(A)`が呼ばれる。Aは生成できる。**しかし、BとDの再生成は誰が呼ぶのか？**

「入力欄ごとに自分の生成処理だけを呼ぶ」設計だと、Aが入力されたタイミングでBとDを再生成する処理をどこかに書き足す必要がある。つまり、

```csharp
private void TextBoxA_Leave(object sender, EventArgs e)
{
    TryGenerateFilePath(FolderKey.A);

    // Aに依存しているB, C, D, Eも再生成しないといけない
    TryGenerateFilePath(FolderKey.B);
    TryGenerateFilePath(FolderKey.C);
    TryGenerateFilePath(FolderKey.D);
    TryGenerateFilePath(FolderKey.E);
}
```

## 質問2

このコード、今は正しく動く。だが、将来「FolderCもFolderBに依存する」というルールが追加されたら、どこを直す必要があるだろうか？

---

`TextBoxB_Leave`の中にも「Bが変わったらCも再生成する」という行を追加する必要が出てくる。つまり、**依存関係が増えるたびに、あちこちのイベントハンドラに再生成の呼び出しを追記して回る**ことになる。これは典型的な「直し忘れ」の温床である。1箇所直し忘れると、画面には古い生成結果が表示され続けるが、見た目には何のエラーも出ない。バグとして非常に見つけにくい。

## 発想の転換：「差分を追いかける」のをやめる

「どの入力欄が変わったから、どの結果を更新すべきか」を追いかける代わりに、こう考え方を変える。

```text
入力欄が変更された
     ↓
現在のA〜Eの入力状態を確認する
     ↓
A〜E全部を、依存関係に従って評価し直す
     ↓
条件を満たしているものだけ生成し、
満たしていないものは「A待ち」のまま維持する
```

どの入力欄が変わったかは、実はもう気にしなくてよい。「今の入力状態全体」を毎回まるごと評価し直せば、直し忘れは原理的に起こらない。

```csharp
private void OnAnyFolderPathChanged()
{
    // Viewの現在値をモデルへ反映
    SyncFromView();

    // A〜E全体を再評価する
    _evaluator.Recalculate(_model);

    RefreshView();
}
```

イベントハンドラは全部この1つのメソッドを呼ぶだけになる。TextBoxA、B、C、D、Eの`Leave`イベント、どれも同じ処理を呼べばよい。

## 「全部作り直す」という言葉の誤解を解いておく

ここで注意したいのは、「全体を再評価する」は「無条件に全部の生成処理を実行する」という意味ではない、ということ。

```text
悪い全体再評価:
  A〜Eの入力状況を無視して、
  毎回A〜Eの結果を無理やり全部作る

今回採用する全体再評価:
  A〜Eの現在の入力状況をすべて確認し、
  条件（Aが有効かどうか）を満たしたものだけ再生成する
```

例えばFolderCが空欄なら、`Recalculate`を呼んでもCの結果は「未入力」のまま変わらない。無駄な生成処理は起きない。「毎回チェックし直す」のであって、「毎回作り直す」わけではない。

## 「差分更新の方が効率的では？」への回答

差分だけ更新する方が処理量は少なく見える。しかし今回はA〜Eの5件しかなく、それぞれの生成処理も文字列の組み立て程度の軽い処理である。この規模なら、全体再評価のコストは無視できる。

一方で、差分更新には「依存関係の伝播漏れ」という重いバグのリスクがある。**処理速度の些細な差より、直し忘れによるバグの方がずっと高くつく。** これが今回、全体再評価を選ぶ理由である。

## この回のまとめ

- 「変更された入力欄だけを処理する」設計は、依存関係が増えるたびに直し忘れが起きやすい
- 「入力欄が変わるたびに、全体を依存関係に従って評価し直す」設計にすると、直し忘れが原理的に起きなくなる
- 「全体を再評価する」は「無条件に全部作り直す」という意味ではない。条件を満たしたものだけ生成する
- 対象件数が少ない（今回は5件）なら、全体再評価のコストは気にしなくてよい
