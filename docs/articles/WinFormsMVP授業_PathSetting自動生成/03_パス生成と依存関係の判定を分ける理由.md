# Part3. パス生成と依存関係の判定を分ける理由

前回、「入力欄が変わるたびに、A〜E全体を評価し直す」という方針に決めた。今回は、その「評価し直す」処理の中身を実装してみる。

## 素直に書いてみる

`Recalculate`というメソッドに、思いつくまま処理を書いてみる。

```csharp
public class FilePathGenerationService
{
    public void Recalculate(PathSettingModel model)
    {
        // Aを評価
        if (string.IsNullOrWhiteSpace(model.A.FolderPath))
        {
            model.A.SetNotEntered();
        }
        else
        {
            model.A.Apply(Path.Combine(model.A.FolderPath, "a-data.csv"));
        }

        // Bを評価（Aに依存）
        if (string.IsNullOrWhiteSpace(model.B.FolderPath))
        {
            model.B.SetNotEntered();
        }
        else if (string.IsNullOrWhiteSpace(model.A.FolderPath))
        {
            model.B.SetWaitingForA();
        }
        else
        {
            model.B.Apply(Path.Combine(model.A.FolderPath, model.B.FolderPath, "b-data.csv"));
        }

        // C, D, Eも同様に続く…
    }
}
```

動く。要件も満たしている。しかし、このクラスの名前は`FilePathGenerationService`だった。

## 質問1

このクラスの中で、実際に行われていることを2種類に分けるとしたら、どう分けられるだろうか。

---

分けるとこうなる。

```text
① パスの組み立て
   Path.Combine(a, b, "b-data.csv") のような、文字列操作

② 依存関係の判定
   「Bを生成する前に、Aが入力済みかどうかを確認する」
   というこの画面固有のルール
```

①は「2つの文字列から1つのパスを作る」という、汎用的でシンプルな処理。②は「Aが親で、B〜Eが子である」という、**この画面・この業務にしか存在しない知識**である。

## なぜ混ぜるとまずいのか

`FilePathGenerationService`という名前は「パスを生成するサービス」という意味のはずだ。しかし実際にはこのクラスは次のことまで知っている。

```text
・A〜Eの入力状態はどうなっているか
・AとB〜Eの間に依存関係がある
・依存関係が満たされていないときはどう振る舞うべきか
・各項目の状態をどう遷移させるべきか
・パスの組み立て方
```

名前と実態がずれている。この状態を放置すると、次に何が起きるか考えてみてほしい。

たとえば「FileB/FileD検証は、Aの他にF（新しく増えた入力欄）にも依存する」という仕様変更が入ったとする。この変更をするには、`FilePathGenerationService`の中の依存関係判定部分を触ることになる。しかし、このクラスは「パス生成サービス」という名前でチームに認識されているので、他のメンバーは「パス生成のバグかな」と思って調べに来る。実際に触るべきは依存関係のロジックなのに、名前がそれを教えてくれない。

**クラス名は「このクラスが何を知っていて、何をする責任があるか」を示す看板である。** 看板と中身が食い違っていると、後で読む人（未来の自分を含む）を迷わせる。

## 分離する

2つの責務を、それぞれ別のクラスに分ける。

```csharp
// ① パスを組み立てるだけ。A〜Eの依存関係は一切知らない
public interface IFilePathGenerationService
{
    PathGenerationResult GenerateA(string folderPath);
    PathGenerationResult GenerateDependent(string folderPathA, string dependentFolderPath, PathType pathType);
}
```

```csharp
// ② A〜Eの依存関係を判定する。実際のパス組み立てはIFilePathGenerationServiceに委譲する
public class PathSettingEvaluator
{
    private readonly IFilePathGenerationService _generationService;

    public PathSettingEvaluator(IFilePathGenerationService generationService)
    {
        _generationService = generationService;
    }

    public void Recalculate(PathSettingModel model)
    {
        EvaluateA(model.A);
        EvaluateDependent(model.A, model.B, PathType.B);
        EvaluateDependent(model.A, model.C, PathType.C);
        EvaluateDependent(model.A, model.D, PathType.D);
        EvaluateDependent(model.A, model.E, PathType.E);
    }

    private void EvaluateDependent(PathGenerationItem a, PathGenerationItem dependent, PathType pathType)
    {
        if (string.IsNullOrWhiteSpace(dependent.FolderPath))
        {
            dependent.SetNotEntered();
            return;
        }

        if (a.Status != PathGenerationStatus.Success)
        {
            dependent.SetWaitingForA();
            return;
        }

        var result = _generationService.GenerateDependent(a.FolderPath, dependent.FolderPath, pathType);
        dependent.Apply(result);
    }

    // EvaluateAは省略（Aは依存先がないので単純）
}
```

## 質問2

この分離によって、`IFilePathGenerationService`をテストするとき、何が要らなくなっただろうか？

---

`IFilePathGenerationService`は「AとBの2つのフォルダパス文字列から、1本のパスを組み立てられるか」だけをテストすればよくなる。**A〜Eという画面構造も、依存関係も、状態遷移も一切知らなくてよい。** 逆に`PathSettingEvaluator`をテストするときは、`IFilePathGenerationService`を差し替え可能なので、「Aが未入力ならBはWaitingForAになる」という依存関係のルールだけを、実際のパス組み立てロジックと無関係にテストできる。

責務を分けると、**テストする対象が小さくなり、何を確認しているかが明確になる。** これは「クラス数が増えて面倒になる」というコストを補って余りある利点である。

## この回のまとめ

- 1つの処理の中に「汎用的な処理」と「この画面固有のルール」が混ざっていないか、意識して見る
- クラス名は責務の看板である。名前と実態がずれると、次に触る人（未来の自分）を迷わせる
- 「パスを組み立てる」（`IFilePathGenerationService`）と「依存関係を判定する」（`PathSettingEvaluator`）は別の関心事なので、別クラスに分ける
- 分離すると、それぞれを独立してテストできるようになる
