# WinFormsアプリの設計ドキュメントをどう書くか

クラス図・クラス設計表・コントロール表の使い分け

C# WinForms でデスクトップアプリを設計するとき、クラス図をどこまで書けばいいか迷うことがある。

コントロールも全部書こうとするとごちゃごちゃになる。  
かといって省略すると実装漏れが起きる。

この記事では、クラス図と表形式を組み合わせた現実的な設計ドキュメントの書き方を整理する。

---

## 基本方針：層ごとに書き方を分ける

WinForms アプリは大きく2つの層に分かれる。

- **ロジック層**：`Service`、`Repository`、モデルクラスなど
- **UI層**：フォーム、コントロール、イベントハンドラ

この2つは性質が違うので、同じ形式で書こうとするから無理が生じる。

```
① クラス図          → ロジック層の構造・依存関係（全体把握用）
② クラス設計表      → ロジック層の publicメソッドを中心に整理
③ フォーム・コントロール表 → UI層の実装漏れ防止
```

この3点セットで、「クラス図がごちゃごちゃになる問題」と「実装漏れ問題」を両方カバーできる。

---

## ① クラス図：ロジック層だけ書く

クラス図にはビジネスロジック層を書く。コントロールは出さない。

```
MainForm ──uses──> PlayerService
MainForm ──uses──> InventoryService

PlayerService ──uses──> PlayerRepository
```

フォームとロジック層の接続点だけ矢印で示して、コントロールの詳細は後述の表に任せる。  
これだけでクラス図はかなりスッキリする。

---

## ② クラス設計表：設計フェーズ版

設計フェーズではまだ型や引数の詳細が決まっていないことが多い。  
この段階では **「何をするメソッドが必要か」を洗い出す** のが目的なので、役割の列が最重要だ。

**`PlayerService`**

| メソッド名 | 修飾子 | 引数（仮） | 役割 |
| :--- | :--- | :--- | :--- |
| Save | public | Player | プレイヤー情報を保存する |
| Load | public | id | IDを元にプレイヤーを取得する |
| Delete | public | id | プレイヤーを削除する |
| Validate | private | Player | 保存前のバリデーション |

**`InventoryService`**

| メソッド名 | 修飾子 | 引数（仮） | 役割 |
| :--- | :--- | :--- | :--- |
| AddItem | public | item | アイテムをインベントリに追加する |
| RemoveItem | public | itemId | アイテムを削除する |
| GetAll | public | - | 所持アイテム一覧を返す |
| CheckCapacity | private | - | 所持上限チェック |

### 引数・戻り値はどこまで書くか

設計フェーズでは引数は「あるかも」程度でいい。型も仮で構わない。`-` でも問題ない。  
実装中に変わることを前提に、**仮と明記しておく**と後から見たときに混乱しない。

アクセス修飾子は設計段階でもある程度決まるので書いておくと実装時の迷いが減る。  
`private` メソッドを書くかどうかは好みが分かれるが、「内部でこういう処理が必要そう」という洗い出しとして書いておくと抜け漏れに気づきやすい。

### 戻り値・型は実装後に足す

戻り値の型や正確な引数型は実装後に確定するので、必要であれば列を追加すればいい。

| メソッド名 | 修飾子 | 引数 | 戻り値 | 役割 |
| :--- | :--- | :--- | :--- | :--- |
| Save | public | Player player | void | プレイヤー情報を保存する |
| Load | public | int id | Player? | IDを元にプレイヤーを取得する |

この形は「設計書」というより**実装後のリファレンス**として機能する。  
個人開発や小規模チームなら IntelliSense やコード自体が代替してくれるので、必要に応じて判断すればいい。

## ③ フォーム・コントロール表：UI層の実装漏れ防止

コントロールの詳細はこちらの表でカバーする。  
そのままコードレビューのチェックリストにもなる。

**フォーム一覧**

| フォーム名 | 役割 | 開くタイミング |
| :--- | :--- | :--- |
| MainForm | メイン画面 | 起動時 |
| SettingsForm | 設定画面 | メニュー→設定 |

**コントロール一覧（`MainForm`）**

| コントロール名 | 種類 | 役割 | 呼ぶメソッド |
| :--- | :--- | :--- | :--- |
| btnSave | Button | 保存ボタン | PlayerService.Save |
| txtPlayerName | TextBox | 名前入力欄 | - |
| lstInventory | ListBox | 所持アイテム一覧表示 | InventoryService.GetAll |

---

## まとめ

| ドキュメント | 対象 | タイミング | 目的 |
| :--- | :--- | :--- | :--- |
| クラス図 | ロジック層 | 設計フェーズ | 構造と依存関係の把握 |
| クラス設計表 | ロジック層のメソッド | 設計フェーズ | 必要な処理の洗い出し |
| フォーム・コントロール表 | UI層 | 設計フェーズ | 実装漏れ防止 |
| 型・戻り値を加えた設計表 | ロジック層 | 実装後（任意） | チーム向けリファレンス |

設計フェーズで最も重要なのは**役割の列**だ。  
「このメソッドは何をするのか」を言語化する過程で、設計ミスや抜け漏れが見つかることが多い。  
型や修飾子の正確さより、役割が明確かどうかを優先して書くと設計書として機能しやすい。
