# C++で定数はどこに定義すべきか

スコープから考える、最も自然な置き場所の決め方

C++でコードを書いていると、定数をどこに置くべきかで迷うことがあります。

たとえば、次のようなパターンを見たことがあるはずです。

* ヘッダファイルの上の方に定義する
* クラス内に `static constexpr` として置く
* 関数の中にローカル定数として置く
* 名前空間にまとめる
* `#define` で書く

どれも「動く」ことはありますが、問題はそこではありません。
本当に考えるべきなのは、**その定数がどの範囲で使われるものなのか** です。

結論から言うと、C++で定数の置き場所を決めるときの基本原則はシンプルです。

> **定数は、使う範囲が最小になる場所に置くべきです。**

これが最も重要です。
この記事では、その考え方を整理しながら、どのケースでどこに置くのが自然なのかを解説します。

---

## 1. まず結論

最初に判断基準を示します。

**定数の置き場所の基本ルール**

* その関数の中でしか使わない → 関数内に置きます
* そのクラスの複数のメンバ関数で使う → クラス内の `private static constexpr` などで置きます
* クラス外からも共有したい → 名前空間にまとめて置きます
* プロジェクト全体で使う共通定数である → 専用のヘッダに、名前空間つきで整理して置きます

この判断基準だけで、かなり迷いが減ります。

---

## 2. なぜ「置ける場所」ではなく「使う範囲」で考えるべきなのか

C++では、定数をいろいろな場所に置けます。
しかし、置けるからといって、そこが適切とは限りません。

たとえば、ある `private` 関数の中でしか使わない文字列定数を、ヘッダの先頭に書いてしまうとします。

```cpp
#pragma once
#include <string_view>

inline constexpr std::string_view TYPE_A = "A";
inline constexpr std::string_view TYPE_B = "B";

class MyClass {
private:
    void Process(const std::string& type);
};
```

これは動くかもしれませんが、設計としてはあまり良くありません。
なぜなら、この定数は `Process` 関数でしか使わないのに、ファイル全体に見える場所へ露出しているからです。

このような書き方には、次の問題があります。

* スコープが広すぎます
* どこで使う定数なのかがわかりにくくなります
* 「クラス全体の概念」なのか「関数ローカルの都合」なのかが曖昧になります
* 将来コードを読む人が追いにくくなります

つまり、定数の置き場所は「技術的に置けるか」ではなく、**意味的にどこに属するか** で決めるべきです。

---

## 3. 一番小さい単位で閉じるのが基本です

### 3-1. その関数でしか使わないなら、関数内が最適です

たとえば、`if` 分岐の比較に使う文字列定数が、ある `private` 関数の中でしか使われないとします。
この場合、最も自然なのは関数の中に置くことです。

```cpp
#include <string>
#include <string_view>

class MyClass {
private:
    void Process(const std::string& type) {
        constexpr std::string_view TYPE_A = "A";
        constexpr std::string_view TYPE_B = "B";
        constexpr std::string_view TYPE_C = "C";

        if (type == TYPE_A) {
            // Aの処理です
        } else if (type == TYPE_B) {
            // Bの処理です
        } else if (type == TYPE_C) {
            // Cの処理です
        } else {
            // その他の処理です
        }
    }
};
```

この形の良いところは明確です。

* その関数だけを読めば定数の意味がわかります
* 不要に外へ露出しません
* クラス全体の知識にしなくて済みます
* 将来その関数を削除したときに、定数も一緒に消せます

このように、**関数専用の定数は関数の中に閉じる** のが基本です。

---

## 4. クラス内で共有するなら、クラスに属させます

### 4-1. 複数の private 関数で同じ定数を使う場合

関数ごとに同じ定数を何度も書くのは冗長です。
その場合は、クラス内に定数を上げるのが自然です。

```cpp
#include <string>
#include <string_view>

class MyClass {
private:
    static constexpr std::string_view TYPE_A = "A";
    static constexpr std::string_view TYPE_B = "B";
    static constexpr std::string_view TYPE_C = "C";

    void Process1(const std::string& type) {
        if (type == TYPE_A) {
            // 処理1です
        }
    }

    void Process2(const std::string& type) {
        if (type == TYPE_B) {
            // 処理2です
        }
    }
};
```

この場合、これらの定数は「関数ローカルな都合」ではなく、`MyClass` というクラスの内部ルールになっています。
そのため、`private static constexpr` に置く意味があります。

ここで大事なのは、**クラスに属する理由があるかどうか** です。
単に「見た目を整理したいから」という理由でクラス上部に持ち上げるのは弱いです。
複数箇所で使う、またはクラス全体の概念として意味がある場合に限って上げるべきです。

---

## 5. クラス外でも使うなら、名前空間に出します

クラスをまたいで共有する定数は、クラスに閉じ込めるべきではありません。
そういう定数は、名前空間にまとめるのが自然です。

```cpp
#pragma once
#include <string_view>

namespace app::constants {
    inline constexpr std::string_view ConfigFile = "config.json";
    inline constexpr std::string_view LogFile    = "app.log";
}
```

使う側はこうなります。

```cpp
#include "constants.h"
#include <iostream>

int main() {
    std::cout << app::constants::ConfigFile << "\n";
}
```

この形の利点は、定数が「どこに属するものか」がわかりやすいことです。
また、クラスの責務を不必要に増やさずに済みます。

---

## 6. 「とりあえずヘッダに置く」は危険です

実務でも、ヘッダの上の方に定数を書いているコードはよく見かけます。
しかし、それが適切とは限りません。

たとえば次のような書き方です。

```cpp
#pragma once
#include <string_view>

inline constexpr std::string_view MODE_READ  = "read";
inline constexpr std::string_view MODE_WRITE = "write";
```

これは共有定数であれば問題ありません。
しかし実際には、「ある1つのクラスの中の、ある1つの関数でしか使っていない」ということがよくあります。

その場合、ヘッダ上部に置くのはスコープが広すぎます。
コードを書いている本人は「整理したつもり」でも、読んでいる側からすると「この定数は誰のものなのか」が不明瞭になります。

つまり、定数を上の方に置くこと自体が整理ではありません。
**本当に整理されているコードとは、定数が必要な場所に、必要な範囲だけ見える形で置かれているコードです。**

---

## 7. `#define` は基本的に避けるべきです

昔のC/C++コードでは、定数を `#define` で書くことがよくありました。

```cpp
#define TYPE_A "A"
#define TYPE_B "B"
```

今のC++では、これは基本的に避けるべきです。

理由は次の通りです。

* 型がありません
* スコープがありません
* デバッガで追いにくいです
* 名前衝突しやすいです
* 単なる文字列置換なので安全性が低いです

C++には `constexpr`、`const`、`static constexpr`、`inline constexpr` など、より安全で意味の明確な方法があります。
特別な事情がない限り、定数定義に `#define` を選ぶ理由はほとんどありません。

---

## 8. 文字列定数なら `std::string_view` が無難です

文字列定数を定義するときに、`std::string` を使うべきか迷うことがあります。
しかし、固定文字列の比較用定数であれば、まずは `std::string_view` を考えるのが自然です。

```cpp
constexpr std::string_view TYPE_A = "A";
```

これは文字列リテラルを参照しているだけなので、比較用の定数として扱いやすいです。

一方、次のような書き方は、必要以上に重くなりやすいです。

```cpp
const std::string TYPE_A = "A";
```

もちろん、動的に文字列を扱いたい場面では `std::string` が必要です。
しかし、「ただの固定文字列定数」であれば、`std::string_view` の方が意図に合っています。

---

## 9. 判断に迷ったときの実践ルール

実務で迷ったときは、次の順番で考えると判断しやすいです。

### 9-1. その定数は何か

* 単なる比較用文字列なのか
* 数値コードなのか
* クラスのルールなのか
* アプリ全体の共有設定なのか

### 9-2. どこで使うか

* 1つの関数だけか
* 同じクラスの複数関数か
* 複数クラスか
* プロジェクト全体か

### 9-3. 最小スコープに閉じられるか

* 関数内に置けるなら、まず関数内を検討します
* 関数内では重複するなら、クラス内へ上げます
* クラスをまたぐなら、名前空間へ出します

この考え方に従えば、「とりあえずヘッダの上に置く」ような雑な設計を避けやすくなります。

---

## 10. 具体的な使い分けの早見表

**関数内でしか使わない**

```cpp
void Process(const std::string& type) {
    constexpr std::string_view TYPE_A = "A";
    constexpr std::string_view TYPE_B = "B";
}
```

**クラス内の複数関数で使う**

```cpp
class MyClass {
private:
    static constexpr std::string_view TYPE_A = "A";
    static constexpr std::string_view TYPE_B = "B";
};
```

**クラス外でも共有する**

```cpp
namespace app::constants {
    inline constexpr std::string_view TYPE_A = "A";
    inline constexpr std::string_view TYPE_B = "B";
}
```

---

## 11. 結論

C++で定数をどこに定義するべきかという問いに対して、唯一の絶対解があるわけではありません。
しかし、判断の軸ははっきりしています。

> **定数は、使う範囲が最小になる場所に置くべきです。**

この原則に従えば、次のように整理できます。

* 関数専用なら関数内
* クラス内部で共有するならクラス内
* クラス外でも使うなら名前空間
* 広く共有するなら専用ヘッダで整理

逆に言うと、これ以上でもこれ以下でもありません。
「どこに置くと見た目が整うか」ではなく、**その定数がどこに属するものか** を基準に判断するべきです。

定数定義は小さな話に見えますが、ここが雑だとコード全体の責務がぼやけます。
逆に、定数のスコープを丁寧に決めるだけで、コードの読みやすさと保守性はかなり変わります。

C++では文法の選択肢が多い分、迷いやすいです。
だからこそ、「使う範囲が最小になる場所に置く」という原則を基準にすると、設計がぶれにくくなります。
