# LNK2019 リンカエラーの構造と診断

Visual Studio で `#include` が通っているのにビルドが失敗する。エラーコードは `LNK2019`。
これはコンパイルエラーではなくリンカエラーだ。2 つは根本的に別の問題を指している。

この記事でその構造を解剖し、素早く原因を絞り込む診断手順を整理する。

> `インスタンス生成と初期化.md` 第3章で扱った「クラス外定義のときは `クラス名::` をつける」と
> 表裏一体の知識。そちらと合わせて読むと分割コンパイルの全体像がつかめる。

---

## 第1章：コンパイルとリンクは別のフェーズである

C++ のビルドは **2 段階**で動いている。

```
[コンパイル]  各 .cpp → .obj（オブジェクトファイル）
[リンク]      全 .obj → .exe（実行ファイル）
```

`#include` は **コンパイル段階**の操作だ。ヘッダに書かれた宣言をコンパイラに読み込ませる。
リンク段階でやっと、各 `.obj` の中に「宣言に対応する実装」が存在するかが照合される。

### エラーの種類で発生フェーズが分かれる

| | `cannot open include file` | `LNK2019` |
| :--- | :--- | :--- |
| 発生フェーズ | コンパイル | リンク |
| 意味 | `.h` ファイルが見つからない | 実装（`.cpp`）がリンク時に見つからない |
| 典型的な原因 | インクルードパスの設定ミス | `.cpp` がビルド対象に入っていない、またはシグネチャ不一致 |

`LNK2019` が出ているなら、**ヘッダは見つかっている**。コンパイルは通っている。
問題はその先——リンカが実装を探せない——にある。

> **ポイント：**
> `#include` は「宣言を読む」指示であって「実装を探す」指示ではない。
> リンカが初めて実装を探しに行く。

---

## 第2章：`.cpp` ファイルはプロジェクトへの登録が必要

### 「フォルダにある = ビルドされる」は誤解

Visual Studio の C++ プロジェクトは、`.vcxproj` ファイルに登録されている `.cpp` だけをコンパイルする。
フォルダに `.cpp` を置いただけでは、プロジェクトはその存在を知らない。

```
// 内部では .vcxproj がこのような形でファイルを管理している
<ClCompile Include="ItemBox.cpp" />   ← これがなければビルドされない
```

### 手動でファイルを移動するとどうなるか

Finder や Explorer でファイルを移動した場合、`.vcxproj` は**古いパスを持ったまま**になる。
ソリューションエクスプローラーで赤い感嘆符が付いているファイルがあれば、これが原因だ。

**修正手順：**

1. ソリューションエクスプローラーで対象の `.cpp` を右クリック → **「削除」**
   （ディスクからファイルは消えない。プロジェクトの管理対象から外れるだけ）
2. プロジェクトを右クリック → **「追加」→「既存の項目」**
3. 移動先の正しい場所にある `.cpp` を選択して追加
4. ビルドし直す

### `.cpp` は `#include` するものではない

これも LNK2019 の原因になり得る誤解だ。

```cpp
// main.cpp

#include "ItemBox.h"    // OK：ヘッダをインクルードする
// #include "ItemBox.cpp"  // NG：.cpp をインクルードしてはいけない
```

```cpp
// ItemBox.cpp（プロジェクトに登録されていれば自動でビルドされる）

#include "ItemBox.h"
#include <iostream>

void ItemBox::print() const
{
    std::cout << name_ << "\n";
}
```

`.cpp` はプロジェクトに「登録する」もの。`#include` で引き込むものではない。

> **ポイント：**
> `.cpp ファイルはビルド対象として登録するもの。`#include` するものではない。`

## 第3章：シグネチャの不一致も LNK2019 を起こす

`.cpp` がプロジェクトに正しく登録されていても LNK2019 が出る場合がある。
ヘッダの宣言と `.cpp` の定義でシグネチャが 1 文字でも違うと、リンカには**別のシンボル**に見える。

### `const` の有無が典型的な罠

```cpp
// ItemBox.h
class ItemBox
{
public:
    void print() const;   // const あり
};
```

```cpp
// ItemBox.cpp
#include "ItemBox.h"
#include <iostream>

void ItemBox::print()     // const が抜けている → 別のシンボル
{
    std::cout << name_ << "\n";
}
```

コンパイラは宣言（ヘッダ）と定義（`.cpp`）を**別々に見る**。
「`print() const` の宣言はある。でも `print() const` の実装がない」——これが LNK2019 の正体だ。

### namespace のズレも同じ結果になる

```cpp
// ItemBox.h
namespace game
{
    class ItemBox
    {
    public:
        void print() const;
    };
}
```

```cpp
// ItemBox.cpp（NG）
#include "ItemBox.h"
#include <iostream>

void ItemBox::print() const    // namespace game が抜けている
{
    std::cout << name_ << "\n";
}
```

```cpp
// ItemBox.cpp（正しい）
#include "ItemBox.h"
#include <iostream>

namespace game
{
    void ItemBox::print() const
    {
        std::cout << name_ << "\n";
    }
}
```

ヘッダで `namespace game` に包まれた関数は、実装側でも `namespace game` の中に書かなければならない。

### シグネチャ不一致パターンのまとめ

| 不一致の種類 | ヘッダの宣言 | `.cpp` の定義（NG） |
| :--- | :--- | :--- |
| `const` 抜け | `void print() const;` | `void ItemBox::print()` |
| `const` 過剰 | `void print();` | `void ItemBox::print() const` |
| namespace 抜け | `namespace game { ... }` | `void ItemBox::print() const` |
| 引数型の違い | `void set(int n);` | `void ItemBox::set(std::size_t n)` |

> **ポイント：**
> コンパイルが通っても「シグネチャが正しい」とは限らない。
> コンパイラは宣言と定義を別々に見る。リンカが初めて両者を照合する。

## 第4章：診断フローチャート

`LNK2019` のエラー文には、**未解決のシンボル名**が含まれている。

```
error LNK2019: 未解決の外部シンボル
    "public: void __cdecl game::ItemBox::print(void)const"
    が関数 _main で参照されました
```

これを見れば「`const` 付きの `print` が見つからない」とすぐ読める。
その上で、次の順に確認する。

```
ビルドエラーが出た
│
├── "cannot open include file"
│   → ヘッダのパス問題
│       └── プロジェクトプロパティ → C/C++ → 追加のインクルードディレクトリを確認
│
└── LNK2019
    │
    ├── ソリューションエクスプローラーで .cpp を確認
    │   │
    │   ├── 赤い感嘆符が出ている
    │   │   → ファイルが移動されて参照が切れている
    │   │       └── 「削除」→「追加」→「既存の項目」で新しい場所を指定
    │   │
    │   ├── ファイルが見えていない
    │   │   → .cpp がプロジェクトに未登録
    │   │       └── 「追加」→「既存の項目」で .cpp を追加
    │   │
    │   └── ファイルが正常に見えている → プロパティを確認
    │           .cpp を右クリック → プロパティ
    │           ・「ビルドから除外」= いいえ  になっているか
    │           ・「項目の種類」= C/C++ コンパイラ  になっているか
    │
    └── .cpp の登録は問題なし → シグネチャ不一致を疑う
            ヘッダの宣言と .cpp の定義を並べて比較する
            ・const の有無
            ・namespace の有無
            ・引数の型
            ・クラス名のスコープ（ClassName:: が付いているか）
```

## 第5章：正しいメンタルモデルの定着

3 ファイルの役割を整理すると、混乱の多くは解消される。

| ファイル | 役割 | `#include` するか |
| :--- | :--- | :--- |
| `ItemBox.h` | クラスの**宣言**（何があるか） | する（`ItemBox.cpp` と `main.cpp` の両方から） |
| `ItemBox.cpp` | クラスの**定義**（どう動くか） | しない（プロジェクト登録でビルド対象になる） |
| `main.cpp` | エントリポイント | `ItemBox.h` をインクルードする |

### リンカの仕事

リンカは各 `.obj` ファイルを見て、「宣言されたシンボルの実装がどこかにあるか」を照合する。
`.cpp` がプロジェクトに登録されていなければ `.obj` が作られず、リンカは実装を発見できない。

> **ポイント：**
> `.h` = 宣言（何があるか）／`.cpp` = 定義（どう動くか）。
> リンカの仕事は定義を探すこと。`#include` はリンカに何も伝えない。

なお、`.cpp` を `#include` すると同じ定義が複数の翻訳単位に入り、別のリンクエラーを引き起こす。
これは **One Definition Rule（ODR）** の違反だ。ODR とビルド全体の体系については `roadmap.md` で整理する予定。

## 理解度チェック

### 問1

次の 2 つのエラーのうち、LNK2019 はどちらか。それぞれの原因の違いも答えてほしい。

```
エラーA:
fatal error C1083: インクルード ファイルを開けません。
'ItemBox.h': No such file or directory

エラーB:
error LNK2019: 未解決の外部シンボル
"public: void __thiscall ItemBox::print(void)const"
が関数 _main で参照されました。
```

---

**正解：**

LNK2019 は**エラーB**だ。

エラーA はコンパイルエラー。`ItemBox.h` というファイルがインクルードパス上に見つからない。
エラーB はリンクエラー。ヘッダは見つかりコンパイルは通ったが、`print() const` の実装がリンク時に見つからない。

2 つはフェーズも原因も診断方法も異なる。

---

### 問2

次のコードで LNK2019 が発生している。原因を特定し、修正方法を答えてほしい。

```cpp
// Player.h
class Player
{
public:
    void takeDamage(int amount);
};
```

```cpp
// Player.cpp
#include "Player.h"

void Player::takeDamage(int amount) const   // ← 注目
{
    hp_ -= amount;
}
```

---

**正解：**

ヘッダの宣言は `void takeDamage(int amount);`（`const` なし）だが、
`.cpp` の定義は `void Player::takeDamage(int amount) const`（`const` あり）になっている。

リンカにとって 2 つは別のシンボルであるため、宣言が求める `takeDamage(int)` の実装が見つからず LNK2019 になる。

修正は `.cpp` の `const` を取り除き、宣言と定義のシグネチャを一致させる。

```cpp
void Player::takeDamage(int amount)   // const を除去
{
    hp_ -= amount;
}
```

### 問3

`ItemBox.cpp` をフォルダ `src/Item/` から `src/` 直下に Finder で移動した後、
Visual Studio でビルドしたら LNK2019 が出た。何が起きていて、どう直せばよいか。

---

**正解：**

Visual Studio の `.vcxproj` は `src/Item/ItemBox.cpp` というパスを記録していたが、
ファイルが `src/ItemBox.cpp` に移動したため参照が壊れた。
コンパイル時に `ItemBox.cpp` がビルド対象として処理されなくなり、実装が消えた状態になっている。

ソリューションエクスプローラーには赤い感嘆符が出ているはずだ。

**修正手順：**
1. ソリューションエクスプローラーで `ItemBox.cpp`（赤い感嘆符）を右クリック → **「削除」**
2. プロジェクトを右クリック → **「追加」→「既存の項目」**
3. 移動先の `src/ItemBox.cpp` を選択して追加
