# AIが書いた技術文書の「嘘になる単純化」を見抜く品質レビュー

〜 9回分の研修スライドを作る中で、実際にレビューで直した箇所から作ったレビュー手法 〜

> **この資料の位置づけ**
> 今期目標②「AI活用のノウハウ資料作成」の1件目。テーマは **ドキュメント作成（品質レビュー）**。
> 要件定義の作り方は別資料（別プロジェクトのアプリを題材）で扱う。
>
> **根拠の出どころ**：本リポジトリの git 履歴（`docs/goal_management/slides/` の初稿→FIXコミット）と、レビュー規約 `docs/goal_management/slide_design_guidelines.md` §8。
> 文中のコミットID（`2eca03e` など）は `git show <ID>` で差分を確認できる。

---

## 1. 何が問題なのか

生成AIに技術文書や研修資料を書かせると、**読みやすく、自信ありげで、そして時々ちょっと嘘**になる。

特に初心者向け資料では、「分かりやすくする単純化」が、いつの間にか **「実装上の事実」として断定される** ことが起きる。

| AIが書きがちな文 | 何が問題か |
|---|---|
| 「`counter++` は CPU が実際に3つのステップで実行している」 | 説明用のモデルを、実機の事実として言い切っている |
| 「プロセスAとBの `0x1000` は全く別の物理メモリに変換されている」 | 共有メモリなど例外があるのに「常に」と読める |
| 「`delete` 後も実行するとアドレス値はそのまま残っている」 | 手元で動いた結果を、保証されたふるまいのように見せている |

どれも **初心者には「分かりやすい」ので、レビューで見逃されやすい**。
そして受講者が現場に出たときに「資料と違う」「バグになった」という形で効いてくる。

だから品質レビューの目標は、AIの文章を難しくすることではなく、次の一文に尽きる。

> **分かりやすさを維持しながら、嘘になる単純化はしない。**

## 2. このレビュー手法ができた経緯

最初から原則があったわけではない。**直した箇所を並べて、パターンを抜き出した**ものである。

```text
第5回 初稿 6f7a8b4 → FIX 65e40d8
第6回 初稿 fcd1d4f → FIX b04a1fb, 07e9f8f
第7回 初稿 b604145 → FIX 2eca03e
      ↓
  fc3e735  直した内容を「7大レビュー原則」として規約化（AGENTS.md / ガイドラインに反映）
      ↓
第8回 初稿 a2a7af4 → FIX 3c1d78c, 27cfefc
第9回 初稿 f2cc826 → FIX f0ded49
```

流れとしては、**AIが書く → 人が指摘する／AIにレビューさせる → 直す → パターンを原則にする → 規約として次回のAIへの指示に入れる** という循環になっている。

### 正直に書いておくこと

- 規約化（`fc3e735`）の **後に作った第8回・第9回でも、FIXコミットは発生している**。原則を渡せば初稿が無欠になる、というものではなかった。
- したがって原則の役割は「AIが間違えなくなる」ことではなく、**レビューで何を見るかを共通言語にして、見逃しを減らす**ことと考えるのが妥当。
- 「FIXの量が減った」と言えるほどの定量比較はしていない（差分の行数は第5〜8回で 数十行規模のままで、明確な減少は読み取れない）。

## 3. 共通の物差し：A / B / C / D 分類

レビューの中心になる道具。**断定している文を見つけたら、その根拠がどの種類かを判定する。**

| 区分 | 根拠の種類 | 書き方のルール |
|---|---|---|
| **A** | 言語規格・OS仕様などで **保証される事実** | そのまま断定してよい |
| **B** | **特定の** OS / CPU / ABI / コンパイラでの仕様 | 対象環境を明示する |
| **C** | 一般的な実装・傾向 | 「一般的には」「多くの環境では」と限定する |
| **D** | 初学者向けの説明モデル・比喩 | 「概念的には」「イメージとして」と前置きする |

**ルールはひとつだけ：A 以外を、無条件の一般論として断定しない。**

### 警戒する語（引っかかったら分類する）

`必ず` / `常に` / `絶対` / `完全` / `すべて` / `〜だけ` / `〜しかない` / `安全` / `同じ` / `直接` / `正体` / `そのまま`

### 弱くしすぎない

「環境によって異なります」と書いて逃げるのも **失敗**。
**どこまでが保証で、どこからが環境依存か** の境界線を引くのがレビューの仕事。

## 4. 7つのレビュー観点と、実際に直した例

以下はすべて、リポジトリ内の実際のFIXから取った Before / After。

### 観点1：説明用のモデルを「実装の事実」にしない（概念モデル ≠ 保証）

**第7回 `2eca03e`**

| | |
|---|---|
| Before | 「人間には1行に見える処理の**機械語の3ステップ**」<br>「**CPUが実際に実行している** 3つのステップ」 |
| After | 「`counter++` を**概念的な** Read-Modify-Write として分解すると」<br>「概念的な3つの複合操作」<br>＋注記「コンパイラや最適化により、実際の機械語が必ず3命令になるわけではありません」 |
| 分類 | 3ステップ分解は **D（説明モデル）**。「CPUが実際に」と書いた瞬間に A のふりをしていた |
| 直し方 | 図やモデルは残す。**「概念的な」と明示し、実機の保証ではないと注記する** |

→ モデルを消すのではなく、**ラベルを付け替える**のがコツ。

---

### 観点2：断定文に根拠区分を付ける（A/B/C/D）

**第7回 `2eca03e`**

| | |
|---|---|
| Before | 「`0x1000` と `0x1000` は、OSとCPU（MMU）によって**全く別の物理メモリへ変換されている**」 |
| After | 「Aの `0x1000` とBの `0x1000` が**同じ物理メモリを指す保証はない**」<br>「**『同じ仮想アドレス値 ＝ 同じメモリ』ではない**」 |
| 分類 | Before は C（一般的な傾向）を A のように断定していた |

**第6回 `07e9f8f`**

| | |
|---|---|
| Before | 「4つのバイナリ契約が**完全に一致している**必要があります」 |
| After | 「4つのバイナリ契約が**双方で互換になるよう合わせる**必要があります」 |
| 分類 | 「完全一致」は警戒語。実際に要るのは互換性であって、同一性ではない |

---

### 観点3：「例外があるから曖昧に」ではなく、保証範囲の境界線を引く

**第7回 `2eca03e`（上の仮想アドレスの例の続き）**

After では曖昧にせず、**例外の位置を正確に書き足している**。

> ※注: 共有メモリ等の明示的な仕組みを使えば、別プロセスの仮想アドレスが同一の物理ページを参照する構成も可能です。

**第5回 `65e40d8`**

| | |
|---|---|
| Before | 「変更された `.cpp` だけを再コンパイルすればよいため、ビルド時間を大幅に短縮できる！」 |
| After | 「**実装の `.cpp` だけを変更した場合は**、その翻訳単位だけを再コンパイルすればよい」<br>＋注記「多くのファイルから `#include` されている共通ヘッダを変更した場合は、それを読み込んでいるすべての翻訳単位が再コンパイル対象になります」 |

→ 「いつでも成り立つ」を「**この条件で成り立つ**」に絞り、**条件の外側に何が起きるかも1行で書く**。

---

### 観点4：名前が同じことと、実体が同じことを混同しない

**第5回 `65e40d8`**

| | |
|---|---|
| Before | 宣言＝「関数の名前、引数の型、戻り値の型（**シグネチャ**）だけを伝える」 |
| After | 「宣言からコンパイラが知ること：関数名／引数の型／戻り値の型 など」<br>＋注記「C++の規格上、関数の『シグネチャ』には通常 **戻り値型は含まれません**」 |
| 分類 | 「シグネチャ」という**名前**を日常語の感覚で使い、規格上の**定義**とずれていた |

同じコミットで、リンクエラーの診断チェックも具体化している。

| | |
|---|---|
| Before | 「引数の型違い（`int` と `size_t`）、`const` の有無」 |
| After | 「ポインタの指す先の `const` 違い（`uint8_t*` と `const uint8_t*`）、メンバ関数の `const` 有無、`MyClass::` の付け忘れ」 |

→ 「見た目が似ている」で終わらせず、**何が一致していれば同じと言えるのか**まで書かせる。

---

### 観点5：「たまたま動く」と「規格上正しい」を分ける

**第8回 `3c1d78c`**

Before のスライドは、`delete p;` の前後で `p` を出力する実験コードを載せ、実行結果として次を示していた。

```text
delete前: 0x600000001000
delete後: 0x600000001000 （アドレス値はそのまま残っている！）
```

そして「`delete p;` はポインタ変数 `p` の値を書き換えない」と結論していた。

| | |
|---|---|
| 問題 | **手元で動いた出力を、規格が保証する事実として扱っている**。<br>C++規格では `delete` 後のポインタ値は「無効なポインタ値」になり、参照外しは未定義動作、それ以外の使用も実装定義の扱い。「値が残って見えた」は処理系の見え方にすぎない |
| After | 出力デモ自体を削除し、論点を **「ポインタ変数そのもの」と「指している先のオブジェクト」は別物** に置き換えた。<br>「`delete p;` は `p` を自動的に `nullptr` にしてくれるわけではない」＋最大の危険として UAF を説明 |

→ 実験結果を載せるなら、**「この環境ではこうなった」と「規格が保証すること」を別の行に書く**。分けられないなら実験結果は載せない。

---

### 観点6：層を混ぜない（言語規則 → コンパイラ/ABI → OS → CPU → ハードウェア）

```text
C++ language rule  （言語規格・メモリモデル）
  ↓
compiler / ABI     （最適化、呼び出し規約、シンボル解決）
  ↓
OS / loader        （仮想記憶、モジュールロード、スケジューラ）
  ↓
CPU / MMU          （機械語命令、アドレス変換）
  ↓
physical hardware  （物理メモリ、キャッシュ）
```

**第7回 `2eca03e`（atomic の説明）**

| | |
|---|---|
| Before | 「**CPUのアトミック命令を活用し**、Read-Modify-Write を**決して割り込まれない1つの操作**にする」 |
| After | 「対象の操作を **C++ memory model 上**、atomic な操作として扱う」<br>「他スレッドから『操作の途中の状態』が観測されないようにする」<br>＋「必ず1本のCPU命令になるわけではない（ロックフリーでない実装もあり得る）」<br>＋「スレッドが途中で一切停止（プリエンプト）されないという意味でもない」 |
| 分類 | Before は「C++の `std::atomic` の保証」「CPUの命令」「OSによるプリエンプション」の **3つの層を1文に混ぜていた** |

→ 文の主語が**どの層の話か**を確認する。「CPUが〜」「OSが〜」「C++が〜」を混ぜた文は疑う。

---

### 観点7：セルフレビューは「検索」で終わらない

警戒語を grep して満足するのは不十分。**ヒットした各文について次の4つを判定する。**

1. 根拠は何か（規格 / 特定OS / 実装傾向 / 説明モデル）
2. どの環境まで成り立つか
3. 教材上の概念図ではないか
4. 例外は、受講者のメンタルモデルを壊すほど重要か

**判定4が重要**。例外をすべて書き込むと初心者に読めなくなる。
「共有メモリの例外」は書く価値がある（プロセス分離の理解を誤らせる）が、「全ての最適化パターン」まで書く必要はない、という取捨選択が要る。

## 5. 運用手順：レビューの1サイクル

```text
① 生成     AIに初稿を書かせる（規約ファイルを渡した状態で）
② 抽出     警戒語を含む断定文をすべて拾う
③ 判定     各文を A / B / C / D に分類する          ← §3
④ 層確認   主語がどの層の話か確認する（混ざっていないか）← 観点6
⑤ 実験確認 動かした結果を載せている箇所は「環境の結果」と「保証」を分ける ← 観点5
⑥ 修正     限定語・注記・モデルのラベル付けで直す
⑦ 記録     新しい型の指摘は原則に足す／規約に反映する
```

- ②〜④は **AIにやらせられる**（断定文の列挙、A/B/C/D 案の提示）。
- ただし **最終判断は人が行う**。根拠区分の判定には、規格・ABI・OSの知識が必要で、AIが自信ありげに誤判定することがあるため。
- ⑦ が重要で、直した理由が規約に残ると、次の資料を書く AI にも渡せる。

### AIと人の役割分担（案）

> 【要確認】実際の作業で誰が何をしたかは、あなたの記憶に合わせて直してください。

| 工程 | AI | 人 |
|---|---|---|
| 初稿の執筆 | ◎ | 構成・題材・受講者像の指定 |
| 断定文の抽出・列挙 | ◎ | — |
| A/B/C/D の仮分類 | ○（案を出す） | **◎ 最終判定** |
| 層の混在・名前と実体の混同の検出 | ○ | **◎ 最終判定** |
| 例外を書く価値があるかの判断（観点7-4） | △ | **◎**（受講者像を知っているのは人） |
| 直し方の選択（削除 / 限定 / 注記） | ○（案） | ◎ |
| 原則・規約への反映 | ○ | ◎ |

## 6. 付録：レビュー観点表（チェックリスト）

そのままレビューに使える形。研修課題のレビュー観点表にも転用できる。

| # | 観点 | 確認すること | 引っかかったら |
|---|---|---|---|
| 1 | 概念モデルの昇格 | 図・比喩・簡略化を「実際にそうなっている」と書いていないか | 「概念的には」等を付け、実装の保証でない旨を注記 |
| 2 | 根拠区分 | 断定文は A/B/C/D のどれか。A以外を一般論にしていないか | B→環境明示、C→限定語、D→前置き |
| 3 | 境界線 | 「環境による」で逃げていないか。保証と環境依存の境目が書かれているか | 条件と、条件の外側の挙動を1行ずつ書く |
| 4 | 名前と実体 | 同名・同形・同じ値を根拠に「同じもの」と言っていないか | byte幅・レイアウト・ABI・規格上の定義を確認 |
| 5 | 動いた≠正しい | 実行結果を根拠にしていないか（特に UB・寿命・並行処理） | 「この環境では」と規格保証を分けて書く／載せない |
| 6 | 層の混在 | 1文に言語・コンパイラ・OS・CPU の話が混ざっていないか | 主語の層を一つに絞り、他の層は別文にする |
| 7 | 検索止まり | 警戒語の各ヒットについて根拠・環境・概念図か・例外の重要度を判定したか | 判定結果を残して再レビュー |

## 7. 適用範囲と限界

- 今回の根拠は **C++・低レイヤ（メモリ・リンカ・DLL・スレッド・寿命）** の研修資料。規格・ABI・OSなど「層」が明確な分野なので A/B/C/D が使いやすかった。
- 他の分野（要件定義書など）に使う場合は、A〜D の定義を読み替える必要がある（例：A＝顧客合意済みの事実、B＝特定部門の運用、C＝一般的な傾向、D＝仮説・たとえ話）。
- AIレビューで **検出できなかった嘘** は、本資料の対象外（記録していない）。
- 「どれくらい品質が上がったか」の定量評価は未実施。
